# 编排互动课件

形成或修订教学策划、呈现简报和呈现脚本时，同时遵守 [main-progression.md](references/main-progression.md)；教师控制器只作课堂兜底，不能代替正文主推进。

目标是经过教师逐阶段确认，得到两份脱离聊天仍可审阅、可修改并足以支撑制作的当前 Markdown。聊天记录不是交付真相，但用户确认是进入下一阶段的必要条件。

## 不可跨越的阶段门

阶段只约束当前对话行为，不建立审批状态文件、Hash 或额外合同。

| 当前阶段 | 本阶段唯一目标 | 完成后的强制动作 |
|---|---|---|
| 教学信息发现 | 补全教学意图与实施边界 | 展示教学简报摘要，请教师确认；不要写两份文件 |
| 教学简报已确认 | 形成教学策划 | 只写并展示 `01-teaching-plan.md`，然后结束本轮 |
| 教学策划待确认 | 等待教师审阅 | 未收到明确确认前，不询问呈现细节、不写脚本 |
| 呈现信息发现 | 补全阅读/操作体验与视觉取舍 | 展示呈现简报摘要，请教师确认；不要写脚本 |
| 呈现简报已确认 | 形成教学呈现脚本 | 只写并展示 `02-presentation-script.md`，然后结束本轮 |
| 呈现脚本待确认 | 等待教师审阅 | 未收到明确确认前，不启动 Builder |
| 两份文件均已确认 | 交给干净 Builder | 只传当前文件、材料与仍有效约束 |

“明确确认”必须是教师已经看过当前摘要或当前文件之后给出的肯定答复。文件存在、代理认为内容完整、教师最初说“直接做完”或在制品生成前预先授权，都不能代替确认。教师要求修改时，修改后重新展示当前摘要或文件并再次等待确认。

一次回复不得跨过两个阶段门。尤其禁止在同一轮中：生成策划后继续询问或生成脚本；生成脚本后继续启动 Builder；一次生成两份文件。

## 交互原则

1. 直接读取教师提供的文件和材料，不要求复述已经写明的内容。
2. 只询问会改变教学目标、内容正确性、课堂实施、评价方式或呈现体验的缺口。材料越完整，问题越少，但不能因此跳过摘要确认和制品确认。
3. 优先使用弹出式结构化选项；每轮聚焦 1–3 个相互关联的高影响问题。选项表达不了的原文、数据、题干或特殊要求才请教师填写。
4. 只有主题或信息稀疏时，至少经过“补全信息”和“确认摘要”两个独立用户回合；摘要仍有关键缺口时继续提问，不设置轮次上限，也不为凑轮次重复已知问题。
5. 不预设课型、教学法、片段数量、页面结构、互动比例或视觉风格；应根据本课目标和教师选择形成方案。
6. 本 Skill 不选择 Native、Runtime、Component，不写 `projectMode`、节点类型、API、Schema、工厂、命令、代码、Project 或导出物。

## 1. 教学信息发现

读取主题、材料路径、既有两份 Markdown 和用户本轮补充，区分：

- 已由材料确定的事实；
- 可以合理提出、但需要教师确认的建议；
- 会改变目标、内容边界、课堂实施或评价的关键缺口。

围绕本课实际需要判断是否已经明确：学习者与前置基础、课时与环境、内容范围与准确来源、可观察的学习结果、学习困难、教学推进方式、评价证据、已有素材与限制。它们是诊断视角，不是要求教师填写的固定表单；材料已回答的内容不得重复询问。

涉及版本、来源或学科事实而材料无法确定时，先核查权威来源，不把检索结果伪装成教师选择。

信息足以起草时，先展示一份简短的“教学简报摘要”：已确认事实、拟采用的教学主线、评价证据、课堂条件和仍保留的假设。请教师确认或指出修改。未确认前不得创建或改写 `01-teaching-plan.md`。

若教师提供了可直接使用的策划文件，展示将采用的文件、关键教学主线和仍有效假设，请教师确认“采用已有策划”；确认后才视为策划已确认，不要重写已闭合内容。

## 2. 形成并确认教学策划

教学简报确认后，先阅读 [teaching-design-quality.md](references/teaching-design-quality.md)，再创建或修订 `01-teaching-plan.md`。

策划深度为中等：另一位教师脱离聊天也能判断为什么这样教、怎样推进、如何知道学生学会，但还不是逐页分镜。内容应覆盖学习对象与条件、教学价值、学习目标、内容与教学主线、关键困难及处理、评价证据、材料依据和仍存在的假设。

策划必须呈现完整教学过程，而不是题目清单。每个新概念或关键认知跨越都应有相应的现象、讲解、建模、示范、证据分析或讨论支持；不能只在答题反馈中首次出现知识。

写完后展示文件链接，并概括最重要的教学主线、取舍和假设，请教师选择确认、修改文件后再来或指出一个缺口。然后结束本轮。未确认前不进入呈现信息发现。

## 3. 呈现信息发现

只有策划明确确认后才开始。重新读取当前 `01-teaching-plan.md`，围绕尚未确定且会影响可感知体验的内容分轮询问，例如：

- 教师主导、学生个别操作或共同观看的课堂方式；
- 演示页、流式讲义、无限画布的使用场景及节奏控制；
- 哪些内容需要讲解、示范、逐步揭示、练习、实验或总结；
- 互动中的反馈、重试、揭示、教师接管和评价边界；
- 视觉气质、已有素材、投影环境、设备、无障碍与静态导出要求。

这些仍是诊断视角，不是固定问卷。材料和策划已明确的内容不再询问；不要让教师选择 Native、Runtime、Component 或工程实现。

信息足够后，展示“呈现简报摘要”：整课体验主线、不同教学片段的呈现作用、关键互动、视觉方向、教师控制和不可静默改变的取舍。请教师确认。未确认前不得创建或改写 `02-presentation-script.md`。

若教师提供了可直接使用的脚本文件，同样先展示采用摘要并确认“采用已有脚本”。

## 4. 形成并确认教学呈现脚本

呈现简报确认后才创建或修订 `02-presentation-script.md`。每个片段（页、场或世界区域）应让 Builder 无需猜测即可还原教师可感知的体验，按实际需要写明：

- **教学作用**：导入、讲解、建模、示范、引导练习、独立应用、评价、总结或迁移；
- **表面**：演示页、流式讲义或无限画布，同一课可混用；
- **布局与入场**：主要分区、逐字文案、公式、数据、解释、素材引用和第一眼看到的内容；
- **讲解与操作**：教师怎样讲或演示，学生怎样观察、思考或操作；
- **状态**：交互前、中、对、错、揭示、返回、重试、重播等真实需要的路径；
- **动态类型**：整页少字的连续动态，或局部互动；
- **边界**：教师控制、评价、静态导出、无障碍及不能静默改变的教学与视觉取舍。

不要写图层 kind、组件包名、Runtime API 或命令名。写完后展示文件链接和最重要的体验取舍，请教师确认，然后结束本轮。未确认前不得启动 Builder。

## 5. 交给干净 Builder

两份当前文件均明确确认后使用 `$build-courseware-project`。优先启动不继承长聊天的干净 Build Coordinator；只传：

- `01-teaching-plan.md` 与 `02-presentation-script.md` 的当前路径；
- 原始材料路径；
- 交付目录；
- 教师仍然有效的额外约束；
- 两份文件已在当前对话中分别明确确认这一事实。

不要要求教师提供、打开或切换到编辑器仓库；Builder 自行发现产品根目录与能力索引。不要传旧草案、被否决方案、冗长讨论摘要或内部推断，也不要要求 Builder 运行已删除的 `agent-kit` CLI。

Builder 发现真正的教学内容缺口或必须改变教师已确认的体验时，返回本 Skill 修订相应阶段；纯技术分解留在 Builder。
