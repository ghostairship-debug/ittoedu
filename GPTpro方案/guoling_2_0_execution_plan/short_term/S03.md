# S03｜事务、资源、撤销与崩溃恢复

**阶段：短期基础设施 · 2.0 必须完成**  
**实施依赖：** S02

## 交付物

统一单文档操作提交器、资源生命周期、操作幂等索引、小型恢复日志和统一 History。用户手改、直接 AI、导入完成均通过它；聊天记录不能作为恢复文档的唯一依据。

## B01 内部检查点

沿 S02 的三个内部检查点接入事务能力，不增加批次、完成归属或验收用例：

1. 纯 TypeScript 内核单测通过，不依赖 Electron；覆盖提交、幂等、资源与 History、停止屏障和残缺恢复日志。
2. 主进程 DocumentRegistry 与窄 IPC 接通，两份课件和一份未保存 Markdown 并存；验证每文档提交顺序、独立历史及回执丢失后的查询。
3. renderer 投影与薄 V9 Driver 接通；非当前页修改、撤销、保存重开与恢复成立，素材引用不丢失。交接记录实际命令、结果与剩余缺口，局部通过不提前宣布 B01 完成。

## 原子提交路径

`plan局部操作 → 在文档队列内核对版本/读写足迹 → 准备已持久化资源引用 → 追加可恢复操作记录 → 更新权威内容/revision → 通知视图 → 返回结果`。

恢复日志必须具备崩溃后可判定的事务边界。使用已有可靠存储或长度/校验/commit标记的顺序日志；不能假设多个 JSON 文件依次写入就等于事务。无需为此构建分布式事件溯源平台。

正式“已应用”回执应具备可重放的操作记录；资源准备或日志失败则不提交正式内容，用户未确认显示草稿仍保留并提示重试/另存。磁盘目标文件保存异步独立，`已应用`、`恢复稿已保全`、`已保存到原文件`三态不混用。

## 操作身份与幂等

内置调用由宿主将 toolCallId 与 runId 映射为 operationId；外部 MCP 使用宿主预发的操作票据，不把 JSON-RPC request ID 当成跨重连幂等键，也不让模型自报权限/版本。`operationId + payloadDigest`首次执行记录结果；相同ID/相同载荷只回原结果；同ID/不同载荷拒绝。超时不知道是否执行时先查询，不改用新ID再执行。

停止在队列中建立取消屏障。已越过正式提交点的操作如实保留；屏障之后的写入拒绝。停止不是把整场任务的成功操作回滚。网络回执失败也只补发结果，不再次写内容。

## History 与资源

沿用资源感知 History 的语义。内容变更和素材引用在同一历史条目内；undo/redo 都走正式操作队列，不能一边恢复对象、一边释放其素材。

每个完整工具操作是一个默认撤销边界；同文档相关批量操作可为一条事务。流式文本完整结束时仅一条记录。人工穿插后，普通 Ctrl+Z 严格按顺序；选择性“撤销本次AI”只有逆操作可证明不覆盖后续写入时才提供。

资源存储使用受管引用，History、未完成草稿、消息附件和导出任务均持有引用。删除画布对象不立刻删除仍被撤销历史引用的 Blob。整理历史与清理资源独立执行，清理错误不破坏文档。

## 性能与校验迁移

现有全量 step 可作为过渡；禁止为每个token创建完整快照。普通 planner 逐项改为不可变局部修改/结构共享，并建立它实际触及的不变量检查。完整 import 与未知来源整文档替换继续全量结构校验。

不要先全局移除 `courseProjectDocumentSchema.parse`。每个操作从全量检查转局部检查时，补齐同等不变量的单测和差分回归，确认其余内容未受影响。撤销资源合并规则保持原有正确行为。

## 文件保存与恢复

保存固定某个已提交 revision，写临时文件后原子替换；保存期间的新操作保持dirty。重启根据最后完整checkpoint和后续日志恢复；残缺尾记录截断，已提交操作去重重放。恢复不会自动重跑模型或继续付费任务。
