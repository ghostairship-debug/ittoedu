# 参考案例：一个持续存在的全局背景物件

案例 ID：`coffee-continuous-underlay`。目标：在原生 Flow 图文之下保持统一底色、氛围和同一物件的连续叙事；复杂局部活动仍各自可编辑。

## 适用条件与复用层级

适合章节顺序明确、停下来阅读为主、章节之间需要视觉连续性的叙事。可改写的是状态映射、参数绘制与生命周期机制。咖啡的杯、果皮、种子、烘焙纹理、粉末与液体属于主题素材，不能声称为任意主题的通用形变器。

- 唯一背景：Project 底色提供启动时底色；Global Underlay 的一个 Source 实例绘制整幅背景；Flow Surface 采用 `background.mode: inherit`；Flow Paper 只负责排版。
- 前景：原生文字、图片、组、SVG 与三个局部程序仍在 Surface。必要的文字衬底和按钮背景属于局部信息保护，不重新绘制整章不透明底色。
- 正式 GLX 的实例 ID：`926a6155-1814-4a16-ba47-24c1c1f5dbc8`；定义 ID：`96347310-25a2-4382-bde7-1c46f6d5ba9f`。真实投影路径以 `project.list` 为准。
- 作者源文件：[background-runtime.js](background-runtime.js)。GLX 的 Source 工作空间入口历史名为 `underlay-poc.js`，最终实现由上述文件经正式 `project.apply` 提交。修改源码文件本身不会自动同步入 GLX。

## 阶段、物件与轨迹

| 阅读阶段 | 主要材料形态 | 桌面锚点（视口比例） | 动作 |
| --- | --- | --- | --- |
| U01 开篇 | 陶杯与咖啡液面 | .47 / .85 | 与开篇实物呼应，保持低对比度 |
| U01 起源子锚点 | 红色咖啡果 | .91 / .73 | 杯体收束，果皮与叶柄出现 |
| U02 生长 | 成熟果实 | .46 / .65 | 同一物件移到图文空隙 |
| U03 处理 | 分开的果皮与种子 | .96 / .74 | 果皮向两侧剥离，显露双种子 |
| U04 交接 | 生豆 | .62 / .33 | 组织收束，保持阅读缓冲 |
| U05 烘焙 | 烘焙豆 | .96 / .77 | 颜色、纹理、裂隙逐步改变 |
| U06 水 | 粉末、溶质、液体场 | .95 / .76 | 颗粒从集中分布向液体扩散 |
| U07 回味 | 盛有咖啡的杯 | .49 / .83 | 分散的物质重新回到杯中 |

桌面与手机的 `x/y/size` 分别配置。手机物件偏右、缩小并部分出画，保护正文与操作控件。轨迹不是多个定位图片的淡入淡出：位置、转角、尺寸、果皮分离、种子权重、颗粒扩散、液面、材料色与纹理共同插值；细线轨道保持连续身份。

## 状态与生命周期

`context.teacherController.read()/subscribe()` 提供唯一的阅读事实。程序使用当前 scene 的 targets 顺序与 `reading.activeInstanceId` 决定阶段，映射与现有统一导航一致。程序不监听外部宿主 DOM、不另建滚动观察器、不保存第二份章节状态、不写回作者内容。

物件从当前已画出的参数开始，1350ms 平滑过渡。为保护深色到浅色章节的文字，浅色目的阶段的底色与氛围色默认在180ms内到位，物件继续移动和变形；深色目的阶段仍按完整时长过渡。可用 `paperDurationMs` 调整浅色纸面的时长，运行时将其钳制在1ms到物件总时长之内。新的跳章会取消旧帧循环，并从屏幕实际颜色和形态连续接续，目的阶段以最后一次阅读状态为准。停稳后停止 requestAnimationFrame。`suspend/resume/dispose`、页面可见性、ResizeObserver 和减少动态偏好均有对应处理。减少动态模式直接画目标状态。纸张纹理由确定性小图块生成，不持续闪动。

## 修改入口与必要素材

1. 调整 `instance.data.chapters` 的目标 ID；必须从新 GLX 的真实标题实例取得，不能拷贝咖啡旧 ID。
2. `instance.data.stages` 可覆盖阶段颜色、位置、大小与绘制参数；`originTarget` 是可选子阶段；`durationMs` 是切换时长。
3. 咖啡形态由 Canvas Path2D、曲线、渐变和确定性颗粒绘制，无网络素材依赖。
4. 新主题可重写形态绘制，或以 `symbols` 提供内联 SVG。小型糖水样本使用后一种方式验证替换素材、阶段映射和轨迹；它的复用等级是机制与配置，不代表所有题材都无需改代码。
5. 该作品的背景仅有一个实例，最终统一修改其共享定义 Source；不要同时维护一个无用的旧定义和一个实例源码副本。发现的导出诊断另记软件交接，不在作品中隐藏诊断。
