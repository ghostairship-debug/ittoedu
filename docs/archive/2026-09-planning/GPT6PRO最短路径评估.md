## 0. 决策摘要

### 0.1 产品前提

手动编辑器负责点选、拖动、颜色、字号等容易直接操作的修改。AI 的主要价值集中在手动编辑费力、需要综合判断、需要批量处理，或者普通用户无法完成的改动，例如：

- 重排整页、统一多页视觉风格、在保留内容的前提下改变展示方式。
- 批量改写、修改多处关联内容，同时保持公式、答案和教学逻辑一致。
- 修改组件内部布局、动画、交互、状态转换和 Runtime 源码。
- 处理复杂素材局部、跨对象关系，或将静态内容改造成可交互内容。

**本方案不建设“改颜色、改字号、挪位置”的自然语言确定性命令快通道，不用这一类任务的成绩代替真实 AI 编辑能力。** 图片改色事故只作为基础链路异常和越界修改的回归案例。

### 0.2 总体方向

保留现有 CLI 接入、正式创作工具、候选预演和事务提交体系。优化的重点是让 AI 在已有工程上少做无效工作：

1. **减少无意义的模型往返。** 同一批可以共同生成的修改一起提交；完成后不再为了确认或总结开启新推理；需要实际观察才能继续的任务保留迭代。
2. **减少重复阅读和重复生成。** 一次提供目标、相关依赖和必要能力，优先局部补丁，避免重新输出整份工程或未变源码。
3. **把检查与修复限制在真正受影响的部分。** 保留必要运行验证，去掉重复资源传输、重复准入和没有新增证据的审查。
4. **把错误控制在局部。** 修改范围、保持条件、版本和证据由宿主检查；修复有预算，失败不自动升级为更大范围重写。
5. **让复杂内容本身更容易修改。** 在已有组件和 Runtime 上暴露有价值的参数、状态和调试信息，降低每次修改的理解成本。

“宿主”指编辑器和其本地运行服务，不是额外增加的一个大模型。宿主负责事务、资源、状态、检查和停止；AI 继续承担设计、内容理解、源码修改等需要智能的工作。

### 0.3 首批只做什么

首批交付聚焦四项：分段计时；有条件结束与有限修复；上下文和候选输出减重；候选内合并修改、复用检查结果。

先在相同模型、相同接入渠道上验证收益，再决定是否增加直连 API、并行子任务或专用代码应用模型。不要把更换框架、建设多 Agent 平台或引入全新协议体系设为前置条件。

### 0.4 成功标准

衡量“从用户提出要求到首次得到正确、可用修改”的时间，同时衡量首次成功率、越界修改率和等待尾部。只缩短首字时间、增加进度消息，或让错误结果更快出现，都不算主要目标达成。

## 1. 工作范围与非目标

### 1.1 三类真实工作负载

| 类型 | 典型任务 | 主要难点 | 合理的执行特点 |
|---|---|---|---|
| A：批量与设计编辑 | 重排一页；统一八页版式；同步修改多处讲解 | 关系理解、整体一致性、内容保护 | 尽量一次形成完整候选，必要时进行一次针对性视觉检查 |
| B：组件与交互编辑 | 改答题流程；增加提示阶段；调整动画与控制联动 | 状态、事件、代码、运行结果 | 定向读取，局部修改，运行受影响路径，失败后局部修复 |
| C：结构性改造 | 静态讲解改互动实验；跨页重构课程流程 | 目标拆分、跨对象依赖、设计决策 | 允许分阶段，但每阶段必须有真实产出和清楚的继续理由 |

这些是调度与评测分类，不必给用户增加三个复杂模式按钮。可以由入口、已有目标信息和首轮模型判断共同决定，避免额外增加一个固定路由调用。

### 1.2 明确不做

不把小改命令库作为本轮成果；不以关键词或正则替代复杂语义理解；不要求所有任务一次成功；不强制所有任务经过“规划—执行—评审—复核—总结”五个模型；不为了提速取消版本保护、撤销能力、源码准入或必要试运行。

不把“所有 AI 编辑都不得改变几何”写成全局规则。重排页面本来就要改变位置和尺寸，保护条件必须来自本次任务。

不把“每个失败都自动换最强模型”作为默认兜底。缺资源、版本冲突、错误权限和运行环境故障首先需要正确分类。

### 1.3 三个边界

**设计自主权与修改授权分开。** AI 可以自由决定授权范围内的实现方式，但不能把“修改这页”扩展成改写整套课件。

**主观效果与客观成功分开。** 工具成功、没有报错、视觉效果符合预期，是不同层次。宿主不能用“提交成功”证明设计质量。

**开发验证与用户操作分开。** 全量回归、导出矩阵和多模型评测在开发阶段执行，不应全部挂到每次用户编辑的关键路径上。

### 2.2 对当前架构的判断

现有“AI 提交候选—私有预演—正式工具—事务提交”的路线可以继续使用。它已经解决了一部分目标定位、资源引用、过期写入和撤销问题。[R2][R3]

应调整的是循环调度、候选粒度、观察范围和验证成本。没有证据表明必须先替换编辑器架构或退役 CLI。

### 2.3 需要首先获得的事故信息

那次图片修改至少应还原：每轮请求与结果、实际选择的工具、候选是否被拒绝、拒绝原因、是否改变载体、几何字段是否变化、素材内容是否重生成、首次可见结果何时出现。

必须区分四种“轮次”：用户补充了几次、宿主续跑了几次、CLI 内部进行了几次模型调用、生成并检查了几个候选。不能把它们统一记为“三轮”。

## 3. 延迟模型与排查顺序

### 3.1 分开四种时间

| 指标 | 定义 | 用途 |
|---|---|---|
| 首次状态反馈时间 | 发送到界面明确显示已接收、目标范围和当前阶段 | 排除假死；不代表修改完成 |
| 首次有效候选时间 | 发送到形成可完整预览的候选 | 判断生成路径效率 |
| 首次正确修改时间 | 发送到满足任务验收的可用结果首次出现 | 核心指标；离线用人工或任务测试确定正确性 |
| 全任务结束时间 | 发送到任务停止、回执保存、结果状态明确 | 识别成功后仍在续跑的浪费 |

对需要用户点击应用的任务，单独记录“系统候选就绪”和“用户决定”之间的等待。报告包含用户等待的端到端时间，也报告排除明确用户等待后的系统时间，不混在一起比较。

### 3.2 用关键路径分析，而非相加所有计时

串行路径可以近似写成：

```text
总时间 = 首次观察准备
       + 各模型轮次的启动/排队/输入处理/推理输出
       + 工具执行与必要检查
       + 局部补充观察
       + 最终应用与显示
       + 用户等待（单列）
```

存在并行时，要看最长依赖链。不能把同时发生的模型生成、资源准备和截图采样全部相加，再宣称优化比例。

延迟指南将减少请求次数、减少生成量、并行和流式交互列为不同优化手段；在本项目中应分别测量其贡献，不能只关注每秒 Token 数。[S1]

### 3.3 优先级

第一优先级：重复模型回合、选错工具导致的返工、整文件重写、同一候选的重复验证。

第二优先级：首轮缺少关键信息导致的补读、资源重复传输、CLI 启动与队列、过长历史。

第三优先级：图片编解码、IPC 轮询、截图尺寸、缓存和网络细节。若实测显示第三类占主导，应立即调整优先级，而不是机械照表实施。

控制器目前有 250 毫秒的读事件轮询等待。[R2] 可以记录其影响，但不能把这一项解释成分钟级耗时的主要原因。

## 4. 目标执行流程：一个主 Agent，按需要继续

### 4.1 主流程

```text
用户要求 + 冻结的目标与工程版本
                  │
                  ▼
    目标摘要、依赖信息、相关工具、必要图像
                  │
                  ▼
       主 Agent：理解 + 设计 + 形成候选
        │                         │
        │ 缺必要信息              │ 可执行候选
        ▼                         ▼
  定向读取 / 实际观察      私有文档计划多步修改
        │                         │
        └── 回到同一任务          ▼
                          受影响范围检查
                                  │
                   ┌──────────────┼──────────────┐
                   ▼              ▼              ▼
                可以结束       确需下一阶段     检查失败
                   │              │              │
          按现有策略应用/预览   局部回执与观察   分类后的局部反馈
                   │              │              │
                   ▼              └──────┬───────┘
           保存回执、结束                 ▼
                               在预算内继续或修复
```

框图中的节点是软件步骤，不意味着每个节点调用一次模型。

### 4.2 按任务选择迭代程度

**批量与设计任务：** 首轮信息足够时，直接形成一份包含多项修改的候选。需要视觉判断时，仅检查受影响页面或区域。不要固定加一轮独立规划和一轮“最终确认”。

**组件与交互任务：** 首轮可以先读取目标源码及关联状态，再输出补丁；必要运行检查由宿主执行。检查失败后返回失败路径和证据，不让模型重新读全项目。

**结构性任务：** 允许先形成简短设计方向。只有架构选择会实质改变用户目标、成本或可逆性时，才在实施前请求用户选择。用户已经给定的范围、风格、素材和功能要求，不重复询问。

### 4.3 与现有实现的衔接

继续使用 `GenerationTaskController`、`createGenerationCandidateCoordinator` 和正式工具。新增的能力尽量是几个策略函数和少量可版本化字段，不引入新的持久化任务引擎。

第一版保持原有协议兼容：只有明确识别新元数据的适配器才能使用提前结束；旧适配器走有预算的兼容路径。不能把缺失元数据解释成“默认已经完成”。

## 5. 结束、继续与修复：优先改控制器

### 5.1 什么情况下可以结束

对已形成完整候选的任务，下面条件共同满足后可以结束，不再调用模型说“改好了”：

1. AI 声明本次候选覆盖了当前任务的全部拟执行部分，没有依赖下一次观察的未完成步骤。
2. 候选通过目标范围、保持条件、结构和必要运行检查。
3. 按现有 `applyPolicy` 完成应用，或进入明确的待用户应用状态；两者在界面上不能混淆。
4. 实际提交回执已保存，且没有未处理的硬性失败。

其中第 1 项只是继续/停止的声明，第 2 项提供客观证据。对于审美、教学表达等主观效果，宿主只能表明“已按当前方案生成并通过技术检查”，不能自动宣称“设计符合所有预期”。结果预览和用户反馈仍然重要。

**特别注意：工具返回成功，不足以结束一个多阶段任务；模型返回 `done`，也不足以证明任务完成。**

### 5.2 什么情况下值得继续

允许的继续理由应当是具体、可记录的，例如：需要观察新交互运行后的状态；需要使用前一步真实生成的资源；还有事先声明的后续阶段；检查发现了可修复的问题。

下面情况不应自动继续：重新总结已提交内容、复述回执、没有问题也再审一遍、模型临时想“再美化一下”、为了更漂亮而超出本次目标。

### 5.3 建议的最小增量元数据

以下是设计草案，不是当前仓库接口；落地时扩展正式 Schema，并由生成器同步工具卡和适配器，避免多份手写定义漂移。

```ts
interface EditExecutionPolicy {
  maxHostContinuations: number;
  maxAutomaticRepairs: number;
  softDeadlineMs: number;
  hardDeadlineMs: number;
}

interface CandidateProgress {
  disposition: 'final-candidate' | 'stage-candidate';
  coveredRequirementIds: string[];
  pendingRequirementIds: string[];
  continuationReason?:
    | 'needs-runtime-observation'
    | 'needs-generated-resource'
    | 'remaining-stage';
}
```

任务要求直接来自用户输入和当前目标。允许 AI 在首轮候选中整理要求，但这不能成为新的授权来源：不得自行删除原要求，再声称全部完成。

最初不必建设复杂目标证明系统。先用少量要求标识、未完成项、明确继续理由，加上宿主实际检查。对无法机器核验的要求标记为“由预览确认”。

### 5.4 控制器中的关键改动

在成功 `apply` 并保存回执后，先调用本地完成判定。判定结束则更新终态并退出；只有需要下一阶段时才调用 `captureNext` 和 `continue`。[R2]

建议顺序如下：

```text
准备成功
→ 等待应用或自动应用（保留现有规则）
→ 保存真实回执
→ 判断是否必须继续
    ├─ 无待处理目标且证据满足：结束
    ├─ 需要真实观察：获取局部观察后继续
    └─ 元数据缺失：兼容处理，受预算约束
```

回执写入异常不允许重新提交已经生效的修改。沿用当前实现中“回执保存可重试，真实提交不可重复”的原则。[R2]

### 5.5 失败分类与处理

| 失败类型 | 首选处理 | 不应采取的处理 |
|---|---|---|
| 格式或 Schema 错误 | 返回字段路径、期望类型、短示例；可定位时只修局部 | 重跑完整设计过程 |
| 目标/版本过期 | 停止旧候选，获取当前差异；只在新鲜目标上重新计划 | 直接套用旧补丁、自动扩大写入范围 |
| 未授权修改、违反保持条件 | 指明具体越界字段或对象；局部重提 | 为了放行候选自动降低约束 |
| 编译/运行错误 | 返回目标、错误栈节选、触发步骤、失败截图或状态 | 重新生成无关页面和全部组件 |
| 资源/认证/网络错误 | 检查资源或接入状态，单独计数，必要时有限退避 | 当作模型能力不足，反复换模型 |
| 技术通过但主观效果不满意 | 接收用户针对性反馈，重新定义相应修改目标 | 偷偷进行多轮审美优化 |
| 相同故障反复出现 | 无进展检测触发停止或一次有依据的升级 | 无限重试直到额度耗尽 |

### 5.6 预算与无进展检测

建议首批试验默认值：A 类最多一次自动修复；B 类最多两次；C 类按已声明阶段分别计数，并另设全任务上限。上限是防失控配置，不是对复杂任务合理轮数的永久结论。

同时限制墙钟时间、候选次数和宿主续跑次数。CLI 内部调用次数拿不到时，记录为未知，用墙钟与可观测事件限流，不能伪装成准确的一次模型调用。

连续出现相同“错误类别 + 目标 + 关键诊断”，且没有新增证据或有效变化，应停止同一路径重试。不要只比较候选全文哈希：增加一句注释也会改变全文，却并不代表取得进展。

达到软预算时停止额外美化和非必要观察；达到硬预算时取消未提交工作并展示当前状态。已经提交的阶段保留，明确哪些完成、哪些未完成。禁止自动撤回用户随后手改的内容。

## 6. 上下文：首轮给对信息，后续只补差异

### 6.1 三层上下文

| 层级 | 内容 | 默认发送策略 |
|---|---|---|
| 任务层 | 用户要求、目标范围、保持条件、当前版本、相关历史结论 | 始终提供，保持简洁 |
| 目标与直接依赖层 | 当前页面/组件、父级布局、引用素材、关联状态、关键源码 | 首轮按任务需要提供 |
| 全工程层 | 其他页面、完整资源、长历史、全部能力说明 | 提供索引与按需读取入口 |

重排页面需要整体空间信息，不能只给被选中的两个节点；修改评分逻辑需要题目数据和状态流，不能只给点击回调。上下文减量应减少无关内容，不能牺牲解决任务必需的关系。

可参考 tldraw 按焦点和视野提供不同细节级别的做法，但不需要迁移到其画布架构。[S2]

### 6.2 首轮观察包建议

对页面设计任务，提供页面尺寸、完整目标页概览、可编辑对象简表、阅读顺序、锁定对象、关键文本和公式、必要截图。让截图和结构化对象使用可对应的标识，避免模型“看见物体但找不到可编辑对象”。

对交互源码任务，提供目标模块源码或相关完整函数、调用与事件关系、公开输入输出、当前运行状态、资源引用、已有测试入口。小模块直接给全文往往比先搜再读更省往返；大模块再按符号或区段读取。

对跨页任务，先提供各页摘要和公共规则，再把本轮负责的页面展开。不能只看到第一页就生成整套统一方案。

### 6.3 能力发现改进

沿用现有工具卡和延迟发现机制。[R4] 首轮按任务需要预展开最可能用到的工具，并提供少量正确用法。参数编辑、源码编辑、载体转换要说明适用条件，减少误选。

限制初始工具集不等于永久限制创作能力。缺少能力时允许一次定向扩展，并且只有明确授权的写入目标可以被使用。不要因为初始卡中没有某工具就告诉用户“不能做”。

工具说明由正式合同生成，例子与 Schema 一起测试。删掉重复口号，保留目标身份、载体适用性、前后值、引用方式和易错边界。工具搜索与程序组织批量调用可借鉴 Anthropic 的相关设计，但不需要为此接入完整的新框架。[S3]

### 6.4 后续观察使用增量

后续包优先包含：刚刚实际改变了什么、当前版本、失败目标的最新状态、必要截图、仍未完成的目标。历史全文和未变资源不重新发送。

增量包必须带基准版本。模型会话已丢失、切换模型、依赖改变或版本不连贯时，重新建立紧凑完整快照，不能让一个没有基准的模型解释差异。

### 6.5 避免上下文缓存陷阱

长会话可以保留稳定设计约定和已确认决策，但旧工程状态不能压过实时观察。资源引用使用内容身份或版本；过期源文件、截图和状态不能被当作当前事实。

不以“Token 越少越好”为唯一目标。一次多给两段关键源码，比缺信息后追加三次读取更有价值。

## 7. 输出与候选：少重写，善用现有多步事务

### 7.1 局部补丁优先，不强制一律补丁

| 修改对象 | 优先输出 | 合理例外 |
|---|---|---|
| 页面/内容结构 | 受影响节点、字段或有序操作 | 结构整体重做时，可输出受影响子树 |
| 组件公开配置 | 需要变化的参数和关联字段 | 合同本身需要扩展时，进入源码修改 |
| Runtime / 组件源码 | 基于明确版本的局部补丁、函数级替换 | 小文件或大范围重构时，完整文件可能更可靠 |
| 资源 | 已有资源引用、外部处理结果引用 | 真正需要新素材时生成或导入新资源 |

目标是减少不必要输出和非请求修改，不是把“必须使用 diff”变成新仪式。比较补丁与整段输出时，记录输出量、补丁失败率、首轮成功率和总时间。

### 7.2 补丁必须绑定基准

补丁至少关联目标文件或对象、基准内容身份、修改区段及必要上下文。文本替换只有唯一精确命中时才应用；不能在存在歧义时悄悄使用模糊匹配。

基准不匹配时返回冲突区段，由模型依据当前内容修复。可以保留未冲突的私有结果，但正式提交必须再次检查当前版本。

禁止让模型为了输出补丁自行编造文件名、资源 ID、对象 ID。目标标识来自观察，创建对象通过实际工具回执引用。

### 7.3 同一候选容纳整批关联修改

当前协调器已支持多步候选、前序结果引用和最终合并事务。[R3] 因此，应优先改模型示例和候选组织方式：

```text
调整实验参数面板
+ 更新动画逻辑
+ 修改说明文字
+ 同步重置行为
→ 放入同一候选，按依赖顺序预演
→ 对最终状态验证
→ 一次应用 / 一次撤销
```

不要为四项修改分别启动四轮模型，再额外启动一轮核对。需要前一步真实运行输出时才分阶段。

### 7.4 合并同一对象的连续操作

模型或宿主可将语义兼容的同对象配置合并；例如一次候选中分别改变同一组件的三个公开参数，应尽量形成一次参数提交。

不得跨越有依赖的操作重排：先创建、再引用、再替换必须保留顺序；后一步依赖运行观察时不能提前合并。相对修改合并还要明确基准，防止“再增加 10%”被重复解释。

### 7.5 限制无价值的输出

用户能看见简短设计摘要和实际变化即可。默认不要让模型输出长篇计划、逐工具说明、完整历史复述或大段最终总结。

精简输出不能截断源码或候选。若达到输出上限，应明确返回不完整候选并拒绝应用，禁止解析部分结果后误标成功。

## 8. 验证：保留真实证据，减少重复成本

### 8.1 验证分层

| 层级 | 检查内容 | 适用场景 | 是否一定要再调用模型 |
|---|---|---|---|
| V0：事务与边界 | 目标、版本、引用、字段合法性、未授权变化、可撤销性 | 所有候选 | 否 |
| V1：结构与静态结果 | 布局边界、缺失内容、关键公式/答案保持、补丁与语法检查 | 页面、文本、源码相关修改 | 否；无法自动判断的事项另列 |
| V2：受影响行为 | 挂载、关键交互、状态变化、生命周期、相关视觉结果 | 公开参数影响行为、新增/修改源码 | 通常由宿主执行；失败后才回模型 |
| V3：设计或语义判断 | 整体视觉、教学表达、是否符合参考方向 | 真正需要主观判断的任务 | 按需进行一次定向评估或交给用户预览 |

V2 不等于全工程全路径回归。V3 也不必永远由第二个强模型执行。针对明确行为，实际触发和状态断言通常比一句“我看起来检查过了”更有价值。

### 8.2 先复用已有分级

组件代码已将外层属性修改与公开参数、完整准入分开；Runtime 文本与部分配置也有不同检查路径。[R5][R6] 应测量各路径，不要简单删掉所有动态检查。

可先做低风险优化：合并同对象配置；避免重复发送未变资源；复用相同源与依赖的静态检查；把同一候选最终状态的行为验证集中处理。

### 8.3 候选最终态验证

同一个候选连续修改一个组件时，没有必要让每个中间版本都完整跑一遍最终验收。可以在私有状态中完成纯数据计划，对最终状态进行一次受影响行为验证。

但这需要区分“计划数据”与“执行新代码”。任何提前执行的新源码仍必须经过相应准入。生成后备截图、读取实际测量结果等依赖运行的步骤不能为了省检查而跳过。

实施顺序：先通过合并候选减少重复；确认收益后，再考虑让工具返回可合并的验证需求。不要第一步就拆解所有工具的执行模型。

### 8.4 检查复用与失效规则

静态检查缓存建议关联源码身份、依赖版本、合同版本和检查规则版本。公开参数变化可以复用未变源码的语法检查，不能直接复用旧参数下的行为成功。

行为结果还受输入、尺寸、初始状态、资源、渲染后端和运行环境影响。缓存键不能只包含源文件哈希。任何影响本次要求的输入变化，都应重新运行相关行为。

在用户当前状态下的正确性，不能完全由“以前跑过一次”代替。第一版优先缓存编译/静态结果和不可变资源；行为缓存谨慎后置。

### 8.5 资源传输优化

当前动态准入请求会构造资源 Base64 负载。[R7] 可分三步优化：

1. 记录每次负载字节数、转换时间、传输时间、挂载时间，确认是否值得做。
2. 在单次任务内复用未变资源，按内容身份只传差异；接收端缺失时明确请求补齐。
3. 再考虑跨任务缓存已加载的不可变资源，设置内存上限和失效策略。

不能在不知道动态代码依赖哪些资源时盲目裁剪。优先保持完整资源可访问，减少重复字节；依赖声明可靠后再缩小物理加载范围。

预热资源或进程，不等于复用上一个任务的活动组件实例。后者可能带入事件、计时器和状态污染。保留隔离边界，每次清理运行状态。

### 8.6 失败反馈必须可执行

模型需要收到：失败目标、失败步骤、错误类别、最相关诊断、触发条件、当前版本和受影响截图/状态。日志可按需展开，不默认发送完整重复栈和全部资源。

只说“验证失败，请修复”会制造新的探索轮次。把反馈做具体，是减少重试时间的一项直接改动。

## 9. 素材与对象保护：复杂修改也不能顺手改坏其他部分

### 9.1 保护条件按任务制定

| 用户要求 | 应允许 | 应保护 |
|---|---|---|
| 保留内容，重排页面 | 位置、尺寸、层级、布局关系 | 关键文案、公式、答案、引用资源的内容 |
| 调整插图局部视觉效果 | 指定区域的相应视觉属性 | 未授权区域、主体结构和必要透明度 |
| 修改互动题的反馈机制 | 反馈呈现、相关事件和状态 | 题目答案、其他题目、无关导航逻辑 |
| 将静态讲解改为互动演示 | 明确范围内创建/替换对象和新增逻辑 | 用户要求保留的知识内容、其余页面 |

保持条件分为强条件和软条件。强条件用字段、资源身份、像素区域、引用或行为断言检查；软条件用预览和必要的视觉判断。不要把主观“风格一致”伪装成精确哈希检查。

### 9.2 避免重新生成整张素材

复杂任务可能包含“保留原插图结构，只改变其中一部分”的需求。优先使用原素材的结构化属性、局部掩码、图像处理或已有素材工具；确实需要生成式处理时，限制区域并保留原始版本。

这部分沿用/扩展素材工具能力，不建设专门的小改自然语言命令入口。AI 可以在一个复杂候选里组合使用这些工具。

对原生图形和 SVG，能通过绘制属性修改的内容不要重建几何路径。对位图中的局部效果，区域由用户点选、分割工具或已有对象信息确定；语言模型引用区域，不逐像素编写掩码。

单纯宽高不变不代表图形没有被破坏。还需考虑透明度、轮廓、区域外像素，以及阴影/渐变是否被压平。生成式图片编辑也不能保证区域外完全不变，重要素材应有差异预览和回退能力。

### 9.3 实例与共享资源分开

修改一个实例的视觉效果时，不能默认覆盖其他页面共用的原素材。需要创建派生资源或实例级覆盖，并保持原资源可撤销。

用户明确要求统一全部实例时，再采用共享修改。执行前在候选摘要中展示预计受影响的实例范围，而不是每次都弹出额外确认框。

### 9.4 载体转换须有明确理由

编辑困难不构成自动把原生对象换成图片、把组件替换成整页 Runtime 的理由。转换可能破坏后续手动编辑能力。

当用户要求的功能确实超出原载体时，允许提出转换方案，并说明保留与失去的可编辑能力。关键转换可以在原有候选预览中确认，不需要另建审批流程。

## 10. 扩充底座：让复杂内容具备可编辑结构

### 10.1 重点是减少理解与重建，不是堆模板

一个底座的价值应体现在：已有布局/事件/状态机制可以直接复用，AI 不必每次重写基础代码；内容的关键参数、数据和行为能够被观察；已有素材和测试入口可以直接使用。

只积累大量静态成品、没有编辑入口和依赖描述，可能改善初次生成，但未必改善后续编辑。

### 10.2 优先建设的能力

| 能力 | 建议内容 | 对复杂任务的直接收益 |
|---|---|---|
| 公开数据与配置 | 题目数据、选项、实验参数、难度规则、显示层级 | 批量调整无需重新理解全部实现 |
| 可观察状态 | 当前阶段、提交结果、暂停状态、关键数值 | 运行检查可验证具体目标，不只看截图 |
| 生命周期合同 | 创建、更新、暂停、恢复、销毁、必要的状态迁移 | 避免修改后重新挂载导致进度丢失 |
| 稳定组件边界 | UI、内容数据、业务逻辑、渲染机制分离 | 只修改受影响模块，降低输出量 |
| 实例化与测试样例 | 可运行示例、典型输入、关键行为检查 | AI 直接参考正确接口，减少探索轮次 |

### 10.3 Runtime 参数化的合理范围

当前 `runtime.configure` 可修改的内容有限。[R6] 后续可从使用频率高、由本项目控制的互动底座开始，增加正式参数描述和更新机制。

例如“把单一实验扩成可对比两组参数的实验”可以组合已有数据结构、参数组和显示组件；AI 仍需决定交互与教学表达，但无需重写计时器、事件总线、基本图表和恢复机制。

公开参数应声明类型、范围、单位、关联约束和更新影响。某些参数可以热更新，某些需要重置实验；不能把所有更新都伪装成无状态的小改。

不要尝试自动把任意旧 Runtime 全面参数化。只对高频底座逐步补齐；长尾内容继续允许源码编辑。

### 10.4 与 Skill 的分工

Skill 保留简短工作原则：先识别目标和可复用底座，优先最小必要变化，集中提交关联修改，依据实际失败局部修复，满足要求后结束。

接口和能力来自正式 Schema；学科知识和设计参考按需加载；代码范例放在可检索的参考资产里。不要把所有设计知识、所有工具合同、所有测试要求塞进一个越来越长的 Skill。

模型需要一定自主权决定实现路径。宿主约束修改范围和提交条件即可，不把每一类任务都硬编排成冗长流程。

## 11. 批量、并行与渐进预览

### 11.1 先批量，再并行 Agent

优先级建议如下：

```text
一个候选组织多项修改
→ 一次工具调用支持合适的批量输入
→ 独立的本地准备/检查并行
→ 真正独立的模型子任务并行
```

前两项往往不需要多 Agent，就能减少模型往返。只有实测主导延迟来自独立内容的串行生成，再考虑并行模型。

### 11.2 可并行与不可并行

可以并行：不同页面的独立文字改写、独立资源准备、不共享状态的静态检查。跨页统一设计可以先产生一份简短共同规范，再按页执行，最终检查一致性。

不宜直接并行写入：同一组件源码、同一导航图、同一公共样式、同一资源注册表，以及存在创建—引用依赖的操作。

模型子任务只产生私有候选，宿主统一检查读写范围与冲突。子任务不能各自无条件提交到正在编辑的工程。

第一版即使引入并行，也建议从两个独立任务开始测量，不默认递归扩张子 Agent。并行减少墙钟时间，可能增加成本、限流和合并工作，三者要一起报告。

### 11.3 预览与正式提交分开

页面设计可以在形成完整局部结构后展示临时预览；源码修改可展示变更摘要和通过检查后的行为演示。未闭合 JSON、半段源码和缺依赖组件不能进入正式运行环境。

预览应复用现有私有候选能力。[R3] 不新建一个与正式文档长期不一致的编辑器副本体系。用户接受后再按既有事务应用。

tldraw 提供单次请求、持续循环和流式画布操作的参考；本项目应学习可见产出与任务模式的区分，而非照搬其数据模型。[S2]

### 11.4 进度反馈只报告真实状态

可显示“已读取目标组件”“正在生成交互修改”“候选已就绪”“发现重置后状态未恢复，正在修复”。不要输出虚构百分比，不把长篇思考文本作为主要进度。

取消必须终止旧任务的后续写入权限。已有 `epoch` 和版本检查应继续覆盖模型返回、检查完成、资源生成和实际提交前。[R2][R3]

用户在 AI 工作期间手动改了相关对象，候选需要重新基于当前版本计划；用户只改了无关对象时，是否支持局部重基应作为后续能力，不在首批以放宽全局版本检查的方式冒险实现。

## 12. CLI、模型、缓存与专用执行路径

### 12.1 先优化现有 CLI 路径

保留 CLI 的多轮读代码、运行和修复能力。通过项目可控制的配置缩小工作目录、提供任务相关工具与文件、减少无关技能加载、明确本轮输出和结束条件。

记录进程是否冷启动、会话是否真正恢复、每轮准备了多少文件、模型何时开始返回。会话 ID 相同不等于底层连接与进程已经复用。

只能通过适配器和 CLI 实际支持的接口调整执行预算、思考配置和工具权限。没有公开控制接口的内部行为，应如实记录限制，不靠提示词承诺严格上限。

### 12.2 何时增加直连 API

| 路径 | 适合任务 | 主要优势 | 主要代价 |
|---|---|---|---|
| 现有 CLI 继续承担编辑 | 需要读代码、运行、修复的 B/C 类任务 | 保留成熟原生 Agent 能力和现有接入 | 内部调用及部分开销不易完全控制 |
| 可选直连 API | 目标与上下文已经齐全的整页设计、批量内容修改、边界明确的复杂候选生成 | 更容易控制单次输出、流式候选和工具范围 | 新增接入、鉴权、成本与适配维护 |
| 设计模型 + 专用代码应用 | 大源码修改中，应用阶段输出成为实测瓶颈 | 有机会减少大量未变代码的输出时间 | 多一次调用、错误归因与应用边界更复杂 |

第二条仍然处理真实 AI 编辑，不是小改命令翻译通道。所有路径都进入相同候选协调器和正式工具，不能开一个绕过校验的快捷入口。

建议仅在现有 CLI 的可观测启动/编排成本占比较高，或候选生成任务明显不需要完整 CLI 能力时，再做 API 对照实验。

### 12.3 模型选择按工作负载评测

A 类重点看布局、内容保护、结构化候选和输出速度；B 类看目标代码理解、正确补丁和修复成功率；C 类看分解质量、长程一致性和能否及时收敛。

不预设“快速模型一定更快完成”，也不预设“强模型一定最慢”。首轮稍慢但少两次修复的模型，可能有更低的总耗时。

首批不建设独立路由模型。已有入口或首轮任务判断能决定策略时直接使用；只有分类本身困难且路由收益经过验证，才考虑额外模型。

允许一次有依据的模型升级，但升级时携带紧凑任务包、当前版本、已经完成的工作和失败证据。不能把整段噪声日志、所有旧候选无差别塞给新模型。

### 12.4 缓存分两类

**模型前缀缓存：** 固定系统指令、稳定工具定义和公共范例尽量保持一致，动态工程信息后置。具体是否命中、可控制参数和保持时间以实际提供方与接入通道为准；不要假设 CLI 一定暴露 API 的缓存控制。[S4]

**本地资源与检查缓存：** 缓存源码索引、不可变素材、编译结果和可复用资源负载。以明确版本失效，不能缓存用户任务的成功结论。

缓存只能优化对应阶段，不能消除成功后额外一轮模型调用，也不能修复错误的目标或源码。

### 12.5 专用代码应用后置

Cursor 的公开实现把代码修改的应用作为专门优化环节，说明“设计修改”与“大量代码的应用”可以采用不同方式。[S5]

对本项目，先比较函数级补丁、精确文本补丁、受影响子树替换和全文输出。只有应用成本在真实任务中占主导，才增加专用模型。不能拿厂商展示的 Token 速度直接承诺本项目端到端时间。

### 12.6 本地图像与计算开销

大图片编码、解码、差异计算或大型结构处理可能需要 Worker/独立进程。先记录主线程占用和输入规模，再移出阻塞任务。

连接复用、截图分辨率和事件批量传递同样按证据优化。截图降采样不能让关键公式、细小控件或视觉错误不可辨认。

## 13. 观测与诊断：先让耗时可解释

### 13.1 最小事件集

复用现有会话事件，不新增独立遥测平台。建议补充以下时间点和关联字段：

```text
task_started
observation_ready
agent_launch_started / agent_launch_ready
model_or_cli_first_output
candidate_received
candidate_prepare_started / candidate_prepare_finished
validation_started / validation_finished
preview_ready
user_apply_wait_started / user_apply_wait_finished
commit_finished
receipt_persisted
continuation_requested
repair_requested
task_finished / task_cancelled / task_failed
```

模型内部首 Token、推理 Token 和实际调用数只在通道确实提供时记录。否则使用 CLI 首输出等可观测代理字段，并标明数据来源。

### 13.2 记录结构建议

```json
{
  "traceId": "task-001",
  "taskClass": "interaction-edit",
  "projectRevision": 42,
  "adapter": "configured-cli-adapter",
  "model": "reported-model-or-unknown",
  "hostContinuations": 1,
  "modelCalls": null,
  "modelCallsSource": "not-exposed",
  "candidateCount": 2,
  "automaticRepairs": 1,
  "failureClass": "runtime-behavior",
  "inputBytes": 18000,
  "outputBytes": 5200,
  "resourceTransferBytes": 2000000,
  "cacheHit": null,
  "terminalState": "completed"
}
```

以上数值只用于说明字段，不是本项目的实际运行数据。跨进程时间用关联 ID 对齐；本地持续时长使用单调时钟，避免系统时钟调整影响分析。

### 13.3 三张最有价值的报表

**阶段耗时表：** 各阶段 P50/P95，冷启动与热启动分开。

**失败归因表：** 工具选择、格式、版本、资源、运行、主观不满意、网络/认证分别统计，并关联修复成功率。

**任务效果表：** 首次候选正确率、最终成功率、首次正确修改时间、非请求变化、取消率、平均费用或可用成本代理。

不只统计成功任务。失败、超时和取消单列；比较优化方案时，不能通过更早取消困难任务来“美化”成功样本的平均耗时。

### 13.4 调试数据默认本地保存

日志默认记录元数据、摘要和必要引用。完整源码、用户图片、认证数据、个人内容不自动上传到外部分析服务。完整回放包由用户或开发者明确导出，并排除凭据。

诊断是本轮开发辅助，不扩展成大型安全合规项目。

## 14. 分阶段开发计划

本节按依赖顺序和验收门槛安排，不给未经团队评估的日历工期。每阶段都应保留可回退版本；阶段是否继续由实际收益决定。

### 阶段一：循环止损与最小测量

#### P0-01：补齐任务分段计时

**修改入口：** `generationTaskController.ts`、现有 CLI 事件适配器、`prepareGenerationCandidate.ts`、`dynamicCandidateAdmission.ts`。

**实施内容：** 贯通 `traceId`；增加上述关键时间点；分开宿主续跑与内部模型调用；记录候选次数和拒绝类别；导出本地 JSON 诊断包。

**验收：** 任何一次慢任务都能看出时间消耗于模型/CLI、资源准备、验证还是应用等待；未知数据明确为未知。诊断功能关闭时不影响编辑语义。

#### P0-02：有条件结束与有限继续

**修改入口：** `src/shared/generationContract.ts`；`generationTaskController.ts`；现有协议/适配器；相关合同测试。

**实施内容：** 增加可版本化候选进度元数据与本地策略；成功保存回执后先判断是否结束；需要继续时记录理由；增加墙钟、候选和修复预算。

**验收：** 完整候选成功后不为总结额外调用模型；真正需要运行观察的任务仍能继续；缺元数据的旧适配器可兼容；预算触发后不会继续写入；不能仅靠模型声明跳过检查。

#### P0-03：无进展检测与精确失败反馈

**修改入口：** 控制器错误分支、候选协调器、正式工具诊断传递。

**实施内容：** 错误分类、重复故障指纹、局部证据反馈、一次有依据的升级入口；保留真实提交与回执写入的幂等边界。

**验收：** 相同失败不会无限循环；已提交结果不会重复应用；无关页面不会因修复被重做。

**阶段一退出门槛：** 原有链路回归通过，停止/取消/版本冲突可靠，能对事故案例和一组真实复杂任务输出可解释的分段报告。此时不必先更换模型。

### 阶段二：减少阅读、输出和候选碎片

#### P1-01：目标化观察与能力包

**修改入口：** `src/renderer/authoring/generation/authoringObservation.ts`、`generationSnapshot.ts`、`generationCapabilities.ts`、现有 CLI profile 构造入口。

**实施内容：** 按 A/B/C 类任务组织目标及直接依赖；截图与对象标识对应；首轮预展开相关工具；后续增量观察；稳定公共前缀。

**验收：** 减少因为缺少已知目标信息产生的读取回合；不因减量遗漏父级布局、关联状态或关键依赖；冷启动与恢复会话都能得到正确基准。

#### P1-02：局部补丁和完整批量候选

**修改入口：** 正式源码工具及合同、候选协议、`prepareGenerationCandidate.ts`、CLI 示例/Skill。

**实施内容：** 根据现有源码入口增加或完善基准绑定的补丁支持；保留全文回退；指导模型将一批关联修改放在一个候选；合并同对象兼容配置。

**验收：** 补丁唯一命中才应用；冲突不误写；多步依赖和一次撤销正确；批量任务不逐对象开启模型回合；输出减少不以提高修复率为代价。

#### P1-03：任务级保持条件

**修改入口：** 正式请求合同、候选准备和最终检查。

**实施内容：** 从用户要求与选定范围构造可机器检查的保护条件；添加内容/资源/几何/实例范围检查；软条件进入预览。

**验收：** 页面重排可正常改变布局；要求保留的公式、答案和素材不会被静默替换；源码修复不越界改其他组件。

**阶段二退出门槛：** 相同模型对照中，A/B 类首次正确修改时间有明确下降，首次成功率和内容完整性无实质退化。先解释退化案例，再调整提示或模型。

### 阶段三：验证和资源链路提速

#### P1-04：合并验证与复用资源

**修改入口：** `dynamicCandidateAdmission.ts`、`componentConfigureTool.ts`、`runtimeConfigureTool.ts`、候选协调器，以及动态宿主请求处理入口。

**实施内容：** 优先避免同对象重复配置触发多次验证；测量并复用未变资源负载；缓存静态检查；必要时汇总最终态行为验证。

**验收：** 新执行代码仍经过准入；公开参数变化验证实际受影响行为；缺失资源能补齐；进程复用不残留旧事件与状态；重复验证次数和传输字节可量化下降。

#### P1-05：渐进预览与有效取消

**修改入口：** `generationPreview.ts`、任务界面、控制器和已有私有候选流程。

**实施内容：** 展示完整可预览阶段；区分预览与已提交；按真实事件报告进度；取消传播到运行检查和资源处理。

**验收：** 未完成源码不执行；取消后的迟到结果不能覆盖新任务；已完成阶段和未完成部分清晰；一次用户接受对应一致的撤销行为。

**阶段三退出门槛：** 在资源较大、组件较多的测试工程上确认实际收益，同时保持相关运行和生命周期回归通过。

### 阶段四：按数据选择的后续建设

#### P2-01：高频互动底座可编辑化

为使用频率最高的两到三类底座补参数、状态观察和关键行为测试。不要全量改造所有旧内容。

#### P2-02：可选 API 路径与模型评测

对目标上下文充分的复杂候选任务做同任务对照。只有速度/成本/正确率综合收益成立时接入产品；复用正式候选提交链路。

#### P2-03：受控并行或专用代码应用

仅在分段数据证明独立生成或大段代码应用是瓶颈时实施。记录额外费用、合并冲突、限流和首次成功率。

#### P2-04：Worker、连接与进一步缓存

根据主线程阻塞、冷启动和缓存命中数据实施；不以推测代替优化依据。

## 15. 评测与验收设计

### 15.1 对照原则

先建立现有版本基线，再用同一任务、同一工程副本、同一模型与接入渠道对照。固定软件提交、目标资源和运行环境；记录实际模型版本、配置及服务时间段。

冷启动与热启动分开；随机交错运行新旧路径，减少网络或服务负载变化的偏差。模型支持可控随机参数时记录参数，不支持时不要假装输出完全可复现。

第一轮只改变流程，避免同时更换模型、扩大工具权限和删验证。后续通过单独实验识别各项收益。

| B07 | 将实验参数变化联动到图表和说明 | 三处结果一致，更新不丢失必要状态 |
| B08 | 改变评分规则并保留已定义题目数据 | 评分边界正确，数据不被重建 |
| C01 | 静态函数图讲解改为可拖动参数演示 | 知识内容保留，互动改变正确量 |
| C02 | 静态几何关系改为可操作验证过程 | 条件保持，图形与结论联动 |
| C03 | 增加两组实验对照及统一重置 | 状态独立，对照规则一致 |
| C04 | 为多页内容增加一致的学习进度与回看 | 导航、状态和内容引用正确 |
| C05 | 将一个复杂组件拆为可复用内容与逻辑部分 | 外观/行为基本等价，后续编辑入口清楚 |
| C06 | 在现有互动流程中增加一个有前后依赖的阶段 | 原有阶段保持，新阶段可进入可退出 |
| C07 | 替换授权区域的技术载体以支持新功能 | 转换范围准确，其余对象和手调能力保留 |
| C08 | 对已经部分完成的任务继续修改一个阶段 | 不重复已完成相对操作，不丢已有成果 |

### 15.3 另外六个链路回归

这六项不用于证明复杂 AI 编辑已经好用，但用于防止严重可用性故障：

| 编号 | 故障场景 | 预期 |
|---|---|---|
| R01 | 原始“改色三轮、十分钟、形状变化”案例 | 能定位耗时与越界来源，已授权范围外不被静默修改 |
| R02 | 用户在任务期间手改目标 | 旧候选不覆盖新状态 |
| R03 | 应用后回执持久化失败 | 不重复应用，实际状态清楚 |
| R04 | 两次相同运行错误 | 有限修复，无进展后停止 |
| R05 | 用户取消后旧模型结果迟到 | 不应用，不污染新任务 |
| R06 | 候选包含多个前后依赖步骤，其中一项失败 | 未提交候选不留下半成品；已提交阶段如实保留 |

### 15.4 建议的性能试验预算

下表是**用于首轮压测和产品讨论的目标/预算，不是实测成绩或交付承诺**。适用测试包约束为：目标内容已在本地；A 类约一至八页；B 类涉及少数组件/源码文件；C 类为有限范围互动改造。大规模重写、外部素材生成和特殊网络等待应另分桶报告，不能排除后假称全量达标。

| 类型 | 首次有用候选/阶段的方向目标 | 最终结果的方向目标 | 初始软/硬预算 | 宿主续跑 / 自动修复上限 |
|---|---|---|---|---|
| A 批量与设计 | 约 10–20 秒 | 约 20–45 秒 | 45 / 90 秒 | 2 / 1 |
| B 组件与交互 | 约 20–40 秒 | 约 45–120 秒 | 120 / 180 秒 | 4 / 2 |
| C 结构性改造 | 首阶段约 30–60 秒 | 约 120–240 秒 | 240 / 360 秒 | 8 / 3（全任务） |

完成基线后，应根据任务难度和可用模型调整这些数字。预算过低会导致过早中断，过高会重新出现长期等待。调整必须结合最终成功率，不能只看平均时间。

界面中的状态反馈应明显早于有用候选；但没有真实结果时，只显示正在处理，不能把假预览当作有效产出。

### 15.5 发布门槛建议

**第一项：正确性。** 关键要求和保护条件的回归样本全部通过；单次撤销、保存恢复、相关运行行为不退化。样本中零越界不等于能够证明所有未来任务零越界。

**第二项：有效提速。** 在固定 A/B 任务集上，首次正确修改时间的中位数争取降低至少 30%，且不能以降低首次成功率、增加取消或减少任务范围为代价。30% 是项目决策阈值，需通过对照得到，不是预测收益。

**第三项：尾部受控。** 没有无预算续跑，没有成功后仅为总结新增的模型请求，失败终态明确可解释。

**第四项：统计口径。** 初期可每种模板重复三次排查明显问题；这样的样本不足以稳定估计分类 P95。准备发布前扩大样本，报告样本量、分桶结果和不确定性，避免用少数成功样本作精确速度宣传。

## 16. 三个端到端示例

### 16.1 整页重排：保留公式，改为“例题—图解—结论”布局

**首轮输入：** 页面整体截图、对象简表、全文与公式、页面尺寸、原有阅读顺序、不可删除的要点。

**AI 工作：** 同一轮中确定新布局并形成多步候选，调整目标对象，不重新生成无关素材。无需先调用一个规划模型，再调用另一个执行模型。

**宿主工作：** 在私有文档预演，检查公式/关键文字保留、对象范围、主要溢出和遮挡；形成完整预览。审美质量由必要的定向观察或用户预览判断。

**结束：** 候选声明已经完成全部拟修改部分，客观检查通过后，按现有应用策略结束。没有明确问题，不追加“再检查一次整体是否更好看”。

**失败修复：** 某段公式超出容器时，只反馈对应对象、当前宽高、溢出量和局部截图，模型修复受影响区域。

### 16.2 互动修改：为答题流程加入提示、二次尝试和最终解析

**首轮输入：** 目标组件源码、题目数据结构、提交事件、当前状态流、现有显示区域和合同。

**AI 工作：** 修改状态转换和相关界面，保留题目数据与原评分要求；必要时加入少量新状态。补丁只覆盖相关模块。

**宿主工作：** 执行首次错误—提示—第二次作答—最终解析等任务相关路径，检查重置、返回与重复点击。不要顺带运行所有无关课程导出矩阵。

**结束：** 关键行为通过后显示结果并结束。只有缺少运行后的真实信息，才返回局部观察继续。

**失败修复：** 二次尝试后解析未显示，返回该状态和触发步骤。修复同一状态分支，不重写整套答题组件。

### 16.3 跨页与组件协同：改为“先预测，再实验，最后总结”

**首轮输入：** 相关页面摘要、实验组件接口、已有导航关系、要保留的知识结论。

**AI 工作：** 确定三阶段安排。能一次形成的结构和文案在同一候选中提交；需要实验运行结果支撑的部分保留为明确后续阶段。

**并行选项：** 各页文案可在共同规范下独立生成；实验组件和导航的共享修改仍由主任务组织。未经冲突检查的子任务不能直接提交。

**宿主工作：** 验证阶段可达、实验联动、返回路径和内容完整性。阶段应用后保留实际回执，下一轮只收到变化和待完成目标。

**停止：** 超过预算时说明哪些阶段已有结果，哪些尚未完成。保留可用成果，由用户决定后续方向，不继续隐藏运行。

## 17. 执行约束与可直接交给开发 Agent 的任务说明

### 17.1 防止本方案在实施时再次膨胀

不要先重构所有创作工具；不要先建立通用路由平台；不要把所有旧组件改造成新合同；不要把每个策略都做成独立服务；不要为未经测量的开销引入常驻进程池；不要新增默认多模型互审。

每个改动都回答三个问题：减少了哪一个可观测开销；保留了哪些正确性边界；用哪组任务判断是否值得保留。

优化造成首次成功率下降、错误写入扩大或取消不可靠时，应回退对应改动，而非继续叠加提示和补丁掩盖问题。

### 17.2 首批开发任务文本

```text
任务：改善 ittoedu 中真实复杂 AI 编辑的等待时间。

产品边界：
- 容易手动完成的小修改不建设 AI 确定性命令快通道。
- AI 重点服务整页/多页、批量内容、组件交互和源码修改。
- 保留现有 CLI、正式工具、私有候选、事务、撤销与版本保护。

本次只完成阶段一：
1. 读取当前代码，确认 generationTaskController 和候选协调器与
   方案引用基线的差异，不覆盖用户已有改动。
2. 增加分段计时，区分宿主续跑、候选次数和可观测的 CLI 事件。
3. 在正式合同中增加兼容的完成/阶段元数据。
4. 成功应用并保存回执后，只有明确需要继续时才捕获新观察并续跑。
5. 增加墙钟预算、修复预算、继续理由与无进展检测。
6. 返回具体失败目标与证据，不用全项目重生成作为默认修复。

约束：
- 不把工具成功或模型 done 声明直接等同于任务完成。
- 不取消新源码的必要准入与受影响行为检查。
- 不改变用户现有 applyPolicy。
- 回执保存失败不得重复实际提交。
- 旧适配器不能因为缺字段被误判为完成。
- 不默认换模型、加多 Agent 或引入新工作流框架。

验证：
- 完整候选成功后不为总结再调用模型。
- 真正需要运行观察的阶段任务仍能继续。
- 相同失败有限修复，超预算不继续写入。
- 取消、过期候选、用户并行手改、回执写入失败均行为正确。
- 用几项真实批量/交互任务对照原路径，导出分段记录。

交付：
- 代码与聚焦测试。
- 改动文件、实际行为差异、仍存在的限制。
- 原路径与新路径的真实记录；没有测量的数据写未知。
- 本次没有实施的后续阶段，不宣称已经完成。
```

### 17.3 方案取舍结论

最先值得投入的是循环与候选组织，其次是上下文、局部补丁和验证去重。底座可编辑化是长期收益较大的能力，但不应阻塞前面的修复。模型、连接和并行策略以实测决定。

最终要达到的体验是：用户提出一个值得交给 AI 的修改，AI 理解相关内容、完成一批有边界的变化、验证必要结果，并及时结束。既保留复杂创作能力，也不把每次编辑都变成一场漫长的通用软件开发任务。
