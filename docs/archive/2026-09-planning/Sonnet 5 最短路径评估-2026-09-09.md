# Sonnet 5 最短路径评估

对《AI编辑最短路径产品决策报告.md》(以下简称"原报告")的独立评估。

## 我的结论

**方向认同，但先别当执行文档用——它和仓库里已经存在的规划严重重叠却没有互相引用，这个风险比任何一条引用错误都大。**

原报告的核心判断("接口优先、AI自主选接口、宿主准确执行"、"自动模型路由不宜本轮先行"、"保留原生CLI循环")站得住脚，我核实了它引用的全部15处内部代码行和约40条外部链接(9个开源项目的固定commit + 6篇官方文档 + 2个竞品资料)，绝大多数准确，几处具体错误也都是可修的小问题。但我自己翻仓库时发现一件原报告完全没提的事：它讨论的四个主要机制——图片改色、能力按需发现、模型选择、聊天JSON分流——在仓库里都已经有对应的、更早的、写了执行步骤和验收标准的路线图任务卡(`r18-098`/`r18-096`/`r18-091`/`r18-101`)，以及更精确的数字目标(能力说明≤12KB，而不是原报告讨论的5,200字节预算)。原报告一次都没提到这些任务卡的编号。

这不是说原报告没用——它用开源项目做了独立佐证，还提供了一个此前没有的真实失败案例，这些都是增量价值。但如果不先把它和已有任务卡对一遍表，很容易变成仓库自己反复警告的"第二套工程真相"。

3. **仓库既有规划的交叉核对**：这部分不在原报告的核验范围内，是我自己做的——我读了`AGENTS.md`、`COURSEWARE_DEVELOPMENT_PLAN.md`、任务看板、以及`docs/development-plan/reviews/1.8-ai-assistant-gap-register.md`和`docs/development-plan/roadmap/1.8/`下的具体任务卡，看原报告的技术判断是否和这些已经存在的、Owner已经过目的规划文档吻合。

## 二、最重要的发现：原报告讨论的问题，仓库里已经有任务卡了

这是我认为整份评估里最有价值的部分，因为它不是"引用对不对"的问题，而是"这份报告接下来该怎么用"的问题。

### 2.1 具体对应关系

`docs/development-plan/reviews/1.8-ai-assistant-gap-register.md`(诊断基线2026-09-07，比原报告早2天)已经把创作助手的真实使用缺口编号为G01-G12，并且`docs/development-plan/roadmap/1.8/`下已经有对应的任务卡文件，每张卡都写了"允许写域"、"执行步骤"、"验收与可信反例"、"停止条件"：

### 2.2 一个更值得注意的细节：报告的"新发现"可能是"旧问题的新证据"

原报告的headline案例(那次9分30秒的改色失败)发生在2026-09-09。但gap register的"当前结论"写着："**089–104相关产品实现已集成**。真实Codex关键链已有识图零写、图片改色...的直接证据。"——也就是说，按仓库自己2天前的记录，G01(AI看不到图片)和G02(图片改色路径)在2026-09-08就已经有"已修复"的证据。

我核对了真实会话日志，失败原因是**这次具体的PNG数据块校验失败**，触发了`semanticReplacementTool`的错误兜底(用绿色文本块替换原图片)——这更像是G02修复之后暴露出来的一个更具体的次生失败模式(特定PNG兼容性 + 错误的失败兜底路径)，而不是一个全新的、无关的问题。而`r18-098`的验收用例(T02/T03)恰恰明确要求覆盖"含内容图的局部改色"和"禁止遮盖冒充"，这次真实失败正好是T02/T03要防的那类情况。

这里有必要提醒一句：这个仓库自己的记忆里记录过一次教训——[[w2-courseware-failure-root-causes]]那次，两个课例"全部自动门禁通过、manifest写成engineering candidate"，但人工体验后发现阻断性失败，根因是形式校验没有覆盖语义/行为层面。我不确定`r18-098`当前的验收状态具体如何(我只核对了任务卡的范围定义，没有找到它的最新验收记录)，但原报告提供的这次真实失败，无论r18-098当前状态如何，都应该被当作"验证G02/r18-098是否真正关闭"的直接证据来使用，而不是被当成一个独立、全新的问题重新讨论一遍。

### 2.3 已有的数字目标比原报告更具体

`docs/development-plan/AI_ASSISTANT_VSCODE_BENCHMARK_ASSESSMENT.md`(定义gap register证据基线的文档)第145行已经写明：

> 速度拆为宿主准备、CLI启动、首个原生事件、首个可读文本、模型/工具执行、准入、应用和呈现。建议本地状态反馈<500ms、可读事件到UI的p95<300ms；简单任务初始文本能力说明≤12KB，较当前约119KB能力定义显著降低。

"约119KB"和G07的"127KB"基本对得上(tools 87KB + dynamicCapabilities 32KB + 页面约1KB)。这意味着已有文档给出的目标是**把119KB压到12KB以内，约10倍压缩**，比原报告"首轮提供少量完整信息"这种定性表述具体得多。原报告的Appendix A只讨论了图片变换接口的传输投影示意，没有对齐这个已经存在的12KB数字目标。

同时我要提醒一点容易被忽略的地方：G07拆解的127KB里，**87KB是"tools"定义本身**，只有32KB是"dynamicCapabilities"(原报告L2脚注讨论的能力卡机制大概率落在这一部分)。原报告的架构边界明确"保留原生CLI的文件、终端、网络、Skills、连接与模型循环"——如果87KB的tools定义是三个CLI自带的原生工具协议的一部分，这部分很可能不在这次能动的范围内。也就是说，原报告提出的修复大概率只能动32KB这部分，而不是全部119KB。这不代表原报告的方向错了，但如果不说清楚，容易让人以为"接口投影"改完之后请求会从119KB降到12KB附近，而实际可触达的压缩空间可能明显更小。建议原报告或后续执行者明确一句："本轮改动预期能把dynamicCapabilities部分从32KB降到多少，tools部分是否可动、由谁批准。"

### 2.4 我的建议

不要把原报告直接当成新的执行清单来排期。建议下一步是：找一个人(或者下一轮请求我)把原报告的六个"推荐的产品行为"小节，和`r18-091/096/098/101`的"执行步骤"逐条对一遍，标出：哪些是重复的(可以合并，原报告的开源引用可以作为这些任务卡的补充论据写进去)、哪些是原报告独有的新点(比如"回执决定执行事实"这条，我没有在r18-101的执行步骤摘要里看到明确对应，值得确认是否已覆盖)、哪些措辞有出入需要以哪个为准。这件事原报告自己的行文逻辑其实也认同——它反复强调"不能维护第二套随意漂移的参数定义"、"不建立第二工程真相"，只是没有把这条原则用在自己和已有任务卡的关系上。

## 三、外部引用核验：总体结论

40条左右的外部引用(9个开源项目固定commit + 6篇官方文档 + 2个竞品资料)绝大多数**核实无误**，且原报告在细节上相当审慎——它自己主动指出的两个"反例"(tldraw的Update动作要求完整图形schema、Excalidraw摘要机制不覆盖颜色/文本变化)都被验证为真实存在，说明作者确实读过源码，不是挑着引用。

| 1 | WPS文章链接已失效(两次WebFetch均404) | wps.cn上有同主题不同slug的文章(如`ai-work-summary-records-results-review.html`)，需要替换链接或标注"引用时可访问、现已下线" |

以下是分项详情。

### 3.1 语义动作层论据(tldraw / Penpot / Excalidraw MCP)

三个项目的具体代码事实**基本都核实无误**。值得注意的细节：

- tldraw的`SelectedShapesPartUtil`比原报告描述的更精简——只传形状ID，不传完整几何；`MoveActionUtil`确认只用`shapeId, x, y, anchor, intent`，几何计算全在客户端完成。但原报告自己点出的反例(`UpdateAction`用和`CreateAction`同一个`FocusedShapeSchema`，即"更新"在schema层面仍是完整图形而非差量)也被验证为真——这条反例是成立的，说明tldraw本身也没有完全解决"更新"场景的最短路径问题。
- **license边界原报告没白强调**：`templates/agent/LICENSE.md`是标准MIT，但仓库根`LICENSE.md`是tldraw自定义许可证，明确禁止在生产环境免费使用，需要商用许可证且内置License Key校验和遥测。也就是说模板代码可以自由复用，但驱动它的tldraw SDK本体商用是受限的。
- Excalidraw MCP的"变化摘要不覆盖颜色/文本变化"这条被验证得非常精确：`computeDiff`只比较四舍五入后的x/y/width/height，完全不比较`strokeColor`/`backgroundColor`/`text`/`opacity`等字段，纯改色或改文字时该摘要函数直接返回空字符串。
- **一个原报告没提到、但很相关的反例**：tldraw团队自己在2026年8月发的博客《Agents can't point》承认，模型"指代/引用"画布对象(this、here、there)本身就是一个语义动作层解决不了的上游问题，他们的应对方案是另加一套"带位置锚点的评论"机制。这提醒我们：语义动作层解决的是"如何执行编辑"，不是"如何准确知道编辑的是哪个对象"——这两件事原报告目前当成一件事在讨论。
- **Excalidraw MCP的活跃度被高估**：仓库创建于2026-02-04，最后一次提交在2026-03-24，到今天(2026-09-09)已经约5.5个月没有新提交，实际只有约7周的活跃开发期。5262星、487 fork很大程度上是因为挂在官方excalidraw组织下(主项目12万+星)沾光，把它和tldraw、Penpot放在同等权重引用需要加活跃度限定。

### 3.2 按需发现/上下文管理论据(Cloudflare Agents / Pi / Aider / Continue)

- Cloudflare的搜索实现"对中文不友好"这条被验证得比原报告说的**更严重**：分词函数全程只有`[a-z0-9]`这类纯ASCII正则，没有任何Unicode-aware处理，纯中文查询("换成绿色")会被`tokenize()`直接返回**空数组**——不是"处理得不好"，是完全拿不到token，等于这条查询路径根本不工作。
- Pi**不是小众项目**：这点需要向你更正——它有10.3万星、1.29万fork，2026年5月才从个人仓库迁移到现在的组织下，相当有影响力，原报告如果预设它是"小众参考"分量偏低是不准确的，实际上它的证据分量应该更高一些。
- Aider的两处引用是四个项目里核实精度最高的——`repomap.py`第340行、`editblock_coder.py`第38行都精确命中对应逻辑的起始点，PageRank加权(已打开文件权重×50，提及的文件/标识符×10)和失败反馈机制(用`SequenceMatcher`给出近似匹配建议)都确认属实。

### 3.3 模型路由论据(RouteLLM / LiteLLM)

- RouteLLM的源码自己承认局限——`controller.py`第109行原话："Our current routers were only trained on first turn data, so more research is required here."路由决策只看`messages[-1]`(最后一轮内容)，整个Controller类没有跨调用的会话状态。这条自我披露的局限，比原报告转述的还要直接，支持原报告"首轮训练数据与多轮应用存在边界"的判断。
- LiteLLM的`lowest_latency.py`(部署间选延迟)和`complexity_router`(按复杂度跨模型路由)确认是两个不同子系统，LiteLLM自己文档里就有"Comparison with auto_router"表格，原报告"延迟路由选择服务部署，与理解编辑接口不是同一问题"这条区分成立。
- 顺带一提：LiteLLM引用的那个commit,核实时发现提交时间是**今天**(2026-09-09)，是main分支最新合并——只是巧合，不影响核验结论。

### 3.4 OpenCode / ACP协议

- 原报告最关键的一条"翻案"论断——**"两条models.dev超时日志不能直接解释下拉框失灵"**——核实后证据非常扎实：`models-dev.ts`的`refresh()`把失败原因包在`Effect.tapCause(...).pipe(Effect.ignore)`里，缓存清空(`invalidate`)只在请求**成功**之后才会执行，失败时已缓存的目录完全不受影响。这条判断站得住。
- 但要提醒：仓库自己的`G04`已经记录了一个更具体、更早诊断出来的根因——"Codex写死low，OpenCode默认Big Pickle，且Big Pickle不返回强度选项"，也就是说UI没有从真实adapter能力生成选项，这是和"模型目录超时"完全不同、且已经有task card(`r18-091`)在跟的问题。原报告的OpenCode章节没有提到G04，读起来容易让人觉得"根因还没定位"，但实际上已经有一个更明确的诊断在旁边。
- ACP协议的分组能力核实后**比原报告呈现的更确凿**：`schema.json`里`SessionConfigSelectOptions`确实有真正的二级分组结构(`SessionConfigSelectGroup`，含group id/name/嵌套options数组)，不只是原报告说的松散`category`标签。但这个能力**只写在schema.json里，官方中英文提示词文档全文搜索"group"零命中**，而且OpenCode v1.18.26自己也没用这个能力(只输出扁平数组)。原报告"应兼容的协议边界，不能当成本次已证明的根因"这句措辞，核实下来把握得恰到好处——没有把这个当前没被触发的兼容性风险说成已经坐实的根因。

## 五、原报告论证上可以补强的三处

除了具体引用错误，我认为原报告在论证层面有三处可以做得更好：

**1. "自动模型路由不宜先行"这句话需要收窄，否则会显得脱离现状。** 到2026年9月，自动模型路由已经是GPT-5、Cursor Router等旗舰产品的出厂默认架构(Cursor Router公开数据：Balance模式比Opus 4.8便宜41%且效果更好，Intelligence模式成本降68%且满意度超过Fable级别)，AWS/Azure/Google也都有官方方案。如果"不宜先行"被理解为"这项技术不成熟"，现在已经不准确。但原报告真正的主张其实更窄——"这个课件产品不该在本轮自建复杂度分类器"——这个窄主张是站得住的，而且有一个很好的外部支持：Cognition(Devin)2026年的Fusion架构博客明确说"现有的混合模型工具在多数基准上看起来不错，但写不出真正能合并的代码"，因此没有采用简单的自动路由，而是用"主智能体+更省钱的sidekick智能体"精细编排。建议原报告把论据从"路由不成熟"改成"路由已在别处成熟，但这不构成本产品本轮自建同类分类器的理由，Cognition对'朴素路由写不出可合并代码'的公开质疑支持这个更谨慎的窄立场"。

**2. "工具检索式发现"这个方向的证据基础应该更新。** 原报告只引用了Anthropic的Tool Search Tool(2025-11)。到2026年年中，这个方向已经从"一家平台的测试版"变成至少三个生态(Anthropic、OpenAI/Azure、LangChain)都有官方方案的成熟模式——OpenAI为GPT-5.4+推出了官方Tool Search(最高减少47% prompt token)，LangChain在2026-04发布了"Progressive Tool Disclosure with Deep Agents"官方指南。这些新证据是**加强**而不是削弱原报告"常用接口直达、长尾接口一次发现"的判断，补充引用会让论证更有说服力，也避免显得只知道Anthropic一家的方案。另外，Anthropic自己在2025-09-29(比报告引用的两篇更早)发过一篇《Effective context engineering for AI agents》，核心论点和原报告"已有信息不让模型重述"几乎同构，原报告没有引用这篇更贴题的文章，值得补上。

**3. 5,200字节的能力卡预算修复，和已知的127KB/119KB总量问题不在一个量级上，建议明确讲清楚能覆盖多少。** 见第二节2.3的讨论——这不是错误，是范围没讲清楚，容易造成"修完就能显著变快"的预期，而实际可触达的压缩空间可能只是总量的一小部分(约32KB里的一部分)，因为87KB左右是三个原生CLI自带的工具协议定义，按现有架构原则(保留原生CLI能力)大概率不在这次改动范围内。

另外一个小提醒：原报告的headline案例(9分30秒)和同一批reviews目录下两天前(`1.8-cli-call-format-repair.md`)记录的真实端到端测量(Codex基础生成约1.9分钟、OpenCode约1.6分钟、源码修订2.0-2.9分钟)放在一起看，更支持"这是失败重试级联导致的异常值"而不是"这是当前的典型延迟"，这其实也印证了原报告自己的核心论点(Agent回合数不是底层模型请求数、失败会扩大探索)——但原报告没有引用这个近在咫尺的基线数据做对比，加上会让"这不是常态，是特定失败级联"这句话更有说服力。

## 六、原报告写作时未覆盖到的2026年新进展(不影响结论，仅供参考)

原报告的知识边界卡在"2026年9月9日可访问的官方资料"，我自己的知识截止在2026年1月，所以专门检索了1月之后的行业变化，供你判断这些是否需要纳入下一轮报告：

- **"语义动作/减少模型输出冗余"这个方向2026年有新的独立论文**：SimpleTool(2026-03)发现工具调用输出里大量是冗余、低熵的JSON分隔符和参数名，用特殊token压缩后端到端加速3-6倍，和原报告"减少模型输出中的固定身份与工程结构"的论点几乎同构，可以作为比开源项目更"学术"的旁证。
- **"patch vs action"没有形成行业统一答案**：连OpenCode自己都按模型能力在字符串替换(edit)和统一diff(apply_patch)之间切换，不是单一范式获胜；真正跨系统一致的模式反而是"编辑后立即用测试验证"(Edit-Test Loop)，这个视角原报告没有涉及。
- **Devin的规划阶段优化**：经强化微调后把"规划阶段"的模型-工具往返从8-10次降到约4次(2倍提速，同时提升文件选择准确率)，思路上直接对应原报告"减少模型回合"，是很有力的旁证，可以补充引用。
- **Figma Agent**(2026-05公测)采用"多模型策略，没有统一大模型，每个工具挑最合适的模型"，呼应原报告"操作语义比模糊的图片处理更可执行"这一定位。
- 我们检索后**没有找到**比原报告更严谨、专门针对"AI课件/白板编辑延迟优化"的公开分析文章——这方面原报告本身具备一定原创性。中文同类竞品(Boardmix、希沃白板)公开资料同样只有营销/教程性质，和原报告对WPS/飞象老师的处理方式(只能证明功能存在，不能反推架构)是一致的。
