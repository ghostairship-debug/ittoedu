## 原生崩溃的决定性证据

当次实际 LocalDumps、Windows Application/WER 记录、匹配 PE 与官方 PDB 公用符号已交叉核对。

| 进程 | 当次实际故障 | 已排除的误归因 |
|---|---|---|
| MCP Main 49412 | electron.exe+0x2c3c4a，实际指令 0F0B；属于 RenderProcessHostImpl::InitializeChannelProxy 的预置条件 UD2，邻接 ReadOnlySharedMemoryRegion::Duplicate / TransferSharedLastForegroundTime | 普通 CPU 扩展指令不兼容；JavaScript send 日志直接造成 Main 崩溃 |
| Renderer 96108、96308 | 同 MCP profile，约半秒前在 kernel32 初始加载链报 c00000fd；DbgHelp 实际展开各17帧，无递归 | 课件 JS 深递归、把它们当成内置路线或 GPU 进程 |
| 内置路线页面 | 先 Target crashed，随后 Main 仍读回、保存 revision30、处理导出冲突与超时，模型循环终态 partial；03:04:55才被授权清理 | 两条路线 Main 都自然崩溃、失效 frame 日志意味着保存丢失 |

两个 renderer dump 捕获时系统 committed/limit 分别约99.20%和99.53%，commit余量约697MB和408MB，可用物理内存约424MB和164MB。三份 dump 的 PeakCommitment 达同一上限约87.5GB。renderer 预留栈8MiB，但故障 RSP 距 StackBase 只有约8KiB，已提交栈约20KiB；这与递归耗尽8MiB不符，和压力下新 guard page 无法提交相容。

Main 分支和匹配源码指向可选 last-foreground-time 共享内存区域。转储没有收录关键堆成员的原值，也没有取得精确 Win32 分配错误码，因此**最强工作假说是资源压力下 renderer／共享内存初始化失败，随后触发条件陷阱；尚不能宣布这是唯一根因或已经修复**。Main 所属 job 的 private commit 峰约21.48GB，不等于该进程物理 RAM，更不能直接推成泄漏。

同时间段没有查询到 System Resource-Exhaustion-Detector 2004事件；这不反证转储携带的压力。PEB NtGlobalFlag均0，当前IFEO也无对应调试项，没有人为启用 loader snaps 的证据。只读取了约2.83MB的 Electron PDB Range索引及约1.9MB的匹配 ntdll PDB，未下载3.9GB整包，也未上传转储。

## 已定位的软件资源成本

当前专业 Text、Shape、Image 等已有 DOM／Canvas 实现，不能误称为全部专业节点都套 iframe。主要 iframe 来自 Web、HTML Program 和自定义 Source。

原MCP revision32有232个Web、35个文本和一个导航节点，资产为0。一个自身data约9.7KB的小Web，也收到约17.49MB的整课 targets：包括完整project、surface和每实例data。232份序列化体量算术约4.06GB，不能与heap、job commit或UD2因果画等号。

首次访问挂载已减少首开扇出，实际初页16iframe；已访问页面保留realm、输入和状态，inactive文档也保World，仍会按有限访问累计。现有证据不足以称为泄漏，但逐realm重复整课数据是可以继续消除的具体成本。

默认Web／HTMLProgram已知adapter没有读取整课targets。自定义Source的API5同步instance、surface、project读取，以及跨未访问页数据读取有正式合同和既有行为证据，必须保留；现桥也没有可直接复用的通用异步数据查询接口。

**最小修复方向：由唯一 targets snapshot owner 为已知adapter提供窄传输投影，保必要目标身份、presentation及现父动作端口；自定义Source先保现同步读取能力。** 这比取消隔离、每次切页销毁状态、加调用次数/内存预算门或另造通用RPC平台更符合当前证据。动手前应核对各adapter实际消费者，修后只对同原页观察的载荷、资源峰和行为作一次相关对照。
