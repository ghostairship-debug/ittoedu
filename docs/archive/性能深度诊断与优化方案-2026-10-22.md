## 1. 结论与阅读顺序

**主要根因是变化传播和数据处理范围过大，而不是某一个控件或单一解析库慢。** 当前多个入口把“一次局部输入／选择／移动”转换为整工程捕获、整正文重建、整历史编码、全运行世界同步及跨进程／iframe 广播；同一份媒体又在多个 owner 与 realm 中重复物化。文件观察、工具流式预览和若干生命周期缺口进一步放大空闲与久用成本。

建议沿现有 DocumentSession、资源服务、运行宿主和文件协调 owner 修复，形成以下主线：

1. **局部变化只处理局部数据**：去除整媒体捕获、全文反复转换、全实例失效和无关对象重挂。
2. **派生数据按真实依赖复用**：让缓存位于复制、解析、签名和 IPC 之前；内容、选择、相机、状态分别失效。
3. **持久化表达增量化**：保留完整撤销／恢复能力，改写每次重写全部历史的表达，保存提交边界不变。
4. **只合并可以替代的临时工作**：悬停、几何预览、目录刷新、目标发现、过时显示版本；正式事务、命令、副作用和已承诺回执保持顺序。
5. **消除源头重复后再迁移重计算**：归档、解析、像素变换等移出 Main／前台 Renderer；不是把重复全量工作换个线程继续做。
6. **资源随真实生命周期释放**：清理已结束编辑预览、已关闭文档选择、旧节点句柄和失去消费者的 watcher；保留用户运行状态与未知结果查证。

本报告的发现清单有意区分“源码确定存在的工作”“只在特定规模／操作下有意义的成本”和“尚需现场测量的归因”。**条目数不等于独立缺陷数，也不是要求全部立即实施。** 重叠项按第 7 节实施包合并；没有证据的全局重写、换框架、通用缓存平台或性能门不列为默认方向。

建议先看第 2 节证据、第 3 节根因、第 6 节方案比较、第 7 节执行顺序；第 5 节提供可直接接手的细项定位，第 8—10 节说明验证、排除项和来源。

## 3. 为什么多种操作会一起卡

### 3.1 一次 Flow 输入的放大链

~~~mermaid
flowchart TD
  A[一次正文输入] --> B[PM 全树身份修复和默认样式]
  B --> C[全文转换与结构协调]
  C --> D[捕获整工程与全部资源]
  D --> E[预览 apply 与全工程验证]
  E --> F[Session 正式 apply / 比较 / changes]
  F --> G[复制编码完整恢复状态并持久化]
  G --> H[完整 snapshot 与资源传回界面]
  H --> I[全运行世界同步与 targets 广播]
  H --> J[缩略图 / 属性 / 组件库重新派生]
~~~

它说明多个叶子问题会在同一个操作内叠加，不能把每个耗时当作独立事件简单相加；也说明仅优化最后的 React render 或只把 parse 搬 worker，无法消除前面数据放大。

### 3.2 数据规模与频率相乘

设 P 为作者工程体积，B 为唯一资源字节，D 为正文节点／文本量，H 为保留历史量，R 为已挂载 realm 数，F 为事件／输入批次数：

- 当前局部输入可能承担 O(P+B) 捕获、若干 O(D) 转换，表格样式或附件协调另有接近二次／笛卡尔扫描。
- 当前 journal 每次处理 G(H)：全部保留模型版本、History、回执与唯一资源组成的对象图。共享资源不会自动使各版工程对象共享。
- Runtime full targets 和全表资源有 P×R／B×R 的扇出，而不是只处理变化实例。
- 流式参数与图像历史反复从头处理前缀，累计可能接近二次；延迟到最后一批不改变这类表达根因。
- generation／sequence 仅丢弃旧结果时，已经发起的 CPU、I/O、IPC 和队列占用依然发生。

以上是调用形状的成本模型，不是硬件上精确的延迟公式。

## 4. 方案必须保持的产品与正确性边界

1. DocumentSession 继续是唯一正式 writer／History owner；投影、缓存、索引和 worker 不成为另一份可写工程真相。
2. 保留当前 Project 11／Published 4／API 5、三表面的真实编辑语义、作者布局、程序运行态和可编辑导出结果。性能修复不默认迁移工程格式或静默静态化内容。
3. 保留最终 CAS、文档身份／epoch／revision、操作幂等、停止屏障、资源引用和授权根；对已知无需重复的机械处理去重，不去掉防实际错写和未知副作用重放的边界。
4. 保留承诺的撤销／重做、恢复与 durable ACK。历史可改为效果表达，不通过截短 Undo、丢回执、提前 ACK 或降低刷盘承诺换速度。
5. 临时显示合并与正式命令分开。移动／悬停可每帧取最新位置；画笔保留中间采样；自定义 Source 的 update 可能有副作用，不一律丢中间调用。
6. 不转移或 detach Session／History 仍使用的 canonical ArrayBuffer。跨 opaque realm 的 URL、权限和资源租约由现有 owner 维护。
7. 按真实关闭／终态释放资源。离屏实例按既有合同保活，不默认销毁重挂、通用堆快照或自动重播。
8. 只核验待证明属性。Hash 用于当前确需的身份／完整性／幂等，不能扩大为一般正确性门；已有效且相关实现未变的证据继续复用。

## 6. 关键方案比较与推荐选择

“最优”在这里指当前证据、已有 owner 和产品约束下的最佳工程选择，包含总工作量、交互延迟、内存、实现与迁移成本。互联网资料支持技术机制，不能代替本软件的实际收益测量。

### 6.1 History 与恢复：现有 journal 内增量效果＋checkpoint

| 备选 | 能解决什么 | 留下什么／代价 | 选择 |
|---|---|---|---|
| 只把现有整state序列化搬worker | 减少Main冻结 | 每次仍处理G(H)、重写全部历史，内存／I/O持续增长 | 配套措施，不能作为最终修复 |
| 压缩当前整state／更快serializer | 部分减少磁盘字节或CPU常数 | 模型版本与回执表达仍重复，保存反读仍重 | 可测，不优先 |
| Session产生状态效果，journal增量追加＋checkpoint | 局改不再重写全部历史；History／receipt可精确恢复 | 需要规范现有操作效果、历史栈动作及旧恢复读入 | **推荐** |
| 迁SQLite WAL | 成熟事务、索引、增量存储能力 | 新依赖、WAL／SHM、迁移；若整state当blob存仍原问题 | 当前无须换存储引擎 |
| 截短Undo／删回执／提前ACK | 减少表面体积 | 改变用户能力、崩溃／重试语义 | 不作为本轮方案 |

推荐边界：

- 正式apply得到 forward／inverse 状态差异，或复用现有source splice／组件字段edit；不创造另一套通用作者语言。
- 追加内容包含序号、epoch、operation身份／摘要、revision推进、History push／amend／undo／redo、binding／saved／stop变化、必要新资源。未变资源按现有身份和版本引用。
- **恢复只重放已经提交的纯状态效果**，不重跑工具、网络、导入、程序、测量或文件发布。不确定外部保存结果仍走现有intent／proof。
- checkpoint保当前模型及全部承诺历史的效果表达／引用，不只留current并丢历史。旧恢复记录按明确版本读入，保原件和真实Undo／Redo；本次方案不迁移真实profile。
- durable record完整写入及必要fsync后才确认正式提交。fsync是异步I/O等待；主要JS冻结来自前面的clone／encode／parse，不混称“fsync同步阻塞JS”。
- 可重建索引合并更新；checkpoint在后台准备，最终替换回到原journal队列，保最新后缀或放弃本次维护。不能后台rename覆盖新提交。
- 普通保存归属用原owner已确认轻量head；首次load或journal文件身份改变时重建／查证，不能把可重建binding索引独自当作提交成功事实。外部文件身份、发布原子性和未知结果查证分别保留必要检查。
- 这属于内部恢复codec演进，GLX作者格式可以不变。checkpoint明确覆盖current／savedModel、past／future、historyGroup amend、receipt digest／result、binding／savedRevision和stop屏障；旧完整恢复记录只在读入边界转换，不自行迁移真实用户资料。

技术参照：[Node V8序列化](https://nodejs.org/api/v8.html#serialization-api)、[FileHandle.sync](https://nodejs.org/api/fs.html#filehandlesync)、[SQLite WAL](https://www.sqlite.org/wal.html)。V8明确等价值的编码字节不保证相同，不能拿serializer字节当一般语义digest。

### 6.2 编辑与投影：结构共享＋真实变化范围

| 备选 | 判断 |
|---|---|
| 机械给所有React组件加memo／useShallow | 输入仍每次新造全project、全courseView、callback，缓存难命中；不能替代依赖修复 |
| 全输入debounce | 可降频，但可能延迟脏状态／恢复／History边界，单次全量工作仍在 |
| 复用既有PM mapping、component edits、不可变引用 | **推荐**：输入保即时，普通文字／mark走局部正式操作，结构变更走现有完整协调 |
| 整体替换PM／CM／Grapes／Zustand | 当前证据指向适配／失效范围，不足以支撑替换成熟载体 |

具体做法：

1. 普通局改保未变子树与资源引用；在真实外来准入／不同信任边界复制，内部只冻必要目标与读集。最终校验覆盖变化字段和实际全局不变量，不能将任意输入直接标为可信。
2. 正式apply返回已知changes供History、通知、投影共用，避免再整工程deep compare／stringify推导变化。
3. Flow按PM transaction变化修身份／DecorationSet／目标block；表格版本只算一次layout和defaults，源映射／Markdown只在需要时物化。
4. 节点能update时保host；对象版本含真实definition／data／style／资源依赖，避免把别页变化等同当前对象变化。
5. 选择、相机、运行态和作者事实分别订阅；缓存真实输入tuple，不用整个EditorState做所有领域公共key。
6. 同值正式操作保轻量查重回执，同值临时状态直接早退；两类语义不能混用。

参照：[PM文档共享](https://raw.githubusercontent.com/ProseMirror/website/master/markdown/guide/doc.md)、[PM transforms](https://raw.githubusercontent.com/ProseMirror/website/master/markdown/guide/transform.md)、[React useRef](https://react.dev/reference/react/useRef#avoiding-recreating-the-ref-contents)、[Zustand selectors](https://github.com/pmndrs/zustand/blob/main/docs/learn/guides/prevent-rerenders-with-use-shallow.md)。

### 6.3 资源：全授权轻量目录、按消费物化、单资产租约

推荐维护现有资源owner和同步URL语义：

- API5的resources.url(assetId)是同步；Source可在运行中计算assetId。**不能只静态扫描闭包后把其余资源从可访问集合删除。**
- 保全部已授权asset的轻量元数据／可寻址稳定地址；已知静态依赖先准备，动态取得时由原授权资源端口实际读取／物化。未知依赖路径保守fallback，不能返回空值破坏既有作品。
- 减少全库base64和每realm全表Blob。地址由现有隔离协议／租约提供；opaque realm需要该realm可读地址，父Blob不能直接照搬。
- 每资产稳定条目与版本，替换一图只换一图；保旧consumer lease直到真正退出。派生预览、缩略图／解码结果按相同资源身份复用。
- transfer仅适用独立临时工作buffer／worker新产物且接收方明确取得所有权；Session／History／保存仍用的canonical bytes禁止detach。
- 导出继续按其离线carrier包装；运行编辑中的短URL不能泄漏进离线最终制品。
- 首次外来图片仍保完整解码准入，可信不可变内部结果复用，不将metadata-only当完整校验。

参照：[MDN Blob URL](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob)、[Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)、[Electron contextBridge](https://www.electronjs.org/docs/latest/api/context-bridge)。

### 6.4 重计算与导出：复用已有隔离执行器，而非新平台

推荐先消除重复解析／打包／冷启动，再复用现有worker／隔离renderer：

| 工作 | 合适位置 | 不宜直接迁移的部分 |
|---|---|---|
| parse5／纯JSON／ZIP／Office parts／像素算法 | Node／Web Worker，按现有模块环境选择 | CAS、文件发布、权限和最终Session状态 |
| DOM布局、字体度量、真实程序图面、PDF打印 | 已有隔离renderer／BrowserWindow | 普通无DOM worker无法测真实layout |
| fs异步读取／刷盘 | 现有文件owner异步I/O | 不为已有异步fs另包worker而增加往返 |
| GUI导出build | 冻结revision后复用既有export executor | UI草稿drain与当前输入owner仍留App |
| 多对象截图 | 单导出冻结publication的隔离host按目标reset | 不同任务／作者状态不能盲共享 |

对截图先注册一次payload／resources，入口传小token，用现有私有protocol读取，避免base64巨大JS字符串。同一导出可按页批量捕获，但每目标初始状态、scope／mask、字体／绘制就绪仍须正确；无法可靠reset的程序目标继续使用隔离fallback。取消信号沿现有requestId穿透到对应任务，销毁作业窗口／worker并停止未开始项，不触碰用户窗口。

[Electron性能建议](https://www.electronjs.org/docs/latest/tutorial/performance)、[fflate异步／流式ZIP](https://github.com/101arrowz/fflate)、[PptxGenJS保存](https://gitbrent.github.io/PptxGenJS/docs/usage-saving/)支持以上方向；Promise接口不等于业务整体已在另一线程。fflate消费buffer选项不得作用于共享canonical bytes。

### 6.5 队列与背压：按任务语义决定能否合并

| 类型 | 默认策略 | 边界 |
|---|---|---|
| 悬停、拖动几何、选区可视预览 | rAF最新坐标；一个在途加一个最新值 | 释放最终指针时精确计算；画笔保采样 |
| 目录刷新、HTML发现、同identity reload | 每owner single-flight，合并dirty／最新版本 | 外部变化和最终最新内容必须被观察 |
| 编译／派生显示准备 | 相同输入共享promise，未发旧版本取消 | 共享任务有其他consumer时不能误取消 |
| 软件控制的纯显示update | 可替代状态合并 | 自定义Source可观察副作用不一律丢弃 |
| AI流式显示持久化 | 相邻delta有序合批、真实待写bytes背压 | 正式终态／cursor／提交事实完整有序 |
| 正式事务／文件发布／工具副作用 | 原owner顺序执行与持久确认 | 不用latest覆盖已授权命令，不自动重放未知结果 |

背压和有限调度约束瞬时资源，不用总调用次数／总字节预算终止合法任务。缓存淘汰只处理可重建派生物和无活owner结果，不删除用户正文／History。参照：[Node背压](https://nodejs.org/learn/modules/backpressuring-in-streams)、[rAF](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)、[coalesced pointer events](https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getCoalescedEvents)。

### 6.6 字体：按实际消费缩门，保持每次精确度量正确

字体属于条件性后续优化，先修整工程／整媒体放大。推荐：

- 保完整face CSS与unicode-range声明，实际即将测量的文字使用真实style／weight／family＋text加载所需faces。
- 每个owner Document／iframe的FontFaceSet独立；父窗口已ready不能替代子realm。仅mount的一次fonts.ready回调也不能保证以后新字符／新字族已就绪。
- canvas、固定frame、autoSize等在相关face就绪后进行本次测量／重测；现测量入口“全manifest都loaded”的断言改为本次需求，不能直接删正确性保障。
- FontFaceSet.load的text按unicode-range匹配，不证明每个glyph覆盖；fonts.check对不存在字族可能为true，不可当指定face已加载证明。
- natural Flow可利用DOM自然重排，但需核其真实consumer；不能把旧GPU注释当所有载体全量等待的永久理由，也不能为了首屏接受错误断行。

参照：[FontFaceSet.load](https://developer.mozilla.org/en-US/docs/Web/API/FontFaceSet/load)、[FontFace.load](https://developer.mozilla.org/en-US/docs/Web/API/FontFace/load)、[unicode-range](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face/unicode-range)。

## 8. 最小充分性能验证与验收口径

### 8.1 用现有样本回答对应问题

不新建性能平台、不跑机械全矩阵。复用以下已有或实际用户作品副本，按改动选相关条目：

| 样本／操作 | 采集必要事实 | 正确性核验 |
|---|---|---|
| 含媒体长Flow：光标、IME、普通输入、大表输入 | 每键主线程耗时、完整clone／serialize／parse／layoutTable次数、pending ACK／分配 | 身份、格式、表格、相邻对象、Undo／保存冷开 |
| 多页GLX：拖动、悬停、切页 | 每帧处理、精确hit在途数、无关runtime sync／thumb重建、iframe保活 | 最终frame／吸附／遮挡、程序状态和焦点 |
| 现有25.58MB HTML：输入、滚动、换图、保存、关闭 | 完整扫描／parse次数、消息bytes、lease／nodes、journal阶段、Main长任务 | 多层／Blob图文、CSS、互动、普通浏览器重开 |
| 含大资源／Source的GLX：局改、保存、动态资源读取 | URL／base64物化量、编译准备端到端、IPC字节、Main归档时间 | 同步动态assetId、权限、固定revision保存与再编辑 |
| 大目录／多未变文件tab／恢复稿 | readdir／hash／附件读bytes、刷新范围、恢复列表payload | 外部替换／删改／附件变化、真实恢复 |
| 冻结长AI会话、固定工具参数delta | 累计parse字符、真实待写bytes、Loaded／预览retain、timeline重算 | 分片转义／Unicode、cursor／终态、恢复与幂等 |
| 大图／PDF／多对象导出 | decode／PNG／getDocument／window启动次数、作业取消 | 像素／alpha／原件、Office编辑性、离线file:// |
| 空启动与首个作品 | 入口→app ready→首帧→可交互，模块／字体读取 | 首次懒功能成功、字体首帧与新增字符度量 |

阶段计时应区分用户可见反馈、正式提交ACK、文件保存ACK、实际落盘、冷开与最终导出；不要以一个内部compile duration替代整条准备时间。CPU、GC、IO等待、IPC传输、布局、解码与网络分别标记。跨阶段并行或嵌套耗时不能机械相加。

### 8.2 判定原则

- 对源码已足以确定边界的整媒体复制、前缀重解析和终态强保留，可以直接开展已授权的对应修复；不以必须先全套profile／全基线作为新门。需要量化收益或比较多个热点时，仅为受影响代表操作留一次足够分阶段的基线，再比较相同输入、构建模式和环境。结果含混或失败指向更广问题才扩测；不为凑次数重复。
- 对源代码可证明的重复工作，优先验“次数／范围已收敛”和用户行为，而不是只看一次快了几毫秒。对网络、磁盘缓存、GPU和CPU波动注明环境，不能把单次倍率当稳定结论。
- 以60Hz场景一帧约16.7ms作为拖动诊断参照，以浏览器长任务／交互轨迹定位冻结；这些不是对所有设备的硬承诺或新的拒绝门。正式目标是操作及时显示、无持续过时队列，重计算期间仍能响应必要输入。
- History优化看增长趋势与真实恢复；内存释放看retaining path和活owner，不只cache.size。Heap snapshot可能暂停进程，只在隔离副本、确有必要时做。
- 用受控慢写／慢compile seam验证背压／取消，不需要重跑真实模型；只做待改行为与可信失败反例。
- 保存、恢复、正式事务相关针对性检查不能用“性能优化”豁免；反之，低风险UI局部派生不需全软件矩阵。

### 8.3 建议交付结果的证据格式

每包保留：触发操作、相关构建／实现、修改前后阶段与调用数、实际用户结果、未覆盖范围。现有日志／诊断可用就复用；新增计时只围绕要改变决定的疑点，不永久记录大正文／资源和敏感payload，不让观察本身成为新热点。

没有本轮实机trace的项保持候选身份。修改使正常输入不再触发全媒体处理可以是确定结构收益，但“整体体验流畅”仍需对应实际操作证据。

## 9. 已排除的误报、已接受成本与尚未确定事项

### 9.1 不再当成未修缺陷

- parse5长文本链保留、资源backing放大、HTML资源worker／snapshot single-flight／CodeMirror按需挂载已有有效修复；不能再用旧OOM直接断言当前同因失败。
- 生产preload主要async invoke，未找到sendSync／remote主链；异步仍有clone成本，二者不能混淆。
- Source编译已有LRU64、pending去重、末文档关闭clear；问题是命中前准备和实际bytes分布，不是完全无缓存。
- Runtime已有首次可见懒加载、IntersectionObserver、activity、离屏延迟Source同步、可选suspend／resume和compiled定时器暂停；不能称所有隐藏页面所有timer持续运行。
- 多数NodeView／observer／media dispose／URL lease已有退出；没有retaining path不能报告全局GPU或DOM泄漏。
- AI已有SSE增量decoder、显示缓冲、事件索引、100项DOM窗口，run／displayBuffers结束有清理；问题是未覆盖的完整前缀、Loaded和EditSession。
- 诊断日志有轮转且不是逐条fsync；普通fetch有Agent，浏览器proxy有pipe，不能泛称所有请求无池／全buffer。
- 原生文字测量已复用window；Task／Published观察窗口和Python作业在已有run finally路径实际销毁。重复冷启动与漏销毁是不同问题。
- 当前4个内置组件包很小；catalog扫描规模尚不足以解释普遍卡顿。源码JSON的20MB则是另一个已确认制品事实。
- React StrictMode effect重放是dev特性，现有dist为production；不能把dev双执行归为所有用户启动行为。

### 9.2 需要保留的已接受／合同成本

- 临时离屏保实例／运行态是既定产品选择。黑盒作者程序后台不保证停止，特定作品可能自行消耗CPU。先减少软件放大，再用实际profile定位不合作程序；本方案不新增通用运行态快照／自动淘汰。
- 网页包file://可双击与仅HTTP托管体积不同；不能静默删除离线fallback，若用户将来选择独立输出模式再明确处理。
- 外来图片完整解码、真实HTML几何、复制完整性、删除前源未变、最终文件CAS、未知副作用查证确有保护属性。可以消除同次重复，不能以“hash／测量耗时”一律删除。
- 某些Source update可产生外部可观察动作，不能把所有回调当纯render。合并仅适用明确可替代的显示状态。
- canonical bytes仍由工程／History／保存共享；worker消费／transfer需独立所有权，否则会破坏原数据。

### 9.3 当前仍需现场判断

1. 哪条链在用户最常用作品中占主要时长，是否存在某个高负载作者程序、错误风暴或巨量外部目录。
2. Windows磁盘／安全扫描／GPU驱动／远程路径／硬件解码是否增加额外等待。本轮未把机器环境猜测列为已证实根因。
3. 数据表达与重复工作消除后，是否仍需Main bundle、更多独立worker、空间索引、长树窗口化或编译context。它们由剩余热点决定。
4. 当前用户窗口究竟使用哪个构建／profile；本轮没有启动或操作该窗口，源码候选不能自动代表已安装发行包。
5. 改动内部journal协议的确切兼容／读入细节，应在后续实施候选中用副本与真实消费者落地；本方案不自动迁移用户恢复稿。

## 11. 最终建议

当前最值得投入的不是扩大堆、增加线程数量或整体换框架，而是按现有owner消除三种放大：**局改变全量、历史反复整写、相同资源在多边界重复物化**。先交付A批与已有启动大依赖切断，再按B／C对应样本推进；D／E由剩余真实热点决定。

所有后续实现应让普通操作的成本更多取决于“此次真实变化”，让重计算离开交互线程，同时保持作品可编辑、可撤销、可保存、可重开、可运行与可交付。这是本方案的成功标准，而不是修完固定数量条目或通过全仓测试矩阵。
