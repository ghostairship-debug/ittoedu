> **适用范围更新（2026-09-17）：本文件是长期产品方向与技术研究，不是当前开发总纲。** 当前版本优先完成[1.9 前端专项](docs/development-plan/R19_FRONTEND_SPECIAL_IMPLEMENTATION_PLAN.md)，已确认形态以[设计说明](双形态UI设计/00-设计说明.md)为准。下文“首个版本”、HTML 混合编辑、Office 内嵌编辑／插件等是研究时的建议，不进入本阶段；Office 初版候选与分期以 C.13 为准。用户已确定的工作空间／可选项目／自由布局及原生编辑器规则优先，不从本文 AI 起草的旧前端建议反向覆盖。

# 01｜执行摘要：一个 Agent，多个工作位置

**产品名称：果铃。定位：AI 原生文件与内容工作台。** 果铃承接找资料、整理文件、创建作品、定点修改和交付。用户在主应用中完成轻量手调；需要精细排版和高级手工操作时，进入 WPS／Microsoft Office，继续调用果铃插件。

本方案只讨论果铃／原一途／ittoedu，不包含 Phlow 游戏项目。它替代 V1.1 中偏重完整办公编辑器的要求，但不直接改变仓库版本号、现有工程格式或已经签署的兼容合同。

## 四项产品承诺
**从真实文件开始。** 打开一份现有文件就能工作，不强制创建项目、导入专有知识库或转换成 HTML。多份资料和连续任务出现时，再组织成项目。

**对着内容修改。** 用户点选文字、对象、单元格或互动区域，AI 获得实际可定位的目标。默认调整当前作品，不为一次局部要求重做整个文件。

**轻操作不绕路。** 改文字、替换图片、调整少量样式和尺寸直接手动完成。复杂重写、布局调整、批量处理和交互规则交给 AI；主应用不复制完整 Office 功能区。

**专业软件继续接力。** 外部编辑是正式工作位置，不是失败退出。插件使用宿主原生接口操作当前文档，保存后主应用接收最新文件。

## 首个有说服力的版本
一组真实资料可以生成普通办公文件；现成 PPTX 能完成指定页的多轮修改；外部 HTML 能保留互动并开放部分画布编辑；用户能进入一个已验证的 Office／WPS 插件继续工作。这四件事比同时列出六种“全面支持”的格式更重要。

**推荐建设主线：文件与任务工作台 → 当前作品定点修改 → HTML 混合编辑 → 单宿主插件接力 → 按需求加深 DOCX／XLSX。** PDF 阅读与页面任务、Markdown 编辑作为基础能力并行补齐。

## 研究边界
资料核查截至 2026 年 9 月 16 日。依据包括官方产品说明、技术文档、许可文件，以及 ittoedu 当前 README／开发总纲和提交信息。未登录实测全部竞品、未运行当前仓库、未完成真实 Office 文件兼容测试。文中“建议”“目标”“验收”是产品设计，不是已经实现的事实；证据索引见末尾。

# 02｜本版取舍：收窄手工能力，保留创作深度

| 事项 | 本版决定 | 对上一版的调整 |
|---|---|---|
| 产品中心 | 文件、任务、作品及其持续修改 | 从“多编辑器集合”转为完成工作 |
| 主应用手动操作 | 少量高频就地编辑，按对象出现 | 不再要求三件套完整手工功能 |
| HTML | 原生区域＋组件／运行时区域可共存 | 增加有边界的外部 HTML 混合导入 |
| Office 高级操作 | 原生宿主＋果铃插件 | 从后置补充前移为正式路线 |
| 自研底座 | 目标定位、局部写入、接力和 HTML 适配 | 不建设完整 Office 排版与计算内核 |
| 共同协议 | 文件身份、版本、选区、能力、结果 | 撤回庞大 Universal Document Core 设想 |
| 原生课件能力 | 数据与能力保留，高级面板退后 | 简化界面不删除结构与行为能力 |
| 文件交付 | 原生文件独立可用，接收者无需插件 | 不用专有容器锁住普通文档 |

## 三种工作位置，不是三套互相复制的产品
**果铃原生表面：**已有互动工程、Markdown，以及可可靠转换的内容。果铃掌握源数据和编辑语义，编辑能力可以较深。

**果铃轻编辑表面：**外部 HTML、Office、PDF 的已支持部分。用户能看、选、轻改；复杂任务通过对应适配器执行。未支持对象保持只读或移交，不假装所有东西都能改。

**专业宿主表面：**WPS／Word／Excel／PowerPoint 内的任务窗格。完整手动功能归宿主，果铃负责上下文和 AI 操作。不是把整个 Office 嵌到果铃窗口里。

## 明确不做
首期不做完整 WPS 替代品、全电脑自主操作、邮件／日历／审批系统、大型知识图谱、可视化 Agent 流程编排器、公开插件商城，以及跨所有格式的无损双向同步。

**轻界面不能用来掩盖弱读写。** 删掉功能区会减少交互建设，但对象定位、字体排版、文件关系与可靠保存仍需相应引擎或受支持的原文件修改路径。一个外观复杂但能够裁剪 UI 的成熟内核，仍可服务轻产品。

# 03｜研究结论：借鉴机制，不复制产品目录

| 研究对象 | 本次能确认的事实 | 对果铃的设计影响 |
|---|---|---|
| Canva Code 2.0 | 官方介绍 HTML 导入、互动保留、直接文字／样式／图片及选中元素 AI 编辑。[S01] | 把“第二轮修改体验”作为竞争项，不宣称此概念独有 |
| 灵犀 | 官方资料描述本地／云端任务、文件处理与 Skills；不同抓取版本的插件说明不一致。[S02] | 独立办公 Agent 已有直接竞争，插件是否全面开放不作既定事实 |
| Claude Cowork | 面向文件及工具执行任务，重点是交付工作结果。[S03] | 首页从任务和文件出发，后台工具轨迹不占据主要界面 |
| Obsidian | 普通本地文件与可重建缓存，允许外部软件编辑。[S04] | 原文件持久存在，项目索引可替换，不强制全格式转 Markdown |
| Lovable | 官方技术文披露编译期 JSX 标识与源码 AST 支撑视觉编辑。[S05] | 框架项目要建立来源映射，不能只靠运行时 DOM 猜源文件 |
| Builder | 注册代码组件时暴露带类型的输入属性。[S06] | 组件保持原实现，以明确属性绑定获得有限画布编辑 |
| Gamma | 提供结构化布局切换与调整。[S07] | 复用布局骨架降低从零排版成本，不增加复杂设计面板 |
| 飞象老师 | 开发者介绍支持文字、语音、图片等教学输入生成互动内容。[S08] | 用具体完整任务承接需求，不让用户先学习编辑引擎 |

## 两个需要纠正的技术推断
**“在浏览器里编辑”与“拥有结构化工程”并不互斥。** Lovable 的公开实现就把运行画面和源码 AST 联系起来。Canva 没有公开足以判断任意 HTML 内部表示及全部往返能力的合同；不能据此认定它只改 DOM，也不能据此给果铃打总体胜负分。[S01][S05]

**果铃原生格式的价值在于明确的作者语义。** 仓库已有节点、命名状态、互动规则与显式编辑目标。这为定向修改提供了可靠依据；是否比竞品更好，仍需相同任务实测。[G1]

## 机会假设
果铃争取的是一类连续工作：用户拿着已有文件和 AI 生成内容，需要反复调整，并最终交给真实客户、同事或学生。开放文件、HTML 混合编辑、跨专业软件接续与可复用任务共同形成使用理由；任何一项单独存在，都不足以证明差异化。

# 04｜用户与首批任务：通用定位，集中验证

## 首批用户
优先选择同时具有“多种文件交付＋需要多轮修改＋有已有材料”的人。建议两组：教育／培训内容生产者，以及小团队中的方案、运营、咨询、市场人员。教育经验可帮助收集样本，但主界面不默认把所有作品叫课件。

先不主攻极重财务建模、出版排版、法律格式审校等高复杂专业场景。它们可通过宿主插件完成部分任务，但不作为主应用首版的全面兼容承诺。

| 首批任务 | 输入与输出 | 必须证明的价值 |
|---|---|---|
| 修改已有提案 | 已有 PPTX＋参考材料 → 当前提案的新版本 | 指定页面改变，已确认部分保留 |
| 改造外部互动网页 | HTML／静态包 → 可继续编辑的作品与发布包 | 保留互动，能直接改已识别内容 |
| 资料整理成正式文件 | PDF／文本／模板 → DOCX、PPTX 或 MD | 事实可追溯，格式可交付，能继续修改 |
| 数据形成汇报 | XLSX／CSV → 分析结果＋可选演示 | 真实计算、可解释口径、不破坏原数据 |
| 文件批量整理 | 用户指定文件夹 → 命名／归类／提取结果 | 先见方案、后执行、可恢复，不擅自删原件 |

## 第一条主任务
建议首先验证“已有 PPTX 定向修改并到专业软件继续精修”；同时用一个现有互动案例验证“外部 HTML 导入后点选修改”。前者证明综合办公价值，后者验证果铃已有能力的延伸。两者共享任务与文件外壳，不应同时引入完整六格式内核。

## 用户故事
“我已经做了一半，不想从头再来。请找到我指的部分，理解要保留什么，把麻烦的调整完成；简单地方我自己改。需要专业功能时，继续在熟悉的软件里做，回来以后你还知道最新结果。”

## 产品不应强行扩张任务
用户只要改一份文件，就不额外生成报告、表格和网页；只问分析，就不自动写盘。一次任务确实需要多个产物时才开启项目组织。互动内容是表达选项，不是每次办公任务的强制附加品。

建议以约 12—20 位首批用户、50 个左右不同任务开始验证；人数与任务数是研究方案，不是市场规模推断。收集首次任务与第二、第三轮修改，而非只收集生成演示视频。

# 05｜文件管理：可持续工作的入口

## 三个用户概念
**文件**是实际作品或资料；**任务**记录这次要完成什么、改了哪里、结果在哪；**项目**是一个可选的长期工作范围，组织文件、材料和说明。模板、片段和常用方法收在“复用”入口，不再成为首页必懂的第四、第五种对象。

## 文件夹即工作范围
用户可以打开单文件，或明确授权一个目录。默认只索引该范围；图片、PDF、Office、Markdown 与 HTML 保持原有文件类型。项目记录存储引用、轻量说明和必要身份，搜索索引可以删除并重建。该取舍借鉴本地文件与可重建缓存的模式，但不要求复制 Obsidian 的插件和图谱体系。[S04]

文件列表同时提供名称、类型、位置、最近修改、相关任务和当前状态。用户既能按文件名找，也能问“找上次那份包含定价对比的方案”；结果先呈现具体文件与匹配片段，再执行后续修改。

## 文件管理的最小操作
| 操作 | 默认行为 | 重要边界 |
|---|---|---|
| 打开／定位 | 直接预览，能跳到可定位的页或范围 | 识别不了对象时不伪造精确命中 |
| 重命名／归类 | 展示旧名、新名、目的地，再批量提交 | 冲突不覆盖；保留可逆日志 |
| 提取／汇总 | 新建结果文件，保留材料来源 | 不默认改原资料 |
| 去重建议 | 标出候选重复项和理由 | 相似内容不自动删除 |
| 移动／删除 | 用户明确授权后执行 | 默认回收站或可恢复路径，不擅自永久删除 |
| 外部修改 | 检测变化、失效索引、重新载入 | 同名不等于同一份；两边未保存时不自动覆盖 |

## 原件、工作副本、交付物
用户明确要求“改这个文件”时，可在受支持条件下修改原文件，并建立恢复点；拖入资料用于创作时默认只读引用。转换或重建必须生成新文件，清楚说明与原件的关系。恢复快照不替代用户备份。

项目不把整段私密聊天写进 DOCX／PPTX 或 HTML 导出包。工作方法与来源可单独导出；发送给他人的文件仍是普通可用文件。

# 06｜工作台界面：内容常驻，工具按需出现

## 默认布局
顶部显示文件标签、路径／保存状态、撤销、交付和“在其他应用中打开”。左侧为文件与当前文档导航，可在页缩略图、章节、工作表之间随文件切换。中央始终展示当前作品。右侧为可收起的 AI 任务面板；收起后保留一个输入入口。

首页只提供“描述任务”“打开文件／文件夹”“继续最近工作”。不先展示六个复杂编辑器、知识库设置和模型控制台。新建文件可以从格式入口进入，但无需先选 Agent 类型。

## 选择与轻编辑
点选对象后只出现适用的几项控件：改文字、换素材、基础样式、移动／尺寸、让 AI 修改。正文沿用选区与就地输入，表格沿用单元格；不强迫所有格式都自由拖拽。

**不提供不能持久化的假编辑按钮。** 某个元素只是预览可见、无法可靠写回时，浮条提供“让 AI 尝试”“在专业软件中修改”或“创建可编辑副本”，而不是允许用户先改、到保存时才发现失败。

## AI 输入区的范围标签
示例：**修改：第 4—6 页｜事实：产品手册｜数据：报价表｜风格：旧方案**。标签由上下文自动填入，可点击调整。用户可追加“保留全部数字”，不必编辑技术字段。

范围以发起时的选择为准，提交前重新验证；用户切换到别的页不会让正在执行的任务误写新页面。新增选择可用于下一条消息或明确补充当前任务。

## 简洁与专业模式
现有仓库已经有简洁／专业界面及不修改工程的模式切换。本版沿此方向进一步降低默认密度，而不是再做一套编辑器。[G1]

原生互动工程中的状态、规则、组件代码等能力保留在高级入口和 AI 操作面。普通用户不看到完整状态机与时间轴；高级用户仍能发现并使用。若 AI 不能完成，用户仍有检查和修正通道。

## 进度与结果
任务面板显示真实阶段与已完成产物，例如“已调整第 4 页，正在处理第 5 页”。结果突出改动范围、需注意的限制、打开位置和撤销入口。详细工具日志折叠；不要用思考动画充当第一个有效结果。

# 07｜主流程：创建之后，仍能持续修改

## 场景：将旧提案改成新客户版本
用户拖入旧 PPTX、最新报价表与产品 PDF，输入“沿用风格，改成给新客户的 8 页方案”。系统把旧 PPT 的风格和旧客户事实分开，使用新报价。缺少关键内容时集中询问；不要求对所有明显信息逐项确认。

生成期间，已经可用的页面可以先显示并允许用户阅读。用户在第 2 页改标题，再选第 4—5 页要求“重组为问题、比较、建议，价格不变”。AI读取相关页、数据和必要模板信息，提交局部变更，不能用开始时的旧文件覆盖第 2 页。

用户需要调整母版与复杂动画，点击“在 PowerPoint／WPS 中打开”，完成保存交接；在宿主中主动呼出果铃插件，继续修改同一作品。专业软件保存后，果铃重新载入最新状态，再按要求生成摘要或 PDF。

## 一次 AI 修改的基本流程
| 阶段 | 用户看到什么 | 产品必须做到什么 |
|---|---|---|
| 接收 | 范围、资料与简短任务说明 | 分析不写盘；修改才取得写入能力 |
| 定位 | 被选目标高亮或范围确认 | 绑定对象／文本范围和当前版本 |
| 执行 | 已完成部分与阻塞原因 | 优先局部操作，不默认重做全文件 |
| 提交 | 变化高亮与完成回执 | 重新检查冲突、范围及保存结果 |
| 续改 | 手改与后续指令随时可用 | 下一轮以最新文档为准 |

## 何时可以整体生成
从零创建、用户明确要求全面重做、或现有文件无法安全编辑且用户同意重建时，可以生成新文件。不能把不支持的局部修改偷偷替换为“新生成了一份相似文件”。

## 检查与自由度
整体重设计可让 AI 有较高自主权；限制来自当前任务，例如不能改数字、不能删案例。不要默认冻结所有结构，也不要为了谨慎加入一套复杂的审批链。成本较高的方向探索可先给一页样例，由任务需要决定。

交付分三件事：保存当前作品、导出分发格式、改编为另一类作品。Word 到 PPT 是内容重组，互动网页到 PDF 是静态表达；产品应明确表达变化，而非称为无损互转。

# 08｜HTML 混合导入：产品承诺与操作体验

**目标：让外部生成的内容在果铃里继续工作，不强制把整个网页转换成果铃工程。** 同一作品允许原生区域、可配置组件和保留运行区共存。兼容深度以区域和动作判断，不用一个全页“支持／不支持”标签概括。

| 区域 | 处理方式 | 用户能做什么 |
|---|---|---|
| 可可靠转换的独立内容 | 转为果铃原生节点与布局 | 就地文字、样式、图文调整，以及原生语义 AI 修改 |
| 不适合拆开的组件 | 保持组件实现，绑定已开放属性 | 点选标题／图片／参数，手改或让 AI 修改这些属性 |
| 高复杂运行区 | 保留源码或构建产物，隔离运行 | 整体定位、外层尺寸、候选式 AI 源码／补丁修改 |
| 跨域或不可访问内容 | 按合法访问能力展示引用或预览 | 不承诺读取内部对象；说明阻塞原因 |

## 首期输入范围
优先支持单 HTML 与含本地静态资源的 ZIP；对联网依赖进行识别并显示。带构建系统的源码目录、npm 安装与开发服务器作为后续能力，不能把任意 ZIP 默认视为可安全自动执行的源码工程。

用户提供 URL 时，首期作为资料或链接使用；有权限且能获得源码的内容可导入。网址可打开不意味着能够取得登录后的完整应用、绕过同源限制或获得后端服务。

## 导入体验
先打开可运行预览，再给出“可直接修改”“部分可修改”“可让 AI 尝试”的轻提示。后台识别高把握目标；不为了追求更高的原生化比例长时间阻塞首次查看。

用户选择“增强可编辑性”后才进一步分析／转换，并可对比候选与原件。导入原始文件保留；转换结果作为果铃工作副本。已有稳定可编辑的区域无需每次打开重新识别。

## 典型例子
一页材料中，独立标题与说明可转为原生文字，图表保留原运行组件并暴露标题／数据／颜色，复杂模拟区域保持运行。用户改标题立即生效；换图表数据走绑定；改模拟规则交给 AI，并在候选中验证行为后接受。

这是一项分阶段能力，不承诺“任意 HTML 全部无损、所有内部元素都可拖拽”。成功标准是正确增加可编辑性，同时尽量保留原有行为。

# 09｜HTML 实现策略：先契约，再识别，最后推断

## 充分利用已有能力
ittoedu 已有 Component API 4、Runtime authoring 目标注册、文字／素材编辑键及稳定地址。应增加外部内容到这些既有能力的适配，不另建一套竞争的作者协议。[G1]

Builder 的可编辑组件依靠注册属性，Lovable 的画面到源码依靠编译标记。两者说明，可靠编辑往往来自显式映射，而不只是“浏览器能看到这个元素”。[S05][S06]

| 开放优先级 | 来源 | 写入策略与条件 |
|---|---|---|
| 1 | 果铃已有作者协议／组件属性 | 直接复用正式目标与事务 |
| 2 | 已支持的 HTML／组件识别器 | 识别静态文字、素材、局部样式或已知配置，验证后开放 |
| 3 | 带源码的编译／解析映射 | 运行对象关联源码与实例，局部改源码后刷新验证 |
| 4 | AI 建议的编辑绑定 | 先成为候选，通过重载与行为检查才固定 |
| 5 | 黑盒视觉区域 | 仅提供带限制的 AI 尝试，不宣布稳定属性接口 |

## 原生转换按“所有权完整的区域”进行
一个看似普通的标题可能由框架状态、脚本查询、CSS 选择器或外部事件控制。不能只凭 DOM 标签简单，就从原运行环境中拿走。

可转换区域应明确谁负责生成内容、布局和状态。无法安全拆分时，保留更大组件或整页运行区。先保持一个相互依赖的区域完整，之后再逐步增加属性；不要把每个 DOM 节点切成一个 iframe。

## 可编辑描述的最小字段
每个开放目标只需记录：稳定身份、所属区域、显示名、可修改属性及类型、实际写入位置、适用限制、对应版本、验证结果。命中框是临时显示信息，不是持久身份。

优先记录“由作者声明／识别规则确认／AI 候选”这些可解释来源，不把模型猜测包装成 0.98 之类未经校准的成功概率。没有真实写回路径时，不显示为已可编辑。

## 避免另起大型编译器工程
首批只支持少数高价值模式：静态图文、独立样式、已知组件配置、现有作者键。新增规则由真实用户文件驱动。通用 AST 工具可以复用，但不以还原任意压缩 JS 的完整业务模型为发布前提。

# 10｜HTML 持久化、行为与安全边界

## 一块内容只有一个权威来源
原生区域由果铃工程管理；组件区域由原组件及其参数管理；源码区域由源码管理。果铃不能保存一份新文本，同时让 React 下一次渲染又用旧文本覆盖它。

运行时修改可以先用于即时预览，但只有写到真实参数、源码或可持久补丁，并经重新加载确认后，才称为已保存。整页导出不能只序列化当前 DOM：运行状态、事件关系和资源依赖可能未进入序列化结果。

## 三种输出清楚区分
**继续编辑的工程：**原生区域、组件引用、参数绑定和原始资源，保持各自来源。

**发布 HTML／网页包：**从最新作者事实构建，声明离线与联网依赖；测试脱离编辑器后是否仍可运行。

**可交接源码包：**对有源代码且修改路径支持的内容，给出源码及必要补丁。部分原生化后的作品不承诺还能反向恢复成原作者完全相同的源工程。

## 必测行为
文字与图片修改应在重载后保留；页面交互、状态切换和关键事件仍可用。响应式布局至少检查声明的目标视口；重复组件应区分修改当前实例与修改全部实例。运行中的互动预览不能因为一个非相关轻改就默认重启、丢失状态；必须重载时明确提示。

Canvas／WebGL 的画面选区只能提供视觉位置证据，不自动成为图内对象身份。跨域 iframe 的内部选择需要对方支持或其他合法可用接口；没有就保留外层目标。

## 新信任边界必须单独处理
当前仓库把运行时视为可信内部生产内容。外部任意 HTML 改变了这一前提，不能原封不动进入现有同文档可信执行路径。[G2]

外部内容使用隔离渲染、关闭 Node 集成、启用上下文隔离与沙箱、限制导航和宿主通信，并由用户授权必要网络／文件操作。Electron 官方明确提出这些基本要求。[S09]

这是一条窄安全边界，不需要新建复杂权限平台。外部代码不能读取模型密钥、整个磁盘或原始主进程接口；任务材料中的指令也不能自行升级为 Agent 权限。源码项目的依赖安装与执行是另一个显式动作。

# 11｜六类文件：轻手调，深 AI，能力分层

以下为首个完整产品的目标范围，分阶段交付。每类都区分新建文件与用户原有复杂文件；实现必须有可靠定位与写回，不能只提供截图上的假手柄。

| 格式 | 主应用的轻手动编辑 | AI 重点 | 重手工需求去向 |
|---|---|---|---|
| PPTX | 选页／对象，改文字、换图、移动缩放与少量样式 | 指定页改版、内容重组、模板延续、批量对象调整 | WPS 演示／PowerPoint 插件 |
| DOCX | 正文选区、文字修正、标题与基础格式、受支持表格值 | 按段／节改写、结构调整、术语与引用修订 | WPS 文字／Word 插件 |
| XLSX | 选区域、改单元格值／公式和基础数字格式 | 数据清理、公式修复、汇总、图表与解释 | WPS 表格／Excel 插件 |
| PDF | 选择、查找、批注、页面整理 | 阅读、提取、页面任务、从源文件更新 | 源文档或专业 PDF 工具 |
| MD | 原文与轻可视编辑，保留未知语法 | 按段改写、整理、改编与资料组织 | 可与外部文本工具共同使用 |
| HTML／原生互动 | 原生节点与已开放组件属性 | 互动生成、行为调整、混合区域修改 | 果铃高级入口；有源码时可交接开发工具 |

## 轻手动不等于 AI 也只能小改
AI 可以完成整章重写、跨页重排、复杂分析或交互规则调整；它需要调用足够有表达力的原生／宿主能力，而非迫使用户操作一整套面板。深度来自后台可操作对象和工具，不来自按钮数量。

## 四种可见状态
“可原位修改”“部分受限”“仅可阅读”“可创建重建副本”。状态按文件和对象决定。普通文件不必显示技术提示；遇到会影响结果的限制时，明确指出哪项动作受限及下一条路径。

## 不做的伪兼容
不将 DOCX 统一转成 HTML 再反复转回；不把 PPT 全页图片当原生可编辑对象；不拿 HTML 表格冒充工作簿；不把 PDF 上覆盖新文字当作真正编辑原文。

旧 .doc／.xls／.ppt 需要转换时，创建转换副本并提示；宏、加密文档、外部数据连接等按检测结果限制，不能自动执行其中代码。收件人打开果铃交付的普通 Office 文件，不应必须安装果铃插件。

# 12｜Office 内部方案：不要以轻界面替代真读写

## 每种格式拆开解决三个问题
**显示：**内容如何准确呈现；**定位：**所选位置如何指向真实对象；**写入：**如何修改当前文件并保留其余内容。三者可以由同一成熟内核承担，也可以由已验证适配组合承担，不能因为有一个预览器就认为另外两个问题自然解决。

原件预览若来自 PDF／图片，不能默认获得原 DOCX 段落、PPT 形状或 Excel 单元格身份。若无法建立可靠对应，应在独立内容视图中明确展示可修改范围，或直接交给宿主插件；不要让用户误以为在原版画布上任意编辑。

## 推荐的内核策略
| 格式 | 首选验证路径 | 不通过时的降级 |
|---|---|---|
| PPTX | 复用现有对象编辑经验，验证常见对象到原文件的定位与局部写回；复杂文件由成熟组件／宿主处理 | 限制内部动作，不把原 PPT 全量转换后覆盖 |
| DOCX | 试用可裁剪工具栏且支持当前文档 API 的成熟组件 | 原件阅读＋明确内容范围修改或插件；暂停自研完整分页 |
| XLSX | 成熟开源表格表面＋真实计算能力＋已验证交换／局部写入 | 数据查看与分析副本、宿主原位修改；不强行整本重写 |
| PDF | 成熟阅读器＋独立页面／批注写入能力 | 复杂文字重排不开放，转源文件处理 |

## 原文件局部修改的原则
保留原包，仅对明确支持的结构做修改，并检查关联关系。Open XML SDK 提供包与格式元素操作能力；它不等于排版引擎或兼容性担保。[S10]

“未知 XML 原样留着”是减少损失的策略，不是无损保证。样式、关系、布局、引用和公式可能依赖被修改部分，仍要按动作测试。openpyxl 官方文档明确提示某些图形会在读取再保存中丢失，不能把通用读写库当作任意文件编辑底座。[S11]

## 表格必须特别处理计算
SheetJS CE 文档说明公式存储不自动计算结果。[S12] 果铃必须用真实计算引擎或原生宿主重算；无法算出的公式标记结果未更新，不能把旧缓存展示成最新答案。跨行列结构修改、共享公式和外部连接不列为首批“轻量必做”。

**补充评估（2026-09-16）：**本章内核策略的逐格式底座核查、当前仓库 PPTX 导入／导出事实、2026 年新出现的 PPTX 开源引擎、“自研轻量底座”的定义与近似保真的可接受边界，见附录C。附录为评估意见，不改变本章决定。

# 13｜外部插件：把专业软件变成正式工作位置

## 标准接力流程
**主应用保存检查点 → 打开目标软件 → 用户呼出果铃插件 → 对接当前文件与任务 → 点选原生内容并修改 → 宿主保存 → 果铃接收最新文件。** 第一次可能需要安装、登录或选择项目；后续应尽量减少步骤，但不能承诺跨所有环境自动接管。

插件保留任务目标、必要资料引用、项目说明和最近修改摘要，不把整个超长聊天原封不动传进去。用户也可以直接在 WPS／Office 中启动一个新任务，之后再在主应用中管理相关文件。

## 插件界面
右侧任务窗格显示当前文件、当前选区、简短对话和变更结果。用户手调时使用宿主自身工具；果铃不再提供第二套平行排版控件。点击“只改这里”应读取宿主真实对象，而不是截图中相似的目标。

| 必须能力 | 验证重点 |
|---|---|
| 识别活动文件和选择 | 多文档、多窗口、同名副本不能串文件 |
| 修改真实内容 | 文字、区域或形状发生原生变化，不只是返回建议 |
| 读取最新状态 | 用户未保存的手动修改也能成为当前任务依据 |
| 保存／错误回执 | 区分内存已改与磁盘已保存 |
| 断线与重新接入 | 不重复执行已成功操作，不偷偷覆盖 |

## 官方接口存在，不等于任意版本都覆盖
Microsoft 的 PowerPoint API 支持形状创建、移动、格式与删除等原生操作；但 Office 的 API 可用性受宿主、平台、版本及 requirement set 限制，必须运行时检测。[S13][S14]

WPS 加载项提供任务窗格和文档操作接口；官方当前说明 JS 加载项适配 Windows／Linux，并提醒使用新的发布路径。不能把 WPS WebOffice、客户端 JS 加载项与其他集成技术视为同一个产品。[S15][S16]

## 不再承诺“打开就自动弹出”
Microsoft 官方说明自 2026 年 3 月 2 日起，Marketplace 插件不再支持该自动打开路径；集中部署／旁加载另有范围。[S17] 产品基线必须是“打开文件后，用户点击果铃按钮继续”。允许的环境可以减少这一步，但不作为基本体验承诺。

# 14｜跨软件状态：同一任务，不是同时乱写

## 一份活动文档只有一个写入所有者
在果铃中编辑时，由果铃的实际编辑会话写入；在 Office／WPS 中接力时，由宿主活动文档写入，主应用的同文件表面进入跟随／只读状态。Agent 不能绕过宿主，直接修改磁盘上的旧 ZIP 包。

这里需要的是轻量写入协调，不是重建一套跨应用协同编辑系统。Windows 文件锁不能单独代表全部状态；插件需要报告活动文件、任务关联、未保存情况与操作结果。

## 关键事件的处理
| 事件 | 默认处理 |
|---|---|
| 外部文档尚未保存 | AI通过宿主读取当前内容；主应用标记尚未同步到磁盘 |
| 外部另存为 | 重新确认文件身份和任务关联，不仅凭文件名匹配 |
| 两处同时出现未保存改动 | 暂停第二写入者，提示保留副本／选择接续位置 |
| 用户关闭宿主 | 按保存状态更新，不自动将旧预览写回 |
| 插件返回后网络断开 | 根据操作回执判断是否已执行，禁止盲目重放 |
| 外部文件已变更 | 使旧目标失效、重新定位；不使用缓存坐标直接写入 |

## 撤销遵从真实能力
宿主支持的撤销首先走宿主；果铃记录任务变化，方便恢复与对比。不承诺所有宿主 API 都能把整个 AI 任务合并成一次撤销，也不承诺跨 Word、PPT 和 HTML 的全局原子撤销。

存在后续人工修改时，恢复旧全文可能丢失用户工作。能够局部反向操作就局部恢复；不能安全恢复则保留当前文件，生成恢复副本供用户选择。

## 插件与 Agent 连接
首期建议复用本机果铃 Agent 服务。插件连接到经过认证、限定文档与操作范围的本地桥；主应用未启动时明确引导启动，不假设浏览器网页拥有本机文件权限。后续若做云端 Agent，另立数据与计费边界。

认证、回调、TLS／来源校验及本地端口可用性进入原型验证。不要把可任意执行终端命令的接口直接暴露给插件页面，也不把 API 密钥嵌入用户文档。

## 首发宿主选择
以 Windows 为第一验证平台。先用同一份 PPT 在 WPS 与 PowerPoint 各完成一个小型 API／分发验证，再只选择一个进入正式首发。选择依据是用户实际安装环境、原生操作覆盖和安装可达性，不是先写完两套三件套插件。

# 15｜Agent 执行：让每轮修改更短、更具体

## 延续已有执行方向
仓库总纲将原生 CLI＋GUI＋编辑器连接作为长期方向，要求保留原生模型循环与 Skills，而非在应用中再造完整调度平台。[G2] 本方案延续这一取舍：增加文件／宿主能力连接，不因为扩展格式就更换全部 Agent 架构。

README 与开发总纲对可见 AI 的描述存在不一致，因此本版只把当前 CLI／协议当可复用基础，不将其称为已经通过外部用户验收的完整 Agent。[G1][G2]

## 一次编辑给 AI 的内容
当前任务、真实目标、相关版本、必要上下文、保留要求、适用操作与最近结果。默认不读整份文件所有内容，更不扫描整个仓库；需要全局一致性时按需扩展。

用户希望“这个图改成能比较两组数据”，AI可以看到该对象、相关数据与页面上下文。用户不必理解 DOM、OOXML 或 JSON。内部按格式提供清楚的工具，例如章节改写、形状批量调整、单元格区域写入、组件参数更新。

## 执行优先顺序
能用原生／宿主 API 精确执行时优先使用；其次是已验证的文件结构修改或源码补丁；视觉自动化仅在缺少接口且用户认可时作为受限后备，不作为第一版共同底座。

简单手调不调用模型。用户主动让 AI 做小改仍然允许，但不专门建设庞大自然语言命令菜单。复杂任务按收益规划，独立文件可适度并行，不默认多 Agent 审查每一行结果。

## 速度控制
界面受理与取消立即响应；优先批量操作相关对象，减少逐字逐元素往返。局部修改只验证相关内容、引用和布局；交付前做必要格式检查。普通任务不强制“规划—设计—审核—确认”四阶段。

连续尝试没有有效进展时停下，解释具体阻塞并保留已有成果；默认给每个复杂任务设置可见消耗上限。首期不再为路由引入一个专门大模型，格式、目标和用户选择足够时直接确定路径。

## 普通用户接入
对外版本需要安装检查、图形化认证和清晰失败提示，不能要求用户理解终端脚本。已购 CLI 订阅能否按当前方式接入、服务能否商用转售，分别核对；不能把个人登录共享包装成产品默认商业方案。

# 16｜资料、样式与常用方法：第二次更省事

## 资料各有角色
事实材料负责内容依据，数据材料负责数字与口径，样式材料负责字体与视觉，案例材料提供表达参考，目标文件是实际被修改的作品。系统自动建议角色，用户可轻改，不把每次上传变成复杂配置。

旧提案中的客户名与价格不能随品牌样式进入新文件。数据缺失应明确占位或集中询问，不能为了排版完整自行编造。关键事实可跳转到原文件及可定位的页／段／区域。

## 项目说明比不可见记忆更可靠
项目说明保存受众、术语、风格、已确认决定与禁改项，用户可查看、修改或停用。一次局部要求不自动变为全局偏好。跨项目默认不共享客户事实；可复用的方法与私有资料分别保存。

## 复用三类东西
**样式包：**字体、色板、标题层级、常用布局与已有范例。不同格式分别实现，不能用一套 CSS 解决全部文件。

**可编辑片段：**一页演示、一段讲义、一组图表表达、一个互动组件。复用后有明确的实例或副本关系，改一个不误改全库。

**常用任务：**需要哪些材料、采用何种方法、生成什么、保留哪些约束。一次成功后保存，下次替换月份／客户／数据即可运行。底层可使用现有 Skills 与模板，不要求用户画工作流节点图。

## 跨文件更新采用“提示＋有范围地执行”
表格数据变化后，提示哪些报告或图表引用过它；用户确认更新指定部分。人工新写的解释不应被一次整体重跑覆盖。未建立可靠引用关系时，显示“检查更新建议”，不伪装自动同步。

## 内容表达按需增加
报告需要互动解释时，生成一个原生互动组件或 HTML，静态文件包含关键步骤图、链接或二维码。用户没有互动需求时不增加此产物。数据、文稿、演示、互动可以共享来源，但不共享一个万能正文模型。

复用能力的成功标准是下一次实际工作更省事，而不是模板数量、知识库文件数或隐藏提示词长度。

# 17｜最小技术结构：复用事实，不复制系统

## 四个职责即可开始
| 职责 | 负责什么 | 明确不负责什么 |
|---|---|---|
| 文件与任务工作台 | 文件引用、项目说明、任务状态、索引与交付 | 不持有各格式第二份完整正文 |
| 现有 Agent 连接 | 原生会话、模型／工具反馈、授权、候选提交 | 不复制原生 CLI 的模型循环 |
| 格式／宿主适配 | 读取目标、声明能力、局部操作、保存回执 | 不将所有格式抽象成同一种节点 |
| 内容表面 | 显示、选择、轻手调、变化反馈 | 不自行绕过唯一写入者改磁盘 |

## 共享一个很薄的操作信封
共用文件身份、宿主／会话、目标地址、基准版本、操作范围、结果与错误。真正的动作仍分格式：文档替换段落、表格写区域、演示移动形状、HTML更新属性。不能以一个看似统一的 move／undo API 掩盖不同语义。

开始只为真实贯通的两三条路径形成公共部分；重复出现且语义相同后再抽取。不要先建设插件市场、通用 RPC 平台、万能文档数据库和跨格式事务系统。

## 当前代码应保留什么
原生工程与发布合同、语义公式、节点／状态／互动能力、Component／Runtime作者注册、稳定目标地址、现有保存与撤销、简洁／专业模式，以及原生 CLI／Skills 连接方向。[G1][G2]

## 当前代码应新增什么
普通文件与任务外壳；格式适配；外部 HTML 隔离入口与作者映射；一个原生宿主插件；文件交接状态；资料角色与轻量复用。仅在这些新增能力需要时修改现有模块，不借机推倒全部作者表面。

## 两条边界变化应写进路线
其一，产品从受控内部课件工具逐步走向外部用户文件工作台，需要补普通用户安装、错误与恢复体验。其二，外部 HTML 不再天然可信，必须与现有可信扩展分开运行。

新增通用工作台在 Course Project V9 之上管理文件，但不把 DOCX／XLSX 硬塞进 V9，不因为产品改名就新造一版原生工程格式。仓库路线变更以 Owner 决策和实际合同为准，本文件不是实现完成证明。

# 18｜底座选择：轻产品也可用成熟内核

|---|---|---|
| 果铃现有引擎 | 原生互动、组件、运行时与作者目标。[G1] | 核心保留，优先增加外部内容适配 |

| ONLYOFFICE Docs | 完整文档服务集成；外部Automation API有额外付费条件。[S22] | 集成后可裁剪UI的备选，不是本版强制底座 |

## 许可要按实际包和部署核对
SuperDoc 2026-07-14 的许可明确区分 AGPLv3 开源代码与专有 @superdoc/docx-engine。[S19] 不得从外层仓库开源就推导全部依赖可免费商用。Univer 的免费核心也不能替代转换服务和相关扩展的许可。[S20][S21]

这些是选型约束，不是建议绕过授权。对闭源分发、内置服务、用户数量、插件独立分发和离线模式要按实际合同确认。演示可运行不代表可以直接面向客户发行。

## 投入决策
优先比较“完成一条真实任务”的总成本：组件许可、部署、集成、维护、兼容返工及用户支持。便宜但无法稳定保存的方案不合格；适用的成熟内核即使功能很多，也可以隐藏重型 UI。

当前建议自研的是作品定位与操作接续、HTML 混合编辑、文件任务体验及可复用工作方法。不要因为想降低授权费用，就自动承担 Word分页、Excel公式长尾、PPT复杂母版三项内核工程。

**补充评估（2026-09-16）：**候选表之外的免费底座核查（LibreOfficeKit／Collabora 许可与嵌入现状、Univer 开源核心范围、Apache-2.0 的 PPTX 新引擎）及按格式的买／造建议，见附录C。

# 19｜路线与止损：按可验证流程扩展

下列是产品里程碑，不是仓库版本号或承诺工期。AI 可加快实现，因此以真实样本和可用路径决定是否继续，不按传统“先做齐底座”的顺序堆投入。

| 阶段 | 交付内容 | 通过条件 |
|---|---|---|
| A：四个短验证 | 原生AI局改、HTML隔离与映射、PPTX局部往返、外部插件接力 | 每条均可重做、保存、重开；许可／分发路径可接受 |
| B：有限内测 | 文件／任务工作台；HTML／MD；PPTX已支持对象；PDF阅读；一个插件 | 用户能独立完成“已有作品连续修改并交付” |
| C：首个完整产品 | DOCX与XLSX轻编辑；资料整理与多文件任务；普通用户接入 | 六类内容的声明范围可用，不把只读宣称为完整编辑 |
| D：持续使用深化 | 任务／片段复用、更丰富HTML识别、第二宿主、来源更新 | 新能力确实减少返工，成本和用户复用成立 |

## 阶段 A 的明确止损规则
HTML难拆分时先保留整个组件，只开放确定属性，不为追求转换比例重写框架。PPTX原文件修改不稳时收窄对象／动作并让插件处理，不扩大自研渲染器范围。DOCX候选许可或接口不适合时更换候选，不预设必须自己补完分页。

插件无法通过正常发布／安装路径到达目标用户时，先解决分发或换宿主；不能把开发者旁加载成功当正式发布完成。通用办公回路不稳定时，暂停增加格式深度。

## 开发顺序建议
第一批改动让现有果铃原生内容可以被 Agent 稳定定位、局改、取消、保存。同步验证 Office 目标操作及外部 HTML 安全入口。第二批把它们放进共同文件工作台，完成真实任务。后续才加入更大资料索引、模板和多文件自动更新。

## 不设虚假的全面覆盖指标
不承诺“覆盖 95% 修改动作”。分格式列出已经测过的对象、动作与文件条件，再测未见样本。原生内容和外部黑盒分别统计，不能用前者拉高后者的成功率。

如果某项能力耗费大量迭代仍然不能稳定通过样本，应降低自动化深度、保留人工选择与插件路径，而不是继续增加隐性兼容层。

# 21｜效果与性能：测完成工作，不测按钮数

## 主指标
一次任务在目标文件中完成，用户能做第二轮和第三轮修改，保存后外部重开可用，并在下一次类似工作中愿意再次选择果铃。正常到 Office 精修、演示或交付计入成功；修复果铃造成的破坏才计入被迫返工。

同时记录首次局改通过率、范围外误改、整文件重生成比例、保存失败、插件接力成功率、平均修复时间和每个被接受任务的实际成本。人工个性化编辑与修复 AI 错误分开记录。

## 第一批样本
建议 50 份左右文件／任务：PPTX 12、DOCX 10、XLSX 10、HTML 12、PDF／MD 6。至少约三分之一在规则调优后才用于验证。此分配是试验设计，可以随真实用户需求调整。

HTML含静态页、动态框架、图表、Canvas和缺源码构建包；Office含中文字体、图表、编号、公式、组合对象及高级只读对象。每个关键样本都做“手改—AI局改—再手改—保存—重开”。

## 必测反例
同名不同文件、用户选区切换、重复组件实例、AI执行时人工改动、取消后迟到结果、外部未保存文档、保存中新增改动、公式未重算、未知对象保存损失、HTML框架重渲染覆盖修改、跨项目材料污染与受限网络资源。

## 初始性能目标
以下是待验证的内部目标，不是现有成绩或所有模型的承诺：典型本地选中与轻手调争取 P95 在 100 毫秒级反馈；受理与停止在 1 秒内显示；有边界局部 AI 任务争取 15 秒内出现首个真实可编辑结果、30—90 秒形成可接受修改。

固定硬件、文件规模、模型与网络条件，分冷启动和热会话；复杂互动、扫描件与大数据另分组。先优化必要上下文、工具往返、重复生成与保存过程，再决定是否换模型。不能用提前出现的一张占位图充当首个成果。

## 发布阻断
声明范围内的已知数据损坏、错文件写入、取消后继续写盘、丢人工修改不能留到发布后修。遇到不支持内容，应限制该能力，而不是带着“多数时候没事”的状态继续承诺完整编辑。

# 22｜发行、商业边界与最终决策

## 首次使用
用户安装果铃后先打开一个文件或选择一个模板，完成小任务；模型接入检查和必要认证在明确需要时出现。安装专业插件是可选步骤，用户不安装也能使用主应用的已声明能力。

插件有独立可理解的入口：在专业软件中选择内容，呼出果铃，做一次复杂修改。安装失败、宿主版本不支持或本机 Agent 未启动时，应给出具体状态，不把问题表现为无限等待。

## 收费设计暂不预设价格
可以区分工作台能力与 AI 执行消耗；第三方 SDK／转换成本纳入商业测算，不承诺无限高成本任务。用户应知道一次任务的预算上限、已经使用的资源和剩余工作。产品自己的重复执行错误不能无限转嫁给用户。

基础文件取回、已生成成果与历史版本规则提前说清。用户不开高级订阅或停用模型后，不应突然失去自己文件。是否提供自带模型，取决于接口与授权政策；本地执行也不代表发送给云模型的内容不会出本地。

## 不以兼容承诺拉新
对外准确写“支持常见 PPT／文档／表格的选择与定向修改，复杂功能可在专业软件中继续”，不写“兼容任意 Office，所有对象无损”。HTML 同样写“分层可编辑与保留运行”，不把黑盒 AI 尝试包装成稳定结构化编辑。

## 最终产品决策
**保留广度，但不同时自建所有深度。** 文件管理和任务连续性构成主应用；原生 HTML／互动及混合编辑是重点资产；Office轻改通过成熟能力与窄适配实现，专业手工操作交给宿主；同一个果铃 Agent 在不同工作位置持续服务。

近期最应投入的是三项：**真实目标的可靠局部写入、HTML 逐步增加可编辑性、一个外部插件的完整接力。** 资料、布局与常用任务复用沿这些真实流程叠加。

衡量果铃的标准应当是“用户已经做了一半的工作，能否更顺利继续完成”，而不是“菜单里有多少种格式”或“能否在一个窗口复刻全部办公软件”。

## C.2 下限与上限的分工
Owner 2026-09-16 明确：AI 原生用于拉高上限，产品下限不能依赖 AI；只能预览、点选而不能所见即所得手动编辑的 Office 文件，不构成可用下限，与 WPS／Office 的体验差距会直接导致无人使用。

接受这一判断的后果是：主应用必须为 Office 文件提供真实的内嵌编辑表面，内核部分自研、部分采用成熟组件；一人阶段无法同时完成三个格式，需要按格式排序，而不是按“六格式同时轻编辑”推进。

## C.3 “网页版 Office”分两类，门槛不同
**A 类：自有模型＋有损导入导出。** 腾讯文档、飞书文档、石墨、Google Docs、Notion、Gamma、PPTist、canvas-editor 属于此类。几乎全部自研，门槛中等；但不承诺“打开用户的 PPTX、修改、存回不丢内容”，导入即转换。

**B 类：以 OOXML 为原生格式、保真往返。** Microsoft Office、WPS、ONLYOFFICE、LibreOffice／Collabora，以及单格式的 SuperDoc（DOCX）与 Univer（XLSX）。门槛不在“做出编辑器”，而在“渲染与 PowerPoint／WPS 一致”和“不丢任何未支持内容”。

第 11 章要求的下限属于 B 类；“网页 Office 都是自研所以门槛不高”的推断只对 A 类成立。当前仓库的 Flow 编辑器与 PPTX 导入→V9→pptxgenjs 导出，也属于 A 类路径。

## C.5 逐格式底座评估
**PPTX：尚未确定正式底座，不预设自研是唯一合理选择。** 候选包括可编辑的单格式引擎、成熟套件集成，以及必要时的有限自研适配。现有 Slide 编辑经验可以复用，但导入为 V9 再导出不等于原文件保真往返。候选的渲染、写回、桌面接入与许可需分别确认，初版清单见 C.13。

**DOCX：没有“免费＋轻量＋保真”三全的选项，是自研门槛最高的一格。** 分页排版是 Word 的全部：样式继承、多级编号、浮动对象、节与页眉页脚、表格跨页、东亚排版。ProseMirror 类编辑器没有分页，不是 Word 意义上的所见即所得。免费选项中：LibreOfficeKit（MPL-2.0，可闭源使用，保真最高）需要 C++ 原生集成、体积大，公开的 Electron 嵌入尝试 electron-libreoffice 已归档且要求 `--no-sandbox`[S30][S31]；Collabora Online 源码为 MPL-2.0，但可执行形态附加专有条款，需法务核对[S32]；canvas-editor（MIT）为国产 Word-like 分页编辑器，DOCX 保真有限；SuperDoc 与 ONLYOFFICE 闭源使用均须购买，SuperDoc 商业条款还限定“一个文档体验”并禁止用于竞争性 DOCX 编辑器。[S19][S33] 现实选项只有三个：购买商业许可、重集成 LibreOfficeKit、或接受“Web 版式无分页＋原包保留写回”。教案／试卷用户对第三种的容忍度未知，建议 PPTX 之后再决定。

**XLSX：有免费可用底座。** Univer 开源核心（Apache-2.0）包含编辑、500+ 函数的公式引擎、条件格式、数据验证、筛选排序；导入导出、图表、透视表、增强公式性能属于 Pro。[S20][S27] 导入导出可自行用 ExcelJS（MIT）映射到 Univer 模型，工作量中等。教育切入场景中优先级最低。

**PDF：**沿用第 18 章 PDF.js 结论，不在本附录扩展。

## C.7 LibreOffice 的角色
LibreOffice／LibreOfficeKit 是唯一免费、许可友好（MPL-2.0）、三格式、高保真的引擎，但不是嵌入式编辑组件。在本产品中最划算的用法是 sidecar：参考渲染（把页面渲染成图，供未支持对象占位与保真比对）、格式转换（.ppt→.pptx、DOCX→PDF 预览）。Windows 上本机已安装 WPS／PowerPoint 时可用 COM 自动化出图，仓库已有“借本机兼容软件另存”入口。是否后期用 LibreOfficeKit 承担 DOCX 分页视图，视 DOCX 决策另定。

## C.8 “自研轻量底座”的定义
不是自研一个 Office，是三件事：

1. **原包保留。** 打开时只把支持的对象解析进编辑器，不支持的原样留在包里；保存时只替换触碰过的 part（该页 slide XML、rels、新媒体），其余字节不变。
2. **只为支持的对象子集负责渲染一致性。** 字体回退表、自动缩放、换行、主题色／字体解析、占位符继承。不支持的对象用参考渲染出图并锁定，不丢、不假装可编辑。
3. **保真回归门。** 一批真实教学文件，打开→改→存→WPS 重开，自动与参考渲染比对。这是护栏，决定敢开放哪些对象。

按此定义，责任范围是“支持的对象子集＋其余不丢”，而不是 OOXML 全集；一人阶段可以承担。

## C.9 近似保真的可接受边界
市场已经证明近似保真可以被接受：WPS 与 Office 之间至今仍有格式跳变，用户仍在两边互开文件。但接受是有条件的、不对称的：

- **通常可接受：**行距／换行微差、字体回退后的字形差异（不溢出）、阴影／渐变等效果近似、动画在本软件内不播放但保留。
- **不可接受：**内容丢失、文件需修复才能打开、对象位置或尺寸错乱、字体回退导致文字溢出或截断、母版／动画／图表数据丢失、未编辑页面发生变化。
- **信任前提：**用户对 WPS 的容忍来自长期使用与免费分发；新工具没有这种信任，首次坏体验即流失，因此开放对象必须比能力更保守。
- **原包保留的意义：**它把保真问题从“整个文件”缩小到“本软件渲染的显示差异＋本软件写回的对象正确性”，这两项都在自己可控范围内。

## C.10 历史参照：“一人写出 WPS”
1988—1989 年求伯君独立完成 WPS 1.0，是 DOS 时代的自有格式文字处理器，当时不存在与 Office 兼容的目标。与 Office 的兼容是此后数十年、大团队的工作：2002 年起金山重写 WPS，投入上百人、历时约三年，2005 年才达到“深度兼容”，至今仍有跳变。两段历史说明两件事：近似保真确实被市场接受，这下调了门槛；“全套对等”仍是团队级工程。一人加 AI 在 2026 年可达的是“子集＋保留＋兜底”，与 C.8 一致，不是复刻 WPS 2005 的全量兼容。

1. **PPTX 优先：**先补原包保留式写回，再建保真回归门，之后按样本逐步开放对象类型。

## C.13 初版候选与当前版本边界（2026-09-17）

### 当前决定

- 当前版本优先完善核心使用流程与已确认的前端方案：工作空间资源管理器、文件夹项目与会话、可收展和调整位置的画布、Markdown 编辑，以及原生 h5lesson 编辑器的场景／状态管理。具体设计以 `双形态UI设计/00-设计说明.md` 为准。
- Office 当前通过对应宿主打开；保留已有材料提取、PPTX 导入和导出能力。本次不引入新的 Office 预览／编辑引擎、转换服务或插件开发任务。
- 后续方向是“原文件 → 可编辑文档状态 → 渲染与选区 → 高频编辑 → 原格式保存”。第一阶段可以只开放预览，但选型要能承接后续编辑；不把 Office→PDF 作为长期编辑主路线。PDF 可用于导出、参考渲染或后备预览。
- 2.1 暂记为候选目标：优先评估 PPTX 的原格式预览与有限编辑闭环，不承诺三格式同时保真；正式范围待当前版本完善后确定。外部 HTML 编辑继续留在长期路线。

### 初版候选清单

| 范围 | 候选 | 简单核实与用途 | 待确认，不作为已通过能力 |
|---|---|---|---|
| PPTX | office-kit/pptx + 配套 preview | 官方仓库提供读写、对象修改和预览；仍为 0.x，明确不是完整保真绘制引擎。[S29] | 中文排版、未编辑内容保留、对象选区接入、打开耗时；尚未运行样本 |
| PPTX | ChristopherVR/pptx-viewer、CasualOffice/slides | 沿用 C.6 的已有调研，保留为备选或实现参考；本轮不重复深查。[S25][S28] | 编辑／渲染／写回是否满足同一闭环，不能将项目自述当作本产品验收 |
| DOCX | SuperDoc | 官方文档描述同一 OOXML 引擎支持读取、分页渲染、编辑与写回，适合继续评估。[S18] | 中文复杂文档、未支持内容保留、商业嵌入条件；未做兼容测试或授权结论 |
| XLSX | Univer + 文件交换能力 | 当前官方导入导出 API 需要转换后端，snapshot 模式也不例外。[S35] | 桌面本地部署、交换扩展许可及往返完整性；不能将开源核心或 ExcelJS 映射直接等同于保真编辑 |
| 多格式套件 | ONLYOFFICE Docs；LibreOfficeKit／Collabora 备选 | ONLYOFFICE 官方架构包含查看、编辑、保存及服务端组件；LibreOfficeKit／Collabora 沿用既有调研，暂不扩大调查。[S36][S31][S32] | 安装体积、服务／原生集成、界面适配与许可；不预判必定比单格式方案更合适 |

统一的是工作台体验与文件会话边界，不强行统一各格式的内部模型。现有 V9 导入／导出不能作为 Office 原格式写回的替代。C.3 的产品分类、C.5–C.7 的成本／许可判断仅保留为历史参考，不据此推导“唯一可用”“全部免费”或“保真已成立”。

### 后续启动条件与研究停止点

当前只记录候选和证据链接，不安装候选、不做性能跑测、不建开发任务、不增加当前版本依赖。未来正式启动时，先用少量代表性文件证明“打开 → 修改一个文本／图片对象 → 保存 → 对应宿主重开”，检查呈现、未修改内容保留及首次打开耗时；只有聚焦证据不足时才扩大样本。C.11 的约 30 份样本不是本轮或选型起步的前置要求。
