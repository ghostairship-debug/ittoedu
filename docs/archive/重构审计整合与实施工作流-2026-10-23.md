## 1. 先核实审计报告，建立当前问题地图

第一步读取 `C:\Users\74755\Desktop\审计报告` 中的报告，结合当前工作树核实：

- 报告针对什么版本、什么入口，今天是否仍可触达。
- 描述的是已发生的问题、源码推断、历史问题，还是改进建议。
- 用户受到什么影响，现有修复是否已经覆盖。
- 与本次组件、Flow、插入、发现、AI 创作及编辑重构有什么共同根因。

优先核实影响核心操作、明显性能和 AI 效率的结论。涉及实际呈现的问题看呈现，涉及性能的问题做对应测量；静态源码不能替代这些证据。

**产物：**一份可追溯的问题映射，归入现有方案或其直接支持材料。原始报告保留，不先逐条照单修复。

## 2. 将审计与重构合成同一份方案

以当前用户任务组织问题：

> 创建内容 → 找到能力 → 正确插入 → 人工及 AI 修改 → 运行预览 → 保存重开 → 实际交付。

每个问题按以下关系归并：

> 用户失败 → 当前证据 → 根因 → 应负责的 owner → 受影响消费者 → 实施切片 → 验收结果。

处理方式分四类：

| 类型 | 处理 |
|---|---|
| 与本次重构同根的问题 | 合并解决，避免再做独立补丁 |
| 独立但直接影响核心使用的问题 | 安排独立小项，不强塞进共享抽象 |
| 已修、失效、重复或不成立的问题 | 说明依据，从实施范围中移除 |
| 尚未证实或当前价值较低的问题 | 保留具体疑问及触发条件，不阻塞主线 |

直接更新[现有方案](组件体系与Flow重新抽象设计方案-2026-10-22.md)，不再建立平行总方案。保留原产品目标，允许依据核实结果调整切片和顺序。

## 3. 实施前完成一次集中架构裁决

针对确实涉及职责变化的部分，比较现有能力复用、局部修复和必要职责调整，选能消除根因的充分方案。

重点判断：

- 业务决定、状态和写入分别由谁拥有。
- 哪些重复判断可以收回，哪些差异确有合法消费者。
- 新抽象解决了什么已核实问题，原路径怎样退出。
- 新核验门保护什么具体失败；没有当前依据的门，删除或改为诊断。
- 是否让模型继续承担了身份、默认值、资源登记等机械任务。

重要结构变化由独立执行者复核。产品目标、费用或权限等真实新增取舍，整理成具体候选后集中交 Owner 决定。普通实施细化自主推进。

**产物：**现有方案中的决定摘要、函数级切片、依赖及必要验收。调查已足以确定改法时即结束，不继续追逐旁支。

## 4. 按切片实施，保护当前有效成果

以实际工作树作为基线，辨明既有改动和本轮改动。未提交状态本身不阻止实施，是否提交由 Git 授权决定。

主执行者负责共同理解、共享文件和集成。子智能体用于：

- 独立核实报告及消费者；
- 实施边界清楚、互不重叠的任务；
- 对重要候选进行独立评审。

每片完成一个可用结果，同时处理其改变的保存、History、运行及输出消费者。现有有效证据继续复用。

局部补丁无法消除根因时，在正确职责边界调整；不为假设性未来扩建框架。

## 5. 持续验证体验、性能与 AI 能力

验证伴随切片进行，最后再用少量完整任务汇合。

| 重点 | 直接证明的结果 |
|---|---|
| 产品体验 | 能找到、插入、定位、继续编辑；人工调整保留；操作和撤销符合预期 |
| 软件性能 | 对应输入、布局、挂载、打开、保存或关闭问题的实际延迟改善 |
| AI 能力 | 能创建有意义的内容组合、准确局改并继续接力 |
| AI 效率 | 首个可用结果、往返次数、输入输出负担、返工和总时长 |
| 可靠交付 | 保存、独立重开、实际运行及受影响输出成立 |

性能与模型对照保持可比条件，分别记录模型等待和软件处理成本。不能通过减少内容、素材、互动或可编辑性获得“提速”。

安全不设独立建设主线；保留防止已知错写、数据损坏、凭据泄露和权限越界所需的现有边界。

## 6. 集中复核复杂度并收口

最后检查本轮实际变化：

- 共同根因是否消除，旧的重复职责是否退出。
- 是否留下双轨状态、额外 writer、重复默认值或多余适配。
- 是否新增了没有直接消费者的抽象、门禁或恢复机制。
- 核心任务是否正确、可编辑、可保存、可重开、可运行。

发现必要问题就修复；未变证据不重复验证。最终报告区分已解决问题、实际收益、未完成范围和需要 Owner 决策的事项，不以持续扩大审计代替收口。
