## 0. 决策摘要

**推荐保留现有技术主干，以共同的“作者目标—操作语义—输入接管—正式提交”协议完成整合。专业编辑器继续存在，同一事实只保留一个权威来源。**

原方案对问题的定位大体正确，已经讨论了精确目标、输入所有权、父子层级、专业编辑、冻结 AI 目标、DOM 所有权和受管文档事件接管。它并非只打算统一工具条，也没有主张把任意程序拆成原生节点。本次不推翻这些判断，更不把其中已有的内容包装为新发现。

需要重点收敛五件事：

1. **统一协议位于工作台层，GLX 的具体选择状态仍可由既有 Bridge 持有。** 独立 HTML、GrapesJS 结构视图和 Markdown 必须有明确接入口；不能让 GLX 专属 Bridge 承担所有文件格式，也不能在它旁边复制另一份选择真相。
2. **内容、布局、实现载体分别处理。** “是不是文字”“按文档还是自由坐标布局”“由原生组件还是源码实现”不能继续共同决定三套互不兼容的点选规则。
3. **统一用户可见的编辑含义，不强制相同底层提交频率。** 普通正文、数据字段和需要重载的源码字段，要共用完成、拒绝保稿、撤销入口和保存链，不能被误实现为每次按键都重写并重载整个程序。
4. **将连续正文投影与普通精确编辑分开验收。** 两者都要做好，但无需先把全部 Flow group 改成一个巨型 ProseMirror 文档，才允许文字、图片和父级整体好用。
5. **落实到完整用户任务，并退出旧裁决分支。** 增加统一类型、隐藏重复工具条或单独接好一种文字，都不算整合完成。

这是基于当前代码、已知产品目标和成熟编辑器机制的推荐路线，不是已经通过用户实验的唯一最优解。需要真实验证的范围已压缩到具体交互和局部技术边界，无需重新进行全架构探索。

## 1. 核心需求：让用户直接接手眼前作品

用户需要完成的事情可以归纳为：改眼前的一段内容；操作包含它的整体；调整更深层的结构或实现；试用修改后的作品。用户不应先判断当前内容属于 native text、document-block、author spot、HTML text node 或 iframe，再猜应该单击、双击、按修饰键还是打开另一套编辑器。

因此，本次的产品目标是：

> **用户始终知道当前在改什么、改动影响哪里；常见修改可以直接发生，更深的修改沿同一目标逐步展开；结果能可靠撤销、保存、再次编辑。**

这里有两个重要区别。

**“能选到”不等于“能完整操作”。** 能给按钮文案画一个框，但属性栏修改整个组件、Delete 删除父级、AI 又收到整块页面，仍然没有满足需求。

**“操作统一”不等于“所有内容具有同样能力”。** 图片替换应有一致入口；Flow 图片的位置由阅读顺序决定，自由画布图片的位置由坐标决定。公式要保留公式编辑，表格要保留单元格语义，程序内部没有可靠作者绑定的像素不能被伪装成可编辑元素。

主要使用场景是 AI 生成后由人进行局部纠正和持续完善。因此推荐日常编辑采用“内容优先、整体显式可达”：点击可编辑文字定位光标，点击图片选中图片，边界、名称和层级路径负责选择包含它们的整体。此取舍与原方案一致，属于产品建议，而非联网资料证明的普遍法则。

## 4. 建议架构：统一规则，保持责任边界

### 4.1 先拆开三条互相正交的轴

| 轴 | 例子 | 应决定的事情 |
| --- | --- | --- |
| 内容语义 | 富文本、纯文本、图片、公式、单元格、图表、组合、程序 | 能编辑什么；内容操作究竟意味着什么 |
| 布局与组织 | 连续文档、Flex/Grid 阅读布局、自由画布、空间 world/HUD | 顺序、移动、缩放、重排和坐标解释 |
| 实现与写回载体 | 原生 data、HTML 源码、作者记录、专业资源文件 | 用哪条已有编译/写回链、是否能热更新 |

同一图片在三种载体中应有共同的“选中、替换、查看属性、交给 AI”操作。它是否能够自由拖动、是否能独立删除、是否会修改共享定义，由布局和真实绑定决定。

**统一判断应是“这个目标支持什么操作”，不再主要是“这个 builtin/这个工作区走哪段特例代码”。** 能力由现有适配器及真实绑定派生，不建设新能力注册中心，不要求模型为每个元素登记一遍。

### 4.2 共同协议需要表达四件事

**作者目标。** 指向对象、对象中的字段、文字范围或单元格范围。目标使用现有正式 ID、字段路径、authorKey/scope 或版本约束下的源码地址。几何框、DOM 节点和 mountGeneration 是视图定位资料，不是持久身份。

**操作及作用范围。** 明确“修改文字”“替换这张图片”“移动整个组”“删除本节点”“修改当前实例的样式”等含义。一个文字字段可以支持清空，却未必支持移除；父对象支持删除，不能让字段的 Delete 自动变成删除父对象。

**输入会话。** 明确当前由正文、局部字段、表格、公式、源码还是对象手势接管输入，如何从一个目标交给另一个目标，以及当前草稿是否已被接受。多个 EditorView 可以保持挂载，只有当前接管者能够解释该轮输入。

**正式提交与结果。** 专业适配器把意图编译成现有 edit/command，继续经过原有版本校验、DocumentSession、History、资源和保存链。成功后更新选择和视图；失败保留输入并说明原因。共同协议不自行保存第二份正文或项目树。

### 4.3 不把“一个 owner”误解为“一个巨型类”

推荐采用下列责任划分：

| 事实/职责 | 唯一权威来源或最终裁决者 | 其他模块的角色 |
| --- | --- | --- |
| 正式内容、历史与资源提交 | 各文档既有 DocumentSession/驱动链 | UI、GJS、PM、runtime 均为输入或投影 |
| GLX 的真实根、容器、场景状态与精确选择 | 扩展既有 GLX Bridge/kernel；粗实例 IDs 从精确选择派生 | 表面、图层、属性不能继续独立改同一事实 |
| 独立 HTML 的精确选择 | 在现有 HTML 文档控制器/适配中收拢；轻编辑与 GJS 消费同一选择 | 预览 handle、GJS key 是可失效的视图定位，不是第二作者地址 |
| Markdown 文档选择 | 既有文档编辑适配承载并映射专业选区 | 工作台不复制一份 Markdown 正文 |
| 当前活动文档/输入接管/统一命令 | 工作台提供一个共同接口与仲裁入口 | 它读取当前文档适配器，不另维护一份可独立写的全格式选择镜像 |
| AI 的已发送目标与授权 | 既有 capture、pin、Main 授权链 | 人工光标移动不改变已发送任务范围 |
| hover、rect、光标、挂载代次 | 对应视图的临时观察和专业 EditorView | 只用于命中与显示，失效时重新定位同一作者目标 |

这保留了原方案“在既有 Bridge 中扩展 GLX 精确选择”的优点，同时把共同行为提升到真正覆盖工作台的位置。无需把 HTML 塞进 CourseV10DocumentBridge，也无需建立第三个全能 store。

工作台的共同实现至少负责：候选到语义目标的选择策略、已选对象继续操作、父级导航、输入交接、命令路由、工具状态与目标标签。各适配器只提供专业事实、定位和写回能力，不能又各自重写这些规则。

### 4.4 状态读取和修改必须单向

建议数据流为：

`点击/图层/键盘 → 共同选择与命令规则 → 当前文档的唯一选择 owner → 统一交互读口 → 工具条/属性/AI捕获`

写入为：

`目标 + 操作 + 作用范围 → 专业 planner/现有 edit 编译 → 既有 Session → 接受/拒绝 → 同一目标的视图更新`

避免让 Bridge、editorStore、局部 selectedSpotKey、PM 选区监听和 workbenchSelection 通过多个 effect 互相修正。迁移到共同读口的那一种目标，旧分支必须同时失去独立裁决权；兼容字段可暂保留只读投影。

`SelectionContextController` 现有冻结捕获、pin 和 prepare 不应直接变成高频交互对象。hover/光标使用当前已加载的投影和局部观察；开始正式编辑、执行操作或发起 AI 请求时，才捕获必需的版本与旧值。原方案已提出不在 pointermove 读取全量工程，本次补充上述实际复用陷阱。

## 5. 用户操作方案

### 5.1 用户只需要理解内容、元素、整体

这三层是用户面对的操作范围，不是新建三棵作者树。布局辅助 div、技术 iframe 和框架包装不自动成为用户必须经过的层级。

| 用户任务 | 建议行为 | 必须避免 |
| --- | --- | --- |
| 改普通可编辑文字 | 单击按位置放光标；拖动选字；双击维持常规选词 | 同为文字，因处于组内或 runtime 而无提示双击失效 |
| 改纯文本字段 | 同样直接定位输入，只展示它实际支持的格式 | 使用富文本 UI 暗示不存在的分段格式能力 |
| 换图片 | 点击选图，出现替换/已有裁切能力；一次动作进入选图 | 先选父组、再猜修饰键、再找深层属性 |
| 移动文字元素 | 拖边框或明确移动把手；正文拖拽柄用于重排 | 在文字正文里拖动时既选字又搬动整个组 |
| 操作整体 | 名称标签、边界和层级路径可直接选择组/组件 | 要求连续钻取多层包装；把技术容器强加给用户 |
| 已选子元素继续拖缩 | 沿用明确选中的语义目标，除非用户明确改选 | 同一位置再次按下退回顶层祖先 |
| 右键/更多菜单 | 与目标高亮、属性栏和快捷键作用于同一范围 | 菜单标题是“内部图片”，命令却使用 owning instance |
| 编辑结构或源码 | 从当前目标进入对应视图并尽量定位同一内容 | 打开另一个无关联工程或丢失定位上下文 |
| 多选 | 对象态使用共同增减选择规则；父子排重；能力取可解释交集 | 多选无法共同执行时静默只改部分对象 |
| 复制/删除 | 由明确目标语义决定；不支持独立操作时说明并提供选父级入口 | 字段操作失败后自动升级成整组件操作 |
| 切换目标 | 记录最初点击的目标，完成前一合法输入后接续这次选择 | 提交重排后按旧屏幕坐标重新选到另一对象 |
| Esc | 先交给输入法/临时弹层；普通输入完成并退出；手势取消本次预览 | 普通文字因为离开编辑而整段消失 |
| Undo/Redo | 使用共同入口与既有 History，优先正确结束/处理当前输入 | 原生字段、HTML、GJS 各有互不知情的正式历史 |
| 编辑与运行 | 编辑态点击内容只编辑；运行态同一按钮正常执行 | 修改按钮文字同时跳页、提交表单或改变业务状态 |

图片的自由拖动、Flow 重排、旋转和缩放仍由实际布局能力决定。图表或公式的点击可以先选中，再通过明显的“编辑数据/编辑公式”进入专业面板；不必为了形式一致而强行单击即打开所有重编辑器。

### 5.2 不增加常驻“轻编辑/深编辑”开关

深度按目标渐进展开：当前内容的常用动作就近出现；完整属性在稳定位置；结构和源码属于更深视图。常见文字与图片修改不要求用户预先选择编辑技术或进入多个不同模式。

编辑与运行仍是必要的输入边界。结构/源码是同一作品的视图，不是新的文档副本；公式、图表等专业表单可以保留明确的应用/取消。

### 5.3 一套上下文，不要求全屏只有一条工具栏

正文格式区、对象快捷条和属性栏可以各有位置，但同一动作应来自共同命令与能力判断。当前在局部文字输入时，外层对象控件不得仍响应 Delete、抢选区或显示另一目标。

优先保留已有 UI 位置，减少布局改动：常用内容操作就近；完整属性在原侧栏；目标路径显示在当前操作区附近。工具条的点按不视为离开正在编辑的内容；打开菜单前保留专业选区，关闭后按需恢复。键盘进入与返回遵循 WAI 工具条模式 [W11]。

### 5.4 一个示例说明统一的实际结果

用户点击咖啡图文组的标题，直接修改文字；点击组内图片进入替换；再点击“图文组”名称调整整体间距；通过当前目标的“交给 AI”只修改这段说明；切到运行点击互动按钮。

其中每一步都应保留明确的目标、作用范围和撤销路径。用户不需要知道标题由 document-block 渲染、图片属于哪一层 group、互动内容是否在受管 HTML 内。这种任务完成程度才是统一的验收对象。

## 6. Flow：精确局部编辑与连续正文分别闭合

### 6.1 先解决共同接管，避免把全部工作压在投影重构上

现有原子组件内部只要有真实作者字段或专业内容 slot，就应通过共同宿主获得可用的文字/图片编辑、属性和 AI 入口。这样可先消除当前“看见但选不到、选中却改不了”的阻断。

同时，确属同一连续正文的内容不能永久退化为很多独立输入框。两项工作并行规划、分别验收，不能以局部可编辑冒充连续文档体验完成。

### 6.2 只有具备明确文档语义的布局进入连续投影

优先覆盖既有 section、标题、段落、列表、引用和明确定义的内容 slot。边框、底色、留白、Flex/Grid 视觉包裹不应天然切断这些内容的文档语义；但自由构图的多个标签、旋转文字、程序 UI 不自动合成一篇文章。

判定使用现有作者语义、正式 childIds 和阅读顺序，不能只看是否有 frame、CSS 类名或 DOM 深度。对无法可靠判定的旧组合保留身份并提供局部编辑，不自动重新解释用户作品。

### 6.3 contentDOM 是专业投影机制，须有单一 DOM 所有者

原方案 T1 应保留：取一个真实咖啡阅读组验证。若采用 contentDOM，其可编辑后代由 PM 管理，React/World 不再并行改写同一后代 DOM；媒体、专业对象和程序保留明确原子边界 [W5]。

验证必须同时覆盖：身份和父子关系往返、Enter/Backspace/粘贴、跨段选区、中文输入、未编辑邻居保留、原 Flex/Grid 布局与自然高度、`.body.md/.body.html` 的已有读写关系。

如果某种组合本来就有独立内容区域，应保留专业 EditorView 并接共同宿主；如果它确属连续正文，则需完善投影，不以局部输入框长期替代。不得为这项 UI 整合无依据升级 Project/Published 格式；若真发现新的持久语义需求，单列论证，不夹带迁移。

## 7. HTML、GrapesJS 与 runtime：补齐共同入口，保留源码

### 7.1 独立 HTML 与 GLX 内 HTML 统一到同一操作协议

独立 HTML 当前有三个有价值的入口：实际运行预览上的轻编辑、GrapesJS 结构投影、源码编辑。它们应看作同一文档的三种视图。

预览里选中的目标在结构视图能够定位到对应作者/源码节点；从结构树选择也能在预览定位。无法映射到静态结构的程序生成字段，应保留它的作者字段地址，并解释为何源码/数据才是该目标的实现入口。不能把运行结果序列化后替换原程序。

当前 GJS 已把 style/move 变化转换为 HTML source edit command，并通过原 Session 提交。继续使用这一机制，整合其选择、命令、工具和生命周期；不重新启用独立保存、私有 History 或整页导出覆盖源码。

不要求为了咖啡创作先补全所有 HTML 可视化能力。架构契约与最小已支持文字/图片/结构的接入在本计划范围内；尚未支持的属性与程序能力保持明确边界。Office 兼容层不在此次扩展范围。

### 7.2 编辑态输入必须在事件发生的 realm 内同步裁决

本次确认 HTML agent 已有 `editMode` 与 click/dblclick 拦截，见 `src/player/htmlPreview/htmlPreviewAgent.ts:363–381,475–482`。这可以复用，但不是完整解决：pointerdown/mousedown、键盘行为、更早注册的作者监听仍需检查。

GLX sandbox 的当前入口主要回报事件。将父窗口收到 postMessage 后再调用 preventDefault，无法撤回子文档已经执行的业务动作。

实施沿已有受管文档初始化路径处理：

- 在可控制且早于作者脚本的启动位置安装编辑输入仲裁；沿现有桥同步 edit/run 和输入接管状态。
- 对编辑手势在本 realm 阻止作者业务处理与浏览器默认动作，再报告精确目标；不只处理末尾 click。
- 已进入专业文字输入的事件交给该输入 owner；不能让通用拦截器吞掉中文输入、选字和工具条。
- 对受管嵌套文档保持原有身份和校验。未确认早期接管能力的外部隔离内容只提供实际支持的整体/源码入口。
- 不把被拦下的业务事件在提交后重新播放。Published/离线作品保持正常运行行为，不带作者编辑遮罩。

`authoredDocumentBootstrap.ts:35–40` 已有同步初始化位置，应优先复用，而非另建 iframe 运行框架。T2 用同一个按钮验证编辑态改文案不执行、运行态正常执行，并加一项 pointerdown 处理的对照即可，不建设通用恶意程序测试平台。

### 7.3 源码字段保真优先于假统一

对源码有唯一精确映射时，沿现有源变更；只有作者记录适用时沿记录写回；数据字段沿数据编辑。选择绑定不可靠时停在当前局部并说明原因，不能按文本相同去替换全页面，也不能静默扩大到父组件。

原生对象、HTML 标签和 runtime 作者字段采用一致的标签、常用操作和命令范围，但不虚构共同的“可独立删除”或“可任意拖动”能力。外观和几何以当前实际可写能力为准。

## 8. 输入、撤销、保存与 AI 的整合约束

### 8.1 统一交接，不统一所有提交时机

建议交接流程：捕获用户初次指向的精确候选与局部光标意图 → 让当前输入 owner 完成合法输入 → 沿既有 flush/ACK 处理 → 重新定位同一候选 → 开始下一次输入。

只保留最新一次明确接续意图，不建立任意事件队列。候选不存在或作用域已变时明确反馈，不用原坐标重新猜另一个目标。中文组词、打开格式菜单、提交被拒、外部内容变化仍沿现有保稿机制。

普通文字的 Esc 表达结束当前输入，不表达丢弃整次修改。尚未被接受的合法普通输入需先交给既有草稿链；提交失败保留草稿并提示，不能显示保存成功。公式/源码等明确“应用/取消”的临时表单另保留其明示语义。

### 8.2 History 的共同含义与写源代价

正文现有 historyGroup 可复用。局部数据字段应传递一致的编辑分组和操作边界，避免因 UI 外壳不同出现不可解释的大块撤销。

源码字段必须单列：`slideAuthoringSlice.ts:205–206` 已提示源码变更可能重载程序。不能把“统一普通输入”实现为逐键改整个 HTML 并反复重载。推荐输入期间使用已有草稿/局部预览，按适配器可靠支持的输入批或完成边界提交；可可靠热更新的数据字段继续增量提交。

共享的是 Undo/Redo 的入口、当前草稿处理顺序、正式 History 和可解释的改动分组，不是每个载体相同的网络请求数。当前 pending 输入怎样进入/退出原有 History 必须在适配器接入时验清；不得新建一个 GJS/HTML/局部文字私有正式撤销栈。原方案没有要求逐键重载，此条用于消除实施歧义。

保存继续使用原 prepare/flush/drain/资源提交。切视图、切目标、保存不能各自创建新的提交入口。恢复内容由既有机制负责，不为本次任务新增通用自动存档系统。

### 8.3 AI 与人工共用语义，不共用可变选区

人工活动目标用于当前交互；AI 发起时捕获目标、版本和实际授权；发送后保持冻结。AI 结果定位通过共同目标解析器回到精确字段或范围，不回退到 owning instance。

“选中这一段”与“允许 AI 修改这一段之外的内容”仍是两个独立问题。保持现有权限策略，不因统一 UI 缩减或扩大既有授权。点选局部后的快捷 AI 操作应显示实际目标和影响范围；模型不负责猜当前 field key、维护 DOM 登记或重建布局。

人工光标移动不修改已运行 AI 的任务范围；AI 完成也不无条件把用户当前正在编辑的位置抢走。用户主动查看结果时再定位相应目标。

## 9. 路线比较与结论

| 路线 | 对核心需求的帮助 | 主要代价 | 本次决策 |
| --- | --- | --- | --- |
| 只统一工具条、补双击白名单 | 能修部分表象 | 目标、键盘、属性和 AI 继续分叉 | 不采用 |
| 所有内容换成同一个编辑引擎 | 表面上减少引擎数 | 重做表格/公式/HTML/输出，仍解决不了跨 realm 事件和源身份 | 不采用 |
| 所有 HTML/runtime 拆为原生节点 | 可增加某些静态内容编辑 | 高保真与程序语义受损，任意内容无法通用拆解 | 不采用 |
| 统一塞进一个 GLX 专属状态 owner | GLX 内收敛较直接 | 独立 HTML/Markdown 要么遗漏，要么被迫侵入 GLX 模型 | 保留 GLX owner，提升共同协议，不扩大该类职责 |
| 共同交互协议、每文档唯一事实源、专业适配与原有提交链 | 直接解决同一目标跨入口不一致，保留专业能力和已通过修复 | 需要把消费端全部接完，不能只增加接口 | **推荐** |

这一路线会减少“表面 × 内容类型 × 实现载体”的重复交互分支，但不会消除所有专业差异。后续新增一种专业内容，应主要补它的目标与能力适配，不再复制一套完整工具条、快捷键、选区和保存逻辑。

## 10. 建议实施顺序：按完整用户任务推进

以下是后续获准开发时的计划，本次不执行。

### 阶段 A：精确目标与命令闭环

选择真实 Flow 图文组和一个已有 runtime 作者字段作为最小样本。共同协议先定义 GLX、HTML、Markdown 的接入边界，实际迁移优先当前阻断最明显的 GLX。

完成精确目标 owner、粗 IDs 派生、共同输入读口，并让高亮、工具条、属性、右键、键盘和 AI 捕获全部消费同一目标。字段 A 切字段 B 即使属于同一 instance，也必须更新上下文。

本阶段退出相应目标的局部选择裁决分支；禁止只新增一个未被消费的类型。Delete/Copy 不得默默升级到整体。验证保存/重开仍是已有链路，不在此阶段重写文档序列化。

### 阶段 B：常见文字、图片与整体操作闭环

收拢 Flow 局部编辑外壳和自由表面的文字外壳，统一接管、Esc、IME、工具条、历史分组和目标交接。补通已有 runtime 图片替换，以及 Spatial/Program 已有作者字段能力的消费者。

同步完成受管 realm 的 T2 输入裁决。可复用命中与几何算法，修改各表面的接线；不重新研发几何引擎。用“改标题 → 换图 → 选整体 → 调属性 → Undo → 保存冷开”验收。

### 阶段 C：独立 HTML/GrapesJS/Markdown 接入

HTML 轻编辑与结构编辑共用文档目标，源码视图尽量定位同一源范围；GJS 保持可丢弃投影，统一菜单和键盘不恢复私有 History。Markdown 使用既有 SharedDocumentEditor 接共同输入与工具口，不重做渲染引擎。

此阶段只承诺接通现有已支持能力；不扩展所有 CSS、任意跨源页面或 Office。未完成此阶段时，可以报告 GLX 已统一，不能报告“整个工作台已统一”。

### 阶段 D：真正连续正文的 T1 与必要投影收敛

针对已识别的叙述组完成 PM contentDOM 或必要的专业投影，保存原有布局、身份、源映射与程序边界。与阶段 B 可以局部并行，但它具有独立的验收条件。

若阶段 B 已解决咖啡需要的实际编辑阻断，不必等待所有潜在组合都被统一投影后才恢复后续创作。若当前咖啡中的一段确实需要连续正文操作，则那一段的 T1 是恢复该部分创作的条件，不能用多个独立框冒充完成。

### 阶段 E：退役旧路径与最终复核

查找仍能独立决定相同目标的旧 handlers、局部选区和菜单入口，逐一退出；只保留没有写权的兼容投影。核对同一次操作没有双重提交、两个 History、两个输入接管者。

只围绕发生变化的路径执行必要回归与真实样本任务，复用前轮已有结果。不重复整个咖啡创作，不重做已经通过的自然尺寸、全局层和发布基础开发。

## 12. 验收：用这些任务决定是否真的完成

| 编号 | 真实任务/定向用例 | 通过条件 |

| A01 | 咖啡组内改标题、段落、图片，再选择整个图文组 | 各目标一步可达；范围清楚；无需隐藏修饰键 |
| A02 | 同一组件字段 A → 字段 B，连续打开属性、右键、AI | 所有入口始终指向各自精确字段，不沿用旧菜单 |
| A03 | 对没有独立删除能力的内部字段执行 Delete/Copy | 不自动删除或复制父组件；给出实际可用动作 |
| A04 | Flow/Slide/Spatial/Program 中对受支持同类字段操作 | 内容操作一致，布局差异明确；无后台第二套输入响应 |
| A05 | 中文组词期间点工具条、切目标、Esc、保存 | 无丢字、抢焦点、提前提交半个组词；失败保稿 |
| A06 | 修改文字导致 Flow 重排，提交 ACK 后接续点击另一项 | 仍进入初次指向的作者对象，不按旧坐标改选 |
| A07 | 当前 pending 编辑与 Undo/Redo、切视图、保存交叉 | 结果和分组可解释，沿同一正式 History；无静默丢稿 |
| A08 | 编辑态点击受管按钮文案/链接；再切运行态点击 | 编辑不执行业务；运行正常；包含 pointerdown 对照 |
| A09 | HTML 预览 → GJS 结构 → 源码 → 预览 | 能映射时维持同一目标；不能映射明确说明；源码不被整页重写静态化 |
| A10 | 真正连续正文组中的 Enter、跨段选择、粘贴、表格操作 | 文档语义成立，其他布局/程序字段不被错误合并 |
| A11 | 手工改字段，AI 修改另一已捕获目标，再手工继续 | AI 不随光标变范围，不抢当前输入；结果精确可定位 |
| A12 | 保存、冷开、再编辑与现有导出链 | 修改保留，身份/布局/资源/作者记录不丢；未编辑邻域不变 |
| A13 | 切全局层、Flow 章节、Spatial 镜头、Slide 状态 | 保留最新修复；不把场景状态重新扩展到 Flow/Spatial |
| A14 | 多选父子对象、跨能力组合、锁定/隐藏目标 | 父子不重复变换；不支持的共同命令清楚说明，不静默部分执行 |

产品效率目标是：普通文字一次点击即可开始输入；换图不必先进入父组；选择整体不要求逐层双击；进入源码/结构不丢当前定位。这些是建议验收目标，并非本次已测得的数据。

不要求一个原生文本 Range 横跨 iframe，不要求任意 Canvas 像素可编辑，不要求源码重载后恢复任意程序现场。不能用这些未承诺能力阻止已有可靠字段的常用操作上线。
