## 0. 归因方法

三组使用**同一模型**（请求 `deepseek-flash`，实际响应均为 `deepseek-v4-1-flash-260910`）、**同一参数**（`reasoning_effort:"max"`）、**同一提示词**（705 字符，`prepared/common-content-prompt.txt`）。三组结果差异因此只能来自环境侧（软件实现、Skill/指令、工具契约）。本报告将每个已证实的问题归入三层：

- **软件层**：宿主实现行为造成的问题——可通过改代码修复；
- **Skill 层**：指令/文档未把软件已存在的契约告知模型——可通过改文档修复；
- **模型层**：模型在充分信息下仍犯的错——不可控，只能登记并由验收侧兜底。

归因原则：模型在证据范围内做出合理推理、但因环境给出错误/缺失信号而绕远路的，主责记软件或 Skill；模型在充分信息下仍做错的，记模型。

## 2. 软件层问题深挖

### S1+S2：上下文经济性是最大的结构性问题（两台发动机：回执无界 + 全历史重发）

**MCP 首轮死亡的直接链条**：tool-56/58/61 三次 `project.apply` 各回显约 100 万字符的 `appliedChanges.changes` 全文 → 每条以约 25–33 万 token 的代价进入后续每一轮请求 → request-29.json 膨胀到 3,978,326 B（其中三条 tool 消息占 3,298,865 字符，`mcp/setup/request29-contribution.json`）→ 供应商 HTTP 400，`no automatic retry`，首轮终止。**逐请求 input 曲线**：r24 136,312 → r25 467,933 → r26 793,112 → r28 821,543——三条巨型回执各制造了一个永久性台阶。

**内置组同病不同症**：无单条巨回执，但 86 轮全历史重发累计 input 13,580,590 tok，中位单轮 88,257 tok，峰值 518,153 tok（r80，压缩后第一轮）。压缩（r79，fromMessage 244，facts 4,584 条）只压缩了消息历史，工程状态在 payload 中重复注入的问题未解决（r54 payload `serializedBytes` 达 2,976,795 B）。

**方向**：(1) `project.apply` 回执改"摘要 + 受影响对象句柄列表"，全文以已落盘路径引用；(2) 公共投影层对 text 回执设上限与截断标记（现有 `receipt-projection` 只处理了 image，`mcp/setup/receipt-projection.diff` 可证）；(3) 工程状态 delta 化注入。三项均对应已证实根因，不新增门禁。

### S3+S4：观察宿主是本轮最大的单一浪费源

**内置组**：38 次 `view.observe` 中 16 次为 `detail:"high"` 且集中在 P7（7 次）/P9（9 次）；13 个含 detail-high 观察的请求合计 input 2,076,057 tok。关键在于：**回执 `identity.revision` 字段其实携带了判定新鲜度所需的全部信息**（P7 的 9 帧横跨 rev23/28/30），但 `diagnostics:[]` 恒空，没有任何"此帧非当前修订版"的提示，模型只能靠肉眼比对内容 + 反复重试去经验归纳（A60–A79），最后发明"整页重做 P9 强制触发渲染"的绕行方案（A76–A78，额外消耗 2 个 revision）。

**MCP 组**：捕获宿主为静态渲染（不执行内联脚本）。模型先怀疑（r32）、再设计决定性探针（r35）、后确认（r40"the checkerboard probe rendered blank"），最终把全部互动页重写为无脚本 CSS 状态机（rev25–31）。而事实是脚本互动在运行时正常工作——内置组同源的"HTML 程序"对象明确"会编译进运行时"（内置 A21–A23）。模型把**截图能力边界**误当**平台能力边界**，这不是模型推理错误，而是软件没有声明边界。

**方向**：(1) `view.observe` 回执显式增加 `fresh/captureRevision vs currentRevision` 与原因枚举（缓存/编译中/失败），填充 `diagnostics`；(2) 工具描述或 server instructions 声明捕获能力："截图为静态渲染，不执行脚本；验证脚本互动用 X"——若产品要求观察可执行脚本，则需给捕获宿主加运行模式（产品决策点）；(3) `observation-failed` 应快速失败并返回替代验证路径，而不是让模型用 5+ 次重试归纳。

### S5+S6+S7：编辑语义、句柄与保存三层契约缺失（软件 + Skill 共同，软件侧先说）

**编辑语义试错**：内置 r7–20（input 820,497 tok）是完整的"API 考古"过程——`from` 导入只落资产不改页面投影（A13–A14）、`content` 直写页面 HTML 返回 unchanged（A15）、`insert` 才是加对象入口（A16）、CSP 禁 iframe 但"HTML 程序"对象可用（A20）。这些全是软件已实现的确定行为，却没有任何一处契约描述让模型直达答案。

**句柄治理**：r39 六连错 `invalid-target` 后，错误信息不给"句柄从哪来"，模型只能放弃对象级修改改走整页重做；`document.export` 两次 `target-conflict` 每次都要手动重开文件。失效句柄如果软件能在执行前自动校验、或在错误里直接附上新句柄，这 8+ 次轮次可全部消除。

**保存语义**：`lastCommittedRevision:32` vs `savedRevision:24` 的落差、516MB journal 与 171KB 磁盘文件的悬殊、QA 侧为找到 `project.save` 试错四次（`partial-save`→`partial-save-3` 的三种失败），都指向同一事实：**commit 与 save 的双层模型从未被写进模型可见的任何契约**。这不是模型的义务去猜，而是软件必须声明的。

### S8+S9：宿主稳定性（观察/预览子系统是共同故障点）

351 个 CDP targets 说明 iframe/预览实例无上限扩张；16 条 WebFrameMain disposal 错误集中在同一秒内（02:46:48.392–50.156）由 `ExecutionDesktopService.eventSink` 触发；两条 Playwright "Target crashed" 发生在 02:46:07/10（点击"关闭预览"与 page.evaluate）；MCP 侧 Main 直接 c000001d 崩溃，终止续轮。**共同模式：观察/截图/导出构建这条"验证旁路"的故障能波及持有正式数据的 Main 进程**。MCP 续轮崩溃时，唯一正式成果（rev32）只存在于 516MB journal 中——验证旁路崩溃威胁了正式数据的安全性。

**方向**：把观察/截图/导出构建进程与持有 DocumentSession/journal 的 Main 隔离（至少做到崩溃不损数据 + 自动恢复）；`nativeCrashRootCause` 在 REPORT 中标记 unresolved，本轮证据支持将"实例数上限 + 崩溃隔离"列为方向。

### S10：file.\* 与工程内容边界

`file.grep` 两次 ENOENT 打向工程路径（工程内容在数据库中），`file.search` 越权一次。模型在第 65 请求自己总结出"工程目录在软件数据库内，普通文件工具不适用"——这本应是工具描述或错误信息里的一句话。

## 5. 方向建议（按优先级，只针对软件层与 Skill 层）

### 软件层（收益/成本比排序）

1. **回执瘦身 + 投影上限**——最小改动、最大收益：直接消除 MCP HTTP 400 与每轮 25–33 万 tok 的固定台阶（S1）。

## 6. 结论

三路的差距不是模型能力差距，而是**环境契约的差距**：

- 裸 HTML 组没有契约问题，4.97 分钟交付，代价是无人兜底的内容错误（三处短路）；
- 内置组有最全的工具与 Skill，但契约靠 152 次调用中的大量试错发现，50.85 分钟、13.58M input，最终交付质量最好（唯一完成保存的正式工程）但代价最高；
- MCP 组契约缺口最大（回执无界、观察能力未声明、保存语义不可见、宿主崩溃），两轮均失败，成果只剩恢复稿。

**可修改的两层中**：软件层三个根因（观察契约缺失、回执无界、句柄/保存语义不可见）解释了本轮绝大部分可避免成本，且全部有逐字段证据；Skill 层的缺口是同一批事实没有写进文档，增补五段即可；模型层的真实错误集中在内容质量（电路短路、答案泄漏）与调用纪律（同型重试、不保存），前者只能靠验收侧检出兜底，后者可通过契约文档化部分缓解。
