# 果铃三路创作验证：收敛版汇总审计报告

**审计日期：2026-10-06｜性质：原始证据复核、当前代码检查、独立离线验证**

审计对象为桌面“审计报告”文件夹内的七份报告，以及它们引用的三路创作实验、保存产物、恢复资料和候选仓库。本报告不按报告数量投票；同一日志被重复引用，不构成多份独立证据。

## 一、收敛结论

**这轮实验不能判定创作链路已经通过完整交付验收，但也绝不是“没有完成有效创作、没有保存、全部写入失败”。** 内置路线已正式保存 revision 30 的九页工程，MCP 路线已保存 revision 24 的八页工程；内置还有成功导出的 revision 28 HTML。真正没有闭合的是：写入结果是否等于用户要求的内容、观察画面是否属于目标页、导入后的交互是否仍然成立，以及最终导出是否对应最终保存版本。[E1、E3、E5]

**最值得优先修的不是再增加提示词或再造一套 Harness，而是三条真实性契约：**

1. **写入真实性：** 工具返回成功或 usable，必须明确对应哪些实际内容变化，不能以资产入库或空操作代替页面内容完成。
2. **观察真实性：** 返回的图片必须属于所请求的页面及版本，不能用正确元数据包装错误画面。
3. **交互保真：** 具有共同 DOM、CSS 状态和表单归属的内容，不能为了细粒度可编辑而拆成彼此隔离、失去关联的 iframe。

这三项会让模型在“得到看似有效的证据”后继续作出错误决策，比单纯慢、贵或某次参数错误更影响可用性。与此同时，课件电路图存在独立的内容质量问题，不能转嫁给 Harness。[E1、E4、E7、E8]

**历史问题必须与当前状态分开。** 当前候选已合入回执投影、V10 恢复归属和 Player 按访问页挂载修复。回执投影的主要收益已用真实代码离线重放确认；这不等于当前整条链路已重新跑通，也不等于此前崩溃根因已经证明或消除。[E2、E6]

## 四、确认的问题及当前状态

### F01｜P0：空内容操作与“可用”结果不一致

**历史实证，当前代码仍存在相关缺口。** T23 对目标页面执行内容操作后返回 committed/usable，T24 读回为空；T26 直接提交内容又返回 unchanged/usable，但插入对象和 HTML 投影均为空。当前 `contentTargetIds` 在空容器下可能返回空集，内容规划因而无编辑；原始资产入库又可能与可见页面编辑分开提交。T31 则明确返回 not_committed/unusable，不能与前述“虚假可用”混淆。[E1、E7]

**修复边界：** 保留 `context/insert/content` 的区别，不把所有 content 自动变成 insert。返回值至少要区分“可见内容发生变化”“内容确实等价”“只有资产保存”“没有可作用目标”。空目标不得以笼统 usable 暗示创作已完成。

### F02｜P0：观察返回了错误目标页或空白画面

**历史图片实证；当前修复后的端到端效果待验证。** 内置实际发送 35 个图片部分，只有 13 个不同哈希。重复哈希本身并非错误证据，但核对目标与实际图片后，多个不同页面的请求确实收到同一张封面；另一组收到白底及导航按钮。T102/P7、T104/P9、T130/P3、T138/P2 等共享封面图片，不能解释成目标页面布局相同。[E4]

内置并非没有图片：主模型消息中确实附带 PNG。已有文档版本新鲜度检查，且曾抑制三次观察结果；真正缺少的是“请求目标与实际渲染画面一致”的保证。独立视觉角色为空不等于主模型没有收到图片；收到图片也不等于已证明提供方模型正确理解图片。[E1、E4、E7]

**修复边界：** 补足页面定位、就绪和版本归属验证；未得到可信画面应显式失败或降级说明。不要伪装成功，也不要一律关闭多页观察。

### F03｜P0：细粒度拆分破坏原生表单与 CSS 状态关联

**历史 DOM 与实际点击记录支持，当前 Slides 导入路径仍有相关风险；当前运行复测未做。** 原 HTML 使用 `#shown:checked ~ #labRoot`、radio 和 label 联动，是有共同 DOM 依赖的交互。保存的 DOM 证据中，原始整体结构与多个拆分片段并存；可见的揭示 label、复位按钮、隐藏 input 等被投影为独立对象/iframe。单个片段中的 `for="shown"` 无法控制另一个文档中的 checkbox。[E8]

历史点击记录中，一次真实 label 点击成功送达后，`shown` 仍为 false，答案区仍隐藏、预测区仍显示。该事实与拆分后的控件归属相互支持；不能仅因底层原始 HTML 仍在，就判断可见交互未被破坏。当前代码对 Flow 耦合 HTML 有整体保留分支，但没有证明 Slides 同类结构获得等效保护。[E7、E8]

**修复边界：** 以交互依赖为最小语义单元，而非每个 DOM 后代都拆。简单文本和独立图形仍可原生化；共享状态、表单归属、CSS 兄弟选择器或脚本闭包的组件先整体保留，再暴露安全的局部编辑能力。不是全部退回不可编辑大 HTML，也不是强迫作者取消脚本。

### F04｜P0（内容验收）：电路示意与计算模型不一致

**独立源码检查确认部分示意存在导线旁路或连接表达错误，不应作为正确电路直接教学。** 裸模型输出的相关 SVG 含横跨左右导体的额外连线；内置封面也存在连接表达不可靠的问题。与此同时，裸模型源代码中的串并联电流、电压公式是正确的：问题不能笼统写成“所有物理计算都错了”。[E9]

**责任区分：** 这是生成内容与教学验收问题，不能仅靠修复回执、提高模型额度或重做 Harness 自动解决。应替换问题图，并核对图、公式、预测、实验数据、解释是否对应同一个电路。对这份物理课件增加针对性校验即可，不建议为整个办公产品先建设通用电路静态验证平台。

### F05｜P1：模型回执膨胀的大头已修，失败分支仍残留

**实际代码离线验证通过。** 使用当前 `modelToolResult.ts` 原函数重放历史 33 次 `project.apply`，总序列化长度从 **8,441,670** 降至 **270,965 个 JavaScript UTF-16 字符**，减少 **96.7901%**，且正式回执输入未被修改。T76 从 1,058,039 降至 14,813 字符。[E2]

但 T31 的失败分支仍保留 68,719 字符，其中含原始 bytes 数据。原因是投影主要识别有合法正式 receipt 的结果，失败时不一定走同一精简路径。当前应补失败回执投影，而不是重做已解决的大头。[E2、E7]

**收益口径：** 96.8% 是这批工具结果的字符降幅，不是整次运行 tokens、价格、内存或耗时降幅。正式持久化回执、撤销和恢复信息应保留；精简面向模型的副本，不应删掉规范数据。

### F06｜P1：执行状态汇总未完整接入项目创作回执

**当前源码确认集成缺口。** `ExecutionEngine` 与 `executionOutcome` 中多处直接识别 `document-operation`、`file.save`，却没有等价处理 `project.apply` 的嵌套正式 receipt 和 `project.save`。这会使已提交变化、保存进度等事实在部分进度和结果汇总路径中缺失；不等于项目实际上不能保存。[E7]

应复用已有正式事实投影，将不同外壳的同类 commit/save 信息归一化，不新增另一套平行提交协议。也不能据此随意断言摘要内容错误：实读的 R79 摘要明确记载 revision 28、九页，并不支持把它说成“只记得 revision 24、八页”。[E1、E7]

### F07｜P1：可见对象 ID 与可操作句柄之间存在缺口

**真实 ID、错误参数类型与能力缺口同时存在。** 六次 `object.update` 使用的 UUID 都能在此前真实工具回执中找到，并非凭空编造；但实例 ID 不等于当前运行可用的操作句柄。六次调用属于 R39 的同一批，不是六次收到错误后仍自适应重试。[E1]

当前课程创作模式下，部分通用 context/inspect 获取句柄路径被关闭，而 frame 又不是任意可写投影。解决办法是让“列出对象—获得合法目标—修改支持字段”有一条闭合路径。仅增加“别乱传 UUID”的提示，或直接删除 object.update，都不能保证用户所需的局部编辑仍然可达。[E7]

### F08｜P1：存储与运行时规模问题，不能等同于模型回执问题

**膨胀事实确认，崩溃因果未确认。** 内置项目 JSON 解压约 4.10 MB、MCP 约 3.20 MB；部分 HTML 含大量计算样式，组件及 iframe 细分也会放大投影与运行时规模。MCP 恢复日志达到约 492 MiB。回执模型副本变小，不会自动消除这些持久化和运行时成本。[E5、E7、E8]

当前 `db5cdf1f` 已在 `ModelPlayer.ts`、`modelProjection.ts`、`publishedPlayer.ts` 接入按访问页投影和挂载，不能忽略该修复；也不能从中推出 Editor 已完成同等惰性化，或此前所有崩溃已解决。未合并 worktree 的名称和内容不是当前主候选的能力。[E6]

**修复边界：** 先测目标创建/销毁、重复挂载、DOM/iframe 数、内存和日志增长，再定位生命周期或数据重复问题。不要盲目删除所有计算样式、对所有操作强制销毁 WebContents，或把“351 个 target”直接写成“截图泄漏导致 UD2”。

### F09｜P1：崩溃、恢复和保存需要分层定责

MCP 存在原生主进程退出记录；内置存在 renderer/GPU 异常退出，但内置主进程在模型运行结束后仍存活，后来才按授权精确 PID 强制关闭。**不能把两条路线都描述成主进程自然崩溃，也不能写成内置在任务完成前一切正常。** Renderer 异常发生早于该次模型循环结束。[E10]

恢复日志是磁盘上的可恢复资料，不是“仅在内存”；但 recoverable 也不是 formally saved。`8ab30bc8` 修复了 V10 恢复归属，不能把小型验证成功外推为约 492 MiB 原始日志已完整恢复。应独立验收正式保存、异常恢复、恢复后继续编辑与再次保存。

### F10｜P1：最终保存、最终导出与模型口头完成不一致

内置最终工程保存 revision 30，成功 HTML 导出仅到 revision 28。旧句柄冲突体现了并发/版本保护在起作用，应改进句柄更新和错误提示，而不是绕过保护。最终一次已换新句柄仍构建超时，则是另一类构建问题。[E1、E5]

按原任务，“正式保存可编辑工程”已有成果；按额外双交付标准，最终版本 HTML 未完成。最终答复应陈述这两个事实，不夸大成全部成功，也不抹去已保存工程。

### F11｜P2：测试环境、工具命名空间与调用错误不能混成产品缺陷

MCP 测试脚本走公开 SDK 和真实 MCP 协议，但只将文本回传给模型，图片另存未回传。因此它可以用于该脚本下的创作观察，不足以代表支持图像反馈的完整外部 Agent。内置实际传图，两者视觉条件不同。[E0、E4]

工作区越界被拒、物理目录不存在、额外 offset 参数被拒等，有些是正确安全/参数校验。与此同时，项目虚拟路径与磁盘路径容易混淆、可用工具与文档能力不完全闭合，也是产品可改进的操作界面问题。应分别修调用、可发现性和能力缺口，而非放宽全部边界。[E1、E7]

### F12｜P2：Skill 有优化空间，但“读错 Skill”不是本轮根因

六份实际读取的 Skill/参考文档版本均为 `27d8ed521d574602`，未截断，与当前迁移候选文件匹配；实际使用 `project.apply`，不是部分报告引用的另一分支 `project.write`。规范已要求正式保存，也提醒不能把结构投影读回当像素验收。[E11]

值得补充的是运行环境明确的交互例子、虚拟/物理路径区别、状态耦合组件编辑方式、对观察失败的诚实表述。不能让 Skill 承诺产品尚未提供的接口，更不能把模型关于“截图不执行 JS”的猜测固化成产品规范。

## 六、最小修复顺序与验收方案

不建议直接重跑三套长程付费创作，更不建议据此再来一次全栈架构重构。先用确定性、短路径样例验证契约，避免把真实软件问题继续变成模型重试成本。
