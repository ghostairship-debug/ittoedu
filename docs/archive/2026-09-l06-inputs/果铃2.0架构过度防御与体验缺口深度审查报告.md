## 1. 执行摘要与核心定性

当前果铃 2.0 的底层设计在**“防恶意注入、防数据覆盖、防单写者冲突”**上建立了一套接近军工级的安全底座，主进程 DocumentSession、事务回执（ACK）以及无损撤销树的实现非常扎实。

然而，在面对**“长程连续交互、大模型认知容错、公网网络抖动、现代人机协作”**时，系统表现出了极度严重的**“受迫害妄想式过度防卫（Over-defensiveness）”**与**“协议形式主义”**。系统设计充斥着大量针对“模型可能发疯破坏数据”、“模型可能产生未知副作用重放”、“外部文件可能被篡改”的层层死锁。

**核心失衡点在于**：
> **系统将“防范 1% 的潜在极端异常”变成了“牺牲 99% 的常规人机体验”；将现代 Agent 成熟的“乐观执行 + 极速回滚”逆转为了“悲观面签阻断 + 动不动就熔断自毁”。**

## 2. 执行引擎与网络通信层：过度防御与早夭机制

### 2.1 网络层的“未查先判死刑”（频繁传输中断的直接真凶）
- **致命逻辑代码**：[`src/main/workbench/providers/OpenAIChatProvider.ts`](file:///D:/果铃工作台/src/main/workbench/providers/OpenAIChatProvider.ts#L208-L213)
  ```typescript
  attempted = true // <--- 致命的提前置位！
  refreshIdle()
  response = await (this.options.fetch ?? fetch)(prepared.endpoint, { ... })
  ```
  在底层 TCP 握手发起、甚至是 DNS 解析开始前，代码直接盲目将 `attempted` 标记为 `true`。
- **后果**：只要遇到公网毫秒级的抖动、TCP 连接重置（`ECONNRESET`）、DNS 解析超时、或代理网关抛出 502/504，远端大模型网关**根本连 1 个字节都没收到、绝对不可能扣费**，系统却一律硬性标记为 `outcome: 'unknown'`。
- **一触即溃的引擎熔断**：
  在 [`src/main/workbench/execution/ExecutionEngine.ts`](file:///D:/果铃工作台/src/main/workbench/execution/ExecutionEngine.ts#L1263-L1266) 中，只要收到 Provider 的 `response.failed`，引擎没有任何微观重试，直接抛出异常中断执行主循环 `drive()`。
  只要该 Run 之前有过任何一次成功的工具写入，Run 立即被定性为 `partial`（部分失败）；
  随后在 `finally` 阶段，系统执行 `gateway.stop(record.runId)`，**直接注销全部句柄与写权限，将长达 10 分钟的任务当场掐死**！

### 2.2 惩罚性单向锁：剥夺 Agent 自我纠错能力
- **终身黑名单（`active.unresolvedToolNames`）**：
  见 `ExecutionEngine.ts` L822-L839。只要某个工具在执行中出现一次未知异常，该工具名立即被加入永久黑名单。代码中没有任何逻辑会去清理该锁定！哪怕模型后续通过 `read` 查明了原因，下一次调用该工具依然被第 964 行直接拦截（`unresolved-prior-tool`）。
- **单次 429 处决整场任务**：
  见 `ExecutionEngine.ts` L112-L130。生图服务一旦偶发收到一次 HTTP 429（Rate Limit），引擎不仅拒绝等待退避，而且直接抛出 `image-rate-limited-for-run` 强制将整场任务截断为 `partial` 停机，连剩下的文本排版和代码修复都不允许完成。
- **空闲超时误杀思考模型**：
  `OpenAIChatProvider.ts` L306 规定：*“SSE comments and transport bytes without framed data do not extend it”*。
  120 秒的空闲超时硬性忽略 SSE 心跳保活行（`: ping`）。对于 DeepSeek-R1、o1 等长思考模型，思考超过 2 分钟直接被本地判定为 `timeout` 强杀。

### 2.3 繁琐被动的续接机制（Continuation）
当前系统无法在会话内部就地自愈，续接必须经历沉重的被动链条：
1. 外部环境捕获终态，重新传入 `retryOfRunId` 发起一个全新 Run；
2. 校验文档的字符 Range 偏移，稍有 1 字符变动直接抛错拒绝；
3. 旧 Run 的所有句柄被销毁，新 Run 重新签发全新句柄；
4. 强制强加 `observationsRequired` 门禁，模型必须把所有文档用 `read` 从头读一遍才能开始干活；
5. 把数十个历史工具回执序列化为一个巨型 JSON 塞入 System Prompt，造成 Token 爆炸。

## 3. 工具网关与安全层：四大“句柄地雷”与协议摩擦

### 3.1 句柄系统的四大地雷（Handle Landmines）
在 [`src/core/tools/DocumentToolGateway.ts`](file:///D:/果铃工作台/src/core/tools/DocumentToolGateway.ts) 中，为了防并发冲突，设计了极度脆弱的指纹机制：

1. **地雷一：自修改报废（Self-Mutation Invalidation）**
   - 模型在 Turn 1 修改了文字框 `t1`，网关成功应用后，`handle.expectedFootprint` 更新，但 `handle.footprint` 保持原值。
   - 模型在 Turn 2 想继续调样式时，网关检测到指纹变化，强制抛出 `target-conflict` 报错！
   - 模型被强迫在每次写入后必须多调一次 `read` 或 `inspect` 换取新句柄 `t2`。大模型无法理解“为什么我自己刚修改完的对象，ID 立即失效了”。
2. **地雷二：场景母版连坐爆炸（Container Footprint Collateral Damage）**
   - 见 [`src/core/tools/ToolTargets.ts`](file:///D:/果铃工作台/src/core/tools/ToolTargets.ts#L134-L169)。场景母版 `course-owner` 的指纹哈希包含了**该场景下所有子图层的全部几何与内容**！
   - 模型只要微调了场景里的一个普通文本框，该场景母版的指纹立即改变。下一轮模型想调用 `native.insert(t_owner)` 增加一个按钮时，母版直接抛出 `target-conflict`！
3. **地雷三：`handle.conflicted = true` 永久中毒，封死救砖通道**
   - 一旦句柄被判定冲突，`conflicted` 被置为 `true`。
   - 致命的是，在 `refreshReadHandle` 中，`conflicted` 句柄连 `read` 和 `inspect` 都不允许执行！句柄彻底脑死亡，模型连“看一眼最新状态来自我纠错”的后路都被斩断。
4. **地雷四：`view.observe` 零容忍版本自增**
   - 网关 L403 规定：`if (handle.revision !== snapshot.revision) throw ToolError('读取句柄不是当前文档版本')`。
   - 模型刚改完文档想看一眼渲染画面，却因为刚产生的版本自增直接被拒。

### 3.2 `tools.load` 协议仪式感与 Batch 缺陷
- **协议仪式感过重**：
  默认暴露的基础工具极其贫乏，连最基本的图形、文本框插入（`native.insert`）、样式修改（`object.update`）都不在默认列表里。模型必须先发一条 `tools.load({ families: ['content', 'layout'] })`，白白耗费一个往返 RTT 和几千 Token。
- **Batch 流水线功能残缺**：
  在 [`src/core/tools/ToolCatalog.ts`](file:///D:/果铃工作台/src/core/tools/ToolCatalog.ts#L83-L98) 中，`$result` 引用**居然只开放给了唯一一个操作：`selection.replace`**！
  模型无法在一个 Batch 里实现“新建一个文本框 -> 修改其背景为红色 -> 绑定点击事件”。模型被逼无奈只能分成多轮调用，进而立刻引爆“自修改报废”地雷。

### 3.3 权限拦截的“宁可错杀”
- 在默认的 `workspace` 模式下，[`AgentFileService.ts`](file:///D:/果铃工作台/src/main/workbench/execution/AgentFileService.ts#L34-L41) 只要遇到工作区外的文件，连 `file.open`、`file.list`、`file.search` 等**纯只读操作都直接硬抛异常**，连审批弹窗都不弹。通用 Agent 连参考桌面上的一份资料都被彻底封死。

## 4. 前端交互与状态脆弱性：撕裂人机心流

### 4.1 Iframe 预览的“洁癖性全刷”（白屏频闪与状态清零）
- 审查 [`src/renderer/documentFiles/html/HtmlPreviewPane.tsx`](file:///D:/果铃工作台/src/renderer/documentFiles/html/HtmlPreviewPane.tsx#L12-L30)：
  局部 DOM 增量补丁（`instance.patch`）的成立前提极为狭窄：必须有且仅有一个处于选中状态的元素、目标必须为文本且处于编辑态、改动必须严格在该节点的局部范围内。
- 一旦 AI 修改了多个段落、新增了标签或调整了样式，代码立即执行 `setStale(true)`，进而触发 `frame.current.src = lease.url`。
- **后果**：整个 Iframe 暴力重刷，页面内的 JS 运行状态、计数器、Phaser 物理引擎状态全部被抹除归零，伴随着屏幕严重的**白屏频闪抽搐**。

### 4.2 元素 AI 临时卡的“上下文瞬间抹杀”
- **绝对坐标漂移**：卡片在点击瞬间记录绝对屏幕像素，用户一滚屏幕，卡片直接脱节飘走；
- **字符绝对比对导致 `textLost`**：只要外部微调了一个标点或前文增删引起了偏移，卡片立即被标记为 `textLost` 彻底禁用；
- **关卡即物理删会话**：只要用户不小心点了空白处关掉卡片，主进程立刻**物理删除该会话**，先前的思考过程和对话记录彻底蒸发。

### 4.3 人为制造的确认障碍与“对暗号”
- **死板的 2–6 选项限制**：`ask_user` 强行限制必须给出 2 到 6 个选项，问单项确认或 7 个参数直接报 Zod 校验错误；
- **教条式阶段确认**：创作 Skill 默认硬性要求“策划完确认一次，框架完确认二次”；规则白纸黑字写着“必须出现‘根据材料自动创作’这几个字才能跳过确认，普通的‘直接做完’不算”，把自然的人机协作变成了死板的字符比对。

## 5. 距离顶尖通用 Agent 的四大核心设计鸿沟

| 维度 | 顶尖通用 Agent（Claude Code / Cursor / Codex） | 果铃当前现状（含 L06 规划） | 关键瓶颈与差距 |
| :--- | :--- | :--- | :--- |
| **1. 终端与命令行** | **Shell 是第一公民。** 具备实时 PTY 流、标准错误捕获与交互式输入，自由执行 git、npm、python、系统构建。 | **零终端。** 没有任何 Shell 工具，L06 规划也仅限于在沙箱里跑特定 Python 脚本。 | 无法利用成熟的开源命令行生态，任何文档转换（pandoc）、音视频剪辑（ffmpeg）都被封死。 |
| **2. 长期记忆与规则** | **工作区规则与记忆。** 依托 `CLAUDE.md` / `.cursorrules`，跨会话长期沉淀偏好，越用越聪明。 | **跨会话零记忆。** 每次新任务都是全新冷启动，L06 明确拒绝向量库与知识图谱，不记录用户偏好。 | 教师的排版习惯、年级学情、教学风格无法跨会话继承，每开一个新课件都要从头调教。 |
| **3. 多文件原子修改** | **全工程 Unified Diff。** 一次输出跨多文件 Patch，统一展示变更树，支持一键审查或回滚。 | **单文件单会话串行提交。** 依赖单一 DocumentWriter，改 5 个文件要串行打开 5 次。 | 无法高效进行跨组件、跨文件的全局重构，耗时长且中途断联易留下半成品脏工程。 |
| **4. 模型原生能力整合**| **原生协同。** 拥抱 OpenAI 原生 WebSearch、代码解释器、原生视觉直传。 | **强行网关抹平。** 强行抹平成统一的 Chat Completions，多模态看图要经主进程二次截图转码。 | 丧失了前沿大模型原生的高速联网检索与原生沙箱计算能力，中转延迟与故障率激增。 |

## 6. 重塑蓝图与演进实施路线（P0–P3）

```
               【重塑前：悲观阻断式】                                 【重塑后：乐观流式驱动】
用户输入 ──> 策划 ──> [弹窗确认①] ──> 框架 ──> [弹窗确认②]     用户输入 ──> 持续流式生成并就地渲染（双缓冲/Morph）
                 │                          │                                    │
           [ask_user 挂起]            [审批阻断]                       可视化 Diff + 嵌入式非阻塞建议
                 │                          │                                    │
           Iframe 暴力重载             元素卡失效自毁                    全量快照保障：随时一键优雅撤回
```

### P0（紧急：彻底根除网络中断早夭与句柄报废）
1. **修正 `attempted` 边界，引入网络瞬态静默重试**：
   - 将 `OpenAIChatProvider` 中的 `attempted = true` 严格后置到收到 `response.headers` 之后；
   - 对连接前错误（DNS 失败、ECONNREFUSED、ECONNRESET、连接超时）及 HTTP 502/503/504，在 Provider 内部实施**标准的 3 次指数退避重试（Backoff Retry）**，绝不上报中断；
   - 允许 SSE 注释行刷新空闲计时器，并将默认超时提升至 300 秒（长思考模型友好）。
2. **句柄系统自愈与解绑**：
   - 修改 `targetFootprint`：场景母版只哈希自身坐标与属性，彻底移除对全部子图层的连坐哈希；
   - 本任务自己修改产生的指纹变化，网关自动同步指纹并放行续写，不再抛出 `target-conflict`；
   - 移除 `refreshReadHandle` 对 `handle.conflicted` 的绝对拦截，保留观察救砖通道。

### P1（高优：消除工具协议仪式感与 Batch 流水线强化）
1. **智能预加载核心编辑工具**：
   - 打开课件工程时，默认直接挂载 `content`、`layout`、`media` 核心工具族，彻底省去每轮任务开始前那一次多余的 `tools.load` 往返；
   - 模型直接调用未显式加载但合法的工具时，网关自动在后台静默补齐加载并放行。
2. **全面放开 Batch 的 `$result` 引用**：
   - 扩展 `batchMutationCallSchema`，允许 `$result: { step: number }` 作为通用的 `target` 占位符；
   - 允许在同一个 Batch 中完成：`[0] native.insert -> [1] object.update (target: $result[0]) -> [2] interaction.compose (target: $result[0])`。
3. **解除 `unresolvedToolNames` 终身黑名单**：
   - 当模型后续成功调用 `read`、`inspect` 或 `file.list` 确认了状态后，自动解除对应工具的锁定，恢复 Agent 的自愈能力。

### P2（中优：前端保态渲染与人机交互润滑）
1. **Iframe 虚拟 DOM Morphing 与保态双缓冲**：
   - 废除粗暴的 `frame.src = url` 全量重载；
   - 引入虚拟 DOM 比对算法（DOM Morphing），只替换变动的节点，最大程度保留 JS 运行状态；必须全刷时采用双 Iframe 交叉淡入（Double Buffering），消灭白屏频闪。
2. **弹性元素 AI 卡**：
   - 采用模糊文本锚定算法（Fuzzy Range Matcher），不因文本偏移就粗暴报废 `textLost`；
   - 移除关闭卡片时物理删除会话的逻辑，将其作为从属对话分支沉淀在历史记录中。
3. **权限读写分离**：
   - 在 `workspace` 模式下放开外部文件的**只读权限**（允许打开与检索参考资料）；
   - 外部写操作统一向下透传至标准的询问卡片，严禁底层生硬 `throw Error`。

### P3（长期：通用 Agent 基础设施演进）
1. **分级受管终端（`terminal.run` / Shell）**：
   - 基于 OS 原生能力（Windows Job Objects）建立带超时与取消的受管子进程管道；
   - 白名单自动放行只读与构建命令（`git`, `python`, `npm`, `pandoc`），高危命令弹窗拦截。
2. **工作空间长期规则与记忆体系**：
   - 建立轻量级 `.guoling/rules.md` 规范与会话记忆蒸馏机制，让 Agent 跨任务继承用户的教学风格与排版习惯。
3. **全工程 Unified Diff 审查面板**：
   - 摆脱单文件串行打开修改的沉重枷锁，支持模型输出多文件原子变更并在 UI 统一审查。
