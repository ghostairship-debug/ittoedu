## 2 一个工具入口和一个搜索选择位置

沿用这条调用链：

```text
内置 AI 或外部 MCP
  → DocumentToolGateway 的 web.search
  → WebResearchService
  → 本次运行冻结的搜索路由
      → OpenAISearchProvider → 现有 Responses 传输 → OpenAI 内置 web_search
      → McpSearchProvider → 现有 MCP 客户端 → 预置托管搜索服务
      → SearxngSearchProvider → 已配置实例的 JSON 搜索接口
      → DeepSeekSearchProvider → 现有官方搜索接口
  → 统一来源结果 → web.open 或 image.search(source)
```

`SearchProviderPort` 与 `WebResearchService` 继续作为边界，只补一个小型路由和所需 OpenAI、MCP、SearXNG 适配。后端选择由宿主依据设置决定；模型只传检索词、结果数量和可用的分页句柄，不传凭据、服务地址或替用户改配置。三类能力不意味着所有服务共用一种供应商协议。

OpenAI 内置搜索通过 `OpenAISearchProvider` 内部的一次 Responses 请求执行，复用现有 OAuth/API 认证与流式解析，不另起 Agent、不交给 CLI，也不向搜索子请求提供文件、文档写入或委派工具。主会话仍只看到果铃的 `web.search`，不同时再暴露第二个原生搜索入口，避免两套路由、重复搜索和重复计费。

这一取舍会在主模型决定调用搜索后增加一次搜索模型请求，换来所有模型和外部 MCP 共用的确定入口。沿用已有 DeepSeek 搜索的调用形态，不借此改造主执行循环。搜索服务只接收检索词及必要的搜索选项，不复制整段聊天或课件内容。

## 3 OpenAI 内置搜索

### 请求与连接

OpenAI 官方 Responses 文档要求在 `tools` 中加入 `{ type: "web_search" }`。原生响应包含 `web_search_call`、来源与 URL 引用；`include: ["web_search_call.action.sources"]` 可取得所用来源列表。本方案以该正式工具为基础，不使用旧搜索专用模型替换用户模型。[官方搜索协议](https://developers.openai.com/api/docs/guides/tools-web-search)

实现要点：

- 在 `ModelRequest` 中增加由宿主构造的原生搜索选项，并同步 `prepare`、序列化与实际发送。普通调用没有此选项时保持现有行为；继续禁止用用户任意 `parameters.tools` 覆盖宿主工具。
- 原生 `web_search` 与普通 `function` 的序列化明确分开。搜索子请求按该通道支持的正式 `tool_choice` 明确要求搜索；不靠“请联网”提示词冒充搜索执行。
- 保留已有 `reasoning.encrypted_content`，合并所需来源 `include`；请求使用实时联网语义。OAuth 与 API 的参数差异在现有协议适配层处理。
- OAuth 使用原有 `chatgpt-responses` 连接与凭据刷新；API Key 使用原有 `openai-responses` 连接。凭据与对应端点保持绑定，不把 OAuth Token 发往 API Key 端点，也不把兼容中转凭据转交 OpenAI 官方。
- 自动模式默认复用当前已选的 OpenAI 连接、模型与受支持参数；可在搜索设置中指定另一条已有且获授权的 OpenAI 连接及模型。不会改主对话角色或偷偷换模型。
- 不因协议名是 `openai-responses` 就推定任意中转支持内置搜索。官方通道按已知协议尝试实际调用，明确不支持的结果按连接修订与模型记入现有能力事实；不增加每次搜索前的付费探测门。

### OAuth 与 API 的证据边界

官方文档证明 Responses API 的原生搜索协议；[Codex 官方说明](https://learn.chatgpt.com/docs/agent-approvals-security#traffic-outside-the-command-network-proxy)证明 Codex 有联网搜索模式。这两项不直接证明果铃当前 OAuth 通道已经接受全部 API 参数。

实施首先用现有 OAuth／`gpt-6.1-sol` 做一次短查询，核实请求声明、真实 `web_search_call` 和返回来源。若该通道明确不接受参数，只修正有协议依据的 OAuth 映射并对相关变化复验；若账号或服务端确实不支持，准确保留该限制，独立搜索路径继续完成，不能改用 API Key 或 DeepSeek 成功后把 OAuth 项勾完。新增 OpenAI API 付费账号不属于自动解法。

### 结果处理

从已保留的 `nativeResponses.output`／`nativeResponse` 解析完成的 `web_search_call`、来源及 `url_citation`。普通文本中出现 URL 不算实际搜索。查询完成但确无结果，与服务端未执行搜索分别处理。

来源标题不存在时可展示域名，缺摘要时留空，不为满足字段补造内容。OpenAI 生成的综合回答可单独作为 `summary` 并保留引用，不能把它写成各网页的原文摘要。工具结果与用户可见来源使用可点击链接；搜索记录保留实际连接、模型、请求 ID 与供应商报告的 usage，金额未披露就保持未知。

现有 `WebSearchResult` 的失败只有 `reason`，需要在成功和失败两条结果分支中保留精简的 `attempts`：实际后端、连接/模型、请求 ID、`outcome`、已报告 usage 与错误；成功结果另外标明最终后端。适配器消费实际收到的模型事件或服务结果，流中断也保留已收到的事实；服务不提供模型、usage 或请求 ID 时留空，不补造。`WebResearchService` 的异常归一化及 `modelToolResult` 不得丢弃这些字段；它们随现有工具回执保存，不另建账本。这样 OpenAI 请求结果未知、随后独立搜索成功时，两次尝试仍可准确解释。

## 4 独立搜索：直接接入 MCP，保留开源 SearXNG

### 无需另交 Key 的现成 MCP 路线

OpenCode 官方说明其网页搜索可直接调用 Exa 或 Parallel 的托管 MCP，无需 API Key。果铃可接入同类服务，不需要安装或运行 OpenCode，也不需要套一层 OpenCode Agent。[OpenCode 搜索说明](https://opencode.ai/docs/tools/#websearch)

本方案采用 Exa 的免 Key 托管入口 `https://mcp.exa.ai/mcp` 作为独立搜索的首个预置，适配实际 `web_search_exa` 工具；网页读取继续复用果铃已有 `web.open`。Exa 官方明确提供免账号、免 Key、有限额的访问。Parallel 的 `https://search.parallel.ai/mcp` 也提供免账号／Key 的限额访问，可作为有具体替换需要时的服务选择，不为列出替代就同时调用两家。[Exa 官方 MCP](https://exa.ai/docs/get-started/exa-mcp)、[Parallel 官方 Search MCP](https://docs.parallel.ai/integrations/mcp/search-mcp)

“客户端／MCP 实现开源”“无需额外 Key”和“搜索引擎本身开源”是不同属性。这里是第三方托管搜索服务；不把它写成完全开源引擎、无限免费或已通过果铃实网验证。SearXNG 仍是本方案明确保留的开源后端。限额、服务错误和实际结果如实反馈，不能自动改成收费账号或新付费路径。

源码已有 `McpClientService` 的 Streamable HTTP、工具发现和调用能力，但生产接线目前主要服务浏览器，尚未成为搜索后端。新增窄范围 `McpSearchProvider`，复用现有客户端、停止信号和回执，将具体服务的搜索参数及结果映射到 `SearchProviderPort`；不改写浏览器 `mcp.discover`／`mcp.invoke` 的含义，不新增通用 MCP 管理平台。外部客户端调用果铃的入站 MCP，与果铃调用搜索服务的出站 MCP 分开接线，共用的正式搜索入口仍是 `web.search`。

具体参数以服务实际工具 schema 为准，不据示例猜字段或分页。Main 已在启动时调用 [installSystemProxy](../../src/main/workbench/network/systemProxyDispatcher.ts)，通过全局 dispatcher 服务默认 fetch；当前 MCP SDK 默认使用该 fetch，优先复用，不另造代理 owner 或假定必须逐调用注入。实网发现具体传输缺口再修该路径。429 按限流及实际响应说明，不直接判定余额耗尽；设置显示所选服务及检索词会发送给该服务。正式分发时记录所用访问模式、限额与适用服务条款，出现具体限制再处理受影响范围，不以尚未核查推定禁止使用或新增全局审批门。

### SearXNG 的实际服务条件

新增 `SearxngSearchProvider` 对接已配置实例的 `/search` JSON 接口，直接取得检索结果，不需要额外模型请求。官方支持 GET 或表单 POST，核心参数为 `q`、`format=json`、`pageno`；实例必须启用 JSON，许多公共实例未启用时会返回 403。[SearXNG 官方接口](https://docs.searxng.org/dev/search_api.html)

SearXNG 真实验收需要一个可用且启用 JSON 的实例。优先使用产品方或用户已有实例；这只是该后端的运行条件，不能再把“用户提供 SearXNG 地址”作为独立搜索整体可用的前置。普通用户通过预置 MCP 即可尝试独立搜索；不要求其安装 Docker／Podman，也不默认给 Windows Portable 捆绑服务器。[SearXNG 官方部署](https://docs.searxng.org/admin/installation-docker.html)

若实施时仍没有可用实例，完成适配及受控检查，明确列出 SearXNG 实网未验和所缺条件，不能用 MCP 成功代签，也不静默取消该后端。新采购、管理员安装或新运营服务仍按既有授权边界处理；无需因此阻塞其他搜索路线或询问一个全局搜索前置决策。

### 结果、分页和端点

独立搜索只补查询、实际标题／URL／摘要、去重、数量及服务确有的续页能力。缺摘要时留空，不把综合回答伪装成网页原文。`limit` 裁取后的余项继续保留；续页句柄绑定原后端、服务／工具、查询与本次运行，先消费余项，再按真实分页能力取下一页。MCP 工具不支持分页时不伪造下一页请求。

自动路由只用于新搜索；已有句柄恢复原后端和结果上下文，不重新走首轮 OpenAI 选择。句柄失效时说明原因，不暗中重开一次付费搜索。部分上游失败时保留已有结果和简短诊断；全失败、正常零结果和分页结束分开处理，不宣称结果数等于全网覆盖。

服务端点来自产品预置或用户保存的设置，模型不能通过搜索参数改写。沿用现有系统代理、连接与安全存储；SearXNG 允许用户明确配置的本机／局域网实例，不将 `web.open` 的公网边界整体放宽。可选令牌不随跨域重定向转发。不额外引入爬虫、Python worker 或公共实例轮询。

## 5 默认选择与失败行为

搜索设置提供 `自动`、`OpenAI 内置搜索`、`DeepSeek 官方搜索`、`独立搜索`、`关闭`。独立搜索当前预置 Exa MCP，也允许选择已配置 SearXNG，界面显示具体服务。默认采用自动；以下为本方案收敛的实现规则，不增加一轮必需产品审批：

| 情形 | 选择 |
| --- | --- |
| 用户指定固定后端 | 只调用该后端；缺配置或失败就说明该后端的问题 |
| 自动模式且配置了搜索专用 OpenAI 连接 | 优先使用该显式选择，不更换主模型 |
| 自动模式没有专用选择，且本次内置任务冻结了可尝试原生搜索的 OpenAI 连接 | 复用本次连接与模型 |
| 没有上述 OpenAI 选择，或其明确不可用 | 使用当前选定的独立搜索，未另选时为免 Key Exa MCP；不因某条专用选择无效就换另一条付费 OpenAI 连接 |
| 只有 DeepSeek 可用 | 提示可选择 DeepSeek 固定模式；自动模式不扫描或自动启用 DeepSeek 连接 |
| 所有路径均不可用 | 说明实际服务错误或所选连接的缺失条件，保留直接读取 URL 的能力；不再统一要求 DeepSeek 或用户自建搜索服务 |

自动模式中，OpenAI 请求失败可以转一次当前选定的独立搜索，回执说明原失败与实际后端；不隐藏原调用可能已产生的用量。不遍历 Exa、Parallel、SearXNG 等全部服务，不重复同一个付费请求、不遍历付费账号，不在用户停止后继续。固定后端模式不暗中切换。搜索成功但结果为空时返回零结果，不因空结果自动扩大搜索或换后端。

DeepSeek 保留现有官方协议和凭据边界，通过固定模式使用，不作为自动模式的付费回退。配置过 DeepSeek 聊天连接不再等于为所有会话自动选择它作搜索后端。

## 6 设置与能力说明

在现有模型设置面板增加一个紧凑的“联网搜索”区域，保存默认模式、OpenAI 搜索选择、独立搜索服务选择、可选 SearXNG 地址及 DeepSeek 搜索选择。免 Key 预置不要求填写凭据；只有选择需要配置的服务时才显示相应字段。搜索服务不进入模型列表。界面显示实际服务、配置状态、错误与用户主动触发的测试结果，不做周期性探活或强制付费能力测试。

搜索设置由 `ExecutionSettingsStore` 管理，进入同一 profile 修订与保存冲突检查；旧配置缺少搜索字段时读取为自动模式。新增可选字段只补默认值，保留现有连接、凭据、模型角色与收藏。凭据不出现在 Renderer 快照、工具输出或工程文件中。

每次运行在 `beginRun` 冻结搜索配置、连接修订与可用后端，内置 AI 和外部 MCP 复用同一个选择函数，但分别冻结自己的运行快照。当前 `ToolRunGrant` 没有模型选择：为它补宿主构造的可选搜索选择上下文，内置入口由 `ExecutionEngine` 传入本次已冻结的 `input.selection`，不在搜索时读取前台会话或新的 profile 角色。该字段不接受模型参数或外部 MCP 工具输入覆盖。

外部 MCP 没有内置主会话模型时，自动模式只使用显式保存的 OpenAI 搜索选择或当前独立搜索预置；固定模式按保存的后端配置执行。不猜测外部客户端模型，也不借用正在打开的聊天连接。工具发现说明此默认规则。用户中途改设置从下次运行生效；停止仍通过现有 AbortSignal 取消搜索和回退。

工具说明继续使用 `web.search`，同时向模型提供本次实际后端与缺失配置的简要信息。区分“工具已注册”“已配置”“实际调用成功”，避免当前这种通用搜索说明背后只有 DeepSeek 的情况。`web.open` 保持独立可用，不因无搜索后端一起隐藏。更新工具说明后同步生成目录与实际打包消费者；只调整与搜索能力有关的 Skill 说明，不增加教学步骤或搜索次数要求。

## 9 所有提问卡固定提供其他想法

本节是用户已确认的产品决定，覆盖普通单选、多选、单项确认及纯文字提问，适用于主聊天区和对象 AI 卡等所有复用 `ask_user` 的入口。

### 统一交互

- 模型给出的选项显示在上方；单选点击即可提交，已有多选仍按原方式提交选择。
- 所有卡片下方固定显示一个标为“其他想法”的文字框及提交按钮。用户不满意现有选项时直接填写并提交，不必先选“其他”、点“修改”或切换模式。
- 文字框本身就是一个独立回答选项，由软件固定提供，不依赖模型声明，也不允许模型关闭。
- 选项提交只传所选内容；文字提交只传用户文字，不自动附带确认选项，也不把两种回答拼接提交。只做非空等既有有效性检查，不增加内容判断。
- 选项可以为零个、一个或多个。只有“确认继续”一个选项时，同样显示文字框；没有选项时就用这个文字框回答，不再另放一套输入框。

不再维护确认卡专属的受限交互。`responseKind` 如为现有记录保留，只用于文案或读取既有记录，不得决定用户能否自由输入；不增加新的确认类型、修改模式或教学阶段状态机。

### 已定位断点与修改边界

当前 [ExecutionQuestionCard.tsx](../../src/renderer/workbench/ExecutionQuestionCard.tsx) 的 `confirm` 分支只渲染确认按钮；[userQuestion.ts](../../src/shared/workbench/userQuestion.ts) 的 `answerProblem` 只接受 `choices:[0]` 且禁止 `other`，后端据此拒绝文字。[既有测试](../../tests/unit/g20QuestionCard.test.tsx)也明确断言确认卡只有一个按钮。三处需按上述统一规则同步修改，不能只补一个前端输入框。

同一文件的 `validQuestion` 还按旧 `responseKind` 限制选项数量，并同时供 `userQuestionInputSchema` 与 `userQuestionViewSchema` 使用；执行器的问题摄取、历史重建和事件视图仍消费这些 schema。本节同步调整输入与视图两端校验，使零／一／多选项及统一自由文本都可进入实际提问与历史显示；不能只放开 `answerProblem`。保留问题身份、选项有效性及既有记录读取，不另造提问协议或要求迁移历史记录。

同步 [executionEvents.ts](../../src/shared/workbench/executionEvents.ts) 的历史折叠校验及 Engine 回答校验；既有“选项＋补充”记录仍可读，新提交才按两条独立路径生成。缺省 `responseKind` 不改变零／一个选项的上述布局。[ExecutionTimeline](../../src/renderer/workbench/ExecutionTimeline.tsx) 对纯文字显示“你的回答”，不一律称“你的补充”；既有确认卡和多选合并提交的测试改为新行为，保留历史记录读取检查。

复用现有回答字段：点选提交 `choices`；文字提交 `{ choices: [], other: "用户输入" }`，返回模型时保持 `selected:[]` 与原文，不伪造“确认继续”。普通选项卡现有的选项加补充文字拼接逻辑也改为这两条独立提交路径。同步修改模型工具说明，明确每个问题都由软件提供“其他想法”，不要求模型额外生成该选项。保留当前稿读取、人工修改和同一任务继续机制。

### 最小验收

1. 让零选项、一个确认选项、普通单选与多选通过实际问题输入及视图 schema，并进入现有组件检查，均可看到且使用唯一的“其他想法”文字框；复用一条历史记录确认重建后仍能显示，主聊天区与对象 AI 卡共用该行为。
2. 通过现有回答链分别验证点选与文字提交。确认题中输入“请缩减到12页”能够被后端接受，模型回执只有文字，没有确认选择；普通选项卡也不拼接两种回答。
3. 在当前构建中实际操作一次策划确认卡的文字提交，确认同一任务收到修改意见并继续；不以组件截图或构建通过代替回答成功。其余类型复用聚焦检查，不重新跑整课创作。

## 10 创作中断的错误原因、恢复与明确提示

### 本次证据与限制

运行 `ec062451-a73b-44d2-9b6f-a79eae0188f4` 于北京时间 2026-10-12 18:03:47 进入 `partial`，最后请求收到 `chatgpt-provider-sse-error`。18:01:10 的前一次 `chatgpt-transport` 已自动重试，第二次尝试成功；18:03:37 的批量修改已有正式回执、修订为 35。结束记录保留 35 次正式文档修改回执，不将此证据代称为用户文件已保存、冷重开或整课完成。

## 14 独立局部 HTML 被错误要求匹配旧投影

### 本次证据与断点

续作运行 `957eb291-cb0c-4bac-8379-9810b393ae1c` 在 18:32:12 用 `project.apply` 向第 13 页旧 Web 内容的 `.content.html` 目标应用新局部互动 HTML，`intent:content` 返回未提交；18:35:35 按错误提示改成 `intent:redo`，仍因无法对应旧投影节点失败。18:36:43 改向页面插入该 HTML 才成功，之后另行定位并删除旧内容。这个绕行不是局部重做路径已经可用的证明。

旧对象存在子节点，因此生成了编辑投影。[componentFileContentSource](../../src/core/projectFiles/componentPlatform/coordinator.ts) 仅因目标文件带 `projection` 就将新的独立 HTML 标为 `scope:projection`，混淆了输入来源和目标范围。[localHtmlInputs / htmlForAssembly](../../src/main/workbench/contentApply/application/html.ts) 随后在普通内容修改和重做两条路径中都调用 `projectedHtmlElements`，要求新源文匹配旧节点标记或结构。错误建议“重做”，但重做仍撞同一映射要求。

本次可确认程序已经插入、初始嵌入画面可见；独立 HTML 预览中的点击通过，不等于工程内完整互动通过。`unsupported-dynamic-url-sink` 与插入重叠曾作为诊断返回，未整份拒绝程序；不能将它们直接写成此次两次失败的原因。

复审另确认了同一修复路径的关联保留缺口：[planContentApply](../../src/main/workbench/contentApply/application/plan.ts) 对实例 `redo` 生成 `instance.remove`，再为新对象分配身份；[删除处理](../../src/core/drivers/courseV10Operations.ts) 清理互动引用、场景状态覆盖／顺序、Spatial 定位／路径／关系及 Flow 段落锚点。组件 `attachments` 更在删除步骤立即清理，后续重新使用旧 ID 也不自动恢复。仅修正 HTML 来源映射，仍可能让新内容接入成功而外部控制失效。这是当前源码可确认的触发条件，不表示已证明本次第 13 页实际发生了全部关联丢失。

### 修复规则

- 明确区分目标范围与输入来源。现有投影读回后修改的输入保留投影映射；由 `from` 读取或直接 `content` 字面量传入的独立新程序，都不因目标带投影就自动被当作旧投影。优先复用已有 `ContentApplySource.scope`（含目标范围）与来源链，不另建内容登记层。
- `redo` 表示在用户已授权的选定目标内重做；独立局部程序可在该范围重新装配，不要求模型复制旧 `data-*` 标记、子节点身份或 DOM 形状。普通 `content` 修改中能无歧义应用的内容继续接入；确需结构重做时给出真实可工作的 `redo` 路径。
- 保留选定目标的外部位置、尺寸及范围外节点、用户布局；内部身份与资源由软件维护，必要的替换沿 canonical transaction 与 History 一次提交。不能借修复绕过最终 CAS、把局部重做扩大为整页覆盖，或全局关闭投影映射。
- 局部重做保留选定目标对外的稳定身份及可延续关联，包括范围外互动、场景状态、镜头／空间关系、段落锚点及组件附着关系。优先在原目标身份内替换实现或内部子树；确需更换身份时，由软件在同一正式事务内完成必要引用迁移。不能把普通删除清理当作重做语义，也不能仅在删除后补回原 ID，任由已清掉的关系丢失。
- 优先组合已有 data/style/implementation/definition 与子树操作完成替换；是否需要补充正式操作由实际语义决定，不预先禁止必要调整。装配返回多个根时，在原目标身份下完整安置这些根或形成同范围组合，不能只取首根、丢内容或侵占邻居。内部测量与外部 frame 保全可以同时成立；只有用户明确授权重新布局外框时才改变它，`redo` 本身不自动扩大几何授权。
- 不要求保留全部旧内部节点，也不机械复制与新实现不兼容的旧数据。指向旧内部节点、确实无法合理延续的范围外引用应明确诊断受影响关系，并沿现有授权边界处理；能保留的由软件处理，不要求模型复制旧 DOM 标记或维护引用表，不新增身份管理平台。
- 失败诊断指明真实目标和可修输入，保留原件；可保真运行的代码不静默降为静态图。源文件导入成功后以工程当前源码为后续编辑事实，避免外部旧副本覆盖人工修改。

### 最小验收

1. 用带旧子节点的局部 Web 目标和不带旧标记的新互动 HTML，在同一小工程中设置指向目标的范围外互动规则、场景状态覆盖及一个组件附着关系。确认 `redo` 在选定范围成功，目标身份或正式迁移结果正确，外部 frame、相邻人工节点及这些有效关联保留；撤销可还原旧内容与关联，恢复重做结果后仍正确。另用一个既有投影局部修改确认映射规则仍有效。
2. 在实际工程消费者中操作外部控制、状态及附着行为，并点击新程序主要动作、返回和清空，确认既定嵌入尺寸、导航和反馈可用；保存并重开这一个工程后复用关键动作检查。不拿独立 HTML 窗口通过替代嵌入验证，不重跑整课创作或付费模型。

## 15 创作前的软件能力披露不足

### 已确认的软件缺口

当前 [ToolCatalog](../../src/core/tools/ToolCatalog.ts) 对未展开能力主要给“页面、表面、状态与位置结构”“交互规则、输入题和答案”等分类名称。[ExecutionEngine](../../src/main/workbench/execution/ExecutionEngine.ts) 让模型在真正缺少能力时才展开；结果是模型可以用已经暴露的静态排版工具完成一种设计，却在设计形成之前不知道同场景状态演变、空间地图与镜头、全局层或现成互动机制可以改变设计本身。

本次模型后期实际加载过 interaction/navigation，仍不足以说明早期设计已经充分获知能力。没有动画、未选 Spatial、使用矩形背景和默认线性翻页，不能分别推导出这些基础设施损坏；表达选择和方法调整见创作评审稿第 3—7 节。

### 修复边界

- 在现有工具发现／能力族说明中提供面向表达结果的能力概览，由 ToolCatalog 一侧同源维护表达文案，按 Gateway 的冻结权限、目标范围、配置及实际支持裁剪。`ToolRegistration` 的 family 不能单独推导状态、Spatial、动画等细分能力；维护解释文案不等于再造一份独立的可用工具清单，工具可用性仍只取实际目录事实。
- 概览说明“能做出什么、适合怎样的表达、如何取得进一步说明”，覆盖实际可用的场景状态、空间探索、图层背景、导航、动画、互动组件与局部程序等。用一两个简短表达例子澄清差异，不能只是列工具名；不强迫模型逐项使用。
- 具体 schema、Runtime API 与组件源码继续按需要加载。篇幅以设计所需信息充分为准，不预设只能压成几句话，也不因上下文窗口大就把所有源码与参考文档前置。一千至几千字可作为文案设计范围，不设强制字数；创作评审稿第 7 节及附录 A 提供分层和表达草稿，最终仍按本轮真实能力筛选，不另在 Skill 维护可用工具目录。
- 通用系统提示与软件能力说明保持通用演示定位；教学方法只进入相应 Skill。空间结构、页、场景是实现载体，不将“先排一套幻灯片”设为创作前提。
- 明确基础能力已存在、当前权限允许、外部服务已配置与实际执行成功之间的区别。软件负责身份、资源、装配、事务及保存；复杂局部程序的内容与逻辑仍可由模型编写，不能承诺所有自然语言创意都由软件自动实现。

当前 [project 工具注册](../../src/core/tools/ProjectFileTools.ts) 已是直接曝光并按实际权限支持，不以读取 Skill 为开启前提；Gateway 的 `courseAuthoring` 标记不能据此解释为 project.* 的准入门。首轮概览送达接到实际发现链，保持已有工具可达，不为解决一个不存在的 Skill 前置门改写权限或开启顺序。

### 最小验收

检查同一实际工具目录在具有创作能力和只有局部编辑权限的两种冻结范围下输出：前者在首轮设计前能看到上述表达能力，后者不宣称越权能力；选定一种后可沿原工具加载链取得并调用对应工具。复用一段短创作样例检查说明是否被实际送达；是否产生优秀作品属于后续真实创作效果，不以说明存在或工具加载成功代签。

## 16 创作尚未完成却主动结束并显示“已完成”

### 本次事实

同一续作运行在 18:43:38 进入 `completed`，最后模型请求 `finishReason:stop`，无 failure、用户停止或任务调整；18:24:50 的“确认框架，进入精修”已经收到回答，没有待答问题。最终正文明确写着“其余4个关卡及大部分页面的视觉精修尚未完成”“GLX尚未保存”，最后工作笔记也列出逐页精修、另外四个关卡、嵌入操作验证、导航、资料核实和保存等剩余事项。

因此，这次不是断连或应用崩溃，也不是模型在正文里谎称成品已齐备。准确问题是：模型在已获准继续的创作中主动以阶段成果收尾，软件又将本轮结束呈现为任务已完成。当前目标笔记的 `goal` 仅为本次输入“继续”，也不能单独代表此前已确认的完整目标。

现有续作事实已经包含 `originalGoal` 和 `userAdjustments`；缺口是本轮笔记承接及结束消费不足，不是整条续作链完全丢失原目标。本轮输入不同于旧指令时，不能只因笔记初始 remaining 为空就推定旧目标已完成。

[ExecutionEngine](../../src/main/workbench/execution/ExecutionEngine.ts) 在模型 `stop` 且无工具调用时进入收口；[executionExitDecision](../../src/main/workbench/execution/executionOutcome.ts) 主要检查已发起操作、未知作业、成果与指定保存/交付回执，没有缺口即返回 `completed`，随后主助手和 Timeline 映射成“已完成”。这套结算证明已发起操作的结果，并不证明用户要求已经全部完成。

### 修复规则

- 通用执行指令明确：阶段成果可作为进度报告，已授权且可继续的剩余工作应按第 18 节推进模式处理；自动模式继续，逐步模式可以在可审阅的关键节点提问。用户要求只做某阶段、主动停止、真实阻断或必须等待用户回答时才在对应边界停下。需要用户回答走现有提问卡，不用普通最终答复代替等待，也不把任务结束当作新的默认确认点。
- 续作的结束判断同时保留原请求、已接受的调整/确认和当前回执；“继续”只是续作指令，不能替换完整目标。复用现有 continuation、消息与工作笔记，不另建第二个任务计划 owner。
- 在现有退出处理内处理本次这样的明确矛盾：最近工作笔记仍列出本次授权目标内的可执行剩余事项、没有待答问题或已知阻断时，让当前模型对照原目标和当前事实继续或说明为何可以结束。一次无进展收尾可沿既有恢复逻辑提醒；反复原地结束就诚实收为部分完成并说明缺口，不能无界自动循环、反复收费或重放已提交操作。
- 工作笔记只作为发现矛盾和继续工作的线索，不升为完成证据或硬门。旧待办可以已解决，也可能是用户未要求的扩展；不要求所有任务创建笔记，不要求机械清空列表，不做全文关键词猜测，更不增加每次最终回答都必须经过的独立审查模型或固定教学阶段状态机。
- 区分“本轮尚未形成有效新笔记”和“模型已明确更新为空”：前者可参考续作链最近笔记，后者不能机械回填旧 remaining 复活已完成任务。清空笔记本身也不证明完成，仍结合原目标、用户调整及正式回执；模型说明旧项已完成、不属授权范围或已被用户取消时有正常结束出口。无进展提醒沿实际工具／文档成果判断，改写或清空笔记不算进展；剩余文字可辅助定位矛盾，不能仅因措辞变化重置提醒次数。
- 界面将“本轮运行已结束”和“用户目标已完成”分开表达。仅由传输 `stop` 和操作结算得到的终态显示“本轮已结束”；已知剩余目标或阻断显示“部分完成”并保留剩余工作及继续入口。模型的最终正文保持原文，不能由软件擅自改写成完成声明。普通讨论的自然结束保持自然，不制造待办。
- 未保存不一概判作失败：纯编辑可以只在恢复稿；明确要求保存或完成文件交付时才按真实保存义务处理。当前作品未保存应准确可见，不能因存在修改回执宣称 GLX 文件已落盘。已结束任务不因本次方案更新自动恢复执行。

### 最小验收

1. 复用本次记录回放，确认“本轮已结束／部分完成”与真实剩余工作可见，主助手及局部 AI 卡不再将传输结束直接说成任务完成；不重发原工具。
2. 用受控模型序列模拟：明确未完成却先收尾，收到提醒后执行剩余操作再给结果；验证已提交动作不重放。另覆盖重复无进展、用户仅要求阶段成果、普通讨论结束和已过期笔记，避免引入强制继续或强制清空待办。
3. 与后续一次短真实创作合并观察：用户确认进入制作后完成已授权结果或明确报告真实阻断；不在仍能继续时仅交阶段说明。真实调用沿既有账号/费用授权，不为不同状态重复整套付费创作。

## 17 写入后分页回读沿用旧快照却不披露版本

### 本次证据与定位

续作中的第 23 页并未证实存在 Markdown/HTML 正式内容不同步。18:37:55，模型从 `.body.md` 的开头读取 6000 字符，回执总长 6580，建立分页快照；18:38:54 的修改已提交 revision 50。随后两次读取均传 `offset:2800`，继续取写入前的同一分页快照，因此仍见 6580 字符旧内容。18:41:22 从 `.body.html` 开头读取当前投影，能够看到新增史料段落。两种表示来自同一个正式 Flow 内容源。

[coordinator](../../src/core/projectFiles/componentPlatform/coordinator.ts) 在确认写入、推进普通观察时保留原 `pagination`；非零 offset 读取优先使用这一旧快照。当前回执只有内容、offset、total 和 nextOffset，没有读取快照版本、当前版本或过时提示。换用同文档的另一个句柄也不刷新该分页快照。这使模型误以为“写入未生效／两种投影不一致”，造成重复调查，并可能诱发无谓重写。

### 修复规则与最小验收

- 保留一次连续分页读取的内容一致性，不在中途暗换正文导致漏读或重复。回执明确本次读取的文档身份与 revision；已不是当前版本时同时标明当前 revision 和“正在续读旧快照，从 offset 0 重新读取可刷新”。复用 project.list 已有的 `revision` 命名及同源结果结构，不为此另造版本协议。
- 工具说明明确：非零 offset 是续读该次快照，不等于查看最新内容；验证刚才修改是否生效时从头取得当前表示。不要求额外登记，不拒绝有价值的旧快照读取，不把内容差异自动解释为保存失败或要求重新写入。
- 用一个聚焦场景覆盖“读取首段→修改同页→续读旧段→从头刷新”：旧段内容连续且版本提示准确；刷新后得到新内容，HTML 与 Markdown 在同一当前版本包含相同正式新增语义。无需逐字节一致、整课运行或付费模型调用。

## 18 恢复自动推进与逐步确认的明确选择

### 当前缺口与已确认决定

用户记忆准确：旧 `LessonAuthoringPanel` 曾提供“手动模式”“自动模式（按材料）”，手动说明为逐阶段生成、教师确认当前文件后再进入下一阶段。2026-09-25 的 `25b12b4b2` 提交随旧课例链路删除该面板；当前 [ExecutionStart](../../src/shared/workbench/execution.ts) 没有推进方式字段，[主输入区](../../src/renderer/workbench/ExecutionAssistant.tsx) 未提供等价选择。当前构建产物同样未找到旧入口。此处为源码与产物静态证据，未冒称已进行 UI 操作。

Skill 与 `ask_user` 指导仍承认“用户明确自动推进时免去阶段确认”，因此现在依赖自然语言和上下文猜测，缺少可见且能经续作保留的偏好。四档权限控制读写与授权范围，提交的 queue/adjust 控制消息处理，都不承担推进方式。

用户明确要求保留两种模式：**自动推进**持续完成约定目标；**逐步确认**允许在关键产物节点问用户继续或修改。这里恢复的是通用任务的推进偏好，不恢复旧教学面板或固定课例状态机。

### 实施规则

- 输入区提供清楚的两项选择，任务运行时仍能看见当前选择。首次开始创作、尚无已选偏好且用户也未在自然语言中明确模式时，通过现有选项卡选择“自动推进／逐步确认”；选择后会话记住，不每轮重问，不以默认高亮代替用户选择。已有选择或明确指令直接沿用，随时可切换。偏好经现有提交、运行记录、续作及调整链统一传递，不能只显示按钮或藏在 Skill 文案中，也不在多个层各存一份独立模式。无需再由产品 Owner 决定一个全局首次默认模式。
- 自动推进：阶段成果作为进度更新，继续完成当前已授权目标，不在策划、框架或每页制作后默认等待。缺少不可替代的输入、超出现有授权、用户要求停下或真实无法继续时仍准确提问／报告；自动不等于扩大权限或反复无效重试。
- 逐步确认：在方向、关键体验原型等足以影响后续工作的节点，先给可审阅的当前产物，再通过现有 `ask_user` 让用户继续或提出修改。沿第 9 节固定提供“其他想法”；回答后继续同一任务并保留人工修改。不按页、工具调用或机械步骤增加审批，不要求每件作品经过同一组阶段。
- 普通状态更新不结束任务，等待确认也不显示“已完成”。用户只要求阶段成果时，可以在对应范围正常结束；模式控制推进习惯，不把原本只读讨论扩成创作。
- 用户中途用自然语言明确改变推进要求时，经现有任务调整链采用最新意思，并使界面选择同步；不让旧按钮状态覆盖用户当前指令。不重放已有操作、不清空当前作品。
- Skill 消费宿主传入的模式，删除与其冲突的固定等待要求；具体创作方法及逐文件拟修改内容见创作评审稿第 3、9 节。本节不决定必须采用哪些场景、组件或视觉风格。实际 Skill 与相关协议留待复审后的统一修改，本轮不提前应用。

模式作为会话级偏好由现有会话持久化 owner 保存，输入区选择器和提问回答使用同一更新入口；运行开始冻结当时副本。首次创作意图由模型根据用户请求识别，缺偏好时沿现有 `ask_user` 发模式卡，携带窄用途标识和稳定模式值；宿主在用户实际选择后写回会话偏好并续作。此用途字段不新增确认题类型，不限制第 9 节的自由文字回答。用户只输入其他想法且没有明确选择模式时，保留原话交模型处理，不靠关键词猜测或默认高亮替用户选择。

明确自然语言已经指定或修改模式时不重复弹卡，识别结果沿同一宿主更新入口写回，并作为有序调整供本轮后续提问／收尾及下次运行消费。原始冻结输入不被追写；现有文字 steering 可以承载后续调整，材料、权限和目标冻结限制继续有效。同步 [executionDesktop.ts](../../src/shared/workbench/executionDesktop.ts) 的发送结构、提交摘要、显式继续比对、元素卡发送、运行记录及 [userQuestion.ts](../../src/shared/workbench/userQuestion.ts) 的自动模式说明，使它们读取一致的初始模式和已接受调整。具体接线属于实施细化，不另列 Owner 二选一，也不维护一份与宿主事实脱节的 Skill 模式。

### 最小验收

同一受控短任务首次无偏好时出现模式选项卡，选择后自动模式跨过普通阶段产物继续到约定结果，逐步模式在一个关键节点展示当前稿并提问；回答后继续且意见生效。复用这两段记录验证续作不重问且保留选择、明确自然语言模式不重复弹卡、用户调整更新选择，以及等待不报完成。实际界面确认选择、提问和文字回答可用；无需两遍完整付费创作或权限全矩阵。

## 19 组件资源摄取与网页导出范围过大

### 已确认的问题

用户关注的是未采用的组件内容随网页一起交付造成体积膨胀，而不是组件被复制到多少个宿主页面。当前源码显示三个相关位置：

1. [库提炼](../../src/core/components/library/extract.ts) 对源码实现将整个 `project.assets` 纳入 `resourceBindings`；[重新绑定](../../src/core/components/library/rebindSource.ts) 又把条目全部 assetIds 提供给每个源码实现。这样提炼一个很小的源码组件，也可能带走原作品内与它无关的大图或视频。当前做法有保全计算式资源名的目的，修复不能忽略该语义。
2. [插入器](../../src/core/components/library/insert.ts) 装配条目的全部实例与 rootIds；`asset.use` 没有包内子集参数。当前条目本身是对象树，没有正式宿主多页字段。程序内部自带的多页仍随完整程序插入；可拆分对象没有在插入入口体现部分选用。
3. [Published V3 构建](../../src/core/publish/componentPlatform/buildPublishedCourseV3.ts) 对定义已有按实例过滤，但对 `project.assets` 无条件全表循环，逐一产生内嵌数据或导出资源 URL。HTML 序列化完整 payload，ZIP 同样接收这些资源；因此完全没有被交付内容引用的残留资源也会进入网页制品。资源延迟解码／加载不能减少单 HTML 已内嵌的下载体积。

这是源码可以确认的资源收集范围问题，不据此声称具体缩减比例。源码目录与资源也需分开：常规源码按入口 bundle，不直接把 owner 目录完整写进网页；但 Published 当前仍保留原实现字段并追加 compiled，Web 数据也追加 moduleGraph 而保留原 data，不能把“编译入口按需”当成作者源码和未用模块文本已经全部裁剪。现有导出还复用同一个 `player.iife.js`，固定运行库开销与单个条目内容膨胀分别评估，不混称同一个原因。

用户随后提供的[天下拼图性能报告](../../output/tianxia-runtime-20261012/PERFORMANCE_RESULT.md)已有原作品静态解析与实际浏览器采样：17.39 MB 主要由字体 CSS 6.12 MB、完整 Player 6.09 MB 和课程数据 5.18 MB 构成；完整访问 24 页后三次普通回访约 5.27—6.14 秒，当页 iframe 为 0。其[CPU 归因](../../output/tianxia-runtime-20261012/PROFILE_ANALYSIS.md)把主导成本定位到 resize 通知、全实例可见性与反复重建全课目录，不能用“资源体积过大”解释全部卡顿。本会话复用此证据，不重复测量，不将不同页的单轮样本写成固定提速／退化倍率。

因此本节的资源范围修复不能代替既有[发布编译 H1—H3](../development-plan/20261010-workbench-consolidated/EXECUTION_PLAN.md#html-publish-authoring)，也不能等到全量重构才处理已证实的重复计算。后续先沿现导航／视图 owner 消除主导重复工作，再按原 H1/H2 完成发布载体；样式减负按 H3、实际依赖范围按本节衔接。当前仅修订方案，没有启动这些产品改动。

### 修复方向与边界

- 沿当前提炼、插入、编译与发布路径维护实际依赖范围，复用已有 `componentAssetIds`、专业内容资源字段、源码模块／资源绑定及解析结果；[courseObjectEdits.ts](../../src/core/course/courseObjectEdits.ts) 的剪贴板复制资源收集同步使用这些规则，不遗漏独立消费者。不建立第二资产库，不让模型手写资源编号或新的逐页登记清单。
- 可拆分库条目按明确选中的对象／子树连同所需定义、素材、行为依赖装配，复用已有对象路径和提炼规则。完整条目仍可完整插入；没有明确选择时，不把未点击或当前不可见内容自行删掉。单个程序内部的页面若需部分采用，应沿其可编辑配置或模块结构缩减，不能仅凭页面名称或一次预览轨迹猜测并裁剪任意 JavaScript。
- 修正“源码组件自动绑定整个工程资源集合”的过宽默认。优先保存并复用该实现已确定的资源绑定与模块依赖；摄取时由软件解析可确定的引用。计算式引用确实需要一组资源时，保留这组范围；无法确定时只对该程序的已知资源作用范围作保全和诊断，不能在后续插入中无故吸入目标工程其余资源，也不能为了减小体积删除可能实际使用的输入。
- 发布只收集此次交付内容及其依赖：专业节点、正式状态覆盖、背景、全局对象、主题／字体／音视频、组件源码与模块资源等都需计入。复用共享引用提取，不只扫描当前可见画面或基础状态。明确无引用的工程残留资源不进入 HTML/ZIP；作者工程保留其原资源与恢复能力，不在导出时顺便删除用户数据。
- “未使用”指没有被此次交付引用，或作者明确排除的内容。尚未进入的分支、暂时隐藏的状态、下一关需要的图片仍然属于有效交付。动态名称或用户输入可能访问的资源不能靠搜索字符串不存在就判定无用。当前 `resources.url(name)` 在绑定未命中时会把传入值作为资源 ID 查询工程资源，因此“未出现在 resourceBindings”也不构成未使用证明；无法缩小这一实际访问范围的程序需如实保全，不能静默收窄后破坏内容。
- API 能访问工程资源不等于每个具体程序都依赖全部资源；按实际引用及是否可证明闭合处理，不仅因“含源码”就一律放弃裁剪，也不强制所有组件新增作用域声明。本轮保留现 API 访问语义，不以裁剪为由拒绝未声明但原本合法的资源访问；仅无法确定闭包的具体程序保留其实际可能访问范围并报告限制，无需新增资源合同取舍审批。
- 对常规源码沿实际入口及模块依赖编译，复用现有 bundler 能力。共享 Player 底座的固定开销与单个组件携带的内容分别记录；本节先解决实际无引用内容，不把体积目标扩大为整套运行库重写或任意程序语义分析。

### 最小验收

1. 用含一个所选组件、一个无关大资源、一个非首屏分支资源的小工程，检查库提炼／插入后的引用与资源清单：无关资源不被吸入，有效分支及组件依赖保留；明确部分选用时不装配其他独立子树。
2. 从该工程导出一次 HTML/ZIP，解析交付资源清单确认可证明无引用项未打包，并实际进入非首屏分支确认图片与互动正常。一个计算式资源名案例验证保留正确范围；无法闭合的实际动态访问如实保全，不把它包装成成功裁剪。不能用仅检查首屏或静态字符串不存在代替依赖判断。
3. 记录资源构成和实际文件体积变化，用来解释去掉了什么；不设无依据的固定压缩比例，不用 Hash 作为正确性门，也不重复全课付费创作。若单程序确实无法安全拆分，明确其保留范围，不将该项冒称完全裁剪。

## 22 将跨轮历史纳入模型窗口预算

### 断点与结果

原 NI-05 要求本轮和跨轮上下文共同受预算约束。当前 [ConversationHistoryIndex.ts](../../src/main/workbench/execution/ConversationHistoryIndex.ts)全量汇入历次用户原文和逐条截取的助手内容，经 [ExecutionDesktopService.ts](../../src/main/workbench/execution/ExecutionDesktopService.ts)、[PayloadCompiler.ts](../../src/core/execution/PayloadCompiler.ts)进入初始消息。[ExecutionEngine.ts](../../src/main/workbench/execution/ExecutionEngine.ts)只压缩初始段之后的内容，超大的初始段会直接失败；显式附件降载不能解决聊天历史累积。

修复后，历史累积不能让一个本身很短的“继续”因旧内容不可压缩而无法发起；当前真正超大、不能无损放入的新增输入仍按事实说明。此断点是静态可达条件，不倒推为第 10 节那次 SSE 失败的既定原因。

### 修改边界

- 将旧轮次、当前用户指令、工具／文档事实区分后，送入现有最终 payload 预算 owner；较早轮次可摘要和归档，不能把“初始消息”整体永久豁免。预算按最终实际发出的请求计算，不能只看消息条数或单条长度。
- 复用现有摘要、历史索引和 context.read；保留当前原话、近期必要交流、有效决定及其原文定位，不能用截断最后几千字或另一份手工记忆取代。旧摘要不是新授权，正式文档事实继续读当前版本。
- 在实际窗口压力下压缩一次可复用的历史范围；同一有效摘要不因每次继续而重复生成。不新建会话系统，不让模型额外维护历史 ID 或每轮固定写总结。
- 摘要沿现有 ExecutionRunStore／`compacted` 的持久化 owner 保存，记录所覆盖的历史来源范围及复用依据，再由 ConversationHistoryIndex 输出。该文件现有 `contentSummary` 只是读取 `run.compacted.summary` 的投影，不能把它当成存储位置；旧单轮摘要也不能未核覆盖范围就代签跨轮内容。无需第二摘要库，原记录和可回读定位保持不变。
- 同步桌面初始输入与执行器续作的边界定义，避免同段历史重复注入；原工具未知副作用、待结回执和停止语义继续沿原 owner。
- 压缩的是模型实际接收的工作视图，原始运行记录及 runId＋原消息序号保持稳定，供 context.read 和回执追溯使用。PayloadCompiler.finalize 的用户／附件清单必须对应压缩后的实际发送位置；不能只缩短数组而留下旧 messageIndex，也不能重排原记录以凑位置。保留原文、附件表示完整性及冻结历史来源范围检查，不靠关闭检查或扩大历史读取权限通过。

### 最低验收

构造一段累计超预算但新输入很短的受控多轮历史，带一份当前附件和一条将被压缩的历史来源，经真实 Desktop→Compiler→Engine 链形成可发送请求；证明最终清单定位和原文／附件校验正确，早期有效约束仍可用，context.read 能按稳定来源回读原文。使用受控模型返回即可证明预算接线，不重复付费整课创作。正常短历史的现有检查未受影响则复用。

## 23 明确生成并插入或替换时由软件完成组合

### 断点与结果

原 W4.2／V22 要求候选不预写、明确目标自动登记／绑定。当前 [HostToolServices.ts](../../src/core/tools/HostToolServices.ts)只生成并返回资源，[DocumentToolGateway.ts](../../src/core/tools/DocumentToolGateway.ts)只登记句柄，随后仍需模型另调 media.insert 或 project.apply。现有测试证明两步能用，没有证明宿主组合。

修复结果是：只要候选时仍只返回候选；明确“生成并插入／替换这里”时，软件在生成成功后应用到已授权的固定目标，报告生成、应用和保存各自结果。

### 修改边界

- 在现有图片工具与宿主服务中表达可判定的候选／插入／替换意图和正式目标，不把当前 target 的文档绑定含义偷偷改成自动替换。普通生成、展示候选不推定应用授权。
- 宿主组合现有图片作业、资源摄取和 canonical apply，沿 DocumentSession 形成一次实际内容应用及其 History；不让模型搬运资源句柄，不创建第二图片 writer。
- 图片工具输入的 strict schema 位于 [HostToolServices.ts](../../src/core/tools/HostToolServices.ts)，新增意图／目标须同源生成到实际工具目录。组合由 Gateway 控制并复用现有 `applyComponentContent` 等正式应用入口，HostAuthority 不直接变成文档 writer；需要回调时只补真实组合所需的窄接口，不预先强制新增一套 Gateway 端口。
- 生成期间固定目标，应用前按现有目标版本和授权检查；人工已改同一目标时保全人工改动并保留可用图片，不能写到当前焦点或覆盖新稿。停止后晚到的图片没有写权，也不能因应用失败再次付费生成。
- 图片生成成功而应用失败时保留资源与准确原因，可按当前授权续作应用；保存只遵循现有用户要求及已确定的首次创作保存规则，不把所有换图变成自动保存。
- 更新同源工具说明和内置／MCP 消费者；第 19 节负责最终实际资源范围，本节不重复实现另一套资源收集。

### 最低验收

## 24 补齐正式正文范围互动及改字映射

### 断点与结果

原 L12 及统一组件设计包含正文范围注释／行为、行内填空和改字映射。当前 [正文合同](../../src/shared/document/content.ts)只有 text/math 行内项，[行为目标](../../src/shared/contracts/component-platform/project.ts)及 [Runtime](../../src/player/components/ComponentPlatformRuntime.ts)只有 instance/surface/project；[Flow 插入命令](../../src/renderer/ui/flow/flowInsertCommands.ts)可在所选块之后插入区块，但没有正式行内插入。块级互动继续保留，本节补的是正文中几个字或一个行内位置的正式能力。

### 修改边界

- 在既有正文语义中表达范围附着及必要的行内互动引用，复用统一组件／行为能力；可持续编辑的文字仍是正式正文，不改成不可编辑 HTML，也不建 Flow 专用互动系统。
- 正文编辑 owner 持有范围随插入、删除、替换的映射；编辑投影只消费和提交语义变化。范围内改字保持合理边界，完全删除目标时移除或明确解除对应关系，撤销可恢复；不依赖易失 DOM 路径或让模型手填字符偏移。
- 同一次正文变更和范围映射进入 canonical transaction／History；人工正文操作、AI 正文修改、复制粘贴及删除的直接路径使用同一映射规则，不各维护一份锚点。
- 接通实际正文选择入口、必要属性／内容编辑、工具操作、工程保存重开、原生试运行及 Published／最终 HTML 消费者。复用现有专业编辑器，不要求给任意程序所有内部能力增加人工面板。
- 普通链接、公式、正文样式及阅读顺序保留；原生与发布表达同一范围和行为，不能只让编辑器高亮正确却使运行目标漂移。

合同与格式影响：同批调整 `content.ts` 行内表达及 `plainDocumentText`／`documentTextLength`，ComponentTarget 与 Runtime target 解析、作者工程／Published schema、Component API 对应描述及同源生成能力资源。按[架构合同 §0](../development-plan/ARCHITECTURE_CONTRACT.md#0-统一组件合同目标与具体实现范围分别记录)确定实际格式表达与读写消费者，不预定 V10／V3／API 5 一起升版，也不恢复旧格式兼容平台。既有文字长度、导出、复制和正文编辑的直接消费必须对应新语义。

### 最低验收

在一个小正文中放置范围注释和行内填空，实际输入与点击可用；在范围前及内部改字后，检查目标仍正确、未选文字及格式保持；删除目标及撤销恢复后再保存冷开、导出 HTML 操作。该小样本可合并证明范围映射和行内原子两种受影响语义，不扩大为全编辑器矩阵。复制及 AI 修改复用同一映射的定向检查，只在消费者不同或实际失败时补一条。

## 28 合并验收缺口与实施衔接

### 28.1 H6 按三种属性分别关闭

软件性能／功能、方法效果分别形成结论，方法对照未结束不妨碍确认已有软件修复；同时不能因软件分项通过就把方法、预置或其他已纳入目标静默取消。尽可能在同一次实施完成全部范围，真实未完成项按第 28.3 节列明。

1. **性能与载体。** 第 25 节沿同一作品、同环境做修改前后对照，证明普通回访重复工作消除和实际发布载体替换；体积、导航响应、状态／互动分别记录。优先用最新天下拼图；旧 Han Jing 只有在其独有行为或失败模式未覆盖时补测，不能把旧不同环境耗时直接相减。
2. **方法改善。** 在同材料、模型、设置下，以相同代表片段比较旧／新方法；保留首次结果与相同修订机会，检查具体材料关系、操作、反馈和画面，不只数按钮和图片。已有严格同条件证据有效则复用；不同课型的阶段成果不能充当严格方法对照，也不升级模型掩盖方法问题。
3. **一次联合交付。** 沿一条当前可用正式内置路线完成代表性作品：正常入口选中并读取 Skill→关键场景→约定作品范围→一次人工移动及 AI 续改→保存／冷开→实际互动与复位→HTML/ZIP 离线运行。正式正文、专业数据和人工布局仍可续编，动态行为正确。与各节用例共享作品和有效证据，不再叠加全能力、全模型、全入口矩阵；外部 Skill 做必要读取，只有相关消费者改变或失败才补外部创作。

真实模型和图片只用既有授权路线；费用、实际模型、生成结果和验收结果分开记录。缺教材原文时不能用课件摘要伪装教材保真，但不阻塞已可验证的编译与机制。历史 Owner 手验、Portable 与发行状态不因本次联合验证被自动签收。

### 28.2 R06 补特定证据，不重做动画系统

原结果称“局部 137deg 中间旋转”，但现 JSON 的 localMiddle 为单位矩阵，测试只判不为 none。后续交付应在原结果旁追加勘误，保留旧记录的日期和证据；当前准确结论是动画执行和最终状态已有证据，局部中间旋转未单独证明。

若要关闭该项，只对这一局部非预置动画采一个确在中途、非单位矩阵且与指定旋转相符的实际画面／变换，并确认最终状态；不能拿关键帧输入或跨对象倾斜截图替签。若该采样暴露真实失败，才进入对应实现修复。无需重跑整套 R06、四课创作或构建全局动画暂停系统。

### 28.3 执行时合并同一职责，避免再次只交局部

用户已明确要求尽可能一次完成，未完成必须告知，不静默取消。当前仍只修订方案；后续获启动指令后，按下列依赖安排内部步骤，不据此擅自拆成只交首批的缩减目标：

- 启动时按创作方案第 10 节先澄清并同步必要的当前授权／执行入口引用，再修改对应产品范围；依赖新能力的 Skill 与分发说明随实现交付，不把整份同步清单变成开工前置。任务板若仍有 §14.8 等活跃写域，仅对本次真实相交部分登记交接、释放或由唯一 Owner 统筹，保留其他未完成范围，不要求为开工提前宣布整批完成。
- 优先闭合第 10、14、16、22 节的中断／错写／终态／续作问题，以及第 25.1 节的已测明显性能退化；独立写域可并行，共享执行器、正文或导航文件保持单 writer。
- 上述独立修复一旦取得有效结果，及时在同一结果文件记录可用状态，不等待发布编译、页面模板等大项才报告；总目标继续推进。定级按当前用户影响逐项判断，不把所有优先项统一标成 P0。
- 第 19、23、25.2—25.3、26 节共用资源、编译、身份与应用能力，按真实依赖合并实现，不为每个历史编号做一套服务。发布变化必须连同最终入口和旧作者投影退出一起交付，不能以 helper 或类型通过标为完成。
- 第 24 节正文范围能力和第 27 节方法范例可在不冲突时推进；范例和预置清单不阻塞既有核心故障修复。第 12—13、16 节的旧 UI／终态承诺只修一遍。
- 每项结果分别注明代码接线、真实操作、保存冷开、导出和仍未证明的属性。重要结构候选按现工作协议做一次独立审查，未变有效评审不重复；本节不新增验收平台、固定重跑门或永久台账。
- 第 14 节对照架构合同 §0.1—0.3 的身份、局部范围和正式应用；第 19、25 节对照 §0.3—0.4 及 API 5 资源／权限／生命周期；第 24、26 节同步正文、目标、库格式与读写消费者。行动前按需读这些当前条目，实际语义改变时同批更新对应合同与生成描述；旧 §1／§2 中明确标为历史的约束不重新变成准入门，不新增合同审批平台。
- 最终逐项对照本方案范围：已完成写明证据；未完成写明具体内容、原因、用户影响及继续所需条件。可继续的工作继续做，部分通过不等于全部完成；任何延期、替代或取消必须明确说明，不删原条款或用缩小后的验收掩盖。真正涉及新采购、凭据或超出授权的条件只限制相关分项，其余持续推进。

本轮回填不改历史结果、AGENTS、工作协议或实际 Skill；之后同步这些入口时，按第 20 节和创作方案第 9—10 节更新重叠引用及失效执行提示词，不保留两份冲突的当前指令。
