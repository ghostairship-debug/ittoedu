## 0 执行目标与完成边界

将 GLX 扩展为能够承载完整 Web 作品的正式创作工程。Flow、Slide、Spatial 成为内置的布局与观看容器，可以作为作品的主要组织方式，也可以在局部组合使用。完整 HTML 应用、游戏、影游和深度互动内容拥有正式的程序承载路径，可以按需要调用果铃的状态、镜头、转场、媒体、资源和原生组件。

改造沿现有统一组件架构推进。对象身份、作者数据、资源、编辑事务、保存和发布继续走现有权威链路。优先提取、复用和修正实际实现，新增代码只补当前契约缺少的能力。当前已经完成的混合 HTML 接入、资源闭包、局部布局、跨页状态、回执与观察修复，作为本次基线使用。[S01][S02]

本轮完成软件架构、基础组件与技术验收。首件精品参考作品的深度策划、内容研究、视觉生成和长程精修，在软件交接后另行开始。技术验证载体用于证明能力，不计为精品参考作品。

### 0.1 必须交付的结果

1. 完整 Web 程序可以成为 GLX 的作品入口，不依赖作者选定三表面之一，也不被强制加入幻灯片导航或固定画幅。
2. 三表面具备正式的容器身份、子内容关系、作用域和宿主接入方式；至少贯通一组实际有价值的局部混合。
3. 原生对象、容器与接入后的代码能够调用同一套状态、镜头、导航及转场执行能力。
4. 自主管理的游戏或模拟可以保留内部循环、物理、镜头和逻辑状态，通过明确接口与果铃协作。
5. 普通原生内容保持可编辑；可定位的 HTML 内容能够局部修改；复杂程序有可靠的参数和源码深改路径。
6. 修改经过正式事务，能够撤销、保存、冷开，并在实际导出产物中保持内容、资源和行为。
7. 容器、行为、背景、转场和混合模板进入现有资产体系，能够在新项目中发现、插入、深改和再次复用。
8. 模型按需读取相关能力和对象，软件继续提供有界、准确的操作回执；效率结论与实际测量相符。

## 2 目标架构与职责

### 2.1 四个层次

| 层次 | 职责 | 主要复用基础 |
| --- | --- | --- |
| 作品工程 | 入口、作者内容、组件定义与实例、源码、资源、依赖和可编辑信息 | Project、DocumentModel、GLX 归档 |
| 公共宿主 | 身份、资源、正式变更、编辑目标、运行作用域、尺寸、输入焦点、实例释放 | DocumentSession、Driver、ComponentRuntimeHost、现有坐标与资源服务 |
| 容器与共用能力 | Flow、Slide、Spatial；呈现状态、导航、镜头、转场、媒体和背景接入 | 当前表面实现、navigation owner、runtime ports、组件库 |
| 作品内容与程序 | 原生内容、可复用组合、局部程序、完整 Web 应用及其特定算法 | 现有原生组件、source/Web 程序、专业引擎 |

容器与普通内容组件可以共享身份、注册、资源和编辑机制。容器额外承担对子内容的布局、坐标、观看和输入范围管理。可复用效果也可以共用库机制，但转场不能因“是组件”就自行成为导航负责人。

### 2.2 必须保持的权威关系

- 作者文档是一份可持久修改的真相。运行 DOM、播放投影和布局测量都是派生结果。
- 每个作者实例在权威父子关系中有一个所有者。移动实例保留身份；重复使用同一素材或定义可以产生不同实例。
- 同一数据、视口、镜头或动画目标的实际状态有明确负责人。其他参与方调用、订阅或读取结果。
- 编辑、试运行和发布使用相同的能力实现与资源语义。渲染适配器可以不同，内容与行为含义必须一致。
- 模型负责内容、设计、算法和意图；软件负责身份分配、引用重写、坐标换算、资源装配、正式提交和交付事实。

### 2.3 本次不建立的平行体系

本次沿现有 Project、组件库、Driver 和 runtime 扩展。避免另建第二份作者树、HTML 专属 History、游戏专属 GLX 格式、独立资源仓库、另一套大而全的创作 DSL，以及与现有导航并行的全局状态同步器。

复杂游戏的内部状态机、镜头和物理系统属于作品程序，可以保留。这里限制的是重复的平台管理真相，不限制作品内部算法。

## 3 通用入口和作者结构

### 3.1 确定作品入口可以引用组件或程序

目标结构应具备一个显式的作品入口引用。这个引用可以指向原生组合、三表面容器或自主管理的 source 程序。宿主不能根据“没有三表面配置”自动补一个 Slide 并强加演示行为。

优先复用现有 definitions、instances、childIds、source workspace 与资源绑定。根入口只声明从何处开始运行，不重复保存一份 HTML 和一棵与其双向同步的原生树。

本方案确定采用“工程拥有顶层实例，入口引用其中一个实例”的语义。工程级根实例集合拥有各主要内容根；普通子内容由所属实例的 childIds 拥有；现有 global underlay/overlay 继续拥有作品级层。入口引用本身不产生第二个所有者，也不要求所有内容都成为入口实例的后代。未激活的根容器保留在工程中，按既有活动策略运行或休眠。

以下为目标职责的类型草图，字段命名由 P0 对照实际扩展点后冻结。它不是当前已存在的 API，也不是要求模型手填的创作协议。

~~~ts
type WorkEntry = {
  rootInstanceId: string
}

type WorkRootAuthoring = {
  // 根集合是所有权关系；entry 只是其中一个根的运行入口。
  rootIds: string[]
  // 仅尚未配置入口的草稿允许缺省。
  entry?: WorkEntry
}

type ContainerAuthoring = {
  // 复用当前对应的类型与含义。
  designSize?: DesignSize
  flow?: FlowAuthoring
  spatial?: SpatialAuthoring
  presentation?: ComponentPresentation
  background?: ComponentBackground
}

type CapabilityTarget = {
  // 由所在实例绑定，跨容器操作时明确指定。
  containerId?: string
  instanceId?: string
}
~~~

建议把容器配置挂在实际容器实例的一个明确作者字段上，子项仍使用现有 childIds。能力声明来自其组件定义或实际注册信息。不要同时在 instance.data、独立 containers 表及旧 surfaces 中保存三份可写容器配置。

根集合、实例 childIds 和现有 global 子项各自记录拥有关系；同一实例只能出现在其中一处。parent/owner 查询和索引从这些关系派生，不再维护一套独立可写的父指针。现有 ComponentContainer 与 owningContainer 需要覆盖工程根集合；迁入目标结构后的表面容器按实际实例定位，旧 surface 目标只在读入或旧操作适配边界解析。

正常运行或导出时，entry 必须指向一个存在的顶层实例。空工程沿现有草稿规则处理，未配置入口时给出准确结果。删除入口需要在同一正式变更中设置有效替代入口，或沿草稿规则清空入口；不能留下悬空引用，也不能自动补入 Slide。

如果现有字段已经足够表达上述语义，直接复用；如果不足，增加最少的显式字段。P0 的输出必须确定一个方案，后续包遵循该方案，不让不同执行者各自选择字段位置。

### 3.2 三表面从顶层分类变成内置容器

Flow、Slide、Spatial 的实际布局与观看算法继续复用。它们应能通过与其他资产一致的发现和插入流程使用，其容器身份可以作为状态、镜头、背景及编辑操作的目标。

三表面内部不要再根据“我是整个作品唯一表面”获取文档、全局键盘或默认窗口。宿主传入其所属根、尺寸、子内容、资源、作用域和可调用能力。

第一阶段至少实现：

1. 三类容器作为主要内容入口的现有能力。
2. 一个正式的完整程序入口。
3. 一组具有实际价值的局部组合，例如 Flow 中的 Spatial 探索区域。
4. 混合作品中进入局部内容、离开并返回来源位置的路径。

不要求排列所有嵌套组合。支持条件应由真实能力决定；不支持的组合给出准确结果，不能静默改变布局类型或丢失内部编辑能力。

### 3.3 现有 V10 结构的过渡方式

P0 必须冻结三个边界：支持读入的文件结构、进入 DocumentSession 后唯一可写的内存结构，以及保存时唯一写出的目标结构。目标完成态以第 3.1 节的工程根集合和容器实例为作者权威；surfaces 只保留有明确用途的输入适配或只读投影。

现行 V10 在读入边界完成一次结构映射，再进入目标 DocumentSession。旧操作先转换成对目标结构的正式操作；现有功能与新功能都只修改同一权威结构。Undo、DocumentSnapshot 和保存读取同一内存结构，不能在撤销时重新猜测新旧格式，也不能让旧操作继续写兼容投影。

同一转换逻辑还须覆盖已有恢复稿与持久 Undo/Redo。当前 DocumentRegistry.restore 直接恢复 Session，不经过 GLX 归档 load；DocumentSession.restore 会校验当前稿、保存稿及 past/future 中的前后模型。[S06] P0/P1 应明确恢复入口怎样在新 Driver 校验前统一转换这些模型及相关引用，保持操作身份、版本关系、dirty/已保存关系和历史内容一致。保留原恢复记录；转换失败时准确诊断，不覆盖原记录，也不通过清空历史使恢复通过。该处理仅承接本轮受影响的现行 V10 恢复数据，不扩展为历史格式迁移平台。

如实现过程中先用旧结构生成容器只读视图帮助提取代码，该阶段不得同时开放另一套作者写入。P1 实现目标结构、正式变更及唯一权威切换能力；实际接入前，受影响的编辑、运行、观察、恢复与输出消费者必须已接目标结构，或消费由唯一真相派生的只读适配。P2 所需接线可前移或与 P1 联合形成可运行的切换包，不能按阶段编号先切断旧入口，再等待后续阶段补回。切换后所有正式作者操作都写同一目标结构，必要适配集中在明确边界；替代路径和受影响保留行为通过后，才退役相应旧职责。

| 原工程有效初始入口为 S1 | entry.rootInstanceId 指向 S1；如果未声明初始入口，沿当前播放器既定的默认选择规则 |
| global.overlay 拥有 G1 | G1 继续由作品级 overlay 拥有；不复制到 S1、S2，也不进入它们的 childIds |
| S2 尚未被观看 | S2 及其作者内容仍由工程保存；观看目录切换激活目标，不改变作者归属 |

这个例子中的 T1、I1、P1、G1 保持原实例身份。表面转为容器时优先保留原表面 ID；若现有命名空间发生实际冲突，由一次明确映射产生新 ID 并重写全部相关引用，不把“所有 ID 全部重建”作为默认步骤。

当前表面配置、状态引用、镜头目标、实例 ID、全局可见性、库引用和作者记录都纳入映射。已有正式动作保持原目标含义，不能仅修改类型就让旧按钮转而操作最近的嵌套容器。纯程序工程则可以只有一个 source 根实例和一个入口引用，global 为空，不需要生成演示容器。

### 3.4 协议版本策略

P0 对新增字段、序列化、发布及 runtime 调用做一次兼容性判断：

- 兼容扩展：沿现行协议增加真实可选能力，补齐所有 producer、schema、consumer 和能力说明。
- 不兼容变更：明确需要升级的工程、发布或组件 API 版本，并让对应生产者和消费者成套切换。只升级实际受影响的协议。

不能为了保留版本号而用隐式开关隐藏不兼容语义，也不预先为了架构名称升级所有版本。GLX 扩展名和现有工程归档体系继续使用。

当前 Project V10 与 Published V3 的 strict schema 均要求 surfaces，Published 还沿 Project V10 结构校验。[S07] 按第 3.3 节确定的根集合、入口及容器实例替换顶层作者结构，Project 与 Published 应作为不兼容格式变化成套切换；P0 确定实际新版本编号及必要生产者、schema、编译和消费者。Component API 是否升级，单独根据实际字段和调用变化判断，不随工程版本机械升级。不能仅因为文件仍叫 GLX 就声称兼容；其他确属兼容扩展的能力仍按前述规则处理。

当前 V10 的一次读入与恢复转换只处理本轮目标实际需要的现行结构，保留原文件和恢复记录，不自动批量覆盖作品。历史 V9 转换和长期双播放器不在本轮范围内。

### 3.5 内容身份和多处使用

同一图片在 Flow、Slide、Spatial 中可使用相同资源，或共享同一个可复用定义；不同容器中的独立放置通常对应不同实例，分别拥有布局。

同一容器内的多呈现状态继续使用同一实例及现有状态覆盖。切换状态、进入转场或生成播放快照，不产生新的作者实例或父子归属。修改共同正文应作用于共同来源，修改某个状态的布局只作用于相应覆盖。

移动一个实例到另一容器时，内容身份、源码及资源引用保持；布局转换由明确操作完成。不能为了跨容器复用，把一个可写实例同时挂到多个父级。

确需同步内容时，使用既有数据或状态绑定。若以后出现同一实体多视图的真实需求，应明确实体与投影的区别，不在本轮暗中增加多父级编辑语义。

## 4 容器宿主和布局接口

### 4.1 容器接入应具备的职责

| 项目 | 宿主或容器需要保证的结果 |
| --- | --- |
| 实例身份 | 容器、子实例和源码区域有稳定、可定位的身份 |
| 子内容挂载 | 按真实 childIds 和内容槽位挂载，沿已有 inline.mount 等机制扩展 |
| 布局输入 | 明确父级分配的内容区域、宽高约束和尺寸来源 |
| 测量结果 | 自然高度等结果属于派生观察，不能写入作者 History |
| 坐标换算 | 父级、容器内容、视口、镜头和程序局部坐标之间有可计算关系 |
| 输入范围 | 明确滚动、键盘、指针与手势的处理者 |
| 观看状态 | 滚动位置、镜头位置和当前局部呈现状态归所属容器 |
| 生命周期 | 挂载、更新、可见性、暂停协作和释放复用现有实例作用域 |
| 编辑与观察 | 同一挂载向编辑器和观察工具提供真实目标与几何 |
| 能力声明 | 软件能判断是否支持状态、镜头、导航、深度编辑等操作 |

子树挂载需要明确单一责任：外层投影创建容器实例，容器接管其子内容的布局和挂载范围，具体子实例仍调用共用渲染实现。外层遍历到容器边界后，不能再独立递归挂载同一批后代；容器使用 inline.mount 时也不能产生第二套实例运行环境。

同一编辑或运行会话的同一有效作用域中，每个实例只能有一个活动挂载、一套相应事件订阅和一条释放路径。独立编辑视图与独立运行视图可以拥有各自的会话。程序内部 DOM 由程序管理，接入的原生子对象由正式槽位挂载；普通转场的显示快照不注册第二套互动实例。

### 4.2 保持三种布局的实际价值

Flow 继续处理阅读顺序和自然高度。Slide 与 Spatial 继续支持作者自由构图和正式 frame。程序负责自己的内部布局，宿主负责分配区域和外部组合。

复用 ComponentLayoutPort 的读取、订阅、测量与挂载代际约束。当前 free-frame、flow-viewport、flow-content 语义若不足以表达通用程序视口，增加明确的适配或最小扩展。所有消费者一起更新，不能把新类型默认为旧 Flow 块。

局部变化只更新相关对象和布局依赖。当前已实施的 stage、slot、variant 等局部布局声明继续有效；不得因容器化重新引入整页重排、自动缩字、覆盖人工 inline 样式或把连续正文拆成大量细碎节点。[S02][S08]

### 4.3 嵌套容器输入规则

输入首先由实际命中的内容和获得焦点的容器处理。全局演示快捷键只在其有效范围内执行。程序中的方向键、输入框编辑和空间拖动不能同时触发外层翻页。

嵌套滚动区域必须有明确视口和可理解的进入方式。返回外层时恢复相应来源位置。锁定、选择、拖动和缩放沿既有编辑机制处理，不由背景或程序偷偷更改文档几何。

### 4.4 容器深改的范围

参数可以调整布局与观看策略；原生子内容可以重组；源码可以实现特殊的布局或交互。源组件的自由度通过正式宿主接口获得，不通过直接修改编辑器私有 DOM、全局 store 或文件系统获得。

容器源码深改后，仍须遵守子内容所有权、布局报告、资源和生命周期契约。无法继续支持某项专业编辑的实现，应准确报告其能力变化。

## 5 状态与导航作用域

### 5.1 区分四类状态

| 类别 | 例子 | 持久化与更新原则 |
| --- | --- | --- |
| 作者定义 | 文案、默认参数、状态布局、镜头路径、初始配置 | 正式事务、Undo、GLX 保存 |
| 观看状态 | 当前章节、当前呈现状态、阅读位置、观察镜头 | 由所属导航或容器维护；按作品需要恢复 |
| 业务状态 | 回答、选择、实验参数、剧情变量、任务进度 | 对应逻辑拥有；共享部分使用现有绑定 |
| 连续临时状态 | 每帧运动、采样、插值进度、悬停 | 保留在 runtime 或专业引擎，不逐帧提交项目 |

作者定义的呈现状态描述 Slide 内一组可编辑对象的目标呈现，仅属于 Slide。Flow 使用章节／标题，Spatial 使用镜头／路线停靠点，三者是导航上的对应层级，不统一保存成呈现状态。业务状态描述内容逻辑，仍使用原共享状态与显式绑定。复杂剧情条件可以由代码推导，再调用所属容器实际支持的能力，不要求枚举全部变量组合。

### 5.2 原生和代码共用实际执行者

沿 ComponentInteractionPort、scope.state、stateBindings 和当前 navigation owner 扩展。原生按钮与程序对同一状态发出的操作，应进入同一个拥有该状态的执行者。

代码决定条件、参数和时机；状态能力执行对象投影与呈现变化。程序自己的业务状态若是权威来源，原生界面读取或订阅它，不能再维护一份独立可写副本。

正式作者修改仍走 Driver。运行时 state.set 不自动变成文档 data.set；需要修改默认值时，使用明确的创作操作。

### 5.3 定义局部目标和默认解析

建议扩展现有动作目标表达，使动作能够明确指向容器。软件根据来源实例绑定默认作用域；跨容器目标使用显式引用。

必须分别确定以下默认语义：

1. 作品级控制台和编辑器导航，操作作品级目录。
2. 新建局部组件中的状态与局部步骤操作，绑定其所属容器。
3. 明确指定目标的动作，始终操作该目标。
4. 现有 V10 动作经过映射后保持原目标，不随嵌套增加而改变含义。

默认负责人在实例接入时按能力绑定，通常是直接所属容器；需要跨层使用时显式绑定相应负责人。执行时不重新向祖先逐个搜索，直至找到一个“似乎支持”的目标。

显式 containerId 指定执行范围，instanceId 指定该动作契约允许的对象或锚点。两者同时给出时，验证对象与范围之间的合法内容或坐标关系；不一致时返回准确的目标错误。只有实例目标时，使用其已绑定的该项能力范围。解析结果同时用于执行、回执和观察。

完整程序根没有默认演示容器，所属容器也可能不支持某项状态或镜头能力。没有适用目标时返回明确的不支持或缺少目标，不自动生成 Slide，也不回退到作品级导航。

currentSurfaceId/currentStateId 等现有读取接口可以在过渡期保留，但其新旧含义必须明确。不能让一个全局 currentStateId 同时代表多个独立容器的局部状态。

### 5.4 状态引用和复制

局部状态必须有明确的所属容器。状态归属和状态标识分别处理：两个容器可以各自使用 overview/detail 等显示名称或局部名称，切换、复制、删除或库插入时不能相互串线。

当前 schema 只要求每份 presentation 内的 state.id 唯一，未要求全工程唯一；两个表面分别拥有 overview/detail 是合法输入。[S07] P0 必须确定目标采用“容器身份＋局部状态 ID”，还是在读入时规范为全工程唯一 ID 并重写引用。无论选哪一种，都须保留局部名称和动作原目标，不能把合法重复 ID 当作坏数据删除或拒绝，也不强制将全部 ID 改成复合字符串。

当前库插入已经重映射状态、规则、动作及源码引用，但存在按裸 stateId 跨表面建表的实现。[S16] 这不直接证明现有库插入已损坏；P1/P3/P5 须按冻结的身份语义同步读入、状态解析、复制和库引用映射。保留局部 ID 时映射要携带所属容器，采用全局 ID 时要区分来自不同容器的合法同名旧 ID；对外部共享状态仍按显式绑定处理。

stateBindings 的标量别名和 scope.state 的结构化数据继续分工。复制组件时重映射内部拥有的状态；对外部共享状态保持显式绑定，不自动连接目标工程的同名变量。

### 5.5 导航完成与取消

一次导航的派发、事实提交、目标就绪和视觉完成沿现有动作回执区分。已提交但观察失败的操作只重新观察，不重放写入。

取消应作用于实际操作范围。新导航可以取消同一视口的旧动作；无关兄弟容器中的独立程序不应因一个局部状态变化被整体重启。退休作用域的迟到回调不能再修改当前目标。

当前导航仍使用单个活动表面、状态读取和转场取消控制器，World 的活动判定也依赖当前表面。[S09] P3 要将执行、回执、观察、实例活动性和取消共同绑定到相应容器上下文，不能只给动作增加 containerId 而继续共用一个全局当前值或取消槽。A06 应同时证明取消容器 A 的旧动作不会取消兄弟容器 B 的独立动作；复用现有 owner、作用域和生命周期机制，不另建全局同步或调度平台。

## 6 镜头和动效能力

### 6.1 镜头编排和镜头执行分层

共用编排表达目标、时长、缓动、顺序和结束动作。具体执行由支持该能力的二维容器、Spatial 适配器或专业程序负责。

原生 Spatial 镜头、camera.present 与导航携带的 camera 配置继续复用当前 camera owner。常见聚焦、路径、返回和视口适配由软件完成，模型无需重复生成插值和坐标换算。[S10]

自主管理游戏可以保留内部镜头。需要平台协作时，暴露当前真正支持的命令、观察值和锚点。不要用二维 pose 假装表达三维透视、碰撞避让或景深；缺少适配时保留程序内部实现。

### 6.2 两个变换层级

外层容器负责其视口和内容区域，程序负责内部世界。相同 DOM 变换、相机对象或可编辑 frame 不能由两套系统同时直接赋值。

原生标注需要跟随程序目标时，通过已有坐标服务或新增的明确锚点适配获得位置。作者对标注的偏移与程序运动按约定组合，不能在下一帧被重绘覆盖。

### 6.3 转场继续由导航调度

转场资产提供视觉行为、参数及完成和清理能力。实际导航负责人决定何时提交目标、何时开始过渡以及何时取消。

复用现有 fade/slide/zoom 和关键帧入口，抽取成可发现、可参数化、可源码深改的基础能力。现有关键帧协议的 transform、opacity、offset、easing 等范围应准确保留；更复杂效果通过实际适配扩展，不能仅在目录中增加名称。

文档级 View Transition 与局部容器动效的作用范围不同。局部转场优先利用可限定目标的现有动效执行；使用文档级 View Transition 时沿现有调度处理其共享资源，不把每个局部容器都当成独立文档调用。必要时选择语义正确的局部基础效果，并准确说明能力范围。

转场中的旧画面可以是显示快照。不要为一个普通导航转场同时运行两套完整互动世界，再额外解决重复输入与副作用。

### 6.4 时间和媒体

普通呈现动效使用相应能力执行。需要帧级音画同步的片段由负责它的媒体或程序时钟管理。共享的是可调用接口、生命周期和外部控制，不要求所有动画、游戏和音频统一进入一个新时间平台。

复用已有 signal、cleanup、挂载代际和必要的 suspend/resume 协作。当前停止、离开、再次进入的含义保持清楚，不为本轮建立万能暂停、逐帧回放或全局存档系统。

## 7 完整 HTML 程序接入

### 7.1 复用当前来源读取与闭包

从实际 from 路径读取 HTML、CSS、脚本、组件源码及同目录依赖。复用 readComponentProjectFileInput、readHtmlClosure、readComponentSourceClosure 和正式资源接入。[S13]

完整程序入口、局部程序、内置组件的源码派生，应共享现有编译、资源与运行基础。它们的宿主位置可以不同，不能复制一份“通用 Web runtime”维护相同职责。

支持范围需以实际运行环境说明：标准前端程序、已有可编译源码及可解析依赖沿现有入口处理；需要服务端或特殊构建步骤的应用保留真实依赖和准确诊断。不能把脚本删除、静态截图或简化占位当作完整程序承载成功。

### 7.2 普通 HTML 与局部程序继续混合

普通正文、图片和可编辑组合优先保留已有身份和结构；紧密耦合的互动可以保留在同一个程序中。外围内容无需为了局部互动而增加全局脚本包装。

完整外来 DOM 程序可以整体保真，后续逐步接入有价值的字段和对象。承载层不承诺把任意 JavaScript 自动逆向为全部原生节点，也不把“包含一个 script”直接等同于整件作品只能整体编辑。

### 7.3 程序与原生能力的正式连接

程序通过其获得的 runtime 上下文或正式代理调用能力。该连接需要具备：

- 稳定的实例与容器作用域。
- 当前允许调用的状态、动作、媒体和资源接口。
- 清楚的异步结果、取消与实例失效语义。
- 可选的内容字段、编辑目标、布局或锚点接入。

不要通过注入私有全局变量、直接跨 iframe 访问编辑器 DOM、共享可写全局 store 等方式绕开正式边界。

### 7.4 源码和资源的权威来源

程序源码沿现有 implementation/source workspace 保存，依赖和素材沿 DocumentResources 归属。GLX 保存的是可继续修改和运行的工程材料。

运行 URL、临时 blob、挂载对象和播放快照不成为作者数据。cw-resource 是工程引用，由资源服务在运行和发布时解析。模型使用实际媒体 source，不把音频转为 Base64 塞入脚本；内部打包实现的编码方式由软件处理。

动态资源分析无法覆盖的情况给出精确 warning，并保留程序。资源缺失、能力不支持和实际运行失败分别报告，不能混为一类，也不能在依赖不完整时宣称离线完全可用。

## 8 可执行背景

### 8.1 区分背景绘制和背景程序

现有 backgroundPaint 继续承载颜色、图片和 CSS 绘制。可执行背景是挂在明确区域、拥有 runtime 生命周期的程序或组件。[S18]

P0 需确定当前背景程序的真实定义、挂载位置和消费路径。优先复用当前组件 underlay、Source 和活动状态机制；若缺少正式角色接入，补对应宿主适配。不能把执行代码藏入 CSS paint 字段。

### 8.2 背景的作用范围

至少明确作品级、容器级和程序内部背景的归属。背景可参与全场景互动，但只能控制声明属于自己的内容，或通过正式动作影响其他内容。

默认装饰背景不拦截前景操作；交互背景明确声明输入范围。背景中的世界坐标、前景内容坐标和视口固定界面分开处理。

背景读取共享参数或呈现状态，输出事件或观察值。它不另存一份与前景竞争的相同状态，也不逐帧向作者文档或模型回传全部数据。

### 8.3 基础资产的开放程度

至少提供可参数化环境效果和可由前景控制的场景效果两类贯通实例，具体复用现有实现决定。允许换资源、参数、分层结构和源码。

验收关注新项目插入、状态联动、输入正确、离开后清理和保存发布。仅有一张背景预览图不能证明背景 runtime 已完成。

HTML 组件目录与结构化库条目可以继续保留各自存储细节，通过当前目录和管理入口发现。不要为本轮建立新的注册表、包管理器或远程资产市场。

| 用途 | 复用的公共机制 | 专有职责 |

### 9.4 参数 结构 源码三层深改

参数层修改内容、数据、主题和常见行为；结构层修改真实子节点、槽位、布局与状态；源码层修改算法、渲染和特殊交互。

每个资产准确声明实际支持的层次。结构层必须对应权威节点或可靠 authoring 关系，不能创建只供模型操作的平行树。

默认局部修改使用实例覆盖或现有源码写时复制机制。定义更新必须明确作用范围。软件应处理源码文件、资源和绑定的闭包变化，保持其他实例隔离。

### 9.5 版本和上游更新

复用已有 packageId、version、来源关系和复制或引用语义。已实例化进入工程的资产固定其来源基线，上游发布新版本不自动改写它们；已有正式链接更新机制的条目继续沿原机制处理。

更新通过明确的正式操作应用，检查实际数据、绑定、公开输入和本地修改。源码派生实例保留本地工作；差异可以通过现有源码或编辑界面呈现，不要求新增专用更新工作台，也不为任意代码建立自动兼容性证明或合并系统。

本轮内置示例至少证明一次输入保持兼容的更新，以及一次含本地源码深改的更新处理。前者可以应用；后者不会静默覆盖，能够查看可取得的来源差异并选择继续保留或明确更新。声称可查看上游差异时，来源基线必须实际可取得；仅保存一个无法对应实现的版本字符串不算完成。范围外的历史条目缺少基线时，准确报告条件，不自动建立历史包仓库。

P0/P5 应明确内置示例的来源基线从何取得，优先复用可读取的目录旧版本，必要时保存该示例所需的来源材料；现有 packageId/version 字段本身不等于已有来源快照或差异能力。当前 replacement 路径即使只更新定义也要求 project.surfaces[0]。[S16][S17] 目标实现应按真实定义及依赖处理更新，使没有演示容器的纯程序工程也能完成适用的库更新，不为更新临时生成 Slide。

## 10 原生编辑和源码编辑

### 10.1 修改落回真实来源

沿现有 ComponentAuthorField、authoring 记录、数据路径、源码区域和正式编辑提交实现。能够稳定定位的普通文本或图片，提供对象级修改；不能可靠映射的动态内容，给出明确的源码或参数入口。[S08]

每个可编辑字段在当前实现下有唯一的权威写入路径：原生数据、原生作者结构或指定源码区域。选择与检查复用现有 authoring 描述，返回真正可用的路径；修改只进入该路径，其他表示由它派生。不能靠同时修改 data 和源码维持两份可写内容。源码覆盖改变字段来源时，同步更新或失效旧映射，不新增独立的字段编辑树。

运行 DOM 的临时变化不直接回写作者文档。作者修改需要经过重绘、状态切换、保存和冷开仍然成立。

### 10.2 保持专业编辑有效

professionalBuiltinKey 可以保留专业编辑入口，但它只是标识。源码深改后应验证实际使用的公开参数、事件、目标和资源是否仍然有效。

如果公开输入保持兼容，继续专业编辑；公开输入、事件或编辑目标有意改变时，同一正式变更需要处理相关数据、绑定、公开 schema 和专业编辑描述。无法继续适配的专业控件明确失效或退出支持范围，保留仍有效的编辑项。这里不要求自动生成任意专业面板，要求实际实现、参数说明、检查结果与面板对能力的描述一致。

不要显示一个看似可用、实际被程序忽略的属性面板。

### 10.3 实例与源码文件隔离

复用 CourseV10Driver 的 sourceScope、expectedFiles 和 scopeComponentSourceEdits 等机制处理实例源码修改。[S06]

修改一个派生实例，不能改变其他引用同一定义的实例。复制组件、进入新项目、Undo、保存和发布都应保持该隔离。

### 10.4 选择与观察

编辑器能够区分容器、原生子对象、程序区域及可定位源码字段。选择、观察、几何和正式修改使用一致的目标。

普通精修从当前选择或局部路径开始，按需要展开正文、结构或源码。观察端不得为一个小修改默认返回全部工程或完整运行 DOM。

## 11 模型能力入口和结果

### 11.1 能力目录来自实际注册

从现有可执行能力、组件目录和 schema 生成短索引。索引说明用途、适用对象、重要条件和详细说明引用。参数约束与执行实现保持同源。

方法型 Skill 说明创作判断和流程；API 说明描述软件接受的操作；范例展示具体质量与用法。三者互相引用，减少复制维护。

### 11.2 保持模型表达与机械执行的分工

| 创作意图 | 模型负责 | 软件负责 |
| --- | --- | --- |
| 插入组件或模板 | 选择用途、内容和适配方向 | 分配身份、实例化、绑定资源和归属 |
| 增加局部状态 | 命名含义、决定呈现变化 | 建立有效引用、投影与正式变更 |

| 替换素材 | 选择实际素材来源 | 接入、引用、保存和发布闭包 |
| 修改一个对象 | 确定改动内容 | 定位真实字段、保留无关内容、提交与回执 |
| 深改程序 | 修改算法或表现方式 | 源码作用域、依赖和其他实例隔离 |

普通 HTML/CSS 和简洁代码仍是正式创作材料。模型不需要填写内部登记表、猜测 ID、拼接运行租约或手动更新多处引用。

### 11.3 复用当前有界回执

本轮沿今天已经修复的结果投影、operation.read 票据、固定版本分页及动作事实回执工作。[S02]

新操作的结果应与实际变更范围相关：

- 创建返回后续需要引用的新目标。
- 修改返回提交状态、必要版本与具体诊断。
- 异步操作返回原操作身份和可继续读取的状态。
- 批量操作准确报告整体与部分结果，明细按需读取。

局部修改的默认结果规模不应随整份作品体积线性增大。不能先序列化完整项目再截断字符串；不能把同一结果在文本和 structuredContent 中完整交付两次。

### 11.4 并行任务和正式提交

策划、源码草稿、素材准备和互不相干的实现可以并行。正式项目修改继续由既有事务 owner 提交，并沿现有版本与预期值机制处理冲突。

同一目标的陈旧修改应返回可定位冲突。执行者重读相关目标后修订操作，不以整份快照覆盖新结果。仅在实际出现频繁无关冲突时，才评估更细粒度的版本机制。

**通过条件：** 两个独立容器的状态和镜头互不串线；程序通过正式接口、原生控件通过原生操作，能够交替控制同一个平台目标并进入同一实际执行者；一次操作只执行一次；快速切换没有旧回调覆盖，取消 A 不取消兄弟 B 的独立动作；作者文档不被播放进度污染。对应 A04—A06、A18。

### P4 完整程序 背景和持续编辑

**依赖：** P2、P3。

**重点入口：** HTML 来源与闭包、源码编译、runtime 接入、authoring 编辑、资源及背景挂载。

**工作：**

1. 让完整 HTML/程序从正式入口创建或导入，不依赖额外的外部网页工程。
2. 保留普通 HTML 与局部程序混合接入。
3. 打通程序参数、动态文案或源码的正式修改和重绘验证。
4. 接通背景 runtime 的作用范围、共享参数、输入和清理。
5. 验证源码实例隔离；对原生组件的源码深改变体，通过保留的专业编辑入口真实修改一项仍受支持的属性。

**通过条件：** V2 的真实输入、动态重绘和内部循环有效；修改经重新渲染与状态切换后仍有效；原生深改变体的专业编辑产生实际效果；背景与前景通过正式接口联动；离开后活动和资源符合生命周期。对应 A01、A07—A09、A17。

### P5 组件库 基础资产和模型入口

**依赖：** P1—P4 已确定的接口；可先并行准备目录和说明。

**重点入口：** ComponentLibraryEntry、extract/insert/references/rebindSource/replacement、目录展示、能力注册和项目检查。

**工作：**

1. 补容器、局部状态、背景及转场的库引用闭包和插入映射。
2. 按第 9.3 节交付基础资产并对应实际条目、插入/附着入口及证据，包含第 8.3 节的两类背景实例；复用和改进已有条目。
3. 打通参数、结构和源码三层深改。
4. 提供短索引、按需 schema 和真实局部范例。
5. 确认新操作消费当前回执与观察机制；按第 9.5 节落实可取得的来源基线、本地深改更新处理及纯程序工程的适用库更新，退出定义更新对首个 surface 的依赖。

**通过条件：** 第 9.3 节各类基础资产及两类背景实例都有实际条目和适用的插入/附着证据；新项目可发现并使用；修改一个实例不影响其他实例；深改保存和再次复用有效；兼容更新和本地深改处理有可取得的来源依据，适用更新在纯程序工程中无需伪造页面；目录声明与真实能力一致。对应 A07、A12—A14、A17。

### P6 保存 冷开与实际发布

**依赖：** P1—P5。

**重点入口：** 工程归档、恢复入口、DocumentDelivery、buildComponentPublished/buildComponentHtml、Published 构建、编译产物与 Player，以及 componentPlatform/delivery、deliveryPages 和 PDF/PPTX/DOCX 输出消费者。

3. 运行真正导出的 HTML 或 Web 包，验证通用入口与混合容器。
4. 检查源码和资产不依赖实施者的临时工作目录。
5. 对当前作品副本执行相关回归，保持已正常的路径，包含 V1 按实际能力冻结的 PDF/PPTX/DOCX 输出；依赖 surfaces 的页序、空间镜头帧和 Flow 讲义消费者接到目标结构或同源只读投影。

**通过条件：** 编辑器里的成功能够在保存与发布后成立；恢复及历史转换后仍可继续编辑；原有静态导出能力无退化，导出实际使用相同内容与能力语义。纯程序根的静态导出按已有输出能力明确捕获范围或准确诊断，不承诺任意程序自动转成可编辑 Office；静态输出不代替 A11 的可运行 Web 产物。离线结论只覆盖真实打包且已验证的依赖范围。对应 A10、A11、A15。

2. 更新实际接口说明、目录、方法引用和任务记录。
3. 完成有区分度的独立复核和必要构建检查。清理若影响加载、运行或导出，对相应代表路径重新执行保存、冷开或实际产物运行；未受影响的结果可以复用。

## 13 验证载体

验证集中在三类载体。可以复用已有 fixture；只补缺少的机制，不在此阶段创作新的精品作品。

### V1 当前 V10 作品副本

选取已有可运行项目，保留原文件和内容指纹。优先使用今天能力交接列出的混合技术工程，必要时增加一份与改动直接相关的现有原生作品副本。[S02]

按 P0 的受影响能力映射冻结当前正常路径、代表性内容、默认行为及必要编辑动作，动作数量由实际影响决定，不以两个编辑动作代表全部保全范围。覆盖变化命中的三表面编辑、专业属性、Source、导航/快捷键、观察/缩放、资源、Undo/恢复、保存与输出；使用已有有效证据和最少代表路径，缺少的相关行为才补验证。已有缺陷单独记录，避免把旧问题当成本轮回归。确认源码、资源、实例、状态和人工布局没有因转换丢失，原有人工入口仍然可用。

在该副本及其隔离恢复记录中，保留一份带未保存修改和 Undo/Redo 的现行 V10 状态，验证当前稿、保存稿和历史统一转换后可恢复并继续编辑。另用现行合法结构中两个表面各有相同局部 state.id 的输入检查引用映射，可复用同一技术副本；不修改原文件或真实恢复 profile。

冻结并执行受影响的原有 PDF/PPTX/DOCX 输出路径，检查内容、顺序及适用的空间镜头帧/Flow 讲义语义。仅选择当前已正常且适用的载体；V1 不覆盖的既有输出能力可补最小相关 fixture，不要求每个作品都能导出全部格式，不把原有不支持项变成本轮新增能力。

### V2 自主管理的 HTML 应用

一个规模受控的前端应用即可，但必须包含 HTML、CSS、JavaScript、相对路径资源、真实输入和动态内容。加入一段程序自主管理的 Canvas 运动或局部镜头，验证程序拥有内部循环的情况。

提供一处静态文字、一处数据驱动文案或参数，以及一次会重绘内容的真实操作。可选音频使用现有本地资源，不调用生成服务。

应用自身不使用三表面布局，也不依赖果铃预设的场景顺序。先证明纯程序入口独立成立；可选能力的正式往返接入由 V3 的强制用例验证，不用为 V2 人为增加演示容器。

### V3 混合容器与复用项目

使用一个小项目覆盖 Flow、Slide、Spatial，至少包含一组局部嵌套；两个可同时挂载的独立容器具有同名局部状态。可以在 Flow 中放两个小型 Spatial 区域，再保留一个 Slide 根入口，以同一类嵌套覆盖独立作用域，避免增加排列组合。

同时包含可单独编辑的原生文字和图片、一个背景 runtime、一项局部交互、一项转场，以及同一资产的两个实例和一个源码派生实例。至少一个派生实例由当前原生组件深改得到，保留一项有意义且公开输入兼容的专业编辑能力。

基础资产按第 9.3 节对应实际使用证据；第 8.3 节的两类背景实例可在该项目中分步替换验证，无需同时叠加。组件更新验证明确来源基线，兼容更新和本地源码深改处理覆盖纯程序工程中适用的定义更新，可复用 V2 的新项目副本。

必须包含程序与原生控件的往返操作：程序通过正式接口操作一个平台管理的局部目标，随后由原生控件操作同一目标，观察一致的真实结果。选择一条代表交互路径覆盖呈现状态、平台镜头和基础转场，确认调用进入共用执行者、动作不重复，并在实际导出产物中复现。

用同一原生对象的两个呈现状态验证共同正文与单状态布局分别修改，再通过原生专业入口修改深改变体的真实属性。以上动作复用项目中已有对象，目标是覆盖作用域、编辑与复制，不追求内容数量。

不要求所有表面之间的排列组合。选择最能暴露真实作用域问题的一组，其他新增验证仅针对实际发现的风险。

### 14.1 必须运行的完整链

对 V2 和 V3，最少完成：

创建或导入 → 真实互动 → 定位并修改 → 再次渲染 → Undo/重做 → 保存 → 冷开 → 实际导出 → 在产物中再次互动。

V1 执行与本轮改动直接相关的原有路径、编辑、保存、恢复与持久历史、运行及静态导出回归。原文件和原恢复记录不覆盖；不通过清空历史或跳过旧输出消费者缩小保留行为。

导出验证使用本地实际产物或既有隔离测试入口，不需要部署线上网站。构建范围覆盖本轮改动命中的 Main、Renderer、Player 和编译产物消费者。

### 14.2 以下结果不能计为通过

- 只改 schema 或增加接口声明，没有实际消费者。
- 三表面被包成不可深入编辑的三个大 HTML 对象。
- 临时 DOM 改动成功，重绘、冷开或导出后消失。
- 程序被转换为截图、静态内容或删掉关键脚本后“运行成功”。
- 控件和 runtime 各保一份可写状态，用同步循环掩盖冲突。
- 为避免竞态而禁用正常快速操作。
- 只启动编辑预览，未运行真正导出的产物。
- 把库源文件复制到特定工作目录，声称已经内置且可跨项目使用。
- 基础组件更新静默覆盖源码派生实例。
- 用软件 fixture 的成功替代精品作品质量、真实作者效率或费用收益。

### 14.3 测试规模和停止条件

静态检查和聚焦测试用于保护具体不变量，实际产品链证明最终行为。相关路径命中既有 authoring 回归时使用对应检查，例如开发入口列出的 test:authoring-regressions；具体命令以当前 package.json 和任务约定为准。[S01]

不机械重跑全部历史压力矩阵、收费作者或所有浏览器。代表链已经充分覆盖改动风险后，停止无关扩测，进入收口。出现具体新风险时，增加能回答该风险的最少验证。

保全范围与检查数量分别判断：受影响能力不能漏项，但共用实现、未变路径及有效证据可以复用。选择最低成本、足以证明该能力仍成立的检查；视觉、焦点、手势和真实输出等属性，不能只用类型或静态检查代替。新增测试通过不抵消旧功能失败，必要验证未通过前不删除替代前的受支持能力。

## 16 主要风险与处理原则

| 风险 | 容易出现的实现 | 应采用的处理 |
| --- | --- | --- |
| 根入口仍受三表面限制 | 给完整程序套一个隐式 Slide 并隐藏 UI | 中性的作品宿主，按所选能力配置视口与导航 |
| 双作者结构 | 新容器与旧 surfaces 都可写 | 读入、会话和写出边界确定；消费者就绪并通过受影响保留行为后统一切换；旧操作先归一 |
| 多父级实例 | 一个实例挂到多个容器并共写 frame | 独立实例、共享定义或数据；移动保身份 |
| 重复挂载 | 外层投影与内层容器都递归创建同一后代 | 容器边界划清子树责任，共用实例渲染和释放实现 |
| 局部状态冲突 | 仅按同名状态查找，或复制时未区分归属 | 保留有效全局 ID，补容器归属和名称作用域；软件负责映射与默认目标 |
| 同一属性双写 | 原生动画与程序直接改同一个 transform | 明确执行者或组合层级 |
| 编辑被重绘覆盖 | 只改运行 DOM | 写回数据、作者记录或源码真实来源 |
| 库深改失效 | 保留专业标识但破坏公开输入 | 验证实际编辑能力并处理契约变化 |
| 发布缺能力 | 编辑器有新宿主，编译产物仍只识别三表面 | producer、schema、编译和 Player 成套接入 |
| 迁移造成体验回退或重复重写 | 先换结构和删入口，到最终阶段再补功能；因名称旧而重写成熟算法 | 按受影响能力闭合切换，先接消费者并证明原行为，再退役旧职责；保留既有算法、人工入口和默认体验 |
| 回执重新膨胀 | 新命令返回完整模型或源码 | 复用当前结果投影与按需读取 |
| 迁移吞数据 | 通过删除未知字段使校验通过 | 保留原件并明确阻碍，不静默简化 |
| 范例前置过重 | 为证明架构先制作整套精品作品 | 三类受控技术载体贯通，随后再策划精品 |

这些处理应落在真实执行模块中。仅在 Skill 或提示词中告诫模型谨慎，不能替代软件保证。
