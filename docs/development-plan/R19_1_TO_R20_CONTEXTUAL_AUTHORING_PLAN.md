用户所说的“1.91”按正式版本写法统一为 `1.9.1`。这条路线把 Markdown 和原生工程的编辑入口逐步统一为：

> 选中内容 → 自动形成临时编辑目标 → 浮现上下文编辑卡 → 人工直接修改或调用 AI → 预览/接受 → canonical transaction 提交 → 可撤销、可保存、可重开。

## 1. 目标与边界

### 目标

- Markdown 排版视图中选中一段内容后，自动识别其所属段落、标题、列表项、表格单元格或公式，生成当前选区的临时编辑目标。
- 选区附近显示上下文编辑卡。普通正文优先显示为“段落”卡；标题、列表、表格、公式、媒体和组件使用对应的语义名称与工具。
- 卡片承载当前对象已有的人工编辑能力，并提供一个通用 AI 指令入口；AI 具体执行什么由教师自己下令，不预设教学专用功能菜单。
- 卡片中的 AI 指令与主聊天框使用同一个冻结目标、同一个候选提交和同一套冲突/过期处理。
- Flow 正文优先复用同一交互壳层；Slide、Spatial、Component、Runtime 按自身语义提供上下文卡，不强行全部伪装成 paragraph。

### 不改变的边界

- 选区是会话态，不会因为被选中就新建或持久化一个工程对象。已有 paragraph/block ID 与文字范围就是目标身份。
- 不增加第二套 Store、Session、History、Markdown 正文或 AI 模型循环。
- 不把源文映射不确定的内容静默扩大为全文修改；无法精确定位时保留稿件并给出诊断。
- 高级属性面板、源文编辑和专业对象面板继续可达。上下文卡是高频入口，不删除高级能力。
- 1.9 已有 040–060 状态不因本文改变；本文是其后的增量纵线，2.0 仍须完成原定全流程、三 CLI、PPTX、S4 与发布门。

## 2. 共享设计

### 2.1 临时编辑目标

在现有 `DocumentSelection`、Flow `textRange`、作者目标和聊天冻结目标之上增加统一的上下文适配层。目标至少包含：

- 所属文件或工程、Surface、位置、revision/contentVersion；
- 语义对象 ID：block、paragraph、list item、table cell、formula 或 Native object；
- 正文 slot 与逻辑文字范围；
- 当前编辑模式：排版、源文或对象；
- 可选的视图矩形，仅用于浮动卡定位，不进入工程数据。

它是“当前选中的对象目标”，不是持久化新对象。目标必须在提交前再次校验 revision、owner、对象身份和范围；失效时零写入。

### 2.2 排版正文与 Markdown 源文映射

排版视图的选区使用逻辑文字偏移，Markdown AI 和文件保存使用源文偏移。两者之间增加可验证的 source map：

- 普通文字只替换对应正文范围，保留 `**`、链接、公式分隔符和其他未选内容；
- 链接文字、链接地址、公式和代码分别作为不同编辑目标；
- 列表项、表格单元格、引用和嵌套课件对象带有明确 slot；
- 源文非法、重复身份、复杂语法或映射歧义时，停在草稿/诊断，不猜测全文范围；
- 源文模式可以直接使用用户选择的源文范围，但发送给 AI 前仍转换成正式目标并经过基准版本校验。

这一步是本路线的主要技术风险，不能用字符串出现位置代替结构映射。

### 2.3 上下文卡与命令适配器

上下文卡只负责显示、选择和提交入口；实际写入分别交给 Markdown 文件 Owner、Flow canonical commands、Native layer commands、Component/Runtime 正式接口。卡片不直接写 Store，不直接写工程文件。

卡片分三层：

1. 当前对象名称、范围提示、AI 输入和关闭/保留选区；
2. 当前对象已有的高频人工操作；
3. `更多` 进入现有专业属性面板或源文模式。

AI 输入保持通用，例如“请修改这里”“把它替换成我下面提供的内容”“检查并修复这段内容”。产品只负责把当前对象、选区、版本和必要上下文交给 Agent，不替用户预判任务类型，也不要求教师从固定动作菜单中选择。

浮动定位必须处理滚动、窗口边缘、缩放、输入法组合、工具条点击不丢选区和只读/冲突状态。

## 3. 分阶段交付

### 1.9.1：选区目标与源文映射基础

**目标：**先让 Markdown、Flow 和聊天都理解同一个可冻结编辑目标，不改变主要视觉布局。

**工作范围：**

- 文件 Markdown 编辑器向外发布排版选区、源文选区和对象选区；
- 复用现有 `DocumentSelection`、Flow block/textRange 和聊天 freezeTarget；
- 建立 Markdown 逻辑范围到源文范围的 source map 与歧义诊断；
- 统一 revision、文件 contentVersion、工程 revision、session token 的失效规则；
- 为段落、标题、列表项、表格单元格、公式和链接建立目标快照；
- 不显示新的浮动卡，不改变现有工具条位置。

**退出条件：**

- 选区能准确读出对象、slot、范围和基准版本；
- 选区变化、文件重载、Flow revision 变化和 AI 停止都会使旧目标失效；
- 中文输入法、公式原子、表格选区和源文诊断不丢失；
- 只读检查和针对性逻辑测试通过，未发生任何工程写入。

### 1.9.2：Markdown 人工上下文编辑

**目标：**先让人工编辑完整走通“选中即出现段落卡”，再接 AI。

**工作范围：**

- 排版视图选中正文后显示段落上下文卡；标题、列表、表格、公式和媒体显示对应语义卡；
- 接入现有格式、段落类型、链接、公式、列表和撤销/重做命令；
- 源文模式显示源文范围工具入口，保留 CodeMirror 的完整编辑能力；
- 卡片操作提交为一次正确的文件编辑历史或 Flow 工程历史；
- 保留现有“正文格式”工具条作为高级/兜底入口；
- 键盘焦点、屏幕阅读器、滚动和窗口边缘定位一起实现。

**退出条件：**

- Markdown 选段、格式化、保存、关闭、重开和撤销/重做连续成立；
- 选择卡片内操作时选区不漂移，切换源文/排版不产生额外历史；
- 公式、链接、列表、表格和资源引用没有被误改；
- 视觉验收确认卡片不遮挡正文、不遮挡公式表单、不制造第二编辑入口冲突。

### 1.9.3：Markdown 人机共编与聊天共用目标

**目标：**卡片 AI 输入和聊天框都能精确修改当前选区。

**工作范围：**

- `DocumentAiTaskController` 接收冻结的逻辑目标和允许源文范围，不再默认把全文作为唯一目标；
- AI 只返回当前目标内的候选，宿主计算和校验精确 edit range；
- 卡片内 AI 与聊天框共用准备、候选、预览、接受、撤回、冲突、Stop 和 stale 处理；
- 无选区时仍可显式选择“修改整份文档”，不悄悄扩大范围；
- AI 修改产生一条独立历史记录，人工后续修改可选择性撤回 AI 结果；
- 目标失效、外部文件修改或教师同时编辑时零工程写入并显示下一步动作。

**退出条件：**

- 同一选区从卡片和聊天发起时，目标、基准和提交结果一致；
- 修改加粗文字、链接文字、公式、列表项和表格单元格不会破坏 Markdown 结构；
- AI 候选可预览、接受、拒绝、撤回，保存重开后结果一致；
- 至少一条真实文件 AI 链和一条确定性冲突/过期链通过；真实模型按既有 Luna/Claude-DeepSeek 授权矩阵执行。

### 1.9.4：Flow 原生上下文编辑对齐

**目标：**把同一套选区卡交互接入 Flow 正文，形成 Markdown 与原生正文的一致编辑习惯。

**工作范围：**

- Flow paragraph、heading、list item、table cell 和公式复用上下文卡壳层；
- 通过 Flow canonical command 提交，保留唯一工程 History、保存、Player、HTML 和 DOCX 语义；
- Flow 的对象选区显示对象卡，媒体、图表、Component 和 Runtime 保持各自正式编辑入口；
- 聊天冻结目标继续使用现有工程 target，不新增一套 Flow AI 写入 API；
- 统一选区变化后的卡片位置、焦点、撤销和错误反馈。

**退出条件：**

- 同一套高频编辑路径在 Markdown 文件和 Flow 正文中可学习、可操作；
- Flow 编辑后保存重开、当前位置试运行、整课预览、Player 和适用导出一致；
- AI 不可用时人工编辑路径完整可用；
- 不出现第二工程对象、第二 History 或把 paragraph 误做成 z-order 图层。

### 2.0：软件内生产闭环与全范围验收

**目标：**把上下文编辑作为 `r20-020-public-authoring` 的轻量通用 Agent 入口，并与现有 2.0 DAG 汇合。

**工作范围：**

- 020：材料、Markdown、Flow/Native/Component/Runtime 的生成、局部编辑、QA、修复、保存重开和导出都能在软件内完成；Agent 通过用户指令完成任务，不新增一套固定 AI 功能菜单；
- 021：内置 Skill 和质量参考能够消费当前上下文目标，不能把选区外内容误作为修改范围；具体工作由用户指令决定；
- 022：卡片和聊天明确显示发送给外部 CLI 的实际材料、文档和选区范围；
- 025：对照三 CLI/有限插件工作流，确认 GUI 没有削弱原生能力和成品质量；
- 030：完成键盘、读屏、错误恢复、帮助文档和上下文卡状态反馈；
- 040：对三 CLI 做有限真实矩阵，分别报告卡片编辑、聊天编辑、首次失败和修复后结果；
- 041：PPTX 在已支持的可编辑文本/对象上使用相同上下文原则，未支持对象明确提示；
- 050/060：Owner S4 验收并冻结源码与离线 HTML 身份。

**2.0 退出条件：**

- Markdown 排版/源文、Flow 正文和已承诺 Native 编辑入口均能从当前选区进入正确上下文工具；
- 卡片 AI 与聊天 AI 使用同一冻结目标和提交结果；
- 选区、人工修改、AI 修改、冲突、撤回、保存、重开、Player、预览和导出没有未关闭的核心数据错误；
- 三 CLI、PPTX、键盘/读屏、速度与成品质量证据满足既有 2.0 DAG；
- Owner 完成 S4 后才创建无后缀 `v2.0.0`，不以 UI 工程检查代替实际验收。

## 4. 依赖与暂停规则

- 1.9.1 必须先使用当前 1.9.0-rc.1 源码基线核对，不重做已经通过的正文合同和文件保存能力。
- 1.9.2 不依赖真实模型，可先用确定性编辑和零模型 UI 验收。
- 1.9.3 依赖 1.9.1 的 source map 和 1.9.2 的人工目标卡；不能用全文 AI 路径冒充选区 AI。
- 1.9.4 依赖 Flow canonical command、唯一工程 History 和现有保存/Player/导出门；不能为卡片新建旁路 writer。
- 2.0 只承接已闭合的 1.9.1–1.9.4 接口；性能优化按真实瓶颈进入 020，不新建缓存、调度或模型平台。
- 任一阶段发现源文映射无法可靠证明，就保留当前稿并缩小支持边界，不通过全文替换掩盖问题。

## 5. 推荐顺序

推荐按 `1.9.1 → 1.9.2 → 1.9.3 → 1.9.4 → 2.0` 执行。1.9.1–1.9.3 先完成 Markdown，因为它能最早验证“选区是编辑目标、卡片和聊天共用目标”的核心假设；1.9.4 再接 Flow，避免同时在文件 Owner、工程 Owner 和三种 Surface 上改动造成定位困难。

这条路线适合 2.0，但 2.0 的承诺应是“统一轻量上下文编辑框架并完成 Markdown + Flow 生产闭环”。Slide、Spatial、Component、Runtime 的完整对齐保留其语义差异，按实际能力逐项接入，不承诺在一个批次内都变成同一种 paragraph 卡，也不把固定 AI 功能菜单列为交付目标。
