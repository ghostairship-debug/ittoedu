# 果铃创作链路与内容承载：根因修复执行方案

2026-10-20｜原实施规格；本轮执行结果及未通过项见 [IMPLEMENTATION_RESULT.md](IMPLEMENTATION_RESULT.md)｜调查基线与证据见 README、EVIDENCE。

## 0. 本轮范围与交付定义

用户目标是可持续人机共编的通用互动内容创作工作台。修复必须减少模型承担的机械职责、保留表达自由，并让主任务在不依赖失败项的范围内持续推进。本轮交付软件修复与必要验证；下一轮另做高质量参考作品。不能把优质参考当软件缺口的补丁，也不能为了等待参考库而暂停已明确的软件修复。

本次“完成”指：本方案必做工作包的真实消费者验收通过、未通过项明确列出、接口和分发同步、原有数据与有效成果保全。测试通过不等于模型创作效率、参考质量或用户整体接受已通过。本方案没有启动完整创作、重新跑 YOU & ME 性能比较、发行或迁移真实数据的授权。

已有有效成果应保留：正式多页/全局导航、UI 资源有效字节快照、观察宿主 20 秒故障出口、任务容量设置、既有资源解析/短 URL/离线音频路径、Source 与内部文本编辑、正式保存与导出。先验证新增缺口，不把这些全部推倒重建。

## 1. 根因收敛与方案选择

### 1.1 三类不同问题，共用一条设计原则

**生产端契约不合适。** `ContentApplyResult` 混合恢复输入、完整变更值和操作结果；公开工具沿内部结果展开。批量结果多次携带同一事务，程序化回读又能拿回完整大对象。最终模型出口投影有效，但容易被新字段、错误路径和新入口绕过。

**作者输入的边界过粗。** 模型用完整 HTML + 公共脚本包装正文。软件为保护任意脚本正确性，把输入整体保留成程序；普通修改维持既有程序身份。正式页与导航修好后，正文粒度仍没有改变。

**运行事实被压扁。** 动作已应用与观察失败混为 unknown；执行实例已结束与历史验收缺口混为未完成；外框合法与内部内容可用混为布局正常。消费者于是重做不必要的工作、阻塞无关任务，或漏掉真正问题。

共同原则：**每个现有 owner 交出对下一步足够、准确、可操作的事实；完整内容按引用访问；不可替代的软件约束在软件中执行。** 统一契约和职责，不集中成一个巨型 owner。

### 1.2 本次明确采用的技术路线

| 议题 | 采用 | 不采用 |
|---|---|---|
| 大回执 | 从公开写工具生产端形成最小充分回执；内部事务独立保留；模型出口兜底 | 先生成巨型公开回执，再到处加字段黑名单或压缩模型 |
| 大查询 | 精确来源、选择字段/范围、默认有界；软件内部可完整读取；最终序列化预算 | 为修复超窗而删除完整读取能力、把一切强行切成很小页 |
| 取消/超时 | 纯读等待独立结束；写操作保原身份和真实结果；不相关工作继续 | 全局增大超时、超时即重试全部操作、把 unknown 追认成功 |
| 内容粒度 | 新创作直接表达普通内容与局部程序；现有 operations/iframe/Source/enhance 组合 | 对任意 JS 做通用依赖逆向拆解，或禁止合法整页程序 |
| 空间 | 真实局部视口 + 有明确策略的局部自排版 + 运行时事实诊断 | 全页自动求解器、私自移动人工对象、隐藏滚动条、统一缩字号 |
| 状态承接 | 复用现有 courseState / bindings / scope.state，明确生产与消费含义 | 新建状态平台、让下一页静默恢复预置答案 |
| 防回退 | 生产者—消费者级反例与薄架构约束，替换旧错误断言 | 添加大量强制文档/审批/全矩阵检验门 |

### 1.3 最小充分回执的含义

它不是一个 `ok`，也不意味着删除一切技术身份。保留影响下一步的提交状态、操作身份、版本、实际目标、必要规范化结果、诊断与精确引用。图片/音频、完整源码、重复输入、全事务变更值留在相应内容/记录 owner。按实际字节与 token 预算输出；字节数和字符数不能混称 token。

## 3. A1：在生产端生成最小充分公开回执

### 3.1 当前定位与约束

直接定位：

- `src/core/contentApply/planning/types.ts`：`ContentApplyPlan`、`ContentApplyResult`。
- `src/main/workbench/contentApply/applyService.ts:507–530`：完整 `input` 与 dispatch receipt 返回。
- `src/core/tools/DocumentToolGateway.ts:350–423`：批量计划/正式提交。
- `src/core/projectFiles/componentPlatform/coordinator.ts:551–628,633–687`：`contentReceipt` 和批量公开结果。
- 同文件 `972–1029`：错误路径可能回传原始输入。
- `src/core/tools/modelToolResult.ts`：目前依字段裁掉 source/changes.value。
- `src/main/workbench/external/ExternalMcpService.ts:444–463`、`ExecutionEngine.ts:2701`：不同消费者的公开交付。

内部 DocumentSession/历史/恢复仍可能需要完整结果。本次不删 `appliedChanges` 的内部用途，不让 UI、撤销、CAS 或恢复依赖公开精简回执反推原件。

### 3.2 具体施工

**A1-1 先映射消费者，再分离类型。** 搜索 `ContentApplyResult`、`.input`、`.receipt.appliedChanges`、`operationFact`、`contentApplyFact`、`reconciledToolResult` 的所有消费者。内部计划/恢复/ACK 保留原结构或明确命名为 internal result；公开工具由一个显式 builder 构造 PublicWriteReceipt。尽量沿既有 `ToolResult` 判别层演进，不增加重复 runtime envelope。

同一操作只在既有操作/运行记录 owner 中保存一份必要载荷。由该 owner 提供稳定记录引用；引用受 run/文档/授权范围约束。不要新建一个影子工程、第二日志数据库或第二事务事实来源。

**A1-2 成功与失败都显式选字段。** 在 `coordinator.contentReceipt` 等对外生产位置构造结果，禁止 `{...internalResult}` 作为公开输出。保留现有 path/frame/viewport 与规范化事实；普通成功不回显输入，失败也不回显全部错误输入。错误只给 code、局部位置、期望形状、有界片段及原件引用。

短入口源码确有后续使用价值时，可作为“小型软件生成结果”返回，例如软件生成的主 Source 包装入口。设置总预算，明确 `preview` 与 `complete`，不把任何 source 文件自动视为短文件。已写入完整 source 不应再次全文返回；内容不变的输入也不必回显。

**A1-3 批次只带一次共同事务事实。** 顶层保留整批正式 commit/revision；每项保留 operationIndex、实际 path/targets、局部诊断、参与提交与可用状态。子项不要再嵌完整批次 receipt，不要把顶层总体状态不加区分复制给准备失败项。保留现行批量原子性/局部准备语义，先在测试锁定，不能顺便改变“哪些成功项会提交”。

**A1-4 处理 ACK 和已读基线。** `coordinator.acknowledge/remember` 是并发正确性的组成部分，不能因回执变短就移除。模型自己刚提交的内容，可以继续作为已知 ACK 事实；软件生成但未实际交付的正文不能标成模型已读；后续人类修改也不能因路径被列出就变成已读。公开 metadata 给出 committedRevision/currentRevision、必要 staleSnapshot，以及按路径精确刷新能力。

局部 `edits.old` 的可编辑基线规则继续成立。完整输入留软件不意味着模型自动看过所有内部数据，也不能以精简回执为借口迫使每次成功后整文档重读。

**A1-5 所有写入口汇合。** 至少检查 project.apply 单项/批量/建页首稿/enhance、普通 object.update/batch、媒体与 image.application、保存/导出及 operation lookup。能够统一的事实由同一 builder 产生；各业务只补自己的结果字段，不重造另一套通用状态。

内置主模型、原生子模型、PTC `tools.call` 和外部 MCP 的写结果共享此契约。PTC 写调用默认也只拿回执；程序确需内容时另行查询。读调用在软件内部可完整消费，不因此向主模型打印全文。

**A1-6 迁移事实解释器。** `modelToolResult` 内针对 ContentApplyResult 的特定形状识别依赖 input；`contentApplyFact` 本身不要求 input，但与其他事实解释器仍依赖当前 commit/receipt 等嵌套结构。类型调整时同时更新 `operationFact/committedFact/serviceToolOutcome/reconciledToolResult`、执行结算、UI 时间线与外部客户端结果判断。由工具注册名和真实宿主执行记录确认“写事实”，禁止从用户/模型自编 JSON 中因为出现 commit 字段就推定真实提交。

**A1-7 退役重复删减。** 新写回执在生产端已足够小后，`modelToolResult` 不再为每个写方法层层重复展开/删字段。保留旧运行记录读取所需的兼容投影与后备保护；旧记录不可批量改写成新回执，历史格式支持只放在读取边界。MCP 规范要求或客户端兼容所需的 text/structuredContent 双表示不擅自移除；先让二者引用同一小公开结果。

### 3.3 公开回执语义草案（拟议，非现有 API）

```ts
// 沿已有 ToolResult/commit/usability 语义落地，不把此草案复制成平行状态系统。
{
  operationId, documentId, beforeRevision, revision,
  commit, usability, delivery,
  targets: [{ path, instanceId?, frame?, viewport? }],
  changed: { count, fields? },
  diagnostics: { items, total, next? },
  detailRef?,       // 原操作记录，不是第二份原件
  resultRefs?,      // 生成内容或规范化差异的实际来源
  currentRevision?, staleSnapshot?
}
```

必要字段随工具语义选择，不强制所有写操作返回空数组和未使用字段。大批次的 targets/diagnostics 也应支持按需展开，保留总数和未展示的错误严重性统计。禁止截断后让模型误以为“全部成功”。

### 3.4 完成条件

同样四项修改，音频或 source 体积从 KB 增至 MB 时，**公开写回执不随源码体积线性增长**。批次项数增长允许 O(n) 必要事实，禁止每项附整批造成 O(n²)。恢复、撤销、CAS、未知操作查证、Source 接续均保持。详见验收 A。

## 4. A2：查询有界、最终交付有界，但保留完整数据能力

### 4.1 不只修 programmatic.read

覆盖 `programmatic.read` 的对象/数组/字符串与 error.data，`project.read` 的 full/默认页，job.status detail=diagnostic、job.logs、context.read、task.note 原来源、delegate 结果，以及 Engine 将工具结果插入 user 消息的续接/查证路径。常规工作记录中的长 summary、artifacts 或错误详情不能成为下一条逃逸通道。

具体入口：`ProgrammaticToolRunner.ts:133–188`；`HostToolServices.ts:501–524`；`ExecutionContextProjection.ts:87–167`；`ExecutionEngine.ts:727,2497,2701–2702,3021`；`ExecutionDesktopService.ts:1257`；`ExternalMcpService.ts:444–463`。这些是调查入口，是否有该字段的真实大输入要逐项标识，不把所有候选风险都说成已发生故障。

### 4.2 查询契约与容量

默认查询应返回足以定位的内容。字符串/数组按现有 offset/limit 扩充安全默认；对象先取所选字段或目录/键概览，明确剩余来源。复用 context/read/journal 的现有身份，不让业务模型手写新 UUID。数组单个元素很大时仍要递归选择字段或以引用承载，不能仅限制元素个数。

保留完整文件/源码读取功能：程序、编辑器、导出和局部计算可以通过已有授权文件/记录接口完整读取；面向模型的 full 表示请求完整内容，超本轮容量时自动返回明确分页/引用，不伪造“已经完整读取”。禁止提供一个能绕过最终消息预算的 model-visible `raw=true`。

默认文本页建议以当前约 8K 字符投影规模为兼容起点，实施时改为统一配置与实际 token/字节预算；不要在十个工具里分别硬编码 8000。大窗口且确需全文时可在预算内多返回，避免机械小页导致往返暴增。新增预算是交付约束，不是文档最大规模。

分页必须绑定不可变来源：run/call/path 或 document/epoch/revision + 字段范围。下一页不能在文件变化后悄悄读取新版本。当前 `project.read` 已有固定来源分页与 staleSnapshot，复用它，不另造游标层。

### 4.3 最终模型请求出口

在 provider 消息序列化前实施共同交付投影。按完整消息（包含 JSON 转义、文本+图片、工具定义、协议包、必要输出预留）计预算。保留 call id、调用参数事实与 response 配对，最新工具轮也不享受内容容量豁免。

保护原生协议，不改写签名思考块/加密项/调用参数来假装实际调用更小。主工具返回内容可在初次交给 provider 前用可信小结果/引用表示；旧原生历史需要按协议允许的完整轮退休/原生压缩处理。Chat Completions、Responses、Anthropic 的序列化分别测试，不只测统一中间 message.content。

**特别处理最新不可缩工具输入。** 历史大回执来自 PTC 子调用参数，未必直接等于主模型生成了同规模输入。但模型也可能真的发出超大源码参数。优先通过 from/已有成果来源避免搬运；若最新不可更改调用参数本身超过支持窗口，不篡改历史、不重复执行。保存真实调用和结果，在支持协议内建立新的恢复上下文并引用旧事实；协议不支持时一次明确返回可恢复阻断及来源。不能继续发同一超限请求直到耗尽额度。

同一响应里错误、部分结果和观察缺口需要优先保留；其余内容可展开。内容未展示必须明确，不能用“成功摘要”替代真实诊断。原始读结果仍保存在原 owner 中。

### 4.4 非阻塞与工具能力保持

tool family 按任务自主展开的方向不变，相关授权内能力可充分暴露。不要把压缩问题误解为必须极小工具集、永久隐藏核心工具或全面降低并发。写工具本身变小，才是第一层节省；仅在请求预算接近边界时做必要上下文整理。

任务状态查询只返回事实与结果来源，诊断详细模式可增加信息，但不返回整个 provider ledger。等待长媒体/子任务继续使用现 job 身份，不把根模型挂在无期限 wait 内；相关执行见 B。

## 5. B：动作、取证、取消和历史结算分别负责

### 5.1 动作事实分离

当前 `HtmlActionService.action` 在收到 `applied=true` 后继续观察，观察失败仍可能统一变为 action-outcome-unknown。`value-mismatch` 虽已单独处理，代码用 `actionMayHaveApplied=false` 控制分支，命名与真实已发事件含义不一致，后续容易回退。

在原 action receipt 中区分四个事实，字段名按现有类型落实：

| 事实 | 可取状态/含义 |
|---|---|
| dispatch | 未派发 / 已派发 |
| application | 确认应用 / 确认未应用 / 未知 |
| goal | 达到目标 / 已测不匹配 / 未验证 |
| observation | 完整 / 部分 / 失败 / 尚未请求 |

这些事实组成一份原操作回执，不另建状态机服务。行为接口可以继续抛错误，但错误携带已确认事实；调用者不能只靠 Error.code 将四个维度压成一个 unknown。事实一经确认不因截图失败而倒退。

施工顺序：先修改 `HtmlActionService.ts:414–464` 保留实际 ACK；接着修改 ViewActionTools、观察模型投影、工具事实解释器和 executionOutcome/settlement。对已确认应用的点击，只允许再次观察，不允许因取证失败自动重放。输入值未保留时承认已发生输入事件，按当前值决定新的纠正动作，不伪称最初从未派发。

`navigate` 也有“动作后观察”的同类路径，逐一核查；media应用后预览、保存后打开、导出后读取等也按同一原则检查。只修真实混淆，不能为所有工具强塞相同四字段。

### 5.2 纯读等待能独立结束

`ProgrammaticToolRunner` 最后的 `Promise.allSettled(pending)` 和 `ReadOnlyToolScheduler` 的 `Promise.all(started)` 都依赖底层返回。已有探针证明：一个纯读不返回时，取消不会立即让调用完成；第二个读已经完成也没有对外结算。本次没有证明真实 UI Stop 永远失效，也没有证明“取消后归档既有结果”属于错误。

在现有 Runner/Scheduler 引入一个共用的小型等待原语，负责：局部 deadline、AbortSignal、执行代际、迟到结果处理、监听器/计时器清理。优先复用仓库已有类似 waitForRun/waitForSourceValue 机制，避免各处再写一个风格不同的 Promise.race。

- **安全纯读**：取消或局部读取期限到达，当前等待进入 cancelled/timed_out，允许本轮及时结算；晚到结果可归档诊断，不可覆盖后续运行的上下文/句柄/完成状态。
- **可能产生副作用的调用**：不照搬纯读语义。明确未派发可取消；已派发仍保未知事实/原 operationId，等待真实查证或执行器收尾。不得简单释放状态后重复派发。
- **作业**：长时生成沿 job id 运行，wait 的局部期限仅结束等待，不代表作业失败。根任务可推进无依赖部分。同一作业不得因等不到而重开新收费任务。
- **资源容量**：逻辑等待取消不等于底层工作已经结束。原生任务配额/进程容量不得提前释放后无限超卖；底层已终止或隔离退出后再释放相应实体资源。任务UI和记录如实区分。

不要直接让 Promise.race 丢失原 rejection；为已发 promise 注册收尾并退役 listener。对可能分配读句柄的“纯读”，迟到分配必须绑定原代际并可清理，不能写入新 run。

### 5.3 顺序与非阻塞的折中

保持原生工具轮合法配对与写屏障。可以及时保存已完成独立读的内部结果和 UI 进度，但最终提供给模型的工具回复遵守其协议顺序；慢纯读在局部 deadline/取消后用真实 timeout/cancel 回执填入，不能伪造数据，随后正常交付已经完成的兄弟结果。

后面的写调用不能越过真实数据依赖/授权/未知副作用屏障。工具轮中完全独立任务可由主模型下一轮重新安排；本次不新建通用 DAG 调度平台。用户 Stop 后不应继续新模型请求或未开始工具；归档已发生副作用的真实结果仍然必须完成。

纯读期限复用现配置，不对所有任务设置一个短全局超时。已修复的观察 20 秒故障出口保持，只补未覆盖的等待消费者。

### 5.4 历史尝试、当前工作和验收缺口分开

`ExecutionEngine.settlementRecord` 当前依同文档集合、同工具名和同 JSON 参数的后续成功读取，排除旧未完成纯读。新句柄/新实例导致难匹配。

在现有 task lineage 的派生工作视图里处理：

1. 旧 run 已终止或其观察代际已销毁，旧纯读等待退役，不再当作仍活跃工作。
2. 退役只表示该尝试不会继续，不写成读取成功。
3. 若旧读承担必要验收，保留该验收目的为未验证，或用新的等价观察承接。等价条件取真实文档/epoch/revision/目标/状态/检查目的；没有这些信息不猜成功。
4. 未知修改保留原操作和影响范围；只阻塞依赖该影响的步骤，不能封锁整件作品的所有安全读取或无关修改。
5. 新观察与旧记录以引用关联，不把全部历史工具再次复制进当前工具轮。
6. 保存、导出、运行验收、历史 unknown 分别展示。revision13 已保存并导出，不因旧观察而改成“文件未保存”；`partial` 也不能伪装成全部已验收。

更新 `executionOutcome.ts`、当前工作记录生成及 UI 表达，复用现系统，不增加第二套“完成徽章”强制门。

## 6. C1：让混合内容直接进入合理的编辑与运行边界

### 6.1 本次不做什么

不以 iframe 数量、原生对象数量或“每页至少 N 个组件”验收；不禁止整页游戏、连续仿真和外来应用。普通内容也可以是可编辑 Web 组，连续正文不必拆成每个词。不要删除 script 探测来强制拆分，否则会破坏未知程序。

### 6.2 利用现有入口建立默认路径

已存在的能力包括：普通 HTML/CSS 测量装配、`project.apply.operations` 同批插入多个片段、`surface.add.pages` 带首稿、标准 iframe/srcdoc 局部文档、Source `enhance`、原生对象插入与正式 click 动作。参考 `material-assembly.md` 和 `web-composition-examples.md`，先实测这些组合，不先设计替代 API。

**路线一：外层普通 HTML/CSS + 明确局部文档。** 外层表达普通正文/图像/布局；真正共用状态的互动以同目录 iframe 或 srcdoc 表达。通过现有 `from` 和同组依赖采集一次采用，软件决定正常内容与局部程序的持久载体。主模型不手工登记实例 ID、拷贝 Base64 或生成宿主桥接代码。

### 6.3 小型决定性技术 fixture（本轮可做，非下一轮精品创作）

建立三个小 fixture 即可：

- 纯标题、正文、配图、一个正式 Next。期望无需整页脚本/程序；配图独立可移动，普通文字局改不改其他内容。
- 外层说明和图片 + 一个局部变量模拟。期望外层可独立编辑，局部计算/反馈保持共同状态；嵌入前后实际净视口一致，资源和导航正确。

对这些输入沿实际生产 `project.apply` 进入工程，检查正式结构、当前 Source、编辑、Undo、保存、隔离冷开与 Published/离线代表消费者。静态 classifier 的 `programReason=null` 只证明没触发第一层程序标记，不等于最终装配已经独立，应测到最终模型和运行画面。

### 6.4 分析结果与装配事实

内容采用回执增加或复用一段很短的实际承载信息（拟议语义）：哪些独立根被采用、哪里保源、原因类别是 executable coupling / CSS或form共同关系 / 外来程序 / 已有作者记录 / measurement unavailable。使用真实装配结果生成，不能用模型自述替代。

纯信息性的保源诊断不是创作失败；预期普通内容却因测量失败整体保源时，标成具体可修软件降级，保留原输入和当前可用结果。不能把所有保源都当成功签收，也不能为消除诊断反复删页重建。

给下一轮参考制作的接口说明应明确：哪种输入会触发整份保源、哪个入口支持按当前结构局部修改、哪些程序内部作者能力已验证。只写实际能力。

### 6.5 普通续改不暗中重组，显式重做可以重新装配

现 `content` 路径保留原 html-program 身份是合理的编辑稳定性选择，本次不自动让删 script 的改字操作把对象拆散。

对用户明确授权的页面/容器 `redo`，应按当前源重新装配，保留与新结构有关的资源、导航引用与可确定的作者记录。能沿现有正式事务重做就不新建“迁移工具”。对于无法可靠迁移的原作者记录/脚本耦合，保原程序并返回具体原因，不能丢记录换取“全原生”。

无需普遍为任意大程序提供自动解包功能。应优先确保从新建起就不产生不必要的整页程序，并给现有作品的明确重做路径正确语义。

### 6.6 Skill 与能力披露：替换误导路径，不叠加禁令

## 7. C2：资源回到资源 owner，不由模型把字节塞进源文

### 7.1 已确定事实

历史四项音频修复把约 569 万字符音频 Base64 放入脚本，再被完整回执重复返回。本轮纯函数对照：普通 `<audio src="data:audio/wav;base64,...">` 和同目录 `voice.wav` 都能抽取为 1 个 8044 字节资源、源文 107 字符；`const p=...; audio.src='data:'+'audio/wav;base64,'+p` 保留原 10837 字符，返回 `unsupported-dynamic-url-sink` 警告。

这说明正常资源化能力存在；动态 JS 分析不是万能。不能据此说资源系统完全未实现，也不应为了这一种绕行写一个通用常量折叠/程序求值器。

### 7.2 正常采用与失败恢复

让 image/media/delegate/compute 的可采用成果统一返回当前合法 source 引用；`project.apply.from` 与 media.insert/media.apply 沿既有资源闭包读取字节并登记。模型选择素材、台词、表达目的和使用位置，软件承担路径转义、闭包、身份、MIME、临时 URL 与打包。

实测媒体生成/采用→源码编辑→保存→重新打开→离线播放。遇到播放失败，工具诊断应给精确阶段：资源缺失、绑定未解析、协议/URL 失败、格式解码错误、播放权限或观察未验证。不应鼓励模型“把 WAV 转 Base64 贴进 JS 试试”。必要时在既有媒体修复入口按合法引用重新绑定，避免模型搬运大字节。

`cw-resource:` 是工程引用，不应作为未解析的裸地址交给浏览器；宿主通过现 resource lease/公开资源端口转成当次运行 URL。候选 source 相对依赖来自该候选的授权 root；不能扩到父目录、凭据或绝对任意文件。

### 7.3 同类扫描与保持项

扫描项目公开回执/源码投影/日志/观察结构中的 data/blob URL、Buffer/Uint8Array、fullObservation、source modules 与整个 project snapshot。只在不需要载荷的边界删去；资源存储、图片模型实际输入、导出单文件内嵌资源都属于合法消费者。

已有 `uiDocumentSnapshot` 有效字节修复与 `resourceUrlLease` 必须保持。测试引用同一 backing buffer 的切片、两个场景共享资源、复制对象、资源替换、页面销毁/重挂载、导出后断网。多个用户资产身份即使字节相同也不擅自合并；底层存储/传输可利用现有去重机制，但不能更改作者语义。

已合法内嵌的第三方程序可继续保源；动态资源警告不升级成整作运行失败。精确指出静态分析没覆盖，不冒称已经不能播放。禁止在资源提取过程中执行任意作者 JS。

## 8. D：固定演示空间由软件承担可确定的适配

### 8.1 三个空间层级分别负责

1. 页面/Surface 与正式 frame：由现有 owner 决定。Slide/Spatial 的人工位置与重叠意图保持。
2. 组件局部视口：现有 `ComponentLayoutPort` 提供 free-frame/flow-viewport 的 inlineSize、blockSize，或 flow-content 的 inlineSize；不另建区域状态表。
3. 内容内部排版：浏览器 Grid/Flex/CSS 与一层很薄的声明式适配执行器。仅在明确允许的局部范围计算/选择，不推断教学语义和全页避让。

当前 `measuredFragmentExtent` 有意在 overflow:auto/scroll/hidden/clip 处停止外部扩展，这是外部几何的合理语义。**不能用这个 extent 判断内部不存在溢出**，也不能把它改成无条件扩框，导致所有人工 frame 被内容撑开。新增内部可用性测量应与外部几何分开，复用观察通道输出结果。

### 8.2 首批局部策略：少量语义，不做万能排版系统

选择可持久在现 source/数据中的可选声明，优先用 HTML data 属性 + 受作用域 CSS 变量，避免升级顶层 Schema。下列是本方案拟议语义，字段名在实现开始时一次确定：

```html
<section data-gl-layout="stage" data-gl-variants="wide compact">
  <header data-gl-slot="heading">...</header>
  <div data-gl-slot="body">...</div>
  <div data-gl-slot="feedback">...</div>
  <nav data-gl-slot="actions">...</nav>
  <aside data-gl-scroll="auxiliary">...</aside>
</section>
```

声明表达：此局部适合固定舞台；哪些区域是持续可达的主要操作；哪些内容可以自然换行；哪个辅助区域允许滚动；作者提供哪些布局变体、间距上下限、字体下限。`stage` 本身就是运行时在该局部执行这些策略的许可；不需要每次运行额外征求确认。不声明的外来内容继续正常接入。

不通过标签猜测某段可以删除、某个活动应该拆成两页，也不把所有 button 推断为主要操作。普通静态文字/原生对象仍使用现插入与布局，不为了适配强制搬进一个整页 HTML。

当布局组本身需要保留 CSS 关系，可作为可编辑 Web 语义组，内部文本/图片继续走既有作者定位；独立外围内容保独立对象。只有需要整体执行脚本的范围才是程序岛。避免把“新增 layout host”变成另一个正文大程序。

**声明必须穿过装配链。** 在 C1 的实际 fixture 中确认声明的持久位置、局部作用域及挂载路径；若测量拆分已把相关属性/布局关系丢掉，不能只在独立浏览器中验证后宣布接通。优先在确有共同布局关系的最小现有 Web 语义组中保留声明，外围独立对象保持独立。软件适配 helper 在宿主运行/编译投影阶段接入，不作为作者 script 写回源文再触发“整个文档含脚本”的保源分类。禁止为了保留一个布局声明，把整页又降成一个程序。

### 8.3 执行器的实际工作

沿现 Web/runtime shared helper 挂载，读取 `context.layout` 或该组件的实际局部 content box。统一扣除 padding/border；明确 CSS px 与页面变换后的屏幕像素区别，不重复减外框/缩放。无需模型计算 1280×720 减标题导航后剩多少。

先让浏览器采用作者基础 CSS，例如 auto / minmax(0,1fr) / auto 的纵向分配与必要 `min-width/min-height:0`。再测量：当前可见内容的 scroll/client 尺寸、关键元素被哪些祖先裁切、主要操作是否完整可见、文字最小字号、允许滚动区是否仍可操作。`scrollHeight` 单独不是充分验收：hidden 裁切、横向溢出、遮挡及不可达焦点也需在代表案例检查。

在已声明范围内有限尝试：选择作者提供的另一布局变体、调整合法间距/内边距、让反馈换行、改变允许伸缩图片区域的大小；不改变正文内容，不调低字号到约定底线以下，不裁掉主要操作。复杂图示和程序内部坐标不能被软件盲改。

选择变体与间距是软件执行；需要删内容、改变表达顺序、分步揭示或拆活动时给出精确失败事实交给模型/人决定。可选参考区只有在作者允许折叠时才折叠，不能为验收私自隐藏文本。

### 8.4 动态测量与生命周期

在 mount/布局输入变化/字体与图片就绪/局部反馈状态改变时更新。复用 `ResizeObserver` 与已有状态、资源事件；只观察该组件，合并同一帧通知。单靠 ResizeObserver 不保证发现固定尺寸容器内部所有内容变化，可对声明的反馈/内容区域采用受限 MutationObserver 或现运行更新事件；禁止全工程无差别监听。

避免读写循环：先读全部尺寸，再写策略，下一帧复测；有限变体尝试，记录已试组合；无输入变化不持续重试。变化中的动画不无限阻塞主任务；报告当前可观察状态，不能宣称穷尽未来动态状态。

运行时选择和测量是派生值，不写 History/dirty。人工指定外框、锁定几何或相关样式覆盖具有优先级；不能因为最初由 AI 创建，就永远允许自动改动。当前局部策略与显式人工覆盖冲突时保人工结果并诊断。保存策略/作者修复沿唯一 canonical transaction；撤销、复制、保存冷开、Published 与导出消费同一语义。

冻结运行代际：旧挂载的 observer、异步字体/资源回调在销毁后不得再写新组件。复用 scope.cleanup 和布局 port 的代际保护。

### 8.5 诊断与回执

优先沿现观察/内容诊断结构扩充；仅在现状确实无法携带时添加小型可选字段。应包含：对象/容器身份、实际视口与 content box、当前状态或 generation、超出方向/量、受影响主要操作、已尝试策略、是否需要语义决策。大 DOM/截图不混进写回执，图像单独走现图片通道。

静态插入测量不执行作者脚本；不能为了提前验收打开任意 JS 的 Main 权限。程序运行态诊断在既有隔离预览/Published 会话内产生。底层失败时保可用内容及原输入，返回未验证，不用整作拒收换取干净状态。

### 8.6 验收试点和边界

先在冻结作品副本选第 08 页和一个有长反馈/辅助原文展开的活动，引入局部声明并验证软件执行策略；再用纯技术混合 fixture 验证新建默认路径。不要一开始改 13 页来手工调到看似正常。

正式验收视口从作品 1280×720 开始，局部使用实际 1040×570/590；加一次合理窄视口/缩放作为边界，不机械跑全屏幕尺寸。对于内容本来允许滚动的 Flow、目录、完整原文，接受合理滚动。固定舞台的关键动作在初始及代表最长反馈状态应可见可达；可读性底线按作品/任务声明，不能把 24px 设置成所有作品的全局硬门。

所有内容不可能都在所有尺寸一屏呈现。合法失败是软件明确报告已穷尽授权机械适配、指出语义取舍所需位置；非法“通过”是隐藏溢出、全局缩字、扩大对象压住邻居。

## 9. E：跨活动结果与可编辑业务事实

### 9.1 修复目标与范围

本次已知内容断点：冻结第09页采访记录仅存在页内 drafts；完成动作只 scene.next；第10页另用 Sam/12/the UK 等默认资料，未显式消费前一步记录。第07页已公开 Mia 的资料，使第09页 B 角色“首次获取未知信息”的设定减弱。这是创作内容问题与已有状态能力使用不足，不构成新建教学引擎的理由。

本轮只在隔离副本/技术 fixture 中证明真实成果交接路径，建立可复用的调用方式；原作与正式高质量再创作留下一轮。不把修正一个活动题材升级成产品通用规则。

### 9.2 复用现有状态

`ComponentRuntimeScope.state` 支持 JsonValue；`stateBindings` 是已声明标量 courseState key 的别名，二者不要混用。结构化采访记录用 scope.state 已有 JSON 能力或可表达的现有数据绑定；确需标量字段共编时用当前 bindings。不要为了记录一个对象私自把 stateBindings 类型改成通用数据库。

最少交接语义是：当前角色/对象、用户实际输入、核对状态、必要的来源/题目身份。预置角色数据和用户作答分开；前页未核对不能在后页静默变成标准答案。介绍页按活动目标展示真实笔记或明确带入字段，不强制替学生完成整理过程。

记录提交和导航顺序由现业务/绑定沿宿主状态完成，后页在首值与订阅上都能读取；不得只订阅变化而漏掉初值。参考现 enhance 的 observe/bindings.observe 能力。完整句与短字段之间若有转换，明确定义且保留原输入，防止拼出“He is He is twelve”。

复制行为区分：同一课的共享配置沿既有复制语义；独立活动尝试不应意外复用上一次学生答案；课程运行 reset 清理用户运行值但不清空作者预置内容。按现 run scope 与复制映射实现，不新增全局尝试ID台账。不要从名字推断性别代词。

### 9.3 局部内容修改与业务逻辑

选一个现有活动，在副本中改人物/题目或选项，通过现语义数据/Source 路径确认判定与反馈同步。此前报告所列“DOM文字与脚本答案重复”尚属风险，必须先复现具体编辑路径再修。

对新创作，建议题目/人物数据一处定义，显示与判定共同消费；简单显示装饰沿 authoring overrides 修改无需引入业务关系。对任意外来代码，不能承诺改一段可见文字就能自动修改未知算法；软件明确编辑范围与真实结果，不扫描 JS 字符串强行替换。

### 9.4 父子任务交接

主任务对真正相依的场景，交代进入信息、本场结果、下一场消费、实际区域和关键状态。软件提供冻结目标、source/素材引用、实际采用路径；不能让父任务反复转抄整课、替换 Base64、接线 UUID。

独立素材任务无需人为添加输入输出业务契约；无需固定内容→视觉→素材→代码四轮串行。媒体与内容可以并行，最终采用按实际依赖汇合。

## 10. F：同类风险核查、集成与防回退

### 10.1 两个已定位条件风险先做短反例

**诊断严重性。** `buildSingleHtml.ts:8,18` 把 report 统一写为“课件加载失败”；`compiledPlayer.ts` 又会 report 制品诊断。先用含一个非致命 warning 的合法制品测试导出结果。若确实误报，保持 report/error 的类型化严重性，只有真实致命初始化/资源主路径失败才进入加载失败；不得删除全部 warning。

**初始化和 dispose 清理。** `compiledPlayer.ts:54–71` 创建资源租约后仍有可能初始化抛错；dispose 中若前一步失败，后续资源释放可能跳过。用注入的 factory throw 与 dispose reject 验证具体泄漏。修复采用原生命周期 finally/逐项 best-effort 清理，保留首个关键错误；不得引入独立资源管理平台。

这两项在原成品未观察到触发，报告必须保持“源码条件风险/新反例是否复现”的区别。短反例未触发或代码已修时，不扩面。

### 10.2 直接同类问题扫描的止损边界

扫描的是同一类生产者—消费者关系，清单如下：

- 回执：成功/失败/部分提交/查证/历史读取，正常输出与嵌套 output，read 的对象/数组/字符串，job detail/log，内部与外部协议。
- 等待：观察 read/select/capture、动作后观察、纯读轮、PTC pending、job wait、运行续接；保已有请求身份与已修的 deadline。
- 内容：外层脚本、事件属性、纯 JSON、form/CSS 状态、嵌套 iframe、持久作者记录、测量失败；避免把保真策略统一变成禁止拆分或统一强制拆分。
- 空间：横/纵溢出、hidden/clip、辅助滚动、动态反馈、字体/图片迟到、人工外框和手动覆盖、Flow与固定舞台差别。
- 资源：正常引用/动态字符串、复制/替换/重新挂载、有效字节视图、离线资源与运行租约。

只把实际发现且影响本目标的近邻问题纳入；其他记入“未验证/后续”，不重启全库审计。新发现可在对应包修复，但需要在最终记录中说明证据和是否改变接口；不把所有静态搜索命中都定成 bug。

### 10.3 防回退应该落实在哪儿

公开回执的明确类型与 builder 通过测试限制内部重对象泄出。避免遍历任意 JSON 删除名叫 html/value 的字段：该名字也可能是用户真实数据。

核心测试以实际消费者收到的内容验收：Wire/MCP/PTC/当前工具轮与运行结算、正式工程结构与真实 DOM、保存冷开与导出。不能只给某个 helper 写一条“返回了对象”就结束。

工具分发同步由既有 `generate:ai-capabilities`、`generate:component-sources` 及安装/分发脚本负责；实施时根据本批实际改动选择。根 skill、bundled skills 与 artifacts 一致；未实现能力不能提前写进生产 skill。

轻量架构约束：公开写回执不引用 internal request/full transaction 类型；记录原件只在既有 owner 持有；运行时布局派生不调用正式 writer；已确认动作不被观察错误改写成未执行。能用类型/单元测试表达就不再写成长篇工作流程。

### 10.4 验证与交付顺序

1. 在改动前用新反例显示当前缺口；已有可复用探针不反复生成。
2. 每包完成后跑对应 focused tests，包括新增反例及直接相邻旧回归。允许测试分组，仅主集成者修改公共测试命令。
3. 相关 TypeScript 工程类型检查；改到 Player/Renderer/Main 才做必要构建。不要用测试直接读取未构建新源码替代实际导出消费者；也不要每改一文件重建全部产品。
4. 在隔离 profile 中，用一个小型混合工程完成：新建/采用→普通文字或图片局改→局部互动→动态布局→Undo→另存→新 profile 冷开→一次离线输出运行。复用媒体 fixture，不调用新收费提供方。
5. 回执/取消与历史结算的故障注入在本包测试完成，不为了证明一个故障让真实作者跑整课。
6. 写 `IMPLEMENTATION_RESULT.md`：已做、未做、实测证据、原件保护、剩余真实边界；更新 CURRENT_STATUS/SOFTWARE_AUTHORING_RESULT 的当前条目，保历史失败。不得按“所有测试绿了”推断创作提速或精品质量提升。

### 10.5 应删除或替换的旧机制

- 成功公开回执和错误公开回执中的完整输入展开，批次子项的整批事务重复。
- 已有 Source 全文回显作为默认续编手段；保留必要短入口/精确内容来源。
- 当前工具轮“内容无限大也绝不调整”的假设；保协议配对而非全文特权。
- 用一个 actionMayHaveApplied 布尔变量表达派发、应用、目标与取证全部事实。
- 以新读取参数必须逐字等于旧读取作为唯一历史纯读退役依据。
- 对固定舞台内部适配一概拒绝的软件职责解释。
- 示例/生产包装函数为普通正文无条件附加整页 script 的默认用法。

不是删除原历史记录、未知写屏障、外来程序保源、完整内容访问或人工 frame 保护。
