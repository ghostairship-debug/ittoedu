# 工作协议：结果驱动开发

> 本文是开发执行规则的唯一落点。任务卡格式见 [TASK_CARD_TEMPLATE.md](TASK_CARD_TEMPLATE.md)，当前协调状态见 [TASK_BOARD.md](TASK_BOARD.md)。
>
> 按动作读章节：选题 §1–2，重要结构 §3.1，验证 §4，并发 §5，删除 §6，交付 §7；不要求每次全文读。
>
> 默认目标是用最短的完整闭环交付正确结果。规则只在能防止错误结果、用户数据损坏、并发写坏或虚假完成时增加步骤；下一步若不能改变实现、裁决或结果可信度，就停止。

**Owner 2026-09-30 长期约束：** 不过度设计、不做纯防御性设计、不加非必要核验门，只做最小充分验证。既有门也必须有当前可观察属性和可信失败依据；Hash／字节比较只在身份、完整性或确定性本身是合同属性时使用。导入以能实际承载和使用为准，能用的内容先保真导入、问题再修；软件维护必要包装，不要求 AI 使用固定源文格式或登记标记。局部可修复问题应诊断，不整份拒绝可用内容。详细长期约束见根 [AGENTS.md](../../AGENTS.md)。

## 1. 默认闭环

```text
明确用户行为 -> 定位必要源码与直接消费者 -> 修改 -> 受影响验证 -> 在原位置记录结果
```

开始前只需能说清三件事，不建表、不写流程文档：

1. **结果**：本次要改变或证明的一个可观察行为；
2. **边界**：当前证据指向的单一真相、直接 producer / consumer 和失败位置；
3. **验收**：什么结果算完成，以及最便宜的有效检查是什么。

普通任务默认由主执行者直接实现和自检，不另设纯协调 Root，不为定位、编码、测试或审题固定角色，不要求默认独审。仅两条能力确实独立且交接成本小于并行收益时才并行；必要独审按 §3.1 触发，无有效评审可复用时由一位未参与实施者集中审受影响范围。Root 可写产品代码，但不能独审自己参与实现的重要候选，也不能在真实创作验收中代写作者作品。

用户或 Owner 的明确实现/主动模块化指令本身足以启动，不要求先出现线上故障。没有明确指令时，只有当前可复现失败、真实 consumer、正式合同偏差，或依赖环、wrong-owner 状态、完整 Store 扩散、重复 writer、已批准 lane 冲突等直接证据已经证明架构偏差，才进入实现；历史 Phase、评估标签、未来可能性和“顺便更完整”都不能自行扩成任务。

默认只读当前路线、目标符号、直接调用者 / consumer 和目标测试。只有改动命中第 3 节边界时才补读架构合同相关条目。普通任务不默认通读整个巨石文件；任务本身是模块拆分时，必须完整读取目标接口、composition factory、相关 Owner state/actions、直接 importers 和目标测试，但不扩大到无关仓库区域。

实现应消除已证实的根因并保持单一真相。“根因”包括错误 Owner、依赖方向反转、巨石写锁阻塞和完整 Store 成为跨域公共 API。命中架构合同的模块化触发条件时，应完成真实 owner 迁移，不以局部代理或 re-export 收尾；其他情况只有直接证据表明局部修改会继续留下双写、重复规则或错误 owner 时才扩大范围。不借修复顺便建设平台、迁移体系、兼容层、覆盖率工程或假设性抽象。

<a id="refactor-evidence-and-preserved-behavior"></a>
### 1.1 重构依据与保留行为（Owner 2026-10-05）

涉及结构调整时，在已有任务卡或交接消息内简短说明以下内容，不新建评估表、模块台账或审批文档：

1. **依据与范围**：对应哪项已批准的具体目标，或哪条当前源码、行为、直接 consumer / 合同证据；准备改变哪些职责及其直接调用者。“更清晰”“更统一”“方便以后扩展”、文件过大或名称陈旧不能单独授权额外重构。已批准的具体结构选择可直接引用，不重复论证；整体重构授权不能代替本包范围的依据。
2. **实现选择**：说明复用现有实现、局部修正与职责迁移的取舍，以及所选边界为什么足以解决问题。局部修正若会保留已证实根因、重复规则或双 writer，允许完成必要的结构调整；不以最小 diff 为目标，也不借此扩大到无关模块。
3. **保留行为**：从实际基线源码、既有用例和真实样本确定本包受影响的核心操作及可信失败路径，写入已有 Acceptance；同时指出 Owner 已明确允许改变的行为。基线包含已确认有效的未提交成果，不只看 HEAD。保留的是用户能力、数据与结果，已批准退出的旧格式、旧 owner 或错误行为不作为保留义务。只记录受影响范围，不盘点全产品。

命名整理、保持行为的局部提取及已明确的接口接线继续自主实施，不逐文件请求 Owner 确认。必要性说明不能代替行为验证；重要结构变化按 §3.1 由独立技术 Reviewer 判断。

<a id="core-journey-selection"></a>
### 1.2 长程开发：从用户操作选题

当前核心旅程未通时，实施者先回答：用户从哪个实际入口做什么、当前哪里失败、本包恢复什么结果。以最普通的一次操作确定检查，合同/源码用于找断点；内部算法在最近层验证，GUI体验用实际入口。按能独立成立的能力划分工作，不将同一事务拆成固定捕获、目标、应用、验证角色；必要消费者由原 owner 接通。

反例依据原失败或本次变化的具体损坏方式，能说明操作怎样触发现有机制、会弄错什么结果。“最小”是足以证明失效的输入，不是最奇特或方便断言的输入；分支可构造、敏感关键词和独立T本身不构成选题依据。

新增问题/补证/续验须在原交接说明影响哪条承诺路径或推翻哪项证据；不清楚时只做能改变判断的最便宜定位，仍无关联则记录并返回主线。临时fixture、私有端口、隐藏启动或观测工具失败不自动扩验收；低频真实错写/丢稿/未知重放仍处理。

普通任务由实施者选题、自检；需要独审时在同次评审核对目标操作、实际候选和断言，不逐叶重复审题。并发服务已选结果，允许空闲。充分证据通过即收口，报告能做什么/还卡哪里；扩面时重新选题，不靠数量证明进度，不造固定时长复审或产品时限。明确授权的剩余目标保留，但不抢占未通核心；不洗绿或放宽正确断言。

<a id="shared-business-closure"></a>
### 1.3 共同业务统一与后续开发（Owner 2026-10-08）

当前已证实共同 Gateway/Session 之上仍有入口业务分叉。涉及这些职责的开发，按以下规则消除同根问题；不为无关局部工作另建覆盖门。

- **覆盖从支持用例出发。** 系统收口取当前生产人工用例、正式作者操作/文件 binding、公开工具及服务入口的并集，按语义归并，在现有执行计划记唯一领域 owner 和全部必要消费者；双向核入口归属与消费者覆盖。不从问题清单/工具目录单向推定全集，不临时减少已有能力。版本或相关职责变化才更新这部分映射，不维护第二永久台账。
- **共同决定只能由领域 owner 提供。** 当前稿/目标/状态/资源解析、语义准备及应用/保存事实属于共同用例；UI、MCP、内置 Agent 保留输入捕获、显示/协议、执行循环及合法授权来源差异。一个 writer、同名函数或同注册不足以证明语义统一。
- **新增能力从共同定义进入。** 复用已有 planner 和服务，人工实际命令及工具注册引用同一能力；跨入口目标/业务结果保留必要具体类型。特殊 UI 必须有真实绑定；结果编码穷尽检查配合有限接线核对，不以编译通过或 manual 元数据推定按钮可达。不把任意作者 JSON 全部类型化，也不建万能注册/编排平台。
- **整批迁移并退役旧决定。** 每个领域 owner 同批接通全部直接消费者、退出端内重复业务与错误依赖、关闭同根已知症状。先明确覆盖/小合同，不先造空统一层后长期靠补丁双轨。现有边界/类型检查只按真实退役绕路扩展；不以字符串、文件数或 Hash 证明完成。
- **当前源码按需提供。** 原输入 owner settle/ACK 后取得当前正式状态；对象/页/整作品按请求范围给实际源码、正式结构及必要依赖，分页保持同一捕获基线。已打开的入口和依赖优先当前 Session，未打开内容读盘；不要求先保存来同步上下文。源码/普通文件编辑已有服务继续使用，不通过覆盖 H5 或整课重导绕开正式事务。
- **完成看最终目标和必要交付。** 中途错误保留诊断，当前结果证明恢复后不再决定 partial；可选观察/警告不推翻已提交事实。共同 owner 提供客观应用/资源/保存事实，模型判断内容目标；不增加 ID/目标登记/checklist。未知副作用仍只查原操作，用户停止或不可恢复异常可以结束并报告未知，不强制无限继续或隐藏付费重试。
- **防回退直接对应真实变化。** 保留行为源自当前实现、有效样本/检查及 Owner 决定；语义联动、身份、人工布局、范围和 History 由原 planner/事务保持。命中 §3.1 时独审实际消费者、旧职责退出和原行为；普通任务自检，未变证据复用。代码候选可撤回，用户工程/恢复稿/未提交成果不回退或删除。

整体统一只有在有限覆盖闭合、业务 owner 实接全部必要消费者、旧重复职责退出及受影响保留行为通过后成立。局部 PASS、续作结果与新单请求完整创作分别报告；不要求每次小改重跑三端 GUI/完整模型矩阵。产品部署/发行继续按 Owner 决定。

<a id="enforceable-methodology"></a>
### 1.4 可执行约束、Skill 解耦与行为保全（Owner 2026-10-08）

以下方法已确认；机制的实际实现和验收按[同一执行包 §10](20261008-core-experience-unified/EXECUTION_PLAN.md#enforced-capability-methodology)，目前为规划，不把文字规则说成 CI/权限已经强制生效。

- 能力收口同时证明：唯一业务决定 owner、所有必要入口真实消费、旧重复决定退出、受影响用户行为保留、防已退出旁路再引入的自动检查有效。人端可直接调用领域命令，不必绕 AI Gateway；合法输入/协议/生命周期差异保留。
- 外部意图与宿主准备事实分离。身份、版本、资源和事务上下文由软件产生，模型可选已观察候选但不维护平台簿记；作者变量和真实第三方业务参数不批量剥除。接口、实际消费者、同源描述与操作指南按能力同批迁移。
- 复用现有依赖检查、类型和行为验证。存量例外按可信基线的精确集合只减不增，不能靠等量替换、扩大 glob 或自动更新洗绿；修掉即收紧。静态导入存在不证明实际调用，元数据不证明 UI 可达，机械检查不代替按 §3.1 必须进行的语义独审。
- 实现权不含单方面改变验收义务的权利。删除/跳过正确断言、扩大例外、修改过滤/可信工作流、重置视觉基线/阈值需独立确认其等价覆盖或已批准行为变化；普通等价测试维护不逐项交 Owner。产品能力取消/降级、权限扩大和新费用仍由 Owner 决定。
- 可信验证义务不能仅取候选自己的选择器或成功退出码；必须核必需检查实际执行、组合候选身份和报告。受保护规则与管理凭据由实施者以外主体控制，候选代码不持管理密钥；缺远端条件时明确是独立 review/本地检查而非硬权限保证。
- 基线包含有证据且未取消的 V9 正常能力及当前有效行为；保留用户结果，不恢复旧生产 Schema/writer。fixture 迁移与行为预期改变分开，已知错误不作黄金答案。测试穿过正在验证的真实 owner/边界；局部性、目标连续、Undo/保存重开及不重放按相关能力保留。
- Skill 分为任务方法、共用操作指南与软件执行职责，实际分发/发现消费者同批迁移。基础正确性不依赖加载创作 Skill；把机械步骤移到 references/scripts 不算收回。不增加强制工作流引擎、每次工具审批或二次模型审核。

每个能力切片留下唯一实现、受保护行为和防再引入检查；先做本切片必需的小机制，不以全仓治理为普通修复前置。现有 S/NI 和任务机制继续使用，不另建登记平台或周期性全仓审计。

## 2. 停止条件

- 定位已经足以决定修改边界，停止继续盘点；
- 目标行为及可信失败路径已被直接证据覆盖，停止追加同义验证；
- 剩余问题只是未触发的假设风险，记录必要的不确定性后停止扩面；
- 新信息会改变产品能力、持久化语义、导出结果或用户数据处理方式时，停止实现并交给产品 Owner 决定；
- 请求只是调查、评审或解释时，交付证据和结论，不自动实施修复。

## 3. 敏感变更触发器

以下改动不使用风险分级，但必须增加与其风险直接对应的检查：

- Schema / contract / 公共 API，保存、重开、恢复、历史、迁移或用户数据；
- Published producer、真实 Player、导出语义、Runtime / Component 宿主；
- Electron main / preload、IPC、网络、权限或安全边界；
- 删除旧路径、迁移 consumer、跨进程 / 跨 Surface / 跨会话异步状态；
- composition root、Store/History、跨 Owner state/action 拆分、依赖方向或公共 selector/command port；
- 自动化难以观察、但会直接改变核心流程或用户可见结果的行为。

命中时只做相关的三件事：

1. 读取架构合同相关条目，并核对直接 producer、consumer 和失败 / 回滚路径；
2. 对用户数据使用副本或 fixture，明确兼容和回退结果；
3. 在真实 carrier 上验证该行为；重要结构变化必须按 §3.1 独立评审，其他敏感变更若流程中已有 Reviewer，则由 Reviewer 审 diff、反例和证据缺口。

触发器不是待办清单。一次改动只承担自己命中的风险，不因“敏感”自动建卡、跑全套测试、通读全部合同或扩成完整矩阵。内部生产工具按架构合同的受控团队/受信代码模型检查；不因出现 Runtime、Component、网络或 Electron 字样自动引入公开恶意插件、多租户或零信任假设，只有信任来源、分发范围、凭据、OS 能力或外部写入边界真实变化时才升级 Owner。Schema、用户数据迁移、安全权限、教师能力取舍、导出语义和最终发布结论仍由产品 Owner 决策。

<a id="independent-structural-review"></a>
### 3.1 重要结构变化的独立评审

以下实际变化必须独立评审，不由实施者自行豁免：

- 重写成熟算法，或整体替换工作台、Player、输出等核心入口；
- 迁移正式 writer、History、保存目标、资源归属或跨进程 / 跨 Surface 异步生命周期的职责；
- 删除或缩减承载受支持核心行为的实现、UI 入口或 consumer。
- 实际权限边界变化，或测试选择、必需检查、可信策略、正确断言/基线保护的实质变化。

触发取决于实际职责和行为变化，不取决于文件名、行数或碰到某个目录。尚未在已批准具体方案中确定的上述结构选择，实施前由 Reviewer 核对直接证据、替代办法和修改边界；已确定的必要迁移可直接推进，但候选合入前仍须核对实际 diff、保留行为及证据缺口。已有具体决策与未变候选的有效评审不重复进行，不要求每个提交签字。

独立 Reviewer 必须是未参与该候选实现的另一执行者 / 会话；集成者参与实现时不能同时完成该候选的独立评审。已有有效评审复用，修正仅做相关增量复审；无可复用评审时调用一位 Reviewer，集中核相关基线、实际 diff、直接调用者及原始样本 / 检查结果。一次集中指出影响本批正确性的行为错误、回退、越界、遗漏消费者和必要证据缺口；纯风格及无触发依据的防御建议不阻断，真实问题仍须解决。结论留在原结果或交接消息，不新增评审平台。

技术裁决由胜任的 Reviewer 承担，产品取舍按 §7 交 Owner。主执行者按需调用，缺少必要 Reviewer 时保全相关候选并标明最小下一步，不把作者自检称为独审通过；其他已授权、非重叠工作可以继续，不重启整轮开发或重跑无变化检查。

## 4. 验证选择

代码集成采用小型固定关键行为基线＋受影响领域/消费者检查＋本次失败反例；先选成本最低且足以证伪成功的证据。1–3 条是组织方式，不是保护行为的上限，也不授权省略固定基线。纯文档/确无影响路径由可信范围规则标明不适用，不自动跑产品矩阵：

先按 §1.2 选定本次必须成立的用户行为，再选下面的证据层。1–3 条、独立测试、最小反例都只是验证方法，不是测试题目重要性的依据；不通过减少命令条数把偏题用例称作“最小充分”。

| 待证明属性 | 首选证据 |
|---|---|
| 局部逻辑、结构、Schema / contract | 解析、类型检查或目标测试 |
| 保存、恢复、历史 | fixture 的保存—重开 / 撤销—重做往返 |
| 视觉、布局、互动 | 真实渲染或浏览器中的行为检查 |
| Player、Runtime / Component、导出 | 真实 consumer / carrier 产物 |
| 模块 owner / 依赖方向 | import graph、SCC / forbidden-import ratchet、窄 public type 检查，加一条代表性行为测试 |
| 制品身份、完整性、确定性 | 仅在它们本身属于合同时使用 Hash / 字节比较 |

只有以下情况才考虑扩大验证：focused check 失败或结果含混；改动跨越多个真实 consumer；相关依赖、夹具、配置或环境发生变化；正在形成集成 / 发布候选。这些条件说明可以调查，不能单独授权续派或抢占主线；仍按 §1.2 判断它影响的用户结果及最低成本证据。完整 build、完整 E2E、`verify`、打包和 release verification 只属于上述候选或其直接风险，不属于普通改动的认真证明。

同一候选、同一命令、同一环境已有有效通过结果时不重跑。后续变化未命中该证据的源码、测试、夹具、配置、lockfile、公共合同或 consumer 依赖闭包时，证据继续有效。生成命令已经完成生成和语义 / 字节比较时，不紧接同义 `--check`。

局部验证按实际覆盖范围和准备成本计量，不按命令条数判断“最小”。运行前核对npm生命周期钩子与测试过滤；依赖制品只按相关变化准备一次。综合测试文件含真实CLI/付费生成时必须显式选中本次目标，exclude/skip/零匹配不算证据。具体当前入口见[GPTpro 测试与证据](../../GPTpro方案/guoling_2_0_execution_plan/delivery/TESTING.md)；未完成新用例不能借旧用例通过报新能力。

模块化不能由行数、文件数、Hash、字符串存在或 snapshot import 列表单独证明；检查必须证明旧 writer 消失、root 无业务实现、Feature 不依赖完整 Store，并用最近层行为覆盖迁移的 owner。模块迁移应从一个 owner 闭环开始，每个提交删除对应旧实现，不建立先双写后清理的中间态。

保留行为优先使用原有用例与真实样本；缺少证据时，只补受影响的关键行为及可信失败路径。预期结果应来自基线行为、正式合同或 Owner 的明确决定，不能仅从新实现反推。修改 / 删除原有断言、用例或检查过滤时，单独说明原用例错误、已批准的行为变化或等效覆盖依据；不得为使重构通过而弱化正确断言、隐藏失败或缩减受支持能力。命中 §3.1 的候选由 Reviewer 一并核对这些调整。

Flaky 命令只原样重跑一次：可复现则修当前问题，随机则隔离记录，不提高 retry 或弱化断言。基线已红时比较当前 diff 与基线，既存无关失败不扩成当前修复范围；但当前任务明确要求恢复的旧能力/旧缺陷仍须完成，不因基线已红而豁免。不把零匹配、skip、缺报告或 fixture 未到达行为断言当成通过；可信检查选择和验收标准变更按 §1.4。

自动化最多证明 `engineering candidate`；真实视觉、互动和教师复核决定 `art candidate` / `accepted`，不能由自动化全绿代替。旧 1.3／1.5／1.8／2.0 的固定签署点仅为历史，本轮完成与发布按当前 Owner 指令及有效证据，不恢复旧阶段门；当前发布暂停。

## 5. 协调与任务卡

单执行者、单会话、写入范围明确的工作不建卡。只有出现多执行者协调、重叠写入风险、跨会话恢复、明确交接或真实阻断时才创建任务卡。

任务状态只有 `queued`、`active`、`blocked`。`active` 必须有唯一 Owner；同一写锁同一时间只能属于一个 active 任务。已分配能力/目录范围内自主创建或修改文件；碰到另一活跃任务写域、共享热点或新的职责范围时才协调。共享实体单 writer；必要并行时先固定独立能力范围并使用隔离 worktree / branch，不逐文件额外审批。queued 不自动启动。

`legacy-inventory` 是 `inventories/legacy-consumers.json` 的专用写锁；任何会改变该文件的任务都必须声明它。迁移 lane 可以并行修改各自产品路径，但不得借其他写锁并行改唯一台账；台账 reconciliation 与删除状态更新由持有该锁的单一 Owner 顺序完成。

路线的Dependencies列开工所必需前置；独立规格的真实consumer集成条件与Acceptance仍约束节点完成，汇合/发布节点显式保留必选线。开发可先使用已经稳定的窄接口完成非重叠叶子，不以部分开发、静态占位或mock替代最终真实接线验收。

路线Write locks表示节点可能触及的写域；协调任务卡只声明当前批次实际需要且已获分配的锁，不从开工到结束机械占住全部可能范围。同一粗锁覆盖不同叶子文件时，由唯一协调Owner在同一任务下持锁，委派精确非重叠叶子到隔离工作区并行；共享实体文件仍由一个writer修改并顺序集成，不创建两个同时争用同锁的active卡，不以省略锁或worktree绕过冲突。新共享改动返回Owner处理，不扩新锁平台或复制状态。

巨石拆分期间 composition root 和共享 History 保持单 writer。首个稳定窄 port 落地并删除对应旧 writer 后，不同 Owner 模块才可按不重叠写锁并行；不为了表示“架构治理”额外建卡、评分或常设委员会。

任务卡只保留六项：状态 / Owner、结果 / 证据、写入范围、写锁、验收、验证。给较弱模型或跨会话交接时，在这些字段内明确：当前失败证据、允许写入路径、越界停止条件、确定结果和按实际保留行为组织的少量精确检查；1–3 条不限制应覆盖的独立风险，也不省略已选固定基线。不要增加流程字段。

完成后删除卡并重新生成任务板；完成事实由实质 diff / commit 和检查结果承载，不设置 done 状态，不做领取或关闭仪式。任务板只是当前协调摘要，不是调度引擎。

完成事实只写一个既有结果位置；计划保留目标与依赖，当前状态只在交接或重要阻断变化时更新简短摘要和链接，任务卡只维护当前协调。暂停时保全候选、原件和证据，写明阻断及最小下一步；本批结束不表示整体计划完成，也不自动启动下一批。

## 6. 删除与 Legacy

删除实现前必须核对：静态与动态引用、IPC / 配置、Preview / Player / Export、build / fixture / release、持久化与跨版本义务，以及替代路径的目标行为。精确删除目标必须证明 consumer 为零；名称含 `legacy`、文件过大、UI 暂不暴露或存在新目录都不是删除证据。Legacy consumer 的机器真相仍是 `inventories/legacy-consumers.json`。

## 7. Git、完成与升级

Windows 隔离 worktree 若以 junction/symlink 借用主树依赖，归档前先仅移除本轮创建的目录连接，不能把实际共享目录交给递归清理。2026-10-01 桌面归档曾沿 node_modules 连接清空主树依赖；该要求保护已发生问题对应的目录，不扩大为通用核验平台。

改动保持可整体审阅和回滚，不混入无关用户修改。只有用户或集成流程要求时才提交；任务元数据与对应实质改动一起提交，不制造领取、关闭、索引刷新或纯流程提交。tracked generated output 只有真实 consumer 要求时才生成并提交。

**Done** 基本事实仍为四项；涉及共享能力还须满足 §1.4 的防再引入、行为及必要指南闭环，文档/本地检查/远端强制保护分别报告：目标行为可观察；单一真相和直接 consumer 一致；最小充分检查通过且适用的独立评审通过；剩余不确定性与风险已如实说明。对模块拆分，还要求职责与 state/action writer 已迁入正式 Owner、依赖方向棘轮通过、旧实现和兼容双写删除、组合根只剩实例化/接线，并由代表性保存/历史/Surface/Feature 行为证明零降级。文件存在、Facade re-export、代码搬家、测试只断言字符串 / 文件、双写兼容路径都不能单独证明完成。

已明确授权的目标、技术选择和重构范围不逐文件或重复审批。本轮独立 V10／V3／API 5、无旧兼容、组件统一、可替换编辑适配及对应布局边界已在 Owner 批准的路线内；其实施细化不因触碰旧 Schema 再请求一次授权。只有超出当前授权的新决定才升级 Owner：迁移真实用户数据、额外取舍教师能力／改变工作流或输出语义、扩大信任／宿主权限、引入新付费路径或重大外部成本、接受真实数据损坏风险，以及最终发布／accepted。当前“先修改文档”仍只执行文档工作，不能据此启动产品代码。
