# 工作协议：结果驱动开发

> 本文是开发执行规则的唯一落点。任务卡格式见 [TASK_CARD_TEMPLATE.md](TASK_CARD_TEMPLATE.md)，当前协调状态见 [TASK_BOARD.md](TASK_BOARD.md)。
>
> 默认目标是用最短的完整闭环交付正确结果。规则只在能防止错误结果、用户数据损坏、并发写坏或虚假完成时增加步骤；下一步若不能改变实现、裁决或结果可信度，就停止。

## 1. 默认闭环

```text
明确结果 -> 定位真实边界 -> 实现 -> 直接验证 -> 交付
```

开始前只需能说清三件事，不建表、不写流程文档：

1. **结果**：本次要改变或证明的一个可观察行为；
2. **边界**：当前证据指向的单一真相、直接 producer / consumer 和失败位置；
3. **验收**：什么结果算完成，以及最便宜的有效检查是什么。

用户或 Owner 的明确实现/主动模块化指令本身足以启动，不要求先出现线上故障。没有明确指令时，只有当前可复现失败、真实 consumer、正式合同偏差，或依赖环、wrong-owner 状态、完整 Store 扩散、重复 writer、已批准 lane 冲突等直接证据已经证明架构偏差，才进入实现；历史 Phase、评估标签、未来可能性和“顺便更完整”都不能自行扩成任务。

默认只读当前路线、目标符号、直接调用者 / consumer 和目标测试。只有改动命中第 3 节边界时才补读架构合同相关条目。普通任务不默认通读整个巨石文件；任务本身是模块拆分时，必须完整读取目标接口、composition factory、相关 Owner state/actions、直接 importers 和目标测试，但不扩大到无关仓库区域。

实现应消除已证实的根因并保持单一真相。“根因”包括错误 Owner、依赖方向反转、巨石写锁阻塞和完整 Store 成为跨域公共 API。命中架构合同的模块化触发条件时，应完成真实 owner 迁移，不以局部代理或 re-export 收尾；其他情况只有直接证据表明局部修改会继续留下双写、重复规则或错误 owner 时才扩大范围。不借修复顺便建设平台、迁移体系、兼容层、覆盖率工程或假设性抽象。

## 2. 停止条件

- 定位已经足以决定修改边界，停止继续盘点；
- 目标行为及可信失败路径已被直接证据覆盖，停止追加同义验证；
- 剩余问题只是未触发的假设风险，记录必要的不确定性后停止扩面；
- 新信息会改变产品能力、持久化语义、导出结果或用户数据处理方式时，停止实现并交给产品 Owner 决定；
- 请求只是调查、评审或解释时，交付证据和结论，不自动实施修复。

## 3. 敏感变更触发器

以下改动不使用风险分级，但必须增加与其风险直接对应的检查：

- Schema / contract / 公共 API，保存、重开、恢复、历史、迁移或用户数据；
- Published producer、真实 Player、导出语义、Runtime / Component 宿主；
- Electron main / preload、IPC、网络、权限或安全边界；
- 删除旧路径、迁移 consumer、跨进程 / 跨 Surface / 跨会话异步状态；
- composition root、Store/History、跨 Owner state/action 拆分、依赖方向或公共 selector/command port；
- 自动化难以观察、但会直接改变核心流程或用户可见结果的行为。

命中时只做相关的三件事：

1. 读取架构合同相关条目，并核对直接 producer、consumer 和失败 / 回滚路径；
2. 对用户数据使用副本或 fixture，明确兼容和回退结果；
3. 在真实 carrier 上验证该行为；合并或发布前，若流程中存在独立 Reviewer，则由 Reviewer 审 diff、反例和证据缺口。

触发器不是待办清单。一次改动只承担自己命中的风险，不因“敏感”自动建卡、跑全套测试、通读全部合同或扩成完整矩阵。内部生产工具按架构合同的受控团队/受信代码模型检查；不因出现 Runtime、Component、网络或 Electron 字样自动引入公开恶意插件、多租户或零信任假设，只有信任来源、分发范围、凭据、OS 能力或外部写入边界真实变化时才升级 Owner。Schema、用户数据迁移、安全权限、教师能力取舍、导出语义和最终发布结论仍由产品 Owner 决策。

## 4. 验证选择

默认执行 1–3 条最小充分检查，先选成本最低且足以证伪成功的检查：

| 待证明属性 | 首选证据 |
|---|---|
| 局部逻辑、结构、Schema / contract | 解析、类型检查或目标测试 |
| 保存、恢复、历史 | fixture 的保存—重开 / 撤销—重做往返 |
| 视觉、布局、互动 | 真实渲染或浏览器中的行为检查 |
| Player、Runtime / Component、导出 | 真实 consumer / carrier 产物 |
| 模块 owner / 依赖方向 | import graph、SCC / forbidden-import ratchet、窄 public type 检查，加一条代表性行为测试 |
| 制品身份、完整性、确定性 | 仅在它们本身属于合同时使用 Hash / 字节比较 |

只有以下情况才扩大验证：focused check 失败或结果含混；改动跨越多个真实 consumer；相关依赖、夹具、配置或环境发生变化；正在形成集成 / 发布候选。完整 build、完整 E2E、`verify`、打包和 release verification 只属于上述候选或其直接风险，不属于普通改动的认真证明。

同一候选、同一命令、同一环境已有有效通过结果时不重跑。后续变化未命中该证据的源码、测试、夹具、配置、lockfile、公共合同或 consumer 依赖闭包时，证据继续有效。生成命令已经完成生成和语义 / 字节比较时，不紧接同义 `--check`。

模块化不能由行数、文件数、Hash、字符串存在或 snapshot import 列表单独证明；检查必须证明旧 writer 消失、root 无业务实现、Feature 不依赖完整 Store，并用最近层行为覆盖迁移的 owner。模块迁移应从一个 owner 闭环开始，每个提交删除对应旧实现，不建立先双写后清理的中间态。

Flaky 命令只原样重跑一次：可复现则修当前问题，随机则隔离记录，不提高 retry 或弱化断言。基线已红时比较当前 diff 与基线，只承担由本次变更新增的失败。

自动化最多证明 `engineering candidate`；真实视觉、互动和教师复核决定 `art candidate` / `accepted`。

## 5. 协调与任务卡

单执行者、单会话、写入范围明确的工作不建卡。只有出现多执行者协调、重叠写入风险、跨会话恢复、明确交接或真实阻断时才创建任务卡。

任务状态只有 `queued`、`active`、`blocked`。`active` 必须有唯一 Owner；同一写锁同一时间只能属于一个 active 任务。共享 worktree 中重叠路径只有一个 writer，其他执行者可以只读调查。非重叠实现若要并行，应使用隔离 worktree / branch 并由协调者先划定写入范围。

`legacy-inventory` 是 `inventories/legacy-consumers.json` 的专用写锁；任何会改变该文件的任务都必须声明它。迁移 lane 可以并行修改各自产品路径，但不得借其他写锁并行改唯一台账；台账 reconciliation 与删除状态更新由持有该锁的单一 Owner 顺序完成。

巨石拆分期间 composition root 和共享 History 保持单 writer。首个稳定窄 port 落地并删除对应旧 writer 后，不同 Owner 模块才可按不重叠写锁并行；不为了表示“架构治理”额外建卡、评分或常设委员会。

任务卡只保留六项：状态 / Owner、结果 / 证据、写入范围、写锁、验收、验证。给较弱模型或跨会话交接时，在这些字段内明确：当前失败证据、允许写入路径、越界停止条件、确定结果和最多 1–3 条精确检查；不要增加流程字段。

完成后删除卡并重新生成任务板；完成事实由实质 diff / commit 和检查结果承载，不设置 done 状态，不做领取或关闭仪式。任务板只是当前协调摘要，不是调度引擎。

## 6. 删除与 Legacy

删除实现前必须核对：静态与动态引用、IPC / 配置、Preview / Player / Export、build / fixture / release、持久化与跨版本义务，以及替代路径的目标行为。精确删除目标必须证明 consumer 为零；名称含 `legacy`、文件过大、UI 暂不暴露或存在新目录都不是删除证据。Legacy consumer 的机器真相仍是 `inventories/legacy-consumers.json`。

## 7. Git、完成与升级

改动保持可整体审阅和回滚，不混入无关用户修改。只有用户或集成流程要求时才提交；任务元数据与对应实质改动一起提交，不制造领取、关闭、索引刷新或纯流程提交。tracked generated output 只有真实 consumer 要求时才生成并提交；repo-index 仍是 ignored、可缺省的本地导航缓存。

**Done** 只有四项：目标行为可观察；单一真相和直接 consumer 一致；最小充分检查通过；剩余不确定性与风险已如实说明。对模块拆分，还要求职责与 state/action writer 已迁入正式 Owner、依赖方向棘轮通过、旧实现和兼容双写删除、组合根只剩实例化/接线，并由代表性保存/历史/Surface/Feature 行为证明零降级。文件存在、Facade re-export、代码搬家、测试只断言字符串 / 文件、双写兼容路径都不能单独证明完成。

已锁定 Owner 边界内、保持 wire/状态语义/用户行为不变的模块迁移不需要逐文件重新审批。以下决定才升级产品 Owner：修改 V9 Schema 或创建 V10；迁移真实用户数据；取舍教师能力；改变用户可见工作流、Surface carrier、教师能力、导出语义或视觉结果；改变信任来源或宿主授权；引入付费服务、重大依赖、网络服务或新权限；接受真实数据损坏风险；最终发布或 `accepted` 结论。
