# AI 修改流程简化与正确性修复方案

日期：2026-09-14。状态：本批工程实现及聚焦验证完成。详见 [实施记录](reviews/2026-09-14-ai-editing-flow-implementation.md)，不代表美术接受或版本 Owner 验收。

依据：[AI 修改流程核查](reviews/2026-09-14-ai-editing-friction-audit.md)。本方案承接 [AI 创作操作机制实施方案](AI_AUTHORING_MECHANISM_IMPLEMENTATION_PLAN.md)，修复当前 1.8 已可用入口中的真实缺陷，不扩展 1.9 的新创作任务族。恢复入口已按 Owner 决定移入属性折叠维护区，本方案保留该结果，不恢复播放按钮或临时默认控制台。

## 1. 目标与成功标准

用户要求修改现有组件时，AI 能直接读取源码、修改文件、交付结果。软件负责取得准确路径与基线、编码候选、做必要验证和一次提交，不要求模型手写协议手续或反复解释已决定的载体。

本批必须达到：

- 合理的组件修改不再因缺少理由文字而拒绝；确定性参数错误在本地立即指出。
- 一份全局控制台放在 20 页课件中，正常源码修改不因重复采样与固定总超时失败；不同页面/状态的实际差异仍受到检查。
- 小组件修改不因无关的 50MiB 工程素材无法传输；组件合法的动态取资仍正常。
- 已满足任务要求的修改正常结束；需要看效果、点击或继续修复时才追加相应工作，不为总结再开模型回合。
- 已经独占的可编辑组件连续修改保持包 ID 稳定，当前工程不随修改次数增加一串重复包。
- 视觉和交互是否正确，以实际呈现及操作证明；提交成功与视觉/教师接受分开记录。

不得通过放宽工程身份、覆盖并发修改、吞掉真实缺失资源、跳过必要行为验证或缩小用户编辑权限来实现上述目标。

## 2. 保持的架构边界

1. 保持 Course Project V9、Published V2、API4 与三 Surface。此次不新增工程持久化版本或第二套项目模型。
2. 保持原生 Codex、Claude、OpenCode 的模型循环、cwd、文件/终端/网络/连接/Skills 与现有授权。观察范围仍只是输入焦点。
3. 复用现有 candidate v1/v2、文件交付、candidate-helper、工具 Facade、prepare 和 EditorTransaction。helper 只生成候选，不能提交工程。
4. 基线、目标、request/session/epoch、资源闭包、取消、迟到结果和唯一文档/资源事务仍由现有 Owner 校验。已提交阶段不因后续反馈失败而重提。
5. 涉及传输或本地证据字段调整时，同步严格 Schema、生成器、各 CLI 适配、主进程与 renderer consumer；兼容合法旧输入，未知字段仍明确拒绝。
6. 本批不新建通用断言语言、审批平台、模型路由层或长期跨任务证据缓存。只收敛已存在流程中的职责。

## 3. 修改包 A：取消无价值硬门，统一候选准备

### A1. 取消强制载体理由

按 Owner 追加决定，从正式候选 Schema 中删除 `lowerCarrierReason` 字段及所有非 native 必须提供它的执行约束，覆盖组件参数修改、已有组件插入、组件源码、Runtime 与 Recipe。载体选择继续由创作指导说明，不以一句理由文字决定结果能否应用。

新提示、示例和 helper 不再要求生成该字段。为兼容旧候选，旧字符串/空值只在传输入口丢弃，正式协议不保留该字段；不能用宿主代填“需要组件”等空洞理由维持旧门。

直接落点：`generationContract.ts`、`authoringToolCarrier.ts` 的相关说明、`codexAppServer.ts`、`profile.ts`、`courseAgentSkills.ts`、能力生成器与 helper。carrier 本身若仍用于工具选择和运行权限判定则保留，不与理由一起删除。

验收：同一合法候选带理由、无理由和旧空值得到相同执行结果；不合法工具输入、越权能力或过期基线仍被原校验拒绝。

### A2. 一处完成明确的传输转换

内联候选、candidate.json 和 helper 统一进入同一个规范化及解析链。Codex 原生结构化输出要求的 JSON 字符串只是适配器传输形式；交给工具前必须成为同样的对象。

仅转换合同明确允许的顶层工具 input 投影和已知旧可选字段；不递归猜测、不反复 JSON.parse 直到“看起来能用”，不改正文或 runtime.js 中原本合法的字符串。坏 JSON 返回具体字段/位置，不替换为空对象。文件路径、候选身份与成功终态的摄取要求保持。

验收：对象与已知字符串投影通过不同交付通道得到同一工具输入；字符串文本/JS 源码原样保留；错误请求、取消后文件、未知字段仍失败。显式双重错误编码在本地得到可定位诊断，不进入完整模型反馈后才暴露。

### A3. helper 负责文件、基线和廉价预检

在现有 helper 增加组件补丁准备能力：根据本轮冻结的组件描述及精确目标读取包 ID、版本、content identity；读取实际修改文件，比较冻结源码，只生成改变/删除的文件，最后输出已有 `component.package` 候选。具体 helper 参数与首个 consumer 同批确定，不另建候选协议。

- 冻结源码保留为只读基线；需要可改文件时在本轮暂存区准备工作副本，不覆盖用于比较和防并发覆盖的原快照。
- 模型只需选择已有组件目标、修改文件并说明实际任务内容；无需手抄长 ID、hash、base64 或将整段 JS 塞进 shell 内联字符串。
- helper 仅从当前 request 的冻结文件读取基线，不读取 live project 补“最新值”；缺省元数据可补齐，显式不一致必须报错，不能静默改成当前版本。
- 将现有工具 input Schema 与静态条件打包供 helper 使用，保持与正式工具同源，避免手写另一套规则。
- 对当前可展开的别名先展开再校验；合法的前序结果引用按已有类型合同检查，真正依赖运行结果的字段明确列为 deferred，不用假值蒙混通过，也不能误拒合法组合候选。
- 同时覆盖手工 draft 和 helper 生成的 draft；调用 helper 是方便入口，合法的直接候选/文件交付继续可用。
- 正常生成命令已经包含预检，不再要求未改文件时先 check、再重复同一预检；输出明确区分“仅检查”与“已生成候选”。

验收：`component.configure {props:123}` 在本地得到和宿主一致的字段错误；修改 runtime.js 不手填基线即可生成合法候选；已变化基线仍被宿主拒绝；媒体/新建页面等现有前序引用不退化。

## 4. 修改包 B：收窄动态准入的工作量与资源

### B1. 拆开重复工程检查与不同场景的实际检查

将当前“每个 location × state 重建完整宿主并采样六帧”改为现有准入函数内的两层执行：

| 检查 | 执行范围 |
|---|---|
| 源码解析、manifest、协议、依赖闭包 | 每份实际变化的源码/包及依赖一次 |
| 宿主接线、resize/update/suspend/resume | 按不同 Surface/宿主模式及实际参数、尺寸等必要条件分组；相同条件复用工程证据 |
| 页面与命名状态中的实际挂载、资源加载、异常 | 保留受影响 authored-context 覆盖；可在同一真实 Published session 内切换并等待真实 ready，不为每个页面追加固定等待 |
| 连续动画采样、具体按钮动作、视觉确认 | 对任务相关场景与不同表现执行；复用已采集且仍有效的帧，避免重复拍同一状态 |

同 props 不等于同语义。源码可读 locationId、courseState、presentation、scope，控制台也可按页面换外观；不能据此删掉差异场景的检查。复用的是明确重复的工程证据，不宣称所有页面视觉相同。首次挂载与切场生命周期有区别，相关路径各保留一个真实检查。

全局控制台使用真实 Session 连续切页和切换状态，覆盖订阅更新、持续实例与最终销毁，不能仅靠每页重建来代替。准入只证明作者当前状态及所选必要行为可运行，不宣称穷举了任意 courseState 组合；任务要求的具体交互分支由已有观察动作补验。

沿用当前 targets 与 Published Owner，不创建持久化“验证计划”或额外场景模型。按实际需要补内部执行分组即可。证据记录实际覆盖的位置/状态及动作，没有执行的检查不能标为通过。

### B2. 超时服从必要工作量，仍能停止异常代码

取消用同一个 20 秒计时器覆盖任意数量目标的矛盾规则。启动、单次挂载或采样保留有界 watchdog；整个准入受原任务剩余绝对期限限制。每组完成后更新进度，不因持续等待悄悄延长原任务期限。

具体单阶段上限由已有失败样本和真实启动耗时确定，不把“换成十分钟”作为修复。单个死循环/永不 ready 必须能终止；合法多页检查可以在原任务期限内完成。需要工作量已无法在剩余时间内完成时说明未完成项，保留当前工程，不能不断重跑同一全部检查。

验收：合法 20 页单控制台真实准入完成；新增一个页面不会增加整套 1250ms 固定采样。第 1 页和第 20 页同 props、按 locationId 显示不同纹理时，两页都实际检查；真实切页/状态更新生效。加入页面特定异常仍被该场景检查发现；单实例死循环或永不 ready、取消、窗口关闭均能终止且未提交阶段零写入。

### B3. 资源按实际宿主依赖读取，避免全工程 base64 大包

先解决字节承载，再收窄可确认的检查范围；不要把解决 64MiB 传输失败依赖于一套“精确分析任意 JS 资源引用”的机制。复用 Published 资源收集与资产解析 Owner，区分必要元数据和实际字节：

- 保留受影响对象所需的场景背景、共享资产、全局内容、组件依赖及 course-state/导航上下文，不能只留下孤立组件而改变合法运行环境。
- 静态可确认的引用形成闭包，编译、依赖和缺资源检查只覆盖本次受影响的闭包。无关场景的旧问题单独报告，不作为局部修改硬门。
- API4 支持动态 `projectAssetUrl(assetId)`。不能仅扫描 JS 字面量来删资产；保留冻结工程的合法资源目录，并让现有资产解析口按需读取对应冻结字节。
- 字节交付复用应用暂存/资源读取机制，采用有作用域的文件或资源引用，避免把整个工程 base64 塞进一条 IPC JSON。若现有传输无法复用，只扩展内部准入资源描述与消费者，不新增 Component API、任意文件读取或通用 RPC。
- 资源引用绑定本次准入和冻结内容；当前 live 资源随后变化不影响检查，结束/取消后释放。总量、单资源、图面及运行内存限制按实际读取工作量执行。

若无法确认某资源是否被动态引用，必须保留合法读取能力，不能以“闭包优化”为由返回空地址、静默缺图或退化为截图。资源加载失败要指向实际资源与使用场景。

准入与最终 Published/HTML 必须具有一致的合法取资语义。先以动态 ID 用例确认现有导出是否遗漏；若证实同一失败，显式扩到现有资产分析/Published producer 修复并记录，不能只让准入窗口显示正常，也不借此重写整个资源系统。

验收：工程含合计 50MiB 无关媒体时，小组件仍能修改；动态拼接 ID、从 props/courseState 取 ID、只在另一页使用的合法图片，在准入、保存重开和离线 HTML 中均正常；必要背景及依赖不丢；实际依赖缺失/超限仍有准确失败；同一资源不随每页重复编码传输。冻结后外部源文件变化不影响本次执行，结束/取消后资源释放。

## 5. 修改包 C：按实际剩余工作决定观察与结束

### C1. 证据与流程决定分开

移除“存在 requires-review 就覆盖 finish”的规则。保留旧证据的可读性，但这个字段只表示自动工具没有判定语义，不再直接触发下一模型回合，也不能反向改成自动语义通过。

优先复用既有 `afterCommit`、任务控制器、正式回执和观察入口：

| 当前事实 | 后续动作 |
|---|---|
| 参数/结构结果已确定，必要验证完成，候选要求 finish | 保存正式结果后结束；不为总结或同一结果再起回合 |
| 用户任务或当前明确步骤需要观察纹理/动画/点击结果 | 执行所需观察；同一内容身份的已有证据先复用，交给原生 CLI 判断具体差距 |
| 有真实异常、缺失结果或未完成操作 | 准确反馈，继续同一任务并复用已生成源码/素材 |
| 已提交但保存回执或后续检查失败 | 显示已应用与剩余问题；只恢复对应环节，不重复提交 |

不增加所有修改都必须填写的验证清单。模型根据任务实际要求使用 observe，并在现有 afterCommit.reason 写具体未完成事项，例如“检查第 20 页的纸纹”；这不是每次修改必填的理由。宿主遵从成功候选的 finish，只有拥有明确未完成动作的现有 Owner 才继续该动作，不靠猜测用户意图建立新关卡。无法自动理解的视觉要求不能伪装成确定性通过。

### C2. 把具体效果检查接到现有观察能力

将视觉/交互检查放进任务需要的那一次观察，优先暴露现有帧、真实目标、加载错误和按钮观察；不足处只补必要的观测值，不创建通用断言 DSL。

本次回归应实际检查：纸纹已经显示而不是仅写入 CSS；目录展开后仍在视口；点击缩放后倍率变化；折叠后能重新展开；课件缩放/平移不带动控制台。算法性的确定条件与美术判断分开，不能把 `backgroundImage != none` 当成整体设计美观的证明。

Luna 提示应要求先看实际结果再宣布完成，但不叠加“先写长计划、先生成检查报告”等固定仪式。观察发现缺陷时反馈具体差距，继续修改既有文件，不重做已正确部分。

验收：仅改公开文案等确定性任务不额外开总结回合；视觉/点击任务确实消费对应证据；错误纹理不会仅凭可挂载就宣称已达成视觉目标；合法 finish、observe、partial、Stop 的既有边界保持。

## 6. 修改包 D：稳定组件身份与当前资源集合

实例模式保留“只修改本实例”的语义，调整 fork 条件：

- 包被多个实例共享，或当前包尚不允许原位编辑时，先生成独立可编辑副本，只重绑目标。
- 已经是本工程独占且可编辑的包，沿用包 ID，使用已有源码修订流程更新版本和内容身份。
- 新副本 ID 由稳定来源身份生成有界名称，不在当前长 ID 后不断追加 `.editable.UUID`。
- 旧工程中的长 ID 正常读取，打开时不批量重命名。只阻止后续继续增长。
- 当前修改导致失去全部有效引用、且只是此前修订遗留的临时可编辑包时，复用资源引用分析移出当前工程；保留用户主动保有的库包及实际依赖。Undo/Redo 所需字节由已有资源历史保存，不能用“有历史”作为把所有旧包留在当前文档的理由。
- 文档、包、后备图及引用调整仍为同一事务，恢复旧源码或 Undo 时资源必须完整可用。

直接落点：`componentPackageTool.ts`、`componentPackageRevision.ts`、`editableComponentPackage.ts`、组件资源引用与事务 Owner。共享模式、仅当前实例模式和源码恢复入口需统一消费相同判断。

验收：独占控制台连续修改 10 次，ID 长度与当前包数量不随次数增长；共享组件仅改一个实例不会影响另一实例；显式共享编辑仍修改所有实例；保存重开、Undo/Redo 与离线输出保持正确。

## 7. 修改包 E：减少模型操作摩擦，定位真实等待

在现有 profile、冻结 request 和 helper 中提供一眼可用的路径入口：本轮 request 的绝对路径、当前目标源码文件、组件元数据文件和 helper 调用示例。使用系统实际 shell 的正确引用形式，避免模型自行拼长路径和内联嵌套 JSON。

保持 cwd 和原生权限；不往用户工程根写容易过期的 request.json 别名。能力查询返回当前工具卡/必要协议，源码放可读文件。默认提示不要求扫描整份 memory、整个压缩能力包或历史结果；仍允许 CLI 按任务需要使用它们，不屏蔽原生工具。

宿主静默时间使用现有事件/计时记录说明：最近活动、是否仍有原生工具运行、候选是否已交付、正在准备/提交还是等待模型。不把“模型最后说在验证”当成宿主正在验证。保持原绝对预算，不用任意短闲置阈值杀死正常推理。

首次 221.6 秒静默的根因尚未确定。本批补足准确阶段证据及反馈，若复测出现相同静默，再沿原生完成事件/传输记录修复已证实问题；不预先建设重试调度器，也不声称这项未知已解决。

验收：helper 能直接从所给路径准备补丁，模型不需要猜 cwd 下的 request；格式错误有具体本地诊断；停止/超时记录真实阶段和已提交状态；日志量与模型实际输入量分别记录。

## 8. 实施顺序、依赖与写域

以下是本方案内的实施分组，不是新路线节点或当前 active 任务。

| 顺序 | 工作 | 依赖与协调 |
|---|---|---|
| 第一批 | A 取消理由硬门与同源候选准备；B 修复多页/大素材准入；D 稳定实例修订 | 先确认共同传输/资源接口。A 与 B 可独立推进；D 修改组件修订 Owner，与 B 的接线由唯一 Owner 合并，禁止双写公共文件 |
| 第二批 | C 准确观察/结束；E 路径、提示与等待信息 | 消费 A 的输入预检及 B 的证据/资源结果；统一更新 profile 与能力生成产物 |
| 第三批 | 聚焦集成与真实 Luna Fast 验证、回归报告 | 前两批对应 consumer 接线完成后执行；发现具体失败再修复对应包，不反复启动全矩阵 |

全局组件 20 页超时是第一批的核心流程阻断；理由门和本地预检可作为同批较快完成项，不等待全部动态重构。必要字段先与现有 Schema/consumer 同批交付，再让下游使用，任一中间状态都不能同时保留两套 writer 或互相冲突的解析规则。

公共写域：generationContract/生成器/profile/helper 由一个 Owner 汇合；动态准入与组件修订接口由一个 Owner 汇合。只有独立叶子才并行；正式开工时再按工作协议建立实际协调记录，本轮不预建任务卡。

## 9. 验证与结束条件

### 9.1 先用不消耗模型的聚焦证据

1. 候选兼容和反例：缺理由、对象/字符串投影、字段错误、合法前序引用、过期基线、取消与迟到文件。
2. 动态准入：20 页单控制台、命名状态和跨 Surface 差异、页面特定错误、50MiB 无关资源、动态 asset ID、缺失真实依赖、单目标不就绪及取消。
3. 任务终态：确定修改直接结束、视觉任务消费证据、观察结果复用、已提交后反馈失败不重提。
4. 资源事务：独占包连续 10 次修改、共享/实例隔离、Undo/Redo、保存重开及适用导出。
5. 已完成恢复入口回归：属性维护默认折叠、恢复可撤销，播放没有恢复按钮或隐式快捷键。

按失败属性选择命名单测、集成或真实浏览器检查；不为上述每行另造一套测试平台。准备一次受影响构建/生成产物后复用，通过且相关实现未变的证据不重跑。

### 9.2 最小真实模型验证组

只用已确认 requested/sent/confirmed 的 Luna，默认 Fast，按 AGENTS.md 自主重跑，无需再次确认额度；不换 Astra 等模型。

| 用例 | 要证明的内容 |
|---|---|
| 修改已有组件的公开文案或简单属性 | 无理由手续、无手抄协议字段，正确提交和结束，没有多余总结回合 |
| 同一自然设计要求的控制台源码定制 | 不提供 CSS 修法、不指定具体实现路线；由 AI 得到可见纹理、可用目录/折叠/缩放，正确观察并保存重开 |
| 将上一项已定制控制台放入 20 页且含较大无关素材的工程，再自然要求一项外观及已有控件行为调整 | 真实 AI 入口能走通多页/资源边界，复用既有源码和元数据，不误改其他内容；验证第二次修改而非每次从空白重建 |

三项先各一次作为首轮记录。只有实现修改或具体失败诊断触发重跑；原失败记录保留。自然任务、自动反馈续跑、测试者给出精确修法后的定向修复分别计数，不能混成首轮成功率。三家 CLI 的协议兼容先用适配器/无模型检查覆盖；没有已确认 Luna 路由的通道不擅自换模型。

每项分开记录：首份候选是否可用、宿主拒绝原因及层级、自动修复次数、人工提示介入、模型/工具/宿主阶段耗时、正式提交、保存重开、实际效果。计时统一采用任务记录的 execution.startedAt、hostCommitRecorded 与 taskEnded；外层脚本耗时另列，不把应用启动/轮询算作模型耗时。小样本不作模型总体可靠性或 Fast 提速比例结论，不预先承诺任意任务必在若干秒完成。

若自然任务全部首轮通过，如实记录“本组未触发真实模型自动修复”，反馈链用历史错误候选的无模型回放验证；不主动拒绝合理结果来制造修复样本。

### 9.3 完成本批的条件

本方案中的六类已证实流程问题都有实现和对应反例验证；必要保护未削弱；真实 Luna 任务能完成所列用户结果，失败与后修复如实记录；类型检查、受影响构建/能力产物和文档同步完成。未复现的原生静默原因仍明确标记，不用它阻断已确认修复，也不谎称已定位。

这些证据证明工程改进和具体任务结果，不替代教师美术接受或版本 Owner 验收。若某项真实用例仍未满足，保持该项未完成，继续定位具体根因，不以“模型不稳定”或“超时了”直接收尾。
