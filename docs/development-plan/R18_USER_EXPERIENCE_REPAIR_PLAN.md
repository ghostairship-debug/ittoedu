## 3. 修复 A：高频接口覆盖与模型兜底

### A1. 以真实入口检验能力是否成立

能力成立必须同时具备：可发现的说明、与用户明确要求一致的当前精确目标、接受该目标的正式命令、资源依赖、实际提交和保存恢复。目标可以在当前选区之外；选择不定义修改权限。任何一环缺失都不能宣称该入口可用。

- 从正式背景 Owner 捕获背景目标，覆盖当前已支持的 Course、Surface、Slide Scene／呈现状态及继承关系。Flow 背景属于页面背景，不伪装为正文插图或普通新增对象。
- 能力卡适用域、snapshot 中的目标和执行器条件使用同一份正式能力与目标解析依据。不能在 prompt、snapshot 和 executor 分别复制“支持某 Surface”的名单。
- 明确指令决定实际修改目标，默认选区只是上下文焦点。例如“本页背景”不能被选中段落抵消，“改另一页”也不受选区限制。按当前冻结工程发现目标；仅核心目标确实含混时询问，续跑继续遵守用户要求。
- 背景图片、颜色、继承／独立背景、移除图片分别遵守正式命令语义。替换背景不能清掉未指定的颜色、模式或其他页面背景。
- 对当前已宣称支持的 D/T/I 高频能力进行入口覆盖核对：文字／公式、属性／位置／层级、插图／换图／单实例修改、页面背景。覆盖表由既有 60 项定义和正式适用域导出，不另建任务计分平台。
- D10（明确背景属性）和 I05（应用图片背景）列为本轮必过门。原 60 项及核心名单不因本轮失败被删改；1.9 任务不通过改名塞进 1.8，也不因难例失败而移出分母。

### A2. 让失败真正回到原生模型循环

正式处理链为：

```text
候选失败 → 保存具体失败 → 交接到同一任务的新观察
        → 将失败、已有成果和可用素材交回原生 CLI
        → 模型修正或选择其他正式路径 → 再检查与提交
```

- 请求交接按同一 task／epoch 和冻结目标验证，在新观察建立后原子替换当前请求。不得用全局关闭 stale 检查来消除假 stale；交接期间真实 Stop、工程替换、草稿变化和超时仍有效。
- 只有原生继续请求得到发送确认后，界面才显示“正在根据失败继续处理”。保存了宿主结果不等于模型已经收到它。
- 失败反馈包含准确的失败步骤、原因、当前仍可执行的目标、资源情况和已成功修改的阶段。模型可按需读取完整诊断；用户只看自然语言解释。
- 快捷语义接口失败时，模型可以发现并组合现有正式基础命令，例如素材导入与背景更新，而非只能重复调用同一个包装接口。更复杂的合法任务仍可使用原生工具和 Component／Runtime 等正式载体，不能把缺一张能力卡当作原生能力全部不存在。
- 同步修正 profile／Skill 中“普通换图只用某一个接口”等封死替代路径的表述：快捷接口是优先路径；按用户明确要求，模型可直接使用正式基础能力或文件路径，无须先失败。基础命令也必须有当前精确目标和可读发现入口，不能只在提示中要求模型“自行兜底”，也不能把 UI 选区当作授权边界。
- 正式工程写入仍经过现有 canonical transaction。兜底不引入 raw Store、live project API、通用工程 patch 或第二 History；不能以“兜底”为名绕过本来就必须满足的目标与资源条件。
- 先前已生成且有效的图片在当前任务续轮中可复用；失败不自动要求重新生成。已提交阶段不得重复执行；未提交失败阶段保持零工程写入。
- 保留当前绝对任务预算和基于实质进展的停止规则。有参数、路径或成果进展可继续；不能通过改摘要或随机 ID 无限重试。

### A3. 恢复与状态询问

- 用户问“为什么停止”“现在怎么样”时，根据实际任务和提交结果解释，不自动把问题拼成下一次编辑目标。
- 用户明确要求“继续”时，接回原目标、最后失败、已提交成果和可复用素材，建立新鲜观察后继续；不能只恢复原生会话却遗漏宿主失败。
- 记录发送失败时保留待送结果；恢复后先确认已提交内容，避免重复提交。真正不可执行时说明缺少的条件和可行下一步，不输出空候选索取诊断，也不以绿色回复代替成功。
- 无法恢复的旧记录如实说明缺失信息，不捏造停止原因或声称已恢复全部上下文。

## 4. 修复 B：正常失焦应用、Flow 空白清选

统一产品规则：**合法编辑在正常离开时应用；点击画布空白时随后清除选择；Esc 或明确“取消”才放弃草稿。**

- Flow Owner 提供一次完整的结束编辑操作：核对原编辑目标 → 提交合法草稿 → 成功后清空正式选择。无草稿时直接清选；提交失败时保留草稿和原因。
- 纸张自身、纸张外滚动区域和无对象的工作区空白均接入该操作，不能只处理 article 的直接 click。
- 正文、表格单元格、图表内文字、普通文字属性、正文公式和浮层公式使用一致的结束规则。Native 表格 blur 改为提交；保留现有 Enter／Tab 导航以及末格追加行的一次原子提交。
- 公式弹窗正常关闭或点击外部时应用合法修改；明确取消和 Esc 保留。无效公式、未填完的占位符保留草稿并指出问题，不能静默丢弃，也不能保存无效内容。
- 为浮层公式补齐正式草稿、开始／修改／结束编辑接线，不能只改弹窗遮罩。
- 点击格式工具栏、属性工具或聊天输入框，不等于取消课件对象选择。跨对象、跨页面提交必须绑定原编辑目标，不能把旧草稿写给新对象。
- 输入法组合未结束时延迟完成编辑；每个完成编辑只产生一条必要 History。失焦但内容未变不制造空历史。
- 不使用一个全局 window.blur 监听器强行提交所有状态。拖动中的连续调色中断仍按手势取消处理；Chart 的整表数据编辑保持“应用数据”的完整事务，不拆成每个字段的失焦写入。

## 5. 修复 C：Flow 自适应宽度与一致定位

### C1. 正式版式设置

采用“**自适应宽度为默认创作模式，固定阅读宽度为明确选项**”的设计。自适应模式下正文容器使用可用宽度并保留适度边距，不再被 760px 的阅读上限截断；文字、媒体、表格、图表和组件共同消费实际布局宽度。

这是版式语义变化，需要正式持久化，不能靠预览 CSS 临时覆盖。已增加窄可选字段 `Flow.layout.widthMode: 'fluid' | 'reading'`，与 Published Flow 对应分支一起完成独立合同提交，保持 strict，不创建 V10：

- 新建 Flow 默认显式写入 `fluid`；`reading` 继续使用既有 `readingWidth` 等字段。
- 旧工程缺字段时按原阅读模式解释，避免打开文件即静默重排；属性中提供清楚的“自适应宽度／固定阅读宽度”设置，通过正式命令保存并可撤销。
- 本次问题工程的 Flow 页面在验收副本中实际切到自适应模式，纳入布局调整及保存恢复验收；不能只用新建空白 Flow 证明修复。
- 旧 reader 遇到新增字段明确拒绝；不能静默剥离字段后按另一版式播放。Flow DOCX 等固定页面导出按其页面可用宽度排版，不宣称与不同宽度屏幕逐像素相同。

以上兼容策略已进入正式 Schema 和 consumer；当前验证见[集成记录](reviews/2026-09-12-r18-user-experience-integration.md)。仅在验收副本中显式切换版式，没有迁移原用户工程。

### C2. 正文与全局横幅的关系

- “全局”表示跨页共享，定位基准由明确字段表达。正文相关横幅、页眉和装饰在 Flow 中使用已有的稿纸定位；教师控制器等屏幕工具保持视口定位。
- 当前横幅通过正式定位及对齐命令修复。不得根据名称包含“横幅”就改变 renderer 行为，也不得自动批量重解释所有旧 viewport 项。
- 编辑、试运行、整课预览和离线 HTML 使用同一 Flow 宽度解析、正文容器边距与 overlay 投影。实际容器宽度参与布局，观察缩放与平移仍独立，不反向改变正文排版。
- 同宽时核对正文换行、媒体尺寸和横幅相对位置；跨宽度时允许重排，但正文与相关横幅保持同一对齐关系。
- 作者为显示选中对象而产生的临时平移必须明确可恢复，并与文档布局区分。不得把作者临时 pan 当作保存坐标，或用它解释所有预览差异。
- 预览的关闭／导航栏放在课件内容区之外，避免覆盖顶部横幅。实际课件内容区作为坐标基准；清理“全屏 16:9”等与 Flow 实际行为不符的文字。
- 窗口 resize、正文滚动和观察 zoom 不重建 Runtime／Component 实例，不清除输入、播放或交互状态。共享全局项在 Slide／Spatial 的现有语义和位置保全。

## 6. 修复 D：全过程可读的聊天

### D1. 唯一用户界面规则

**聊天只呈现人类可读的消息和必要操作。原生事件展示区彻底移除，原始数据只保存在本地日志；不以“折叠诊断”形式保留在聊天中。**

| 区域 | 内容 | 行为 |
| --- | --- | --- |
| 用户消息 | 原始提问、补充、纠正及回答 | 按真实时间保留，不把内部自动续轮当作用户再次提问 |
| 思考过程／执行说明 | CLI 实际提供的公开思考摘要、计划、过程说明，以及必要动作的可读状态 | 流式呈现，可折叠；展开后仍是自然语言，不是结构化事件 |
| 回复摘要 | 本次结果、实际完成事项、未完成事项和下一步 | 稳定保留；明确区分准备好、等待应用、已修改、部分完成与失败 |
| 用户动作 | 必要提问、原生授权、预览应用、停止与撤销 | 直接可见，不能埋进过程或日志 |

“思考过程”展示原生实际公开的内容，不编造不可获得的内部推理。没有公开思考摘要的 CLI 使用它实际提供的过程说明和任务进展，不承诺三个 CLI 输出完全相同的思考内容。

### D2. 信息完整，不再让用户翻 JSON 补全

- 以原生消息身份和先后关系合并 append／replace，只去除重复片段，保留独立的公开说明、转折、失败解释和结论。不能用一句固定进度或最后一段短摘要替代原有全部 text。
- 按消息语义区分公开过程与最终回复。补齐实时、跨原生回合、失败修复、停止及历史恢复的呈现；缺少可靠阶段标记的旧文本保留为普通可读消息，不擅自猜成“思维链”。
- 从候选／结果的结构化数据中单独提取自然语言说明，不因整段属于机器候选就连 summary 一起丢弃。候选说明表示准备或意图，实际应用状态以宿主正式提交为准。
- 工具调用不再逐条输出 `commandExecution` 或“CLI 工具已返回”。影响用户理解的动作映射为准确状态，例如“正在生成图片”“图片已生成，正在设置背景”；其他底层过程只记日志。
- 模型提示明确要求用教师能理解的语言表达公开回复。机器协议、内部 ID、revision、目标别名和错误堆栈留在结构化交付与日志中。正常公式、表格及用户主动要求的代码仍按可读内容显示，不能机械删除所有代码或 JSON 文本。
- 用户消息与补充必须经现有本地任务／事件 Owner 持久保存。若当前只存在待消费队列，则补充窄的持久消息事件；读取时从同一记录派生聊天，不维护第二套会话事实。
- 不额外调用另一个模型总结每条事件。完整日志保留原文及关联身份，聊天投影不能反写或改变任务执行事实。

### D3. 失败和阅读空间

- 对用户解释“发生了什么、影响是什么、下一步怎么办”。常见拒绝、资源失败、授权、连接、超时、Stop 和部分完成由实际分类产生可读提示；不把原始异常字符串直接作为聊天错误。
- 没有明确证据时直说原因尚未确定，不能把猜测包装为“停止原因已确认”。模型仍在修复时不提前显示失败终结；没有正式提交时不提前显示成功。
- 紧凑展示模型／强度与引用范围，配置收在明确入口；输入区保留主要操作，取消大段常驻技术说明，为正文释放主要阅读空间。既有配置能力保持可达，不扩成 1.9 工作台重做。
- 用户向上阅读时不强制滚到底部；继续接收消息不重排已有消息、不丢输入。Markdown、长段落、列表及公式有清晰排版；真实窗口验证，不以组件渲染成功代替可读性。

| G9 响应式与兼容 | 宽窄重排可预测，旧版式与交互状态保持 | 至少两种明显不同内容宽度、滚动、zoom／恢复；自适应与旧固定阅读模式；Runtime／Component 不重置；Slide／Spatial 全局项保全及 Flow DOCX |
| G10 消息完整 | 每段公开 text 都有正常可读的呈现 | 原生记录与界面按消息身份逐段对照：实时、增量＋终态、候选摘要、自动续轮、停止、重开历史；重复快照不重复计数 |
| G11 全程可读 | 用户不看结构化信息也能理解任务 | 正常完成、失败后恢复、中途纠正、提问／授权、停止、部分完成及历史回放；聊天无原生事件入口、无机器候选／原始异常泄漏 |
| G12 结论可信 | 成功、等待、失败与实际课件状态一致 | 模型说明不能覆盖正式结果；首次成功、产品修复后复验、重试次数、耗时、尚未验证的 CLI／Surface 分别记录 |

验证安排：

- 从现有目标用例和最便宜的真实反例开始。类型、strict 合同和受影响构建先检查，再启动真实窗口；源代码、依赖或验证定义未变的有效证据复用。
- Codex 使用用户实际模型／强度和原指令。CLI 版本、服务档、会话新建／恢复条件从真实记录确认，未知值写未知，不为了通过降低模型设置。
- 三个 CLI 的消息分类与历史使用真实记录回放；受改动影响的原生继续／提问至少各用有限短任务确认。图像生成以当前用户 Codex 失败链为主，不无差别重复三套付费图像矩阵。缺认证或原生连接阻断单列，不能用回放冒充真实原生执行。
- 保留第一次失败和后续修复，不把修复后成功改写为首次通过。既有 60 项定义冻结不等于已经执行，不能宣布 49/60 或 80% 覆盖率。
- 新工程候选完成后仍需 Owner 真实使用复核。S3 签署与正式发布独立，不因任务板归零或自动化通过而自动成立。
