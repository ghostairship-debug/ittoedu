# AI 提示、例外与固定步骤审查

日期：2026-09-16。Owner 要求先记录调查结论，再分析 Fable 关于上下文负担的判断。本记录不是实施授权、任务卡或版本验收。

## 范围与结论

回查 1.8 以来 AI 相关提交、当前未提交修改和实施记录，覆盖初始提示、反馈续轮、内置技能、四阶段写稿/构建、候选交付、恢复与运行检查。存在把具体失败经验扩散为通用提示、用重复禁令弥补输入混杂、保留过时固定步骤的情况。不能由此把真实产品修复一并撤销，也不能由静态阅读推算实际延迟比例。

## 已确认需要收敛的内容

1. **标题居中样例进入所有编辑提示。** `src/main/localAgent/profile.ts` 的 `buildGenerationPrompt` 无条件在编辑分支附带“Slide标题居中须textStyle.align=center且frame水平居中”，与任务是否涉及标题无关。`2026-09-09-short-path-implementation.md` 记录文字样例只做框内居中后追加几何说明。应放到相关操作说明，不作为所有编辑任务的常驻提醒。
2. **控制台定制说明进入所有内置技能。** `src/shared/courseAgentSkills.ts` 的 `courseAgentSkillMarkdown` 为包括教学策划在内的每个技能附加控制台纹理、穿透、缩放及“不只改颜色冒充深度定制”等内容。相关能力保留，说明应按任务需要提供。
3. **混合参考材料后追加禁止复制/执行的指令。** `src/main/lessonAuthoringDesktopService.ts` 的 `prompt` 整段注入格式参考与方法文档，随后重复禁止把参考标题写入正文，点名“课例 Markdown 候选校验”；软件内构建加载外部构建方法后，再要求忽略外部命令。应整理适用于本阶段的输入，避免依赖越来越长的反向说明。
4. **交付格式说明累积。** `profile.ts` 同时解释候选 v1/v2、对象/字符串输入、文件/正文通道和 `--check`；`harness.ts`、`generationContract.ts`、`scripts/candidate-helper.ts` 在错误及恢复处继续解释。真实预检、交付、提交的区分和恢复必须保留；模型面对的正常交付入口可收敛，不能仅删提示却保留同样复杂的操作要求。
5. **旧技能固定修复停点表述不一致。** `courseAgentSkills.ts` 的 `qa-repair` 仍有“限定一次局部修复候选”“不能自行循环重试”，与当前同任务依据宿主反馈继续修正的能力容易产生歧义。应明确每次候选等待宿主反馈后可以继续，由既有预算及实际进展约束停止。静态阅读未证明这条文字已经导致特定真实任务停止。

## 运行检查与验收方式

- `nativeInteractionVerification.ts` 对已改 Native 点击规则做真实 Player 检查，有实际价值；检查器曾误判入场动画，后增加排除分支，证据见 `2026-09-16-r19-native-interaction-closeout.md`。其期望结果投影和例外范围需要单独审视，不能把声明执行通过当成用户完整目标通过。
- 该检查将全部动作延迟/动画时长相加，再以累计时间作为允许通过的最早时间；`PublishedInteractionController.ts` 实际按组并行执行 `with-previous` 动作。并行动画因此可能带来确定性的多余等待；本次未测实际任务耗时占比。
- `2026-09-09-short-path-implementation.md` 记录：一次文字任务已经出现正确结果，因模型额外选择 observe 未通过“直接结束”断言，随后收窄提示。正确结果、修复/观察次数、最终耗时应分别计量，不能把期望执行路径混成所有任务的功能成功门槛。
- 每阶段固定调用 Markdown 校验 CLI、Builder 前后逐段映射检查等步骤存在成本，但有早反馈/完整性交付价值；尚不足以直接认定全部多余。必要性应按重复程度、现有宿主检查和减少返工的收益判断。

## 应保留的基础能力

当前工程/导航事实、同源正式 Schema 与适用域、唯一 canonical 文档/资源/History 事务、保存重开、Stop/过期/身份失效保护、真实错误/运行反馈和有效修复源码复用。这些为任意模型提供正确执行与自我修正条件。

## 多次分类路由后仍有缺口的复盘

Owner 要求将本轮判断继续记在同一位置。以下是根据现有方案、源码和上述真实运行证据形成的原因分析，不是新增开发批次或验收门。

1. **不同层面的选择改善，被反复概括成“路由改善”。** Native/Component/Runtime 区分实现载体，参数/组合/源码区分操作方式，能力发现与适用性投影缩小当前可选分支。这些改动确实存在，且各有价值；但选中能力之后，模型仍要理解输入格式、目标引用、候选包装、预检、交付和宿主结果。单独完成其中一层，不能代表完整操作链路已经简单。
2. **目标早已写对，实施与验收没有持续覆盖完整目标。** `AI_COMMON_TASK_EXECUTION_PLAN.md` 第 6 节明确要求“发现一次应足够调用”，并说明拆成长短多次读取但保留工程拼装不算完成。机制方案第 9 节实际交付的是 M0–M4/M6 纵切，完整 M5/B2–B4 另有版本归属；后续又补适用性、反馈和运行诊断。上述历史范围不能被汇总成所有常规任务都已收口，也不能仅凭旧文档推断后来各任务族仍未实现。问题在于没有持续以完整任务证明已宣称的接口简化，而不在于缺少这些设计原则。
3. **减小入口，没有完全消除后续读取和理解成本。** 初始 wire 已去掉重复推荐、能力查询已有按操作剪裁；但完整 request、完整卡及 helper 实现仍可能在后续被读回。本次模型为理解 helper 连续五次搜索/读取，实际工具返回约 41.5 KB，证明只看初始提示预算会漏掉真实负担。执行文件体积本身不是失败；常规调用需要研究其实现才是接口问题的直接证据。
4. **调试目标在“最终提交成功”和“首次按预想路径通过”之间摆动。** 前者容易漏记准备成本，后者容易让一次模型偏差变成全局提醒或固定步骤。标题居中提醒、专项控制台说明和因额外 observe 被判失败的历史样例，是这类偏移的具体证据。功能正确、自行修正、人工干预和完成时间应分别记录，不能为了首次通过率无限扩展提示。
5. **新增能力与补丁持续进入，共用输入及旧规则的退出没有同步完成。** 所有技能附带控制台要求、混合参考材料后追加禁止项、旧 qa-repair 停点与现有续轮机制不一致，说明新增路径有接线与检查，而旧说明是否仍必要、是否应按需加载，没有同等清晰的退出要求。这会抵消前面分类和压缩获得的收益。

责任判断：不能把这些剩余成本统称为模型能力不足。推进与汇报中，把局部能力接通、代表样例成功、完整任务链路简化之间的界线守得不够清楚，又在样例失败后追加了部分通用补丁，这是本轮需要纠正的工程推进方式。已经得到的正确执行、自我修正和保存重开证据继续有效；本次审查不撤销这些证据。

投入原则：停止围绕已能正确完成并自行修正的同一课例无限优化首次通过率；后续改善应优先减少重复读取、协议拼装、无效调用和确定性等待，以最终正确结果及完成时间评估。首轮表现继续作为观测项，不自动转化为新阻断门。开放源码创作仍可阅读实现，常规编辑不应依赖逆向工具实现。自建 harness 仅保留为未来选项，须由实测瓶颈与同等正确性下的收益支持；当前不启动。
