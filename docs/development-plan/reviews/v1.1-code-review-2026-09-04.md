## 2. Findings

### R-01 [P1][继承] 新建/打开/最近工程的异步等待可静默覆盖确认之后产生的新编辑

**位置**

- `src/renderer/app/useCourseProjectLifecycle.ts:158-162`
- `src/renderer/app/useCourseProjectLifecycle.ts:259-268`
- `src/renderer/app/useCourseProjectLifecycle.ts:307-370`
- `src/renderer/App.tsx:139-154,434-485`

**触发与证据**

`sameProjectIdentity` 只比较 `projectId + epoch`，没有比较已经捕获的 `revision` 或 `sessionGeneration`。New 在确认丢弃后先等待 `clearRecoveryProject`；Open/Recent 在文件读取、解压及解析期间等待。`busy` 只禁用顶部工具栏，`Workspace`、`ScenePanel`、`RightSidebar` 和键盘编辑仍可改变当前文档。

用户在丢弃确认之后、替换文档之前继续编辑时，revision 会变化，但 epoch 不变；最终 New/Open 仍会直接替换当前工程。Recent 更是在文件读取完成后才调用 `beginMutation()`，读取期间的编辑不会进入任何 stale 判断。

**影响**

用户已经在确认后新增的内容可无二次确认地丢失，属于受支持流程中的数据覆盖。

**覆盖缺口**

`tests/unit/useCourseProjectLifecycle.test.tsx:112-154` 只覆盖同工程重开后的迟到 Save/Recovery；没有 deferred clear/read/decompress 加中途编辑的测试。

**建议**

为破坏性生命周期操作使用独立的完整 target：在首次等待前捕获 revision/session，并在实际替换前校验；或在整个破坏性窗口真正冻结编辑。不要直接收紧 Save 使用的比较器，因为“保存期间继续编辑仍保持 dirty”是必须保留的行为。

### R-02 [P1][继承] Slide 在 IME 组合输入中进入试运行会无提示丢失草稿

**位置**

- `src/renderer/composition/crossSurfaceCommands.ts:348-373`
- `src/renderer/store/slices/slideAuthoringSlice.ts:328-338`
- `src/renderer/authoring/v9SlideContentEdit.ts:640-646`
- `src/renderer/course/slideAuthoringBackend.ts:693-718`

**触发与证据**

Slide 的 `setCanvasMode('run')` 调用 `commitDraft()` 后不检查结果，继续激活初始状态并切换模式。底层在 `edit.composing === true` 时明确拒绝提交，但 Slice 仍以 `clearContentEdit: true` 持久化结果。

最小 Store 复现结果：`mode='run'`、`v9ContentEdit=null`、canonical text 仍为旧值、`error=null`，随后 `prepareCourseProjectPersistence().ok === true`。即未完成输入消失，旧值还可被正常保存。

**影响**

教师使用中文输入法时点击“试运行”，正在输入的文字可直接丢失，且没有错误提示或恢复入口。

**覆盖缺口**

现有测试分别覆盖“持久化拒绝 composing”和“无草稿进入 run”，没有 Slide composing + run 的组合用例。

**建议**

让 Slide `commitDraft` 返回可判定结果；任何 composing/stale/invalid 拒绝都必须阻止模式切换、保留草稿并显示可操作反馈。

### R-03 [P1][继承] PPTX 预检为绿色，但 producer 可带 error 写出非空残缺文件并报告成功

**位置**

- `src/renderer/export/exportPreflight.ts:187-234,324-417`
- `src/renderer/export/course/buildCoursePptx.ts:730-793`
- `src/renderer/app/useCourseDelivery.ts:278-299`

**触发与证据**

对一个 Schema 合法、含一个有 location 的 Slide scene 和一个无 location 的 Slide scene 的 V9 工程：

- preflight：`summary.canExport === true`，无 error；
- builder：生成 44,219 bytes、1 页 PPTX，同时 report 含“未定位场景没有课程位置”的 error；
- GUI：只在 `bytes.byteLength === 0` 时失败，忽略 producer error，仍写盘并报告成功。

**影响**

用户得到可打开但缺页的 PPTX，成功提示掩盖了交付内容被遗漏。

**覆盖缺口**

PDF 已测试无 location 的同类错误，PPTX 没有；也没有“producer 有任一 error 时 GUI 禁止写盘”的断言。

**建议**

PPTX preflight 应覆盖 page/location producer facts；写盘前必须对 `built.report` 中的 error fail closed，而不是只看字节是否为空。

### R-04 [P1][继承] Web Package 用 CSP 阻断已经声明且实际使用的网络 origin，预检仍通过

**位置**

- `src/renderer/export/course/buildCoursePackages.ts:243-259`
- `src/renderer/export/course/coursePackagePreflight.ts:296-326`
- `docs/development-plan/ARCHITECTURE_CONTRACT.md:53-58`

**触发与证据**

Runtime 源码调用 `fetch('https://runtime.example.com/data')`，工程准确声明 `network.connectOrigins: ['https://runtime.example.com']`。Web Package preflight 返回 `canExport: true` 且 items 为空；生成的 `index.html` 仍固定为 `connect-src 'self'`，没有声明的 origin。

合同把外部 `fetch`、EventSource、WebSocket 和精确 origin 声明列为正式能力；当前产物会被浏览器 CSP 确定性阻断。

**影响**

Preview/在线 HTML 可工作的可信 Runtime/Component，在 Web Package 中网络功能失效，用户事前得不到诊断。

**覆盖缺口**

现有 `coursePackageExport.test.ts` 反而固定断言 Web Package 只有 `connect-src 'self'`，没有带声明 fetch/ws 的解包浏览器运行用例。

**建议**

Web Package CSP 应按精确声明生成并运行相同 source/declaration 分析；若产品决定 Web Package 必须禁网，则 preflight 必须明确阻断或告警，不能绿色降级。

### R-06 [P2][1.1 新增] 陈旧 Player 启动失败会清空更新实例的根节点

**位置**

- `src/player/index.ts:56-79`
- `src/player/index.ts:103-151`

**触发与证据**

在同一 root 上不等待第一次 mount 完成就连续调用两次 `startPlayer`：第二次会销毁 A 并绑定 B；A 随后以 `Course player has been destroyed` 拒绝。catch 虽只在 `activeSession === session` 时清理 session，却无条件调用全局 `reportPlayerBootstrapFailure`，其 `replaceChildren` 会删除 B 已挂载的 UI。

最小 JSDOM 复现结果：全局 presenter 的 session 是 B，但 root 显示旧错误，找不到 Flow/Slide host。该逻辑由范围内提交 `bb1f8485` 引入，基线没有这条 V2 active-session 替换路径。

**影响**

同根节点快速重载/重启 Player 时，当前有效 session 仍存在，但界面被旧失败覆盖。当前产品常规 bootstrap 通常只启动一次，因此按有限可达性定为 P2，而非 P1。

**覆盖缺口**

协议和架构基线测试都只启动一次，没有 pending mount 下连续启动与陈旧失败隔离测试。

**建议**

以 generation/root ownership 或 `activeSession === session` 同时守卫错误渲染和 presenter attach；旧实例失败只能清理自己的资源，不能写当前 root。

### R-07 [P2][1.1 新增] Spatial 选中元素后方向键微移调用 Slide owner 并抛错

**位置**

- `src/renderer/app/useEditorKeyboardRouter.ts:89-100`
- `src/renderer/App.tsx:404-419`
- `src/renderer/store/slices/slideOwnedCommands.ts:669-682`

**触发与证据**

创建 Spatial 工程、添加并选中文字后调用根 `nudgeSelection(1, 0)`，稳定抛出“当前会话没有课程工程”。键盘 router 把 Arrow 发送到 root action；1.1 组合后该 action 落到只读取 `slideBackend` 的 Slide owner，而 Spatial 激活时 `slideBackend === null`。

基线的通用 nudge 使用当前 `editingNodes` 并经跨 Surface `updateNodes`，Spatial 可工作；当前路由由范围内提交 `bb1f8485` 引入。

**建议**

### R-08 [P2][继承] 最近工程列表故障污染恢复决策及已经成功的打开/保存结果

**位置**

- `src/renderer/app/useCourseProjectLifecycle.ts:249-252,343-370,372-415`
- `src/renderer/app/useCourseProjectLifecycle.ts:462-507`
- `src/main/projectPersistence.ts:265-273`

**触发与证据**

启动时 recent 与 recovery 用 `Promise.all` 读取。recent 拒绝会丢弃已经成功读取的 recovery，并直接把 `recoveryDecisionComplete` 设为 true；用户随后编辑时，单一 `recovery.h5lesson` 可被新恢复快照覆盖。打开/保存完成后又等待 `refreshRecentProjects()`，其失败会把已经 apply/ack 的核心操作报告为“打开/保存失败”。

`listRecentProjects` 在 prune 后重写 JSON 时存在真实拒绝路径。该耦合在基线 App 中已经存在。

**影响**

一个辅助 recent 功能的故障可能隐藏恢复提示、在后续写入时替换旧恢复副本，或向用户谎报已成功操作失败。

**覆盖缺口**

没有 `recent reject + valid recovery`，也没有 `successful open/save + refresh reject` 测试。

**建议**

recent 与 recovery 独立结算（或使用明确的 `allSettled` 分支）；recent 故障只能降级最近列表，不能决定恢复状态或改变核心操作结果。

### R-09 [P2][继承] 异步媒体 Add 未绑定 owner/scope，完成时可能写入错误图层域

**位置**

- `src/renderer/app/useMediaImport.ts:32-36,169-190,303-419,478-564`
- `src/renderer/App.tsx:71-79,297-352`
- `src/renderer/course/slideAuthoringBackend.ts:352-374`
- `src/renderer/media/commitCourseMediaAuthoring.ts:665-692`

**触发与证据**

媒体 identity 只有 project/revision/location。Scene 与 Global 间切换不改变这三项，只提升 session generation；解码/去重之后 freshness 仍通过。最终 commit 再读取当时的 `editingScope`，因此从 Scene 发起的 Add 可落入 Global，反之亦然。

这与合同要求的异步 target `projectId / sessionGeneration / location / surface / owner / item / revision` 不一致。基线甚至没有当前的部分 identity 防护，因此属于继承但未闭合的问题。

**影响**

用户在媒体读取期间切换编辑域，会得到保存到错误 owner 的图片或视频；结果可 Undo，但初始操作目标被改变。

**覆盖缺口**

`tests/unit/useMediaImport.test.tsx:136-175` 只覆盖 revision/location 改变；replacement 有 canonical target，Add 没有 owner target。

**建议**

在文件选择前捕获 canonical placement target，至少包含 generation/surface/owner/scope；提交时要么精确写入原 target，要么返回 stale 且零写入。

### R-12 [P2][继承] Slide 全局层批量媒体导入一项一条历史，一次 Undo 不能撤销整批

**位置**

- `src/renderer/media/commitCourseMediaAuthoring.ts:665-680`
- `docs/development-plan/ARCHITECTURE_CONTRACT.md:83-85`

**触发与证据**

在 Slide Global scope 一次导入两张图片，代码循环调用 `placeImage/placeVideo`，每项独立 persist。最小 Store 复现得到 `historyDelta: 2`；一次 Undo 只删除最后一张，第一张仍留在全局层。

**覆盖缺口**

**建议**

用单个全局层批量命令和一条 document + resource transaction 提交所有 items；一次 Undo 必须精确撤回整批。

### R-13 [P2][继承] Flow TextRun style 的运行时 Schema 非 strict，会接受并静默剥离未知字段

**位置**

- `src/shared/contracts/course-project-v9/schema.ts:529-548`
- `src/shared/contracts/published-course-v2/schema.ts:1-15,323-334`
- `src/renderer/project/courseProjectArchive.ts:195-207,222-231`
- `tests/unit/courseProjectCoreContract.test.ts:267-289,640-725`

**触发与证据**

`flowTextRunStyleSchema` 是唯一缺少 `.strict()` 的嵌套 style object。向合法 Flow run style 注入 `unknownFuture: true` 后，运行时 `safeParse` 返回成功，输出只保留已知字段；打开和保存 archive 都使用该解析结果，Published V2 又复用相同 `flowBlockSchema`。

同时，生成的 JSON Schema 对该对象声明 `additionalProperties: false`。因此 `check:contracts` 仍能通过，但运行时与发布给使用者的合同语义不一致。

**影响**

遇到同版本扩展字段或非当前 writer 产生的合法候选时，编辑器不会 fail loud，而会在打开/保存或发布转换中静默丢数据。当前内置 writer 不生成未知 style 字段，因此定为 P2。

**覆盖缺口**

现有 unknown-field 测试覆盖多个 domain object，但没有 Flow run style；富文本测试只 round-trip 已知字段。

**建议**

为 style object 增加 `.strict()`，并新增 V9 authoring、Published V2 及 JSON-Schema/runtime parity 测试。
