## 4. 不能直接照搬的方案

1. **不替换刚确认的目标交互。** 保留单条自动提示、当前页默认、点选后当前选择、清除选择回当前页、明确指令优先、发送时冻结目标。A 的多 chips、B 的顶部 Context Bar 只能补充材料或状态，不能重新堆两个常驻选择器。
2. **不强制换成固定布局。** A 要会话移到右面板；B 要 Rail＋Sidebar、AI 与属性二选一。两者是不同设计候选。没有内容时保留目录聊天；打开内容再展开工作区；保留已确认自由停靠。选中对象不应自动挤走正在使用的聊天。
3. **不直接隐藏 CLI／模型配置。** 当前已决定把 CLI、模型、强度、速度放在输入框上方紧凑一行。报告提出移入高级设置，需另有用户操作证据；不因“更简单”静默隐藏当前有效配置或削弱原生能力。
4. **快路径不变成第二 Agent。** 最小输入和按任务优化可吸收；不能由新路由器接管原生模型循环、限制原生工具／Skills，或把用户的 AI 请求偷偷改为未经确认的确定性动作。手工工具继续直接可用。
5. **不硬编码“一次 repair 后 fallback”。** 保留精确错误、同一任务恢复及已有文件候选通道；根据错误是否可修复、是否有新证据、停止信号和既有任务预算决定。权限、目标过期等失败不能靠 fallback 绕过。
6. **不增设普遍审阅门。** 已授权的简单修改直接形成结果并可撤销；复杂修改也不因报告模板一律多一步批准。预览态、已应用、已保存分别如实展示；外部工具写文件没有宿主历史时，不伪造“一键撤销”。
7. **不以拆分组件为首个强制批次。** 当职责错误或生命周期问题有证据时迁移真实 Owner；不按“每组件小于 500 行”验收，也不只搬 JSX、增 Provider、留重复状态。生成物可折叠审阅，但生成器与消费者的一致改动仍须同批可运行。
8. **不直接采用工期、百分位及重复次数。** 8 秒、500ms、冷启 2.5 秒、100 次保存、连续 10 次、回归 20% 等没有同一冻结样本和当前基线；只能是待测假设。30–90 秒首个可编辑结果与完整材料课件完成是不同指标。
9. **不扩当前发布范围。** A 将多格式统一入口安排到 2.0，又在长期段放到 2.5；B 则分到 2.1／2.2／2.5，不能拼成新承诺。既有 PPTX、三格式材料与 Word 路线不能被整体推迟，也不把 Office 深编辑提前设为 2.0 前置。当前路线明确没有安装器。
10. **不按附件交接命令直接执行。** 当前 `package.json` 没有 `verify:fast` 或 `verify:product`；`verify:release` 则包含更广验证。审查建议不授权 checkout、安装、真实模型、全量测试或开新任务；已有有效证据按受影响范围复用。

这些限制依据[架构合同](../ARCHITECTURE_CONTRACT.md)、[工作协议](../WORKING_PROTOCOL.md)、[2.0 现行路线](../roadmap/2.0/README.md)及[长期产品方案](../../../果铃_AI原生文件与内容工作台_产品方案_V2.0.md)。长期通用工作台方向已有正式研究，不应被误读为当前就要重建全部架构。

## 5. Office 与外部技术：保留什么

**保留“复用成熟内核、先验证选区到原件写回、明确格式边界”的研究方向；不在本次确定供应商、购买、排期或 PoC。** 现有长期方案第 12 节已比简单“转成课件”更严格地区分显示、定位、写入，应继续保留。

- Univer 可作未来表格／文档适配候选，但开源核心不等于全部 Office 能力免费可得。当前官方说明区分 OSS 与 Pro；Slides 的导入导出示例使用 Pro exchange 插件，并要求格式转换后端。不能据报告推断“嵌一个前端组件即可完成本地原格式编辑”。[官方能力边界](https://github.com/dream-num/univer#-open-source-and-pro)、[Slides 导入导出](https://docs.univer.ai/guides/slides/features/import-export)。
- ONLYOFFICE 可作兼容能力候选，但报告建议验证的 Automation API 官方明确属于 Docs Developer，且额外收费；Docs API 集成还涉及文档服务与存储协作，不等于直接装一个轻量 React 编辑器。[Automation API](https://api.onlyoffice.com/docs/docs-api/usage-api/automation-api/)、[集成架构](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/)。
- A 对 Univer 的开源覆盖描述较宽，B 对 Slides Pro 的提示更接近实际集成风险；也不宜简单反推 Slides 所有部分全为商业能力。应按具体版本、包、目标格式和用法复核。
- 未来确有任务后，只选最有价值格式做闭环样例：打开真实文件 → 选择对象／范围 → AI 修改 → 手工接管 → 保存原格式 → 原软件重开 → 检查未改部分与撤销。编辑画布能显示只是第一步。
- tldraw、Gamma、AFFiNE、GrapesJS 等在报告中属于产品／工程参考，本轮未全面复核其版本性宣传，也不据此要求替换现有画布、引入协作或新增 HTML 全编辑能力。

## 6. 建议并入后续方案的顺序

| 顺序 | 建议范围 | 应拿到的实际证据 |
|---|---|---|
| 先处理当前可用性 | 复用此前审查清单：未生成文件的任务可重开、聊天唯一实例、布局不丢草稿／任务、历史可达、普通文档 AI 接线、失效测试断言 | 在新交互下完成任务并得到正确文件，保存重开、预览与导出结果一致 |
| 同步补齐用户反馈 | 自动目标提示＋引用角色；统一保存状态；提交后的变更摘要与真实撤销入口；错误后可继续 | 不看日志即可知道改哪、是否完成／保存、如何恢复；不额外增加常用步骤 |
| 有证据后优化速度 | 复用计时与输入计量，冻结代表任务，定位原生启动／读取／生成／修复／提交；优先消除被证实的重复开销 | 分别报告首次正确结果与全任务结束、失败和干预；同模型配置对比，不能以削弱能力换速度 |
| 最后扩展格式 | 保留 Office 适配、能力声明与保真度研究，沿现有必选线完成 PPTX／材料等交付 | 每种承诺有对应真实文件的读、选、改、保存及外部重开证据 |

建议吸收的核心结果是：**一个用户能自然操作的工作台，一份真实任务状态，可追溯的文件修改，以及能解释的速度与质量证据。** 不把“再定义一组统一类型／Provider／任务中心”本身当成交付。

本轮仅新增此评估文档；未改产品代码、正式路线、任务板或已确认交互汇总，未运行测试或真实 CLI／模型。
